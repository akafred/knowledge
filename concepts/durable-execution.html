Durable Execution & Workflow Checkpointing

The pattern of checkpointing a program's progress to a durable external system (a dedicated orchestrator or a relational database) so execution can resume after a crash from the last completed step — the concurrency, idempotency, and fault-tolerance primitives (queue claiming, unique-constraint checkpoints, leases) that implement it, and the build-vs-buy question of whether a dedicated engine or existing infrastructure should host it.

Also known as: durable execution, durable workflows, checkpointed execution, workflow orchestrator, external orchestrator, Temporal, AWS Step Functions, lease-and-sweeper, idempotent checkpoint, SKIP LOCKED, crash recovery (workflow)

    Google's AX is a Kubernetes-style, open-source control plane that treats AI agents as stateful, checkpointable actors on a purpose-built runtime (Agent Substrate) rather than as microservices or batch jobs, solving the idle-compute and cold-start economics of long-running agentic workloads at the price of inheriting full Kubernetes operational complexity — a trade-off the technical community is already visibly split on rather than one the article itself adjudicates.
  • Presentation: The Agent Harness: Control Planes, Invariants, and Approval Boundaries for Production AI Agents Vinoth Govindarajan · 2026-09-21 source ↗ Reader 🖥️
    The reliability of a production AI agent depends not on the model but on its harness — whether every fact an agent depends on has a single owner and replay path, concurrent state mutations are serialized through one ordered commit path, every unit of work has a bounded lifecycle, every approval is a scoped and expiring authority object rather than a remembered click, and every action is proven with a receipt that crosses the user-visible edge — because a model can only propose an action, and it is the harness, not the model, that commits it and proves it happened.
  • Article: Implementing Durable Workflows on Postgres Without an External Orchestrator Raman Varma · 2026-09-14 Reader 🖥️
    Durable workflow execution is fundamentally a database-checkpointing problem, so a team that already operates a relational database like Postgres at scale can implement production-grade durable execution — concurrent dispatch, idempotency, crash recovery, durable waits, and observability — as a handful of well-understood SQL primitives, without deploying a separate stateful orchestrator such as Temporal or AWS Step Functions.

The article presents 'the database enforces idempotency' without discussing patterns other durable-execution systems use to close exactly this window (transactional outbox, idempotency keys passed to the external call itself, or a two-phase intent-then-commit record).
