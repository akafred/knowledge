Synthetic User Simulation

Using AI agents to simulate diverse end-user personas — with goals seeded from a target agent's own capabilities — that converse with a product agent to generate realistic multi-turn trajectories, used to test, evaluate, and (in privacy-restricted domains) train other agents before real users interact with them.

Also known as: synthetic users, simulated users, user simulation, trajectory entropy, tool call distribution entropy, tool call transition entropy, arksim, golden scenario set

    Because static, single-turn benchmarks with fixed golden answers cannot evaluate multi-turn, tool-using agents whose correctness depends on live backend state and conversational history, teams must replace ad hoc manual testing with AI-simulated user personas that generate realistic, coverage-optimized conversation trajectories against which scenario-grounded, automated evaluation can run inside CI/CD — turning agent testing from the manual bottleneck that keeps roughly 95% of agents stuck in demo into a scalable, continuously-refreshed, self-improving production pipeline.

Open gaps (2)

  • incompleteThe talk never explains how to validate that AI-simulated personas actually approximate real user intent/behavior distributions. Beyond appealing to domain-expert 'interviews' for cold start and matching production data for warm start, there is no calibration metric, statistical test, or audit process offered to confirm the synthetic distribution isn't itself biased — e.g., toward whatever a small number of experts (or the generating LLM) finds salient, which is exactly the caricature concern Participant 3 raised and that the speaker sidesteps rather than answers.
    Presentation: From AI Agent Demo to Production: Automated Testing and Evaluation — read next: Sim-to-real transfer / distributional-fidelity literature (as used in robotics simulation), and work on eliciting representative rather than merely plausible personas from a small number of domain experts.
  • incompleteNo cost/ROI accounting is given for building and running the simulation infrastructure itself. The talk names running cost as a design constraint (avoiding, e.g., 10,000-conversation batches every CI run) but never quantifies the engineering cost of building personas/scenarios, judge-calibration labor, or how the total cost compares to the manual-tester process it replaces — beyond the qualitative, unquantified two-year Pearson relationship.
    Presentation: From AI Agent Demo to Production: Automated Testing and Evaluation — read next: Corpus material on eval/observability infrastructure cost and token/infra economics, for a fuller before/after ROI picture of adopting simulation-driven testing.
