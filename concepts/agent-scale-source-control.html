Agent-Scale Source Control

Redesigning version control, merge gating and checkout infrastructure for workloads where agents, not humans, generate most commits and fetches — always-online thin clients, server-side commits, content-addressed tiered caches, and replacing global-lock merge queues with post-merge and pre-deploy testing.

Also known as: source control at agent scale, Scion, server-authoritative version control, agent-scale monorepo, merge queue at agent scale, post-merge testing, git scaling for agents

2026-10

  • explicitIn Scion the unit of work is a server-created changeset in a write-ahead log (files changed relative to the first parent plus content-addressed pointers to blobs), so accepting changes needs no packfiles, locks, cross-server coordination or ref movement; a ref update is a compare-and-swap on a single Spanner row, separate from changeset creation.
    Redesigning source control at Anthropic · p8
  • explicitBecause all Scion data is content-addressed and immutable, any server or cache can serve it without coordination; the client fetches only the trees and blobs it wants (no negotiation about what it already has), recursively from a root tree, through a strictly enforced tier of scion-daemon (per node), regional scion-cache and authoritative scion-server backed by Spanner and cloud storage, which makes sparse and virtualized checkouts need no special support and isolates failure domains.
    Redesigning source control at Anthropic · p10
  • explicitAnthropic reports that each Scion tier holds a cache hit rate above 99%, the Scion infrastructure footprint is 200x smaller in CPU and memory than the previous git mirroring fleet, CI and research jobs check out code two orders of magnitude faster (seconds rather than minutes), and CI alone realized a 25% CPU capacity win.
    Redesigning source control at Anthropic · p11
  • explicitThe migration was staged: early on, before Scion had its own client, repo format or protocols, it answered only metadata queries (ancestry, blame) for consumers; file contents and working-copy materialization were designed separately later, fed by a git-to-Scion ingestion pipeline, until the monorepo was fully migrated off git in five months.
    Redesigning source control at Anthropic · p13
  • explicitA team of seven built Scion, the Antique code review tool and about half a dozen related systems (code search, a source-control IAM system, tooling for landing large amounts of reviewed code) and fully migrated to them in five months while daily merged volume grew 10x; Anthropic asserts this would formerly have taken a company years of iterative migration with many more engineers.
    Redesigning source control at Anthropic · p14
  • explicitGiven an early internal snapshot of Claude Mythos Preview and no further instructions, Claude rewrote the handwritten prototype git-to-Scion ingestion pipeline into a version using 20x less memory and running 4x faster while preserving implicit ordering and data-structure invariants.
    Redesigning source control at Anthropic · p15
  • explicitClaude's capacity to write large amounts of code let the team build hermetic simulations of every non-trivial infrastructure and source-control interaction it had encountered, plus fuzzing and rate limiting, and led Anthropic to call Scion among the most well-tested and well-defended codebases it has worked on; Claude also found an algorithmic optimization to ancestry queries (one that missed an index) that would have taken an expert days or weeks.
    Redesigning source control at Anthropic · p19
  • explicitScion supports repository-level access control and permissions on individual directories, and the code review tool can express semantic constraints on approvals (distinguishing comment-only changes from sensitive logical changes) so human reviewers focus on the most consequential changes without giving up the monorepo.
    Redesigning source control at Anthropic · p20
  • explicitPer-component 'superfan' Claudes, each watching one system's telemetry and logs in a Slack channel via Claude Tag (scion-daemon, scion-cache, the Antique merge queue), are asserted to catch subtle and novel issues that conventional alerts, which remain in place, miss.
    Redesigning source control at Anthropic · p21
  • explicitScion is not a suitable general replacement for git: it only makes sense for enormous monorepos with tens of thousands of engineers or swarms of agents, it depends on Anthropic's unusually large internal token budget, and adopting it means migrating every piece of the development lifecycle (code review, search, CI), so Anthropic will not offer it as a product.
    Redesigning source control at Anthropic · p24
  • explicitAnthropic expects this class of scaling problem to become commonplace within six to 12 months and recommends git platforms adopt Scion's lessons without leaving the git model: comprehensive server-side RPCs (possibly standardized across forges), novel server architectures behind an unchanged git client model, a redesigned negotiation protocol, and sparse/shallow features that compose well.
    Redesigning source control at Anthropic · p25
  • implicitThe Scion result is a best-case demonstration: a team with pre-release model access, deep in-house expertise, design-judgment engineers and a token budget 'far' beyond what other businesses would spend, so five months and seven people is not evidence about what typical organizations can do.
    Redesigning source control at Anthropic · p29
  • implicitDesigning for always-online clients trades away offline and peer-to-peer resilience: with server-side commits and no full local copies, every agent and job depends on the continuous availability of the Scion service, which is acceptable only because failure domains are tiered and the substrate (Spanner, cloud storage) is highly available.
