Cloud Vendor Portability & Lock-in Avoidance

Structuring code and infrastructure-as-code so business logic and deployment can move across cloud providers largely unchanged — distinct from product/business-model lock-in (see moats), this concerns technical architecture avoiding a single cloud vendor's proprietary surface.

Also known as: vendor lock-in (cloud infrastructure), cloud-agnostic, multi-cloud portability, cross-cloud portability, infrastructure portability

Documents (4)

  • Presentation: How To Run on Three Clouds at Once, and When Not To Ross McFarlane, Kevin Holditch · 2026-09-11 source ↗ Reader 🖥️
    Form3 proves that a regulated payments platform can run truly active-active-active across three cloud providers by treating each cloud as nothing more than another availability zone and building custom Kubernetes operators to extend the platform's own primitives across cluster boundaries where they run out — but the same team's parallel US disaster-recovery build shows that this triple-active design is not a universal best practice: it is justified only when a specific market's resilience expectations, a mature platform-engineering practice, and a willingness to pay a real cost premium all line up, and even then the harder problem — deciding, mid-incident, whether to actually trigger a failover — remains an unresolved judgment call under uncertainty rather than something engineering can fully automate away.
  • Forsvaret med egen data-grunnlov Silje Rognsvåg · 2026-08-18 Reader 🖥️
    The Norwegian Armed Forces are building a 'data constitution' (FDSA) that makes data — not the technology or vendor processing it — the stable core of digital infrastructure, so that suppliers can be swapped without disruption; Norway's Digitalization Minister argues this same data-centric logic should extend to the rest of the public sector.
  • Cloudflare Turns CI Pipelines into TypeScript Workflows Mark Silvester · 2026-08-17 source ↗ Reader 🖥️
    By modeling a CI/CD pipeline as a Cloudflare Workflow — where every stage is a checkpointed, independently-retryable step — @cloudflare/ci trades the inspectability and policy-governability of declarative YAML pipelines for a general-purpose language, a trade whose cost (deep binding to Workflows, Sandboxes, Containers, Durable Objects and R2) only pays off for teams already committed to Cloudflare, while the durable-step execution model and the human-gated self-healing pattern it demonstrates are the ideas worth taking even without the product.
  • Presentation: Clean Architecture for Serverless: Business Logic You Can Take Anywhere Elena van Engelen · 2026-07-27 source ↗ Reader 🖥️
    Structuring Function-as-a-Service applications with a simplified Clean Architecture — a domain and application layer with zero cloud dependencies, whose separation from infrastructure is enforced not by convention but by Gradle module boundaries, wired to cloud entry points via Spring Cloud Function's dependency injection — lets a team write business logic once and deploy it, materially unchanged, to multiple serverless cloud providers, eliminating vendor lock-in without giving up native cloud capabilities.
