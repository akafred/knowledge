Back Pressure (Verification-Bound Autonomy)

The systems-thinking rule that autonomy can only expand as far as verification capacity allows (queueing back-pressure applied to agent autonomy): a loop earns automated status only if its check is cheap, fast, high-frequency, and hard to fake.

Also known as: back pressure, backpressure, back-pressure

    Because verification, not generation, is the real bottleneck of an AI-driven 'software factory,' an engineer's central job is to decide loop by loop how much autonomy each part of the pipeline can earn — full automation ('dark') only where a check is cheap, fast, and hard to fake, human judgment ('lit') everywhere else — with the human's own role relocating from writing code to owning and verifying that outer decision.

Open gaps (8)

  • illogicalThe piece argues both that free-running loops are dangerously unstructured (motivating the pivot to explicit graphs) and that short, low-stakes loops (the nightly lint-fix cron) legitimately earn full autonomy without any explicit graph structure — it never reconciles when a loop needs graph-discipline versus when it's fine to run as a pure loop; length and stakes are offered as the answer for automation-worthiness, but that criterion is never explicitly connected back to the separate loop-vs-graph argument.
    Software Factories, Light and Dark — read next: Read for a unified framework connecting loop-length/stakes-based autonomy criteria with graph/state-machine architecture choices, rather than treating them as two independent recommendations.
  • incompleteThe rule of thumb that 'an agent holds up for three to ten steps, then starts losing the thread past twenty' is stated (attributed to Dex Horthy) without any grounding for why that specific numeric range holds, what model or context window it was measured against, or whether it's expected to shift as context windows and context-management techniques improve — it's treated as a durable constant rather than a fast-moving, model-dependent empirical measurement.
    Software Factories, Light and Dark — read next: Look for benchmark data on agent step-count reliability across model generations and context-management techniques, to see whether this threshold is already stale.
  • incompleteAll observations come from a single practitioner working solo on one greenfield rebuild. The article never addresses how self-correction guidance and the threshold-increase mechanism would behave with multiple developers and multiple concurrent agents sharing the same ruleset — e.g. whether inconsistent judgment calls about suppressions/threshold increases across people or agent sessions would recreate the same 'clean house' management-overhead problem she credits agents with solving for a single author.
    Maintainability sensors for coding agents — read next: Team-scale (not single-practitioner) case studies of agent-maintained lint hygiene across many contributors and concurrent agent sessions.
  • incompleteSeveral central claims — that HTML specs net-reduce token cost, that Opus 4.7's vision model materially improves screenshot-based feedback, that the verification framework meaningfully improves reliability — are asserted from the presenter's own experience with a single demo repo, without any measurement, benchmark, or before/after comparison.
    How we Claude Code — read next: Compare against the corpus's recurring pattern of unreplicated single-author agentic-workflow anecdotes (e.g. extract-anatomy-of-an-agent-harness's own unquantified 'giving the model a way to verify its own work improves quality 2-3x' claim) for how thin this evidentiary base typically is across the corpus.
  • incomplete'Authority' is defined functionally (the system must be obliged to respond) but the essay never distinguishes how that obligation is actually enforced — a technical control (the agent literally cannot proceed without an unblocking signal), a policy/process control, or a cultural/incentive norm. These have very different failure modes, yet 'real authority' is treated as roughly binary rather than as a spectrum of enforcement mechanisms with different robustness.
    Human Oversight Is Not a Human in the Loop — read next: Read alongside back-pressure/verification-bound-autonomy material that treats authority boundaries as engineered, mechanical constraints ('only as much autonomy as you can cheaply and reliably verify') rather than primarily an organizational/cultural property.
  • incompleteThe illustrative failure-mode vignettes (specialist without authority, overloaded manager, reviewer seeing only the final answer, someone discouraged from disagreeing) are presented as plausible scenarios rather than drawn from documented incidents. No specific, named case of an AI-oversight failure grounds the argument, which weakens falsifiability — a reader cannot check whether the five-condition taxonomy actually predicts or explains a known real failure.
    Human Oversight Is Not a Human in the Loop — read next: Compare against concrete incident write-ups elsewhere in the corpus (e.g. production-database-deletion incidents where an agent operated without an approval gate, or major automated-decision failures with public postmortems) to test whether Bataller's framework actually accounts for those specific failures.
  • incompleteThe essay proposes an 'accountability contract' (checklist understood, evidence, who's accountable, system status) but never specifies how any of these fields get populated from an actual hour-scale agentic run whose intermediate decisions are, by the essay's own admission, not fully recorded and cannot all be traced back to input tokens — leaving the central operational question (how do you produce the evidence you're claiming to own) unanswered.
    Own the Outer Loop — read next: Read Osmani's own 'Quality in the Harness' and 'Software Factories, Light and Dark' for the concrete evidence artifacts (tests, static analysis, review gates) he specifies elsewhere, and read agent-governance / decision-provenance literature for concrete audit-trail mechanisms.
  • illogicalThe closing operating model instructs 'put all quality assurances and verification inside the loop' and separately 'put humans in their rightful place, on the right decisions' as if these were sequential, non-competing instructions — but the essay's own earlier claim that 'the agent can ship more than you can review' implies verification-inside-the-loop and human decision-capacity are in tension precisely as loop throughput scales, and the essay never reconciles how 'put verification inside the loop' avoids collapsing into exactly the 'dark factory' pattern its companion piece warns against.
    Own the Outer Loop — read next: Reread the dark/lit factory framework in 'Software Factories, Light and Dark,' which draws this line explicitly and carefully, for how much more precise that essay is on this exact point than this one.
