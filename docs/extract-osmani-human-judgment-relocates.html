Human judgment doesn't leave the software factory. It relocates.

Addy Osmani · article · 2026-08-21 source ↗ Reader 🖥️

Cognitive DebtContext StoreRisk TieringScope DisciplineSoftware FactoryTeam Harness / Team-Layer Coding-Agent PlatformsVerifiability (as the Quality Bar)
As software development moves from hand-coding to operating repeatable, event-driven 'software factories' of coding agents, human judgment does not leave the loop -- it relocates upstream to intent, system design, and the quality bar, and downstream to verification design, risk, and ownership of what ships -- so the best factories are defined by how intelligently they place human attention, not by how completely they remove it.

practical · mixed — A practitioner field report, largely narrative (first-person anecdotes from the author's own multi-project agentic workflow) in service of a practical argument: how and where to place human judgment when operating a software factory. The closing section states the theoretical claim ('judgment relocates, it doesn't disappear') the anecdotes build toward.

Key terms

  • software factory Software Factory
    A repeatable, event-driven loop around software work -- an incoming queue (issues, Slack, backlog) triaged and run through implementation and testing in an isolated environment with explicit human checkpoints -- distinct from simply running a coding harness (Claude Code, Codex) across several ad hoc sessions.
  • verification budget
    A deliberate sequencing of checks by cost and value across the development lifecycle -- cheap, fast, deterministic checks (linting, type checking) run early and continuously; expensive but high-value checks (full test suites, mutation testing, browser testing, security scanning) reserved for later gates (e.g. before a draft PR) -- modeled explicitly on web performance budgets.
  • run classification (success / flawed / blocked / manual)
    A taxonomy (borrowed from Vercel) for labeling the outcome of a single agentic factory run: only 'success' ships to production; 'flawed' means wrong implementation or missing context; 'blocked' means a mechanical/environmental problem (e.g. missing credential); 'manual' means a boundary the factory isn't yet allowed to cross.
  • relocated judgment
    The claim that as agents take over more code-writing, human involvement does not shrink proportionally -- it moves upstream (choosing the problem, architecture, quality bar) and downstream (deciding which verification signals to trust, when evidence is sufficient to ship), rather than leaving the loop.

Arguments

A software factory should be optimized for the reviewer's decision cost, not for raw generation or merge throughput.
Explicit premises:
  • Every version of a software factory still routes its output to one person's attention at the review/approval boundary
  • Removing or deferring human review increases perceived throughput but does not remove the underlying verification work -- it only hides it (per the sibling essay's 'dark factory' framing)
Implicit premises:
  • Human attention, not code-generation capacity, is the scarce resource in an agentic pipeline
  • A factory that doesn't reduce the cost of the decisions a human still has to make hasn't actually bought the organization anything, however many PRs it produces
Inferences:
  • Measuring a factory purely by cycles-per-day or merges-per-day, without tracking reviewer time-per-decision, will systematically overstate its value

Narratives

  • 'A wrong-project mistake': while juggling several parallel agent sessions across different projects, Osmani accidentally pasted a dark-mode implementation prompt into the wrong project's session, and states plainly that he doesn't want his software factory capable of making that same mistake.
    → Grounds the abstract claim that ownership and scoping need to be encoded into the system rather than trusted to an individual's unbroken attention -- the lived instance behind the proposition that factories should encode team/engineering culture structurally.
  • 'The feature I had to relearn': a favoriting feature passed its tests and was merged and personally approved, but days later, when Osmani wanted to tweak it, he found he could not explain how his own merged, approved code actually worked, and had to re-learn it from scratch before guiding the agent on the change.
    → Demonstrates comprehension/cognitive debt concretely -- shows that passing tests and personal sign-off are not the same as retained understanding, grounding the abstract 'comprehension debt' claim in a specific first-person failure rather than a general warning.
  • 'The 82-minute factory run': building out a demo movies app, Osmani's factory took far longer than expected on individual features once verification, retries, and a human decision point were included -- a 'quick finder' feature with no rejections took 7 minutes, while 'Favorites,' with two rejections and a human decision in the middle, took 56 minutes in the same factory.
    → Grounds the 'verification budget' and 'run classification hides cost' propositions in a measured, specific example rather than an abstract claim, and motivates pairing per-stage timing with outcome labels.

Questions addressed

  • ✅ Does increasing agent autonomy mean humans leave the software development loop?
    No -- human judgment relocates upstream (intent, design, quality bar) and downstream (evidence, risk, ownership) rather than disappearing; the best factories are defined by how intelligently they place human judgment, not by how completely they remove it.
  • ✅ When does a team actually need a dedicated software factory rather than just using a stock coding harness across multiple sessions?
    When the work needs to be repeatable and event-driven -- an incoming queue that must be triaged, implemented, and tested consistently without sessions colliding or losing track of who owns what.
  • ⭕ How do you know whether a given verification check is actually buying safety versus just adding overhead?
    The piece proposes studying checks for relevance and noise ('are they irrelevant, are they noisy, are they actually making the system safer') but gives no method for doing so beyond ad hoc observation on the author's own single demo project.
  • ⭕ Where should the trajectory, lessons, and rejected approaches from a long or compacted agent session actually be stored so they survive context-window compaction and are available to a team, not just the one operator?
