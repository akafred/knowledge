Multi Agent Collaboration Gets Persistent Compute in Bedrock AgentCore

Matt Saunders · rss · 2026-08-19 source ↗ Reader 🖥️

Agent-to-Agent ProtocolsAI Unit EconomicsCompute & Energy InfrastructureLong-Running & Managed AgentsMulti-Agent OrchestrationSandboxing
Amazon Bedrock AgentCore's new runtime instances add a persistent, EC2-backed compute option alongside its existing eight-hour microVM sessions, and the right choice between the two is a workload-shape decision (session length, GPU/memory needs, multi-agent co-location, sustained CPU utilization) rather than a wholesale replacement of one by the other.

theoretical · expository — A news-analysis piece: it reports AWS's product announcement (runtime instances for Bedrock AgentCore) and then synthesizes third-party analyses (Enkompass's engineering guide, eCorpIT's cost analysis, Four Signals, daily.dev, LinkedIn commentary) plus a comparison to Microsoft's Azure Foundry hosted agents. It asserts what is true about the new capability and its trade-offs rather than arguing the reader should do anything specific, though it implicitly guides an infrastructure decision (when to choose instances vs. microVMs).

Key terms

  • runtime instances
    A second AgentCore compute option: agents run on managed Amazon EC2 in the customer's own account, for up to fourteen days, with shared file systems and GPU-accelerated instance types, while still using the existing AgentCore APIs, identity and observability model.
  • capacity provider
    A new primitive (per the Enkompass guide) that defines allowed instance families, OS, networking and storage, and acts as a contract between agents and the EC2 capacity AgentCore provisions, patches and scales on the team's behalf — including bounds like min/max instance counts and target utilization.
  • microVM (as contrasted with runtime instances)
    AgentCore's original, default serverless compute model: fast-starting, per-session-isolated, billed per vCPU-hour and GB-hour, capped at eight hours of continuous runtime.
  • agents call each other as tools
    Stormacq's description of the multi-agent pattern instances enable: several specialized agents on one runtime iterate autonomously within a shared session, invoking each other directly rather than each agent calling another agent's API for every handoff.

Arguments

Teams should choose runtime instances over microVMs when a workload needs more than eight hours of continuous runtime, GPUs or large memory, or benefits from several co-located agents working the same files — and should keep microVMs for everything else. strength: high
Explicit premises:
  • MicroVMs cap continuous runtime at eight hours.
  • Runtime instances support up to fourteen days, GPU-accelerated instance types, and shared file systems for multi-agent co-location.
  • MicroVMs start faster, isolate sessions per-request, and bill per-second on actual usage — better suited to short, bursty traffic.
Implicit premises:
  • The workload's shape (duration, resource needs, collaboration pattern) is knowable in advance and stable enough to justify picking one compute tier over the other.
  • Most organizations can and will run a mixed fleet rather than standardizing on one tier — the decision is per-workload, not per-organization.
Inferences:
  • Over time, 'agent runtime' will become a spectrum of tiers (like today's spectrum of serverless/container/VM compute) rather than a single choice, and platform teams will need a policy for routing workloads to the right tier.
Runtime instances are financially worthwhile only for a minority of AgentCore workloads — those with sustained utilization, GPU/memory needs, or dense multi-agent co-location — not as a general upgrade. strength: medium
Explicit premises:
  • The break-even is roughly 24% sustained CPU utilization.
  • MicroVMs can be cheaper for agents with low sustained CPU utilization and long idle gaps.
  • Runtime instances carry a management fee that commitment discounts don't reduce.
Implicit premises:
  • Most agentic workloads today have low, bursty utilization rather than sustained load (otherwise the 24% break-even would rarely bind against them).
  • eCorpIT's break-even estimate is a reliable, generalizable figure rather than a scenario-specific one.
Inferences:
  • As multi-agent, co-located workloads with high sustained utilization become more common (which the article's own framing of 'multi-agent collaboration' suggests AWS wants to encourage), the population of workloads that clear the 24% break-even should grow, making runtime instances progressively more attractive over time even at flat pricing.

Narratives

  • The AWS blog's worked example: several specialized agents (implicitly for code, tests, documentation and security) operating over a common working directory on a single runtime instance.
    → Illustrates concretely what 'agents call each other as tools within a shared session' means in practice, and implicitly supports the proposition that co-location on shared storage is a materially different collaboration pattern from agents calling each other's APIs.

Questions addressed

  • ✅ How should AgentCore support agent workloads that exceed the eight-hour microVM session ceiling, need GPUs/large memory, or benefit from multiple agents working together on the same files?
    By adding runtime instances as a second, complementary compute tier on managed EC2, governed by a new 'capacity provider' primitive, while keeping microVMs as the default for short bursty work.
  • ✅ When is runtime-instance compute cheaper than microVM compute, and what specifically drives the difference?
    Roughly at 24% sustained CPU utilization and above, because instances are billed at flat EC2 rates plus a fixed management fee (with EC2-side, but not management-fee-side, commitment discounts) versus microVMs' per-vCPU/GB-hour metering that penalizes idle time less severely at low utilization.
  • ⭕ Does adopting the vendor-managed runtime-instance layer create new lock-in, beyond the compute/framework portability AWS advertises?

Gaps

  • incompleteThe article never explains how the promised 'shared session directory' and multi-agent co-location interacts with security and blast-radius concerns — if several specialized agents (code, tests, docs, security) share one host and one file system with no API boundary between them, what stops one compromised or misbehaving agent from reading or corrupting another's work? AgentCore's identity and observability model is asserted to carry over unchanged, but identity-per-agent doesn't obviously constrain what agents can do to shared files on the same instance.
    Read next: AWS's AgentCore runtime instance documentation on the shared-session-directory security model; the corpus's existing agent-security material (prompt injection, tool-chaining attacks, blast radius) applied to co-located same-host multi-agent architectures rather than networked agent-to-agent calls.
  • incompleteeCorpIT's ~24% sustained-utilization break-even is reported as a bare number with no stated methodology — what instance family, what management-fee rate, what microVM comparison baseline, and how sensitive the figure is to workload shape (e.g., bursty-but-frequent vs. genuinely idle) are all unstated. The article treats a single third party's estimate as if it generalizes across AgentCore workloads.
    Read next: eCorpIT's original cost-analysis article for its underlying assumptions and instance-type-by-instance-type breakdown; any AWS-published cost calculator or case study for runtime instances once available.
  • incompleteThe article frames the new pattern ('agents call each other as tools within a shared session') as a smile-inducing convenience, but doesn't address how it relates to — or competes with — AgentCore's own Agent-to-Agent (A2A) protocol support, which InfoQ's own earlier coverage (cited in this same article) established as AgentCore's interoperable multi-agent mechanism. Are these two different multi-agent patterns meant for different scopes (same-host co-location vs. cross-network agent discovery), or does the shared-session pattern quietly sideline A2A for same-vendor multi-agent work?
    Read next: AWS's Agent-to-Agent protocol support documentation for AgentCore (the InfoQ article on A2A support for Bedrock AgentCore cited here) and the corpus's broader agent-to-agent-protocols material, to see whether AWS itself distinguishes when to use shared-session co-location versus A2A calls between AgentCore agents.
