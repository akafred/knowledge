Bun Rewrites 535K Lines of Zig into Rust in Four Months, Eliminates Numerous Memory Leaks

Bruno Couriol · rss · 2026-09-20 source ↗ Reader 🖥️

Agentic EngineeringCapacity to Verify AI OutputCoding AgentsIncremental Rewrite GranularityMulti-Agent OrchestrationRust (Programming Language)
A single domain expert, directing dozens of parallel adversarial-review AI agents against a mechanical (behavior-preserving) porting process anchored to an extensive pre-existing test suite, rewrote a 535K-line production codebase into a memory-safer language in months instead of a year and shipped measurable bug and memory-leak reductions — but critics dispute whether passing that same test suite ever was, or could be, sufficient proof that a million lines of largely unreviewed AI-generated code are actually safe.

practical · mixed — Primarily a narrative case report (Sumner's account of the rewrite process and outcomes), but it embeds a genuine argumentative thread via Andrew Kelley's published rebuttal of the safety framing, plus a third-party (vitaminCPP) reframing of the stakes. It implicitly argues 'this approach is worth trusting,' while also reporting the counter-argument that it is not.

Key terms

  • adversarial agentic code review
    A structural separation where an implementer agent never reviews its own work and two reviewer agents (in isolated context windows, seeing only file diffs) have no task but to find bugs and behavioral divergences before a fixer agent addresses them — 'the implementer doesn't review, the reviewer doesn't implement.'
  • mechanical port
    A rewrite that preserves the original code's structure and behavior line-for-line rather than redesigning it — chosen specifically because it lets the existing test suite serve as an oracle, at the cost of some regressions rooted in surface-level Zig/Rust syntactic similarity.
  • unreviewed slop
    Andrew Kelley's characterization of the merged Rust code: over a million lines accepted into production without genuine human line-by-line review, regardless of how many automated gates it passed.

Arguments

The rewrite's process was rigorous enough that the resulting codebase is trustworthy to ship, despite being largely AI-generated.
Explicit premises:
  • Rust's borrow checker converts a known bug class into compile errors.
  • The test suite is decoupled from the implementation language, so it remains a valid oracle across the rewrite.
  • Implementer/reviewer/fixer role separation, run in isolated context windows, was designed specifically to catch divergences before merge.
  • Extensive post-merge hardening (11 rounds of security review, 24/7 fuzzing) found and fixed the regressions that did slip through.
Implicit premises:
  • A sufficiently rigorous process-level verification loop can substitute for genuine human line-by-line review of a million lines of generated code.
  • The combination of the original test suite, fuzzing, and security review constitutes a sufficient oracle for behavioral correctness.
Inferences:
  • If this process generalizes, the bottleneck for future large-scale AI rewrites shifts from generation speed to the quality of the test/verification oracle available — codebases with weaker test suites would be substantially riskier candidates for the same approach.
The safety claim for the rewrite is a sleight of hand and the resulting code should be regarded as unreviewed. strength: high
Explicit premises:
  • Bug elimination in practice comes from dedicated engineering review effort, not from a choice of language or verification pipeline.
  • The article's own admission that the Zig test suite didn't catch all of Zig's bugs undercuts relying on that same suite as sufficient for validating a million new lines of Rust.
Implicit premises:
  • An automated multi-agent review loop is not equivalent in kind to genuine independent human engineering review.
  • Code merged without that human review carries real risk regardless of how many automated gates it passed.
Inferences:
  • If Kelley is right, the 128-bugs-fixed and memory-leak-elimination results should be read as evidence of test-suite/fuzzing thoroughness on this particular project, not as evidence that the rewrite methodology is generally safe — a claim the article does not test on a second codebase.

Narratives

  • Sumner's own account of the week-long spike: starting from 'I didn't expect it to work' skepticism, watching the test-suite pass rate climb over a few days, and moving to 'I'm going to merge this' confidence.
    → Implicitly supports the proposition that empirically watching pass rates rise is treated as a legitimate basis for trusting a large AI-generated change, in place of a priori certainty.
  • The in-process bundling memory test: 2,000 consecutive Bun.build() operations plateauing stably at 609MB in Rust versus climbing past 6.7GB previously.
    → Supports the memory-leak-elimination claim with a concrete, falsifiable before/after measurement rather than an anecdote.

Questions addressed

  • ✅ Can a small, AI-orchestrated effort safely rewrite a large legacy codebase into a memory-safer language faster than a human team could?
    Sumner's account resolves this affirmatively for this case, citing the completed rewrite, bug fixes, and memory-leak elimination — though the resolution is explicitly contested by Kelley.
  • ⭕ Is 'all tests pass' sufficient evidence that a rewrite of this scale is behaviorally correct?
    The article's own account undercuts a 'yes': 19 subtle regressions were found only after merge, via fuzzing and security review, not via the original test suite — yet the piece does not reconcile this with its framing that the process worked as intended.
  • ⭕ What is the true all-in cost of this approach compared to the human-only counterfactual, including internal-vs-external token pricing and the ongoing maintenance risk of a largely AI-authored codebase?
