Presentation: Clean Architecture for Serverless: Business Logic You Can Take Anywhere

Elena van Engelen · rss · 2026-07-27 source ↗ Reader 🖥️

Clean Architecture (Ports & Adapters / Hexagonal Architecture)Cloud Vendor Portability & Lock-in AvoidanceEvolutionary Architecture & Fitness FunctionsModularity & Coupling
Structuring Function-as-a-Service applications with a simplified Clean Architecture — a domain and application layer with zero cloud dependencies, whose separation from infrastructure is enforced not by convention but by Gradle module boundaries, wired to cloud entry points via Spring Cloud Function's dependency injection — lets a team write business logic once and deploy it, materially unchanged, to multiple serverless cloud providers, eliminating vendor lock-in without giving up native cloud capabilities.

practical · mixed — A conference talk arguing for a specific course of action (structure your FaaS code this way to get portability) — practical, not theoretical. Form is mixed: expository explanation of serverless/Clean Architecture/Terraform CDK, two personal narratives (the book-editing workflow, the Dutch pension life-events domain) used as motivating examples, a live demo that functions as empirical demonstration/argument, and an argumentative Q&A where the audience pressure-tests and refines the speaker's abstraction boundaries in real time.

Key terms

  • Clean Architecture (as used here)
    A simplified, three-layer variant — domain, application, infrastructure — appropriate to a single-responsibility function, not the full classical set of concentric rings from the canonical formulation.
  • Business logic
    Domain objects, domain validation, and application-layer use cases — code that has zero dependency on any cloud SDK and is meant to be identical regardless of where it runs.
  • Infrastructure (layer)
    Cloud-specific glue code: function triggers, entry points, and calls into concrete cloud SDKs (Blob storage, S3, SES, ACS) — deliberately disposable, replaceable per cloud, and expected to eventually be machine-generated.
  • Portability / cloud-agnostic
    The property that the same business-logic artifact, unmodified, runs correctly once wired into a different cloud's entry point and infrastructure implementations — demonstrated, not just claimed, via the live dual-cloud demo.
  • Gradle module (as enforcement mechanism)
    A build-tool-level dependency declaration (in settings.gradle / module build files) that makes violating the dependency rule a compile failure, not just a style guideline.
  • Terraform CDK (CDKTF)
    A layer over Terraform that lets you author infrastructure definitions in a general-purpose language (here, Kotlin) and generate/reuse the underlying Terraform config across languages and, in her case, across cloud providers.

Arguments

You can achieve real business-logic portability across serverless cloud providers, without sacrificing native cloud capabilities, by separating business logic (domain + application) from infrastructure code via a Clean-Architecture-style dependency rule enforced at the Gradle module level.
Explicit premises:
  • FaaS functions have a single responsibility, so a simplified (not full) Clean Architecture layering is enough.
  • Domain and application layers have zero cloud dependencies; the infrastructure layer holds all cloud-specific code (triggers, storage SDKs, email SDKs).
  • Gradle module dependency configuration physically prevents infrastructure code from leaking into domain/application — the build fails if it does.
  • Business logic is injected into cloud-specific entry points (the AWS Lambda handler, the Azure Function) via dependency injection (Spring Cloud Function) rather than written inside them.
Implicit premises:
  • The parts of an application that vary between clouds are confined to entry-point/trigger wiring and to calls that touch actual cloud SDKs — everything else (validation rules, domain objects, orchestration order) is cloud-independent by nature.
  • Compiler/build-enforced boundaries are a more durable guarantee of architectural conformance than code review or documented convention, especially under time pressure.
Inferences:
  • The same technique should generalize to other backing services beyond storage and email (queues, secrets, config) as long as they are accessed through hand-rolled interfaces rather than directly through a cloud SDK.
Terraform CDK is the right infrastructure-as-code choice specifically when deploying the same conceptual infrastructure to multiple cloud providers.
Explicit premises:
  • CDK lets you write infrastructure definitions in a general-purpose language and reuse/generate Terraform config for different providers.
  • It brings developers into infrastructure work more easily than raw Terraform HCL, helping DevOps in practice.
  • Terraform modules are reusable and can be authored once and consumed from CDK in different host languages.
Implicit premises:
  • The extra abstraction and verbosity of CDKTF (versus a provider-native CDK like the AWS CDK) is worth paying specifically for the multi-cloud case, even though the speaker herself prefers the native CDK for single-cloud work.
Inferences:
  • Teams targeting only one cloud provider should prefer that provider's native IaC tool over Terraform CDK, per the speaker's own admission.
The interface boundary between business logic and infrastructure should be drawn at 'requires knowing a concrete technology,' not at 'sounds technical' — so an operation like 'save a document somewhere' belongs on the business-logic-facing interface even though persistence sounds like an infrastructure concern.
Explicit premises:
  • The original interface/function name ('upload to object storage') implicitly named a technology-classified concept.
  • Participant 1 argued the abstraction should hide even which kind of store (object store vs. database) is used, not just which cloud.
  • The speaker agreed and reframed the interface as 'save' / 'persist', callable without knowing the cloud or store type.
Implicit premises:
  • Any name that hints at the concrete technology behind an interface is itself a portability leak, even when the implementation is already swapped correctly per cloud.
Inferences:
  • The same audit should be applied to every other infrastructure-facing interface in the talk (email sending, logging) to check for hidden concreteness the speaker did not examine live.

Narratives

  • The speaker's own book-writing/editing workflow — each chapter renamed to track review stage, emailed between author, editorial reviewer, and technical reviewer, with a manual exception path if an already-finalized chapter needs revisiting.
    → Motivates why you'd want to automate a 'validate → save → review → notify' workflow with FaaS event triggers, and grounds the abstract demo application in a real, personally experienced manual process rather than an invented toy example.
  • The Dutch pension domain: participants and pension funds as domain objects, and 'life events' (marriage, divorce, death) that must be registered because they change who has a legal claim on a pension, sometimes decades later.
    → Illustrates, by example, that real business logic can be complex, long-lived, and jurisdiction-specific — implicitly arguing for the value of the dependency rule, since logic this consequential and durable should not be entangled with any one cloud vendor's infrastructure choices.
  • The live cross-cloud demo: uploading chapter 13 via Postman to the AWS endpoint and chapter 8 to the Azure endpoint, watching each get validated, saved to S3/Blob storage respectively, reviewed (via a placeholder random-string 'AI review'), and emailed back with a secure link — using the same business logic in both cases.
    → Functions as the empirical proof-of-concept for the unity and for proposition 4/argument 1 — it is the demonstration that the described architecture actually delivers the promised portability, not just an argument for why it should.

Questions addressed

  • ✅ Does using serverless secretly lock you into a cloud vendor?
    Not necessarily — vendor lock-in is a consequence of how you structure your code, not an inherent property of serverless, if business logic is architecturally separated from infrastructure.
  • ✅ How do you keep FaaS business logic maintainable without pulling in a full container-app's worth of architectural layers?
    Use a simplified, three-layer version of Clean Architecture appropriate to a single-responsibility function.
  • ✅ How do you physically prevent business logic from depending on cloud-specific code, rather than just asking developers to follow a convention?
    Enforce the dependency direction at the Gradle module level so violating code fails to compile.
  • ✅ Exactly where should the line be drawn between 'business/domain' and 'technical/infrastructure' — e.g., is a storage abstraction domain logic or infrastructure?
    The line should be drawn at whether using the interface requires knowing the concrete cloud or technology behind it, not at whether the operation sounds technical — but this resolution only emerged through Q&A negotiation with Participant 1, not from the talk's own upfront design.
  • ✅ Does this approach also work for cross-cloud observability/logging, not just storage and business data?
    Yes, via the same pattern: a generic logging API in business-logic code, with the cloud-specific sink (e.g., CloudWatch) configured only in the infrastructure layer.
  • ⭕ Is the added architectural overhead (extra interfaces, module boundaries, DI wiring, CDK complexity) worth it for teams that will likely never actually run the same function on two providers simultaneously?

Gaps

  • incompleteThe talk demonstrates portability for a toy two-function application with exactly one storage interface and one email interface; it doesn't show how the pattern holds up with dozens of business services, multiple storage backends, queues, and secrets managers, where interface proliferation and dependency-injection wiring complexity could become their own maintenance burden.
    Read next: Look for case studies or post-mortems of large-scale multi-cloud Clean-Architecture systems at real organizations, to see whether the pattern holds under complexity or only at demo scale.
  • incompleteThe cost of this approach relative to its benefit is never argued. Extra interfaces, Gradle module boundaries, DI wiring, and CDK complexity have a real engineering cost, but the talk never weighs that against the — for many teams, mostly hypothetical — benefit of actually being able to switch or dual-run cloud providers, when most organizations pick one primary cloud for reasons (pricing, existing platform investment) unrelated to code portability and rarely execute a true migration even when the code is portable.
    Read next: extract-outsourced-ai-still-own-the-risk#p10 raises the structurally identical unresolved premise in the AI-vendor-lock-in context ('portability is achievable enough to function as a real hedge') — worth reading together to test whether 'engineered portability' claims generalize across domains or share the same unexamined cost side.
  • uninformedThe Q&A's observability answer treats 'generic logger + cloud-specific sink config' as basically solving cross-cloud observability, but doesn't address the harder problems: correlating a single business transaction's logs, traces, and metrics when parts of it run on AWS and parts on Azure, distributed tracing across clouds, or cost/retention differences between CloudWatch and Azure Monitor.
    Read next: extract-infoq-data-driven-platform-engineering (platform engineering and observability federation across a real multi-cloud platform) and writing on OpenTelemetry's cross-cloud adoption as the actual mechanism for correlating traces, not just directing log lines.
  • illogicalThe talk frames Terraform CDK's cross-cloud reuse as a portability win ('same lingo... different dialect'), while simultaneously showing that the actual resource definitions are provider-specific (an AWS Lambda + API Gateway + IAM permission block looks nothing like an Azure Function App block). What's actually portable is the tooling/metalanguage (write infra in Kotlin instead of HCL), not the infrastructure-as-code itself — only the business-logic layer, not the infrastructure layer, is genuinely portable. The talk doesn't name this distinction, which risks readers concluding CDKTF gives infrastructure portability it does not.
    Read next: Compare with writing that distinguishes tooling-level multi-cloud consistency (shared IaC language) from artifact-level portability (the same deployable config running on either cloud) — e.g. Gregor Hohpe on multi-cloud strategy and exit costs.
