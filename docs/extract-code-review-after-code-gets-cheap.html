Code Review After Code Gets Cheap

Markus Eisele · rss · 2026-10-16 source ↗ Reader 🖥️

Agent SecurityAgentic TestingCapacity to Verify AI OutputBidirectional TraceabilityChange Blast RadiusCode Was Never the BottleneckPull Requests & Async Code ReviewRisk TieringSpec-Driven DevelopmentVerifiability (as the Quality Bar)
Because agents make code cheap while human review time stays fixed, teams should stop treating line-by-line reading as the default and instead make evidence a condition of acceptance: agree on behavior and expected blast radius before generation, trace both requirement-to-code and code-to-requirement to expose unrequested drift, scrutinize what the tests actually assert, and scale direct inspection to blast radius and evidence strength.

practical · argumentative — A prescriptive process proposal (O'Reilly Radar essay) argued through a single fictional worked example (a refund-approval feature). Its propositions serve the action: make evidence a precondition of accepting agent-generated code and allocate review depth by blast radius.

Key terms

  • Blast radius Agent Security
    How far the effects of a mistake can spread, including how hard it is to undo (a redeployed previous version cannot recover money refunded twice). It is established before implementation as the set of operations a change may affect, then checked against the implementation. A shared-client change can reach callers outside the diff.
  • Drift (in both directions)
    Divergence between the agreed specification and the implementation: requested behavior that is missing, and unrequested behavior that was added (like the retry). Detected by tracing in both directions.
  • Bidirectional traceability Bidirectional Traceability
    Borrowed from NASA software-engineering guidance: every important requirement maps to implementation and checks, and every behavior change in the implementation maps back to a reason it belongs in this pull request.
  • Evidence
    Specific checks tied to a claim and to the exact revision being approved, with results (not a generic 'tests passed'); must be refreshed if the implementation changes after the run.
  • Review record
    A short per-PR artifact (agreed behavior, evidence, additional behavior, blast radius, open question) that is part of the definition of done; the submitter owns its accuracy even if an agent wrote it.
  • Open decision
    An unplanned addition (such as the retry) that is not treated as an error but stays unresolved until its consequences are understood and a check for it is agreed.

Arguments

Teams should make evidence (agreed behavior, checks tied to the approved revision, stated blast radius) a precondition for accepting agent-generated code, and shift direct inspection to where blast radius is high or evidence is weak. strength: medium
Explicit premises:
  • Code generation is cheap but reviewer time is unchanged, so uniform line-by-line inspection will cap acceptance throughput.
  • Diff size does not predict blast radius; a small change in a shared client can reach every caller and some mistakes are irreversible.
  • Passing tests do not expose unrequested behavior or shared misinterpretation between code and tests.
  • Bidirectional traceability plus a review record makes missing and unexplained behavior visible.
Implicit premises:
  • A pre-implementation agreement on behavior and blast radius is achievable and accurate enough to serve as the baseline.
  • Evidence artifacts produced alongside the change are cheaper to check than the change itself, and are not themselves corrupted by the same agent's misreading.
  • Reviewers can reliably tell routine from high-impact changes before inspecting them.
Inferences:
  • The review bottleneck is partly a specification-quality problem: where requirements are vague, the evidence model collapses back into full inspection.
  • Sampling routine changes turns review itself into a feedback signal for the quality of the checks.
Passing tests, and even AI-judge agreement, cannot establish that an agent's change meets the requirement; a human must check the meaning of assertions against agreed boundary examples. strength: high
Explicit premises:
  • An agent that misreads a requirement will usually write tests with the same misreading.
  • Re-running the tests in separate CI reproduces agreement but cannot reveal that the expected value is wrong.
  • LLM requirement-conformance judgments can reject correct and accept faulty implementations (2026 benchmark study).
Implicit premises:
  • Human reviewers do not share the agent's misreading when boundary examples are agreed up front.
  • The benchmark study's results transfer at least partially to production review agents, despite the author's own caveat.
Inferences:
  • Pre-agreed boundary examples are an oracle independent of the agent and so are worth more than the volume of tests the agent produces.
  • Mutation-style checks (removing a rule) are a cheap way to audit agent-written tests.

Narratives

  • Refund service: an agent implements an approval step for refunds above 100 euros and adds timeout retries to a shared payment client; a timeout may mean the provider already refunded, so a retry could issue a second refund for every caller of the client.
    → Shows that a correct feature can ship with an unrequested high-blast-radius behavior and that diff size, a passing build, and the agent's own summary conceal it.
  • Threshold misreading: the agent reads 'above 100' as '100 and above' and writes tests expecting approval at exactly 100; implementation and tests agree and everything passes.
    → Illustrates that agreement between code and tests is not correctness and motivates agreed boundary examples and point-of-effect assertions.
  • An earlier acceptance test (a 100 euro refund proceeds) is edited by the agent to expect an approval request, so the new code and test agree.
    → Shows why changes to checks must be compared with the agreed baseline rather than with the new implementation.

Questions addressed

  • ✅ Once an agent has written the code, how should it be reviewed without human inspection becoming the limit on how much can be accepted?
    Make evidence a condition of acceptance: pre-agreed behavior and blast radius, bidirectional traceability, scrutiny of what tests assert, a per-PR review record, and review depth scaled by blast radius and evidence strength.
  • ✅ How can reviewers catch behavior nobody asked for when all tests pass?
    Start from the changed files, follow them into callers, and trace implementation back to a requirement; treat unexplained additions as open decisions requiring their own evidence.
  • ⭕ Can a second AI agent be trusted to do the verification and review for the first?
    Partially: useful for proposing missed cases, but its confident explanation should not stand in for checks a human can inspect, given evidence that LLM conformance judgments are unreliable.
  • ⭕ Who verifies the review record when an agent produces it?
    Assigned to the submitting developer and the reviewer, but the mechanism (what makes the record trustworthy) is not specified.

Gaps

  • incompleteThe process rests on a pre-implementation agreement about behavior and blast radius, but the author never says how the blast radius is established reliably (who maps callers and downstream effects, with what tooling) or what happens when the agent's change reaches code nobody listed. The retry-in-shared-client example is caught only because the author constructed it; there is no account of how a reviewer finds an unknown blast radius in a large codebase.
    Read next: Work on change-impact analysis and dependency/call-graph tooling for agent diffs; compare with the risk-tiering and blast-radius treatments in extract-agentic-code-review.
  • incompleteThe review record is authored on the submitter side, often by the same agent that wrote the code, yet is treated as trustworthy evidence. The piece does not address how to keep the record honest (the same agent can omit the retry from its summary, the failure the author describes) beyond starting review from changed files, nor the added reviewer cost of reading yet another artifact per PR.
    Read next: Look for treatments of generation/evaluation separation and independent verification of agent self-reports, e.g. the corpus's material on generator-evaluator splits and shared blind spots among writer, tests, and reviewer agents.
  • incompleteNo empirical evidence is given that evidence-gated review reduces defects or raises throughput; the only case is a fictional refund example with an unambiguous quantitative rule. It is unclear whether the approach works for fuzzier requirements (UX, performance, exploratory work) where boundary examples cannot be written up front.
    Read next: Seek field data on review policies for agent-authored changes (defect escape rates, review time) and approaches for non-crisp requirements, such as evals, telemetry-grounded development, or property-based tests.
  • incompleteReview's knowledge-distribution and design-feedback functions are not considered. If routine changes get less inspection and the team no longer reads each diff, the team stops absorbing how the system works; the argument treats review purely as an acceptance gate for correctness.
    Read next: Revisit the knowledge-sharing and learning functions of review in the corpus (extract-agentic-code-review, extract-async-code-reviews-choking-throughput) and ask what replaces them when inspection is reduced.
