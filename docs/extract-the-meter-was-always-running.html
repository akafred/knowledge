The Meter Was Always Running

Bennie Haelen · rss · 2026-07-23 source ↗ Reader 🖥️

Agent Governance (Internal)Agent ObservabilityAI Unit EconomicsFeedback LoopsGuardrailsPlatform EngineeringPolicy-as-Code
Because a control plane can only govern a loop it can independently observe, organizations running tool-using agents must build one below-the-agent, turn-level, fleet-queryable observability substrate -- not per-run trace viewers, billing dashboards, or agent self-reporting -- and that single substrate, not three separate systems, is what answers cost, delegation, and runaway-action governance at once.

practical · argumentative — Argues for a specific engineering action (build a loop-aware, below-the-agent observability substrate) using a mix of an opening narrative hook, a theoretical reframing (the loop, not the request, is the unit of observation), and a concrete design specification (signal table, SQL query, pilot description).

Key terms

  • control plane Platform Engineering
    The platform layer above individual agents where an organization centralizes observability and enforces policy, access, budget, routing, and execution constraints -- distinguished from the evidence/observability layer beneath it that the control plane reads from.
  • observability substrate
    The fleet-queryable, loop-aware store of turn-level signals (tokens, tools, guardrail decisions, identity/authority) that the control plane reads from -- evidence, not a visualization layer.
  • instrumentation points
    The runtime chokepoints an agent's execution must pass through and cannot bypass -- model gateways, tool proxies, API gateways, execution sandboxes, runtime harnesses, policy engines -- and therefore the only valid place to capture governance evidence.
  • the loop / the turn
    The unit of agent work -- one reason/act/observe cycle -- proposed as the natural unit that traces should represent, replacing the request as the atomic thing being observed.
  • metadata by default, content capture by exception
    A data-minimization design rule: capture structural/quantitative evidence (ids, counts, sizes, policy decisions) by default, and raw prompt or tool-result content only when specifically justified -- enough evidence to reconstruct why a run behaved as it did without an uncontrolled archive of sensitive payloads.
  • loop bound / payload cap
    Deterministic circuit-breaker thresholds (max turns, max tool-result size) whose firing is itself a governance signal -- a run that stops because it hit a bound is categorically different from one that stops because it completed.

Arguments

Organizations must instrument the agent loop itself (turn-level, below-the-agent, fleet-queryable) rather than relying on billing, application logs, or per-run trace viewers. strength: high
Explicit premises:
  • Billing and application logs are request/aggregate-level and can't attribute cost to a specific design choice inside the loop.
  • The agent cannot be a reliable system of record for its own authority, cost, or refusals.
  • Fixed call graphs and service maps don't hold for agents because every run can trace a different path through the same prompt.
Implicit premises:
  • A control plane's enforcement decisions are only as good as the evidence they can read, so incomplete or agent-controlled evidence silently degrades enforcement even when the policy itself is correct.
  • Turn-level metadata (counts, ids, sizes, decisions) is sufficient evidence for governance action, without needing a semantic understanding of what any given turn's content actually contained.
Inferences:
  • If turn-level metadata explains cost, delegation, and runaway-action outcomes but not why the model reasoned poorly in the first place -- a distinction the piece never draws -- then the substrate solves governance's accounting problem but not its debugging/improvement problem.
The same substrate should be built once, because cost, delegation, and runaway-action governance are really one evidentiary problem, not three separate ones.
Explicit premises:
  • All three failure types are only visible through the same turn-level structure: run/turn ids, token/model accounting, tool-call events, guardrail decisions, identity/authority context, and outcome metadata.
  • Building three separate systems for three governance problems would duplicate the same underlying instrumentation.
Implicit premises:
  • The organizational teams that own cost (FinOps), security/delegation, and reliability/incident-response are willing and able to share a single substrate and schema rather than each building bespoke tooling -- a coordination assumption the piece doesn't examine.
Inferences:
  • If those teams have different retention, access-control, or query-tooling needs (e.g., security wants raw payloads under legal hold, FinOps wants only aggregates), a genuinely shared substrate needs per-team views or redaction layers the piece doesn't describe.

Narratives

  • A team opens its first agent invoice, sorts runs by cost, and finds one that cost 40x the median -- and the provider meter, the application logs, and the trace viewer are each individually clean, none explaining why this run wandered while its neighbors finished cleanly.
    → Dramatizes the core distinction the whole piece rests on -- visibility vs. attributability -- and motivates the need for a different kind of evidence than any existing tool provides.
  • Revisited later with a loop-aware trace: turn 3 retrieved 80,000 rows, turn 4 carried that result forward, turn 5 selected the expensive model, turns 6 through 11 retried the same tool call with slightly different parameters, and the run stopped because it hit a loop bound rather than completing cleanly.
    → Turns the abstract signal table into a concrete causal story, showing what the proposed substrate would have revealed that the old trace couldn't -- the payoff example for the whole argument, and support for the reinforcing/balancing-loop reading of proposition 9.
  • A pilot for a large healthcare organization built this observability layer first, on OpenTelemetry, Cloud Trace, and a usage-log table in the warehouse, with the author noting the particular stack matters less than the shape.
    → Grounds the abstract substrate in a real, in-progress deployment and signals that the recipe is meant to generalize beyond the specific tools named.

Questions addressed

  • ✅ Why does an honest, correct bill still feel unexplained?
    Because billing and logs are request/aggregate-level; attribution requires turn-level, causal evidence of what happened inside the loop that produced the cost.
  • ✅ What is the minimum concrete signal set an organization needs to instrument agent loops?
    Run/turn structure, token and model accounting, tool-call events, guardrail decision events, identity and authority context, and outcome/bound metadata, stored in a fleet-queryable table.
  • ✅ Can the agent be trusted to report its own cost, authority, and refusals?
    No -- self-reporting is exactly what fails an auditor and what a clever prompt can talk its way around; evidence must come from instrumentation points below the agent that it cannot bypass.
  • ✅ Doesn't existing tracing/observability tooling already solve this?
    No -- existing tools show one run's path through a UI; the gap is completeness, agent-independence, and fleet-wide queryability, not visualization.
  • ⭕ Given the metadata-by-default, content-capture-by-exception rule, how does the substrate ever explain the semantic 'why' behind a model's choice to retry, escalate, or pick an expensive path -- as opposed to merely the 'that' and 'how much'?

Gaps

  • illogicalThe piece promises evidence 'to reconstruct why a run behaved the way it did' while simultaneously prescribing metadata-by-default, content-capture-by-exception as the data-minimization rule. But in an LLM loop the 'why' is largely semantic -- it lives in the prompt and tool-result content the design says not to store by default. Turn counts, byte sizes, retries, and policy decisions can show that a run wandered (which turn, how much, how many retries) but not what the model was reasoning toward when it chose to retry or picked an expensive model. The recipe answers 'that' and 'how much' more convincingly than the 'why' its own framing promises.
    Read next: extract-fowler-bockeler-static-sensors-iii draws exactly this computational-vs-inferential-sensor distinction for code modularity review and argues explicitly that deterministic (computational) sensors alone are insufficient where semantic interpretation is required -- the same lesson applied to a different loop.
  • incompleteThe instrumentation points -- model gateways, tool proxies, execution sandboxes -- are assumed to be chokepoints the agent 'can't bypass.' That holds when every tool and model call must cross a mediated API. It's less obvious for an agent that writes and executes its own code inside a sandbox, which can perform internal retries, sub-calls, or state changes that never cross an instrumented boundary until a final result is returned. The piece doesn't address what 'below the agent' means once part of the loop is the agent's own generated code running inside the sandbox rather than a call the harness mediates.
    Read next: Sandboxed code-execution agent architectures and network-egress-level containment (the fallback chokepoint when application-layer instrumentation can be walked around from inside a sandbox) -- see extract-prompt-injection-to-data-exfil-in-3-hops for the analogous move of pushing the deterministic control down to a boundary the agent's own code can't route around.
  • incompleteThe piece assumes that once evidence lands in a fleet-queryable store, 'a control plane uses what happened to change what happens next' -- treating technical visibility as sufficient for governance action to actually follow. It doesn't address organizations where the real blocker on acting on inconvenient evidence (a team's own cost pattern, a flagged delegation) is political rather than technical: whether a finding gets acted on depends on who owns the metric, who is implicated by it, and whether disclosure is met with stewardship.
    Read next: extract-tbm-426-trouble-with-mirrors argues that visualizing how a system works and 'embracing transparency' cannot by themselves improve it, because organizational truth is positional and negotiated among parties who each have something at stake in what gets seen -- automating the mirror (a policy engine's deterministic deny) narrows but doesn't eliminate the human, political layer that decides what the mirror is allowed to show and who has to answer for it.
