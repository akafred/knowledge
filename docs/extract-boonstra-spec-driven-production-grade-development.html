Spec-Driven Production Grade Development In The Age Of Vibe Coding

Lee Boonstra · pdf · 2026-06-18 Reader 🖥️

Because agentic coding has eliminated the implementation bottleneck and shifted it downstream to the humans who must review, integrate, and govern AI-generated output, production-grade development requires treating specifications as a disposable-code-enabling source of truth, redesigning team review culture (risk-bundled PRs, conditional approval, no-blame norms, tiered continuous reviewers) around that volume, and backing both with defense-in-depth technical guardrails (sandboxing, policy servers, context hygiene) rather than relying on speed of writing or any single control.

practical · mixed — A Google whitepaper (part of a multi-day series) mixing expository framing, prescriptive technique ('plays' on spec formats, review tiers, policy servers), worked code snippets, and anecdote (the hallucinated-email incident, the fintech review-tier case). Written entirely from the vantage point of Google's own agentic tooling (Antigravity, Gemini CLI, ADK).

Key terms

  • Vibe coding vs. vibe-in-production
    Vibe coding is using AI to generate code rapidly from high-level intent rather than rigid manual coding; 'vibe-in-production' is the author's named anti-pattern — relying on that unvalidated output directly in production without full intention and control.
  • Code is disposable
    Once a rock-solid specification exists, the entire codebase implementing it can be regenerated repeatedly (even in a different language) without loss, because the spec — not the code — carries the design intent; this removes the emotional/sunk-cost attachment developers have to any particular implementation.
  • Context fragmentation
    The digital equivalent of the game 'telephone': an agent loses the plot because it is working from an outdated snapshot of files or specs that have since changed, producing code based on stale assumptions.
  • Conditional LGTM
    A reviewer approves a PR contingent on it passing all automated tests; if tests turn green, the code merges automatically — proposed specifically to eliminate multi-hour cross-timezone approval delays.
  • Policy Server (structural + semantic gating)
    A two-layer governance component intercepting every agent tool call: structural gating is fast, deterministic, role/environment-based allow-listing (e.g., a viewer role cannot call send_email); semantic gating uses a second LLM to judge whether an allowed action's content violates a natural-language policy (e.g., unmasked PII in an otherwise-permitted email).
  • Context hallucination (risk)
    When an agent lacks specific data needed to complete an action, it fills the gap using whatever strings happen to be present in its current context — including sensitive values like hardcoded email addresses or URLs — rather than refusing or asking.

Arguments

As AI eliminates the code-production bottleneck, an organization's safety net must shift from catching mistakes in the code itself to governing the behavior of the agents producing it, because review volume alone cannot catch every failure mode. strength: high
Explicit premises:
  • Implementation speed is no longer the constraint, so review volume increases sharply.
  • A single under-specified agent action can cascade into a serious incident before any reviewer sees a diff (the hallucinated-email case).
  • Static, deterministic permission rules cannot detect every semantic policy violation (e.g. unmasked PII inside an otherwise-permitted action).
Implicit premises:
  • Governance infrastructure (policy servers, sandboxes, context hygiene middleware) is a tractable engineering investment organizations can build and maintain in-house.
  • No single control (sandboxing alone, or human review alone, or structural rules alone) is sufficient on its own.
Inferences:
  • Production-grade reliability for agentic systems requires defense-in-depth — structural gating, semantic gating, sandboxing, context hygiene, and human-in-the-loop checkpoints together — rather than any single control.
Teams should adopt the lowest-tier continuous code-review runtime that catches what actually matters to them, rather than defaulting to the most sophisticated (Tier 3, knowledge-graph-backed) architecture. strength: medium
Explicit premises:
  • Tier 1 (managed/vendor) costs nothing to set up but applies generic criteria that miss what is specific to a team.
  • Tier 2 (a self-written review skill triggered from CI) is roughly a day's work and lets a team encode its own criteria.
  • Tier 3 (a fully custom agent runtime) requires owning evaluation, observability, cost, and on-call, and is needed specifically when the reviewer must retain memory across a multi-PR refactor or decompose large-scale compliance/impact analysis.
  • In the cited fintech example, moving from Tier 1 to Tier 2 resolved the team's actual problem (false-positive compliance comments) without ever needing Tier 3.
Implicit premises:
  • Most teams' real review-failure mode is 'generic criteria miss our specifics,' which Tier 2 already fixes, rather than 'needs persistent cross-run memory,' which only Tier 3 fixes.
Inferences:
  • Tier selection should be driven by diagnosing where a team's review process is actually failing, not by what the most advanced vendor capability can technically do.

Narratives

  • During a routine code update, a browser-automation agent in auto-approve ('YOLO') mode autonomously clicked a newly created button intended for an unrelated, deprecated email agent; lacking a specified URL, it hallucinated a connection and fifty colleagues received false, hallucinated emails.
    → Grounds the abstract 'context hallucination risk' concept in a concrete, named incident, and functions as the paper's central cautionary tale motivating every downstream guardrails recommendation (sandboxing, policy server, context hygiene).
  • A platform team at a mid-size fintech started on a Tier 1 (managed/vendor) continuous reviewer, found it flagging boilerplate auditors had already cleared while missing the one pattern that actually mattered (unmasked PII in log statements), then wrote a 40-line compliance-check skill wired into a GitHub Action (Tier 2) that sharply cut false positives within a week — and never needed Tier 3.
    → Illustrates and supports argument A2's claim that teams should pick the lowest tier that catches what matters, by showing a real diagnosis-and-upgrade path rather than a hypothetical one.

Questions addressed

  • ✅ Does raw code-generation velocity translate into shipped, trustworthy software?
    No — without review and integration capacity to match, speed just produces a bigger backlog of unreviewed output; velocity has to be matched by downstream governance to count as real delivery.
  • ✅ How should specifications be written and placed so agents can act on them efficiently rather than exhausting context budget?
    Treat the spec as a lean, compiled instruction set split across the chat interface, a version-controlled specs/ folder (mixed Markdown + YAML), reusable skills, and layered system-prompt files, rather than one undifferentiated document.
  • ✅ How should team review culture change to absorb AI-generated commit volume without burning people out?
    Shift review focus from line-by-line nitpicking to architectural risk assessment, adopt Conditional LGTM to remove cross-timezone delay, build a deliberate no-blame culture, and impose structural boundaries (quiet hours) against approval fatigue rather than relying on individual discipline.
  • ⭕ Does the paper's own framing of velocity as a goal ever get examined, as opposed to just being managed?
    Not addressed — the question of whether generating a thousand lines of code by lunchtime is itself a target worth pursuing is never raised; only how to safely absorb the review burden it creates.

Gaps

  • incompleteThe paper is written entirely from a Google/Antigravity-and-Gemini-CLI vantage point — every tool, product reference, and worked example (Antigravity, Gemini CLI, ADK, Spanner Graph, Vertex AI Agent Engine) is a Google product — so every claim about what 'coding agents' or 'AI' can or should do is implicitly a claim about this specific toolchain's current behavior, never flagged as distinct from more general, vendor-neutral claims about agentic coding.
  • incompleteThe no-blame-culture proposal names the problem precisely (the person running the most agent-generated code becomes an easy scapegoat) but offers no actual process for implementing it — no RACI, no incident post-mortem format, and no way to distinguish 'broken integration process' from genuine individual negligence in a specific case.
    Read next: Read blameless-postmortem and incident-review literature (e.g. Etsy's blameless postmortem practice, SRE postmortem culture) for a concrete process this paper's bullet point gestures at but doesn't supply.
  • incompleteThe three-tier continuous-review spectrum and the 'Where to start' closing section both frame tier adoption as a single team's own choice, but never address who decides and pays for a Tier 3 investment (knowledge-graph infrastructure, dedicated evaluation/observability, on-call ownership) when the triggering codebase or compliance requirement crosses several teams' boundaries — the same single-team vantage point as the first gap, applied specifically to the review-tooling investment decision.
  • uninformedThe approval-fatigue/burnout claim ('frequent AI users are 45% more likely to experience high burnout') is sourced to a single press report of industry survey data (CNBC citing Quantum Workplace) rather than a peer-reviewed study or the author's own organization's data, and the proposed remedies (Digital Quiet Hours, Agent Insight Sessions) are asserted without any evidence that they specifically reduce AI-approval-driven burnout, as distinct from general workplace wellness practices.
