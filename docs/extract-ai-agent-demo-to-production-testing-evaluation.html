Presentation: From AI Agent Demo to Production: Automated Testing and Evaluation

Zhou Yu · presentation · 2026-09-07 source ↗ Reader 🖥️

Enterprise AI Adoption & ReadinessEvalsFeedback LoopsGuardrailsHuman-in-the-LoopMulti-Agent OrchestrationSynthetic User Simulation
Because static, single-turn benchmarks with fixed golden answers cannot evaluate multi-turn, tool-using agents whose correctness depends on live backend state and conversational history, teams must replace ad hoc manual testing with AI-simulated user personas that generate realistic, coverage-optimized conversation trajectories against which scenario-grounded, automated evaluation can run inside CI/CD — turning agent testing from the manual bottleneck that keeps roughly 95% of agents stuck in demo into a scalable, continuously-refreshed, self-improving production pipeline.

practical · mixed — A conference presentation arguing for a specific methodology (simulation-driven, CI/CD-integrated agent testing). It mixes expository sections (architecture of the scenario model, evaluation metrics), narrative demos (Sparky, the credit-card voice agent, the ArkSim CI walkthrough, the shopping-agent error trace), an explicit argumentative case for why the old evaluation paradigm fails, and a Q&A that surfaces unresolved edge cases.

Key terms

  • Trajectory entropy (tool call distribution entropy / tool call transition entropy / trajectory distance) Synthetic User Simulation
    A family of quantitative diversity metrics for the *simulator*, not the product agent: how spread out the set of tools a synthetic user invokes is (distribution entropy), how varied the sequence in which it moves between tools is (transition entropy), and how far apart different simulated conversations are from each other (trajectory distance) — together used to detect and penalize a simulator that keeps generating near-identical, low-coverage test conversations.
  • Synthetic user / simulated user
    An autonomous AI agent instantiated with a persona (demographic/behavioral profile, a goal seeded from the target agent's own declared tool capabilities, and contextual knowledge) that converses with the product agent end-to-end, over an API, to generate a realistic multi-turn trajectory — functioning simultaneously as a tester, an error-discovery mechanism, and (in privacy-restricted domains) a training-data generator.
  • Golden scenario set (as 'ever-evolving') Synthetic User Simulation
    A curated, versioned collection of (profile, goal, context) test scenarios treated as a living CI/CD regression suite that is deliberately and continuously revised — new scenarios are synthesized whenever production logs reveal a gap between real and simulated user distributions.
  • Realism (as a simulator-quality axis)
    The requirement that a synthetic user behave like a plausible real user pursuing a genuine goal — not merely an adversarial agent trying to trigger errors — verified via reward functions for adherence to the assigned profile/goal and distributional similarity to collected real-user data.
  • Cold start / warm start (applied to user simulation)
    Cold start: no production interaction data exists yet, so scenarios must be bootstrapped purely from domain-expert interviews. Warm start: production data from real human-handled interactions already exists and the simulation should be built to match that distribution.

Arguments

Agent evaluation must shift from static single-turn benchmarks and ad hoc manual testing to simulation-driven, scenario-grounded multi-turn testing. strength: medium
Explicit premises:
  • Static single-turn benchmarks require a fixed golden reference output, which cannot be defined once conversations are multi-turn and context-dependent.
  • Live tool-call state (balances, order status, inventory) changes continuously, so no static reference output can exist to compare against.
  • Manual human-tester recruitment doesn't scale, isn't repeatable across agent versions, and captures unrealistic (non-representative) user-intent distributions.
Implicit premises:
  • A viable evaluation method must be repeatable across successive agent versions without re-collecting fresh human-generated test data each time.
  • A test method needs to approximate the real user-intent distribution to have any external validity — otherwise passing the test says nothing about production readiness.
  • It is possible, in practice, to construct AI-simulated personas that adequately approximate real user goal/intent distributions (this crux assumption is asserted via the Pearson case study, not independently validated).
Inferences:
  • If simulated users can be made sufficiently realistic and diverse, manual human testing could be reduced to a final validation step rather than remaining the primary testing method — a conclusion the talk gestures at ('you only needed a more important manual testing at the end of the day') but does not fully argue for.
LLM-as-judge evaluation becomes trustworthy for agent testing only when grounded in a specific, verifiable simulation scenario rather than asked to judge an open-ended conversation in the abstract. strength: medium
Explicit premises:
  • An LLM-as-judge cannot be assumed to independently know a business's own policies, documents, or ground truth.
  • When the scenario is generator by simulation, the tester already knows the user's goal, so task completion can be verified automatically via rule-based checks against real backend state.
  • Softer, turn-by-turn quality metrics (helpfulness, brand voice) still require an LLM-as-judge, but its reliability can be improved by seeding it with curated hard-negative and hard-positive examples drawn from generated or expert-reviewed conversations.
Implicit premises:
  • Rule-based verification of a known goal against backend state is assumed to be a strictly more trustworthy ground truth than any LLM judgment, without argument.
  • Curating good hard-negative/positive seed examples for judge calibration is itself treated as a tractable, non-circular task; the talk doesn't address who verifies the curator's own judgment, or the judge's judgment of the curated examples.
Inferences:
  • If the judge's seed examples are themselves produced or selected using the same simulation/LLM pipeline being evaluated, the judge and the system under test could share correlated blind spots — an inference the talk's own description of the pipeline invites but never draws or addresses.

Narratives

  • Walmart's 'Sparky' and Amazon's 'Rufus' shopping agents shown answering product questions, pulling in review cards, and maintaining contextual understanding across a shopping session.
    → Establishes that conversational/chat-based commerce agents are already an established, deployed production category — grounding the definition of 'agent' before the talk turns to why evaluating them is hard.
  • A two-call voice-agent demo: a customer applies for and is approved for a credit card, then calls back later with follow-up questions — explicitly flagged by the speaker as 'not actually in production.'
    → Implicitly supports the claim that a technically impressive, working demo is insufficient for production in regulated domains because of compliance requirements (explicit authorization, PII, actioned database changes) — the demo's very polish is the point being undercut.
  • A walkthrough of the open-source ArkSim tool testing a GED-exam Q&A agent: defining agent capabilities and knowledge, generating scenarios, running them in a CI pipeline on every push, and producing a five-dimension scored error report.
    → Supports the technical feasibility and CI/CD-integration of the proposed simulation solution with a concrete, reproducible workflow rather than an abstract description.
  • A simulated shopping-agent conversation about order 1300's shipping status, where the agent progressively fails to answer, deflects, and cannot provide a customer-service email, with the failure traced to a broken shipping-info tool and gaps in a RAG/vector-database pipeline.
    → Supports the claim that simulation surfaces concrete, diagnosable root causes rather than a bare pass/fail score, and that it can find these errors before real users encounter them.
  • For mortgage underwriting, synthetic paystubs, bank statements, and T4 forms are generated — including deliberately corrupted variants (skewed scans, missing pages, poor lighting) — to create corner cases without using real, PII-restricted borrower data.
    → Supports the implicit proposition that simulation is a training-data solution for privacy-restricted domains, not only a testing tool.
  • A rigid 'return order' flow fails because a not-yet-shipped item can only be cancelled, not returned; the fix generalizes the flow to fall back from 'return' to 'cancel' when the order hasn't shipped.
    → Supports the claim that simulation-discovered corner cases translate directly into concrete flow/prompt redesigns, closing the loop between testing and self-improvement.
  • Pearson, serving students across 200+ countries with differing languages, testing policies, and purchasing policies, uses Arklex's simulation over a two-year relationship to make releases 'much more rigorous.'
    → Supports the claim of real, sustained enterprise ROI at genuine scale/complexity, beyond a one-off demo.

Questions addressed

  • ✅ Why do most AI agents never leave the demo phase and reach production?
    Compliance review demands rigorous evaluation, and traditional single-turn, static benchmarks cannot evaluate multi-turn, tool-using, live-state-dependent agents — so agents fail compliance review, especially in regulated industries like finance.
  • ✅ How should multi-turn, tool-using agents be evaluated when no static ground-truth reference can be defined in advance?
    By simulating a known user goal within a specific scenario, so task completion can be verified automatically against real backend state rather than compared to a fixed reference answer.
  • ✅ How can realistic agent testing be scaled without an army of manual human testers?
    By instantiating synthetic user agents as an on-demand API endpoint that can be spun up in parallel, at any time, with configurable personas.
  • ✅ How do you know the user simulator itself is any good, as distinct from the product agent it's testing?
    By optimizing the simulator on three separate axes — coverage (entropy/distance metrics), realism, and cost — with the number of genuine agent failures it surfaces as the ultimate downstream success metric.
  • ✅ How do you keep a simulated-scenario test suite from going stale as real users and products change over time?
    By continuously diffing production logs against the existing simulated distribution and synthesizing new scenarios to cover the gap.
  • ⭕ How do you validate soft, non-binary goals (e.g., 'give me a good product recommendation') that have no crisp completion condition?
    The speaker proposes inferring acceptance/rejection from a model of the simulated user's own prior history, but this substitutes one model-generated proxy (the simulated user's modeled reaction) for another (the recommendation itself), without addressing how that proxy's own accuracy is validated.
  • ⭕ How do you avoid simulated personas collapsing into caricatures of the most salient or distinctive behaviors rather than faithfully representing real user diversity?
    The speaker reframes the question as a cold-start (expert-interview-seeded) vs. warm-start (production-data-matched) distinction, but does not directly answer the caricature-vs-representativeness concern the question actually raised, especially for the harder cold-start case.

Gaps

  • incompleteThe talk never explains how to validate that AI-simulated personas actually approximate real user intent/behavior distributions. Beyond appealing to domain-expert 'interviews' for cold start and matching production data for warm start, there is no calibration metric, statistical test, or audit process offered to confirm the synthetic distribution isn't itself biased — e.g., toward whatever a small number of experts (or the generating LLM) finds salient, which is exactly the caricature concern Participant 3 raised and that the speaker sidesteps rather than answers.
    Read next: Sim-to-real transfer / distributional-fidelity literature (as used in robotics simulation), and work on eliciting representative rather than merely plausible personas from a small number of domain experts.
  • incompleteThe reliability of the LLM-as-judge itself — used for both the five-dimension per-turn scores and implicitly for the calibrated helpfulness/brand-voice metrics — is asserted, not demonstrated. There is no inter-rater agreement with human graders, no measurement of judge drift over time, and no discussion of whether the judge and the agent under test might share correlated blind spots if built on similar underlying models or seeded with examples from the same pipeline.
    Read next: The corpus's own LLM-as-judge material — extract-infoq-strands-agents-clare-liguori#p5 (judge should be a different, smaller model than the agent under test) and extract-beyond-the-200-ok-observability-for-ai#g1 (what makes an automated judge reliable).
  • illogicalThe Q&A answer to the 'soft goals' question (e.g., recommending a product) defines evaluation success as whether a modeled version of the simulated user accepts or rejects the recommendation, based on that user's own prior history. This makes the ground truth itself the output of a model in the same simulation pipeline being evaluated — a circularity the speaker does not flag, since it means the 'ground truth' can never independently disconfirm the recommender it's judging.
    Read next: Literature on reference-free/self-referential evaluation design and evaluator independence; the corpus's own material on judge-under-test correlation.
  • incompleteNo cost/ROI accounting is given for building and running the simulation infrastructure itself. The talk names running cost as a design constraint (avoiding, e.g., 10,000-conversation batches every CI run) but never quantifies the engineering cost of building personas/scenarios, judge-calibration labor, or how the total cost compares to the manual-tester process it replaces — beyond the qualitative, unquantified two-year Pearson relationship.
    Read next: Corpus material on eval/observability infrastructure cost and token/infra economics, for a fuller before/after ROI picture of adopting simulation-driven testing.

Closes gaps elsewhere

  • Beyond the 200 OK: Architecting Observability for AI · g1 — That document's evaluation-driven-development prescription presupposes a reliable automated judge for hallucination/faithfulness/relevance without saying what makes such a judge reliable. This talk gives a concrete recipe: ground the judge in a specific simulated scenario with a known, verifiable goal so task completion can be checked by rule-based verification against real backend state, and calibrate softer per-turn LLM-as-judge metrics (helpfulness, brand voice) with curated hard-negative and hard-positive examples.
  • Don't train the model, evolve the harness · g2 — That gap flags the self-optimizing harness-evolution loop's total dependence on a reliable task judge with no guidance on how to build one (its own judge was a brittle exact-filename grader). This talk supplies the missing eval-construction methodology: build the judge around simulation-generated scenarios with automatically verifiable, rule-checkable goals rather than a single brittle exact-match grader.
