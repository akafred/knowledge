For most AI agents, the four functional types of memory — working, semantic, episodic, and procedural — map cleanly onto a context window plus a handful of git-versioned files (markdown for facts/rules, a CSV for history, more markdown for reusable skills), making vector databases and graph databases unnecessary defaults, appropriate only as 'escape hatches' when a corpus genuinely becomes too large to read.

practical · mixed — Primarily practical — the terminal claim is an action recommendation ('you probably don't need a vector database'). But it is built on a theoretical scaffold: a four-part taxonomy of agent memory (working/semantic/episodic/procedural) that classifies and defines before it prescribes. An embedded infographic (a hand-drawn-style whiteboard image titled 'A practical four-part model') carries additional structural detail not present in the post text: named example files (strategy.md, rules.md, principles.md, examples.md, learnings.md) fanned out from an index.md, a worked context-window transcript for working memory, and a worked CSV example for episodic memory, plus the explicit design instruction 'Start with a file. Structure it when you need to filter or count.'

Key terms

  • Working memory Agent Memory
    What the agent is holding right now: the context window plus the goals and scratchpad it tracks. Explicitly 'not built,' only 'managed' — it is not a persistence artifact at all, it is runtime state that vanishes when the session closes.
  • Semantic memory
    Facts and knowledge: strategy, rules, what 'good' looks like. Implemented as markdown files read before a task, versioned in git. Per the infographic, structured as an index.md fanning out to named files (strategy.md, rules.md, principles.md, examples.md, learnings.md).
  • Episodic memory
    What happened before: past runs, decisions, outcomes. Implemented as a CSV in git, explicitly 'not a database.' Per the infographic, the recommended build path is 'start with a file, structure it when you need to filter or count' — i.e. a plain append-only log, escalated to a table only on demonstrated need.
  • Procedural memory
    How the agent does things: reusable steps loaded on a trigger. Implemented as 'skills, which are also files.'
  • Escape hatch
    A deliberately narrow framing device for vector stores and graph databases: tools reserved for when a memory problem outgrows 'too much to read' at ordinary agent scale, not defaults to reach for up front.

Arguments

Most agents don't need a vector database.
Explicit premises:
  • Agent memory has exactly four functional needs: working, semantic, episodic, procedural.
  • Each of the four can be satisfied by the context window plus git-versioned files (markdown, CSV).
  • Vector stores solve a different problem: similarity search across a collection too large to read (the author's example is 'enterprise search').
Implicit premises:
  • The scale of a typical individual agent's memory (one practitioner's strategy, rules, and history) is small enough to be read directly rather than requiring similarity search.
  • An agent reading/greeping files retrieves 'well enough' compared to vector similarity search for this use case — recall/precision tradeoffs are not a binding constraint at this scale.
  • The instinct to reach for a vector database is driven by pattern-matching to enterprise-search-scale problems rather than an actual scale analysis of the agent's own memory.
Inferences:
  • The argument implies a scale-dependent switch point ('too much to read') at which a vector store does become appropriate, but the author never quantifies where that threshold is.
  • The argument is implicitly scoped to a single practitioner's personal agent; it does not address whether the calculus changes for multi-agent or multi-tenant setups where aggregate memory across many agents/users could reach the scale the author concedes vector stores ARE for.
A dedicated graph database is unnecessary for most agents. strength: medium
Explicit premises:
  • Graph databases provide typed relationship queries (e.g. 'owns', 'depends on') at scale.
  • Linked markdown is already a graph the agent can walk by reading.
Implicit premises:
  • An LLM agent 'walking' linked files at inference time (following markdown links, reading referenced files) is an adequate substitute for typed graph queries for the relationship-reasoning tasks agents actually need to do.
  • The relationships an agent needs to reason about are simple/untyped enough that they don't require the query performance or type-safety a graph database provides.
Inferences:
  • This implies link density and file-naming discipline become load-bearing infrastructure — a sparse or inconsistent set of markdown links degrades the 'graph' the agent can walk, an operational risk the author doesn't address.
  • It also implies a read-time cost tradeoff (context-window budget and latency spent traversing files at inference time) versus an indexed graph database's query-time cost — a tradeoff the author asserts favorably without demonstrating.

Questions addressed

  • ✅ Which storage technology should an AI agent use for its memory?
    Files (markdown for semantic/procedural memory, a CSV for episodic memory) plus the context window for working memory — reserving vector databases and graph databases for genuine scale problems.
  • ✅ How should the different functional needs of agent memory (immediate context vs. facts vs. history vs. procedures) be organized so they aren't conflated into one undifferentiated 'memory' blob?
    The four-part taxonomy (working/semantic/episodic/procedural), each with its own storage mechanism.
  • ⭕ At what scale (file count, corpus size, retrieval latency, number of concurrent agents) does the files-based approach actually break down and require migrating to a vector or graph database?

Gaps

  • incompleteNo threshold or operational signal is given for when a team should graduate from files to a vector database. 'Too much to read' is evocative but not measurable — no guidance on file count, token budget, or retrieval latency at which the calculus flips.
    Read next: Retrieval/RAG literature on when embedding-based search outperforms lexical/structural (grep/read) search at a given corpus size.
  • incompleteThe claim that 'linked markdown is already a graph the agent walks by reading' doesn't address read-time cost: as link density and corpus size grow, an agent traversing files at inference time pays context-window and latency cost that an indexed graph database avoids by design. The tradeoff is asserted, not demonstrated.
    Read next: Corpus material comparing markdown-plus-links against ontology/graph layers for agent memory (e.g. the vault-ld extraction), which explicitly surfaces the sync/drift and query-performance costs this post elides.
  • incompleteThe four-way taxonomy (working/semantic/episodic/procedural) echoes a standard cognitive-psychology memory taxonomy but the post never acknowledges the borrowing or discusses where the human-memory analogy breaks down for an LLM agent — e.g. an agent's 'episodic' memory is explicit, structured, and directly queryable in a way human episodic memory is not.
    Read next: Cognitive-science literature on human memory systems, or corpus material comparing LLM 'workspace'/memory structures against human cognition.
  • incompleteNo discussion of multi-agent or multi-user scenarios. The 'you probably don't need a vector database' claim is scoped implicitly to a single practitioner's personal agent setup; it's silent on whether the calculus changes when many agents or many users share one memory store — which is closer to the 'enterprise search' scale the author himself concedes vector stores ARE for.
    Read next: Material on multi-agent orchestration and shared-state/memory architectures at team or org scale.
  • incompleteNo treatment of concurrency or consistency: multiple agent runs (or multiple humans) writing to the same markdown/CSV files in git raises merge-conflict and race-condition questions that a database would handle natively. The git-file approach's operational risk here is unaddressed.
    Read next: Material on concurrent/collaborative editing of git-versioned agent state, or client-side event-sourcing as an alternative structuring of the same append-only-log idea.
