Because agents can now generate more code than people can read, software quality control must move from human inspection of the code itself into deterministic constraints (tests, checks, metrics) engineered into the harness and environment around the agent.

practical · argumentative — A compressed practical argument: two premises (review no longer scales; therefore quality checks must live elsewhere) drive an imperative conclusion ('Set your constraints'). Not expository — it is making a claim and asking the reader to act on it, not just describing a state of affairs.

Key terms

  • constraints
    The deterministic tests, checks and metrics engineered around an agent that define and bound what output is acceptable — not vague guidelines but specific, automatable mechanisms (unit tests, property tests, acceptance tests, mutation testing, quality metrics).
  • harness Agent Harness
    The environment, tooling and operating-system layer around the agent — the place quality control moves to once it can no longer live in human code review. Used interchangeably with 'environment' and 'operating system around the agent.'
  • back-pressure
    A systems/queueing metaphor: constraints act as resistance that stops bad work from propagating downstream before it becomes someone else's problem, rather than a filter applied after the fact.
  • quality Code Quality
    An itemized, checkable bundle: correctness, maintainability, security, performance ("etc.") — implicitly reduced to properties a deterministic check could plausibly verify.

Arguments

Quality assurance must shift from human code review into deterministic constraints embedded in the agent's harness/environment.
Explicit premises:
  • Agents can now generate more code than people can read.
  • Historically, when humans wrote the code, its quality was verified by directly reading the code.
Implicit premises:
  • Human review capacity is fixed and does not scale with the volume of agent-generated code (the review-bottleneck premise the post never states outright).
  • Deterministic, automatable checks (tests, mutation testing, metrics) are an adequate proxy for the fuller quality checklist the post itself opens with — correctness, maintainability, security, performance, and even 'is it clean/thoughtful/understandable.'
Inferences:
  • If an agent-generating system lacks well-designed constraints, quality will silently degrade rather than fail loudly, because neither human review capacity nor an automated substitute is present to catch it.
  • The design effort in agentic software delivery shifts from writing code to writing and maintaining the harness's constraints — a different, likely underinvested, skill.

Questions addressed

  • ✅ How should software quality be assured when agents produce more code than any human can review?
    Move quality control out of human code review and into deterministic constraints and checks (tests, mutation testing, quality metrics) embedded in the harness/environment around the agent.
  • ⭕ Which quality dimensions can actually be captured by deterministic, automatable checks, versus which require irreducibly human judgment (e.g., 'is it thoughtful,' 'is it clean')?
    Not addressed — the post silently narrows from its own opening checklist (clean, thoughtful, understandable) to the subset that automated checks can verify (correctness-flavored properties), without acknowledging the narrowing.

Gaps

  • incompleteThe post never addresses who builds, tests, and maintains the constraints themselves — the harness's tests and deterministic checks are also artifacts that can be under-specified, become stale as models change, or be gamed/weakened by the very agents they're meant to bound. It treats 'set your constraints' as a one-time, self-evidently sufficient act rather than an ongoing engineering discipline with its own failure modes.
    Read next: extract-agentic-code-review.json (p15: agents will weaken CI to make themselves pass) and extract-anthropic-harness-design-long-running-application-development.json (harness components encode assumptions that go stale as models improve) — both treat the harness itself as needing continuous tending, which this post takes for granted.
  • incompleteNo discussion of which quality signals resist deterministic proxying altogether. Mutation testing and unit tests can catch correctness regressions but not architectural coherence, elegance, or long-term comprehensibility — the very qualities ('clean', 'thoughtful') the post's own opening paragraph names as markers of good code.
