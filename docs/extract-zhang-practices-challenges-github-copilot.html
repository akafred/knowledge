Practices and Challenges of Using GitHub Copilot: An Empirical Study

Beiqi Zhang, Peng Liang, Xiyu Zhou, Aakash Ahmad, Muhammad Waseem · pdf · 2023-03-15 source ↗ Reader 🖥️

Calibrated Trust (in AI Agents)Coding AgentsThe Genie (Beck)LLM Reliability Failures
Mining Stack Overflow and GitHub Discussions from Copilot's first ~17 months shows that the tool's cited benefits and limitations are near-mirror categories of each other (useful code generation vs. limited/poor-quality generation, better vs. unfriendly user experience), making Copilot adoption a case-by-case trade-off across IDE choice, budget, privacy tolerance and code quality rather than a simple win.

theoretical · mixed — Primarily a descriptive empirical study (mining Stack Overflow posts and GitHub Discussions for categorized findings) building toward factual claims about how practitioners used early Copilot — but closes with a practical implications section recommending mainstream-IDE adoption and trade-off awareness.

Key terms

  • Double-edged sword
    The authors' own framing for the finding that Copilot's benefit categories and limitation categories mirror each other one-for-one (e.g. useful code generation vs. limitation to code generation), so there is no single verdict on the tool — only situational trade-offs.
  • Difficulty of integration
    The single most-cited limitation (28.0% of limitation mentions): Copilot failing to work with, or conflicting with, a developer's chosen IDE or other installed plug-ins — distinct from server/account access problems or code-quality problems.

Arguments

Developers and organizations should weigh Copilot's integration, UX, budget, and privacy trade-offs case by case rather than treating adoption as a blanket yes/no decision. strength: medium
Explicit premises:
  • Benefit and limitation categories mirror each other one-for-one across the coded data.
  • Some developers report better user experience than competing AI tools; others report unfriendly user experience with Copilot specifically.
  • Successful integration concentrates heavily in mainstream IDEs, so outcomes depend on context (which IDE, which language/stack) rather than the tool alone.
Implicit premises:
  • There is no context-independent verdict ('good tool' or 'bad tool') available from aggregate public discussion data — only distributions of experience across contexts.
  • Public complaint/praise posts are a reasonable proxy for the trade-offs a prospective adopter should anticipate.
Inferences:
  • Organizational Copilot rollout guidance should probably be IDE- and stack-conditional rather than uniform across a whole engineering org.

Narratives

  • Quoted developer reactions pull in opposite directions on the same axis: one says Copilot 'is a lot more fun to use and does not annoy me like some other AI systems' (GitHub #7254) while another calls it 'an amazing tool with poor user experience' (GitHub #8468).
    → Illustrates the double-edged-sword thesis concretely — the same tool producing opposite verbatim verdicts from different practitioners.

Questions addressed

  • ✅ What languages, IDEs, and technologies do practitioners actually use with Copilot?
    Answered via descriptive statistics over 169 Stack Overflow posts and 655 GitHub Discussions.
  • ✅ What benefits and limitations do practitioners report when using Copilot?
    Answered via qualitative constant-comparison coding into 10 benefit and 15 limitation categories.
  • ⭕ Under what conditions do Copilot's challenges manifest as advantages versus disadvantages, and how can practitioners convert the latter into the former?
    Explicitly named as future work ('Towards an Effective Use of Copilot') rather than answered here.
  • ⭕ Who uses Copilot (developers vs. educators vs. students), and when/how/for what purposes?
    Explicitly acknowledged as unexamined by this study and left for future work.

Gaps

  • incompleteThe data window (Copilot's launch in June 2021 through the November 2022 search date) predates Copilot Chat, inline-chat editing, the @workspace context tag, and Copilot Enterprise (all added by early-to-mid 2024, per later Radar coverage) — so categories like 'difficulty of integration' and 'limitation to code generation' (a ~1000-character response cap) describe the autocomplete-only era specifically and may already have been substantially addressed by the time the paper published.
    Read next: Later, chat-era Copilot studies or Radar coverage to see which of these 15 limitation categories persisted versus were resolved by subsequent feature releases.
  • incompleteThe method mines self-selected public posts (people who chose to complain or praise on Stack Overflow/GitHub Discussions), not a representative sample or controlled study of all Copilot usage — the authors name this as an external-validity threat but do not quantify how it might bias the reported percentages (e.g., toward louder complaints or toward technically engaged early adopters).
    Read next: Controlled or survey-based Copilot usage studies that sample practitioners directly rather than mining public complaint/praise text.
