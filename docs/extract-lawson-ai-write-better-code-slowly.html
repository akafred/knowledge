Using AI to write better code more slowly

Nolan Lawson (Read the Tea Leaves) · article · 2026-05-25 source ↗ Reader 🖥️

AI SlopCode Was Never the BottleneckCode QualityCognitive DebtMulti-Agent OrchestrationPull Requests & Async Code ReviewVibe Coding
LLMs are flexible enough to produce either fast, unvetted slop or slower, carefully reviewed and understood code, and deliberately choosing the latter — running multiple different models to hunt for bugs, personally validating and triaging what they find, and refusing to ship a PR you don't fully understand — is a better way to use AI for programming, even without a velocity payoff.

practical · mixed — Primarily argumentative (rebutting the 'AI coding means slop' framing) and expository (describing a concrete personal workflow), with a few first-person anecdotal beats functioning as evidence rather than storytelling for its own sake.

Key terms

  • slop cannon
    An LLM used purely to mass-produce low-quality, barely-passable code that is shipped in large PRs without real scrutiny.
  • vibe coding Vibe Coding
    Stretched/reclaimed by Lawson to describe his own slower, carefully-reviewed style of AI-assisted coding ('this other, slower style of vibe coding') — the opposite of its usual sense.
  • juice isn't worth the squeeze
    A cost/benefit heuristic for skipping medium- or high-severity findings whose fix would cost disproportionately more effort than the bug's real impact (e.g., 100 lines of code for a narrow edge case).
  • prioritizing and validating
    The author's name for the actual bottleneck in AI-assisted bug-hunting, as distinct from 'finding' bugs, which he treats as already-solved.

Arguments

Running multiple different AI models against a PR, combined with independent human validation, produces a near-zero false-positive rate on surfaced bugs while still catching a large volume of real ones. strength: medium
Explicit premises:
  • The latest public models from Anthropic and OpenAI are individually good enough to find plenty of bugs in an unscrutinized codebase; some are better than others at avoiding false positives.
  • The more, different models thrown at a PR review, the less likely the result is hallucinations or bogus bugs (adopted insight).
  • The workflow explicitly requires the reviewer to do their own research to rule out false positives before writing a final report.
Implicit premises:
  • Different models fail in largely uncorrelated ways (different vendors, training data, architectures), so their false positives don't overlap while genuine bugs tend to be independently corroborated — an unstated independence assumption about model error.
  • The human doing 'your own research' has the time, skill, and incentive to actually verify each flagged item rather than deferring to the AI tools' severity ranking.
Inferences:
  • The technique's reliability depends on genuine model diversity; if the 'different' models converge over time (shared RLHF processes, shared training corpora), the near-zero-false-positive property could quietly erode without Lawson noticing, since his evidence is personal impression across his own PRs, not a controlled or ongoing measurement.
  • The token/time cost of running three separate reviewers plus a human validation pass on every PR is never weighed against the value captured — a resource trade-off the piece's own 'juice isn't worth the squeeze' logic would seem to demand applying to the technique itself, not just to individual bugs.
Developers should deliberately choose a slower, more careful style of AI-assisted coding — reviewing, understanding, and validating AI output — over the fast 'slop cannon' style, even without a velocity payoff.
Explicit premises:
  • His own experience shows no velocity increase from this method.
  • He finds the practice 'very satisfying.'
  • The practice is explicitly the opposite of the '10x productivity' slop-cannon style most people associate with AI coding.
Implicit premises:
  • Code quality, codebase health, and developer understanding are worth pursuing for their own sake, independent of shipping speed.
  • The intended reader is a professional developer with an ongoing stake in a codebase's long-term health, not someone optimizing for a one-off deliverable.
  • Personal satisfaction is itself a legitimate reason to adopt a technique, not merely a byproduct of output metrics.
Inferences:
  • If quality-focused AI use genuinely doesn't move velocity, this undercuts blanket claims that 'AI coding' as a category delivers large productivity multipliers — those gains may be concentrated in (or exclusive to) the slop-cannon style that trades quality for speed, meaning any fair comparison of 'AI coding productivity' needs to specify which style is being measured.

Narratives

  • The Mythos/non-Mythos bug-finding observation: LLM agents thrown repeatedly at a codebase will find far more bugs than a team can act on.
    → Establishes bug detection as already solved/abundant, clearing the ground for the article's real claim that the bottleneck has moved to prioritization and validation.
  • The described three-step triage workflow: fix criticals/highs and repeat, skip low-value mediums, abandon the PR outright if criticals reveal the approach is misguided.
    → Makes the abstract 'slow down and validate' thesis concrete and operational rather than merely aspirational.
  • The recurring 'side-quest': using this review process, Lawson repeatedly ends up fixing pre-existing bugs unrelated to the PR he set out to ship, at no velocity benefit.
    → Implicitly supports the proposition that the practice's value is comprehension and codebase health rather than speed, and normalizes lower velocity as an acceptable, even positive, outcome.

Questions addressed

  • ✅ Is finding bugs in an AI-assisted (or AI-generated) codebase hard?
    No — current agents are already good enough that bug detection is abundant; the difficulty has shifted downstream.
  • ✅ How do you avoid false positives/hallucinations when using AI to review code?
    Run several genuinely different models, then have a human independently research and rule out false positives before finalizing a report.
  • ✅ Is 'AI coding' inherently a fast, careless practice?
    No — argued to be a choice of style the developer makes, not a property of the tool.
  • ✅ Does this slower, careful style pay for itself in higher velocity?
    No clear payoff is claimed; the author explicitly reports no velocity increase and reframes the case for the practice around quality, codebase health, and personal satisfaction instead.
  • ⭕ What is the actual resource cost (tokens, wall-clock time, context-switching into unrelated pre-existing bugs) of running this technique, and when is it not worth doing?
