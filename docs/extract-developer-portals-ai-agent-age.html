Why Developer Portals Must Evolve in the AI Agent Age

Kristopher Sandoval · rss · 2026-09-22 source ↗ Reader 🖥️

Agent Governance (Internal)Agent-Native DesignAgent Tool ManagementAPI Products & SprawlMCP (Model Context Protocol)
The developer portal is not obsolete but must evolve from a human-facing documentation site into a governed capability registry that serves both human developers and AI agents as first-class consumers, because MCP provides a discovery/invocation layer but not the governance, analytics, and lifecycle infrastructure a portal supplies.

practical · expository — An advisory piece: it argues developer portals should be redesigned in specific ways (structured semantic descriptions, documented workflows, MCP servers, runtime discovery) rather than merely explaining what portals are.

Key terms

  • developer portal
    A platform combining API catalog, documentation, sandbox, key management, analytics, and governance — traditionally built for a single human-facing audience, now being repositioned to also serve machine (agent) consumers.
  • governed capability registry
    The author's proposed end-state for the developer portal: a registry that exposes machine-readable capability descriptions under governance, analytics, and lifecycle management, serving both humans and agents.
  • runtime discovery
    The mode by which agents find and invoke capabilities at the moment of need, querying dynamically rather than pre-reading documentation, in contrast to human search-driven, context-dependent discovery.

Arguments

Developer portals must be redesigned as governed capability registries serving both human and agent consumers, not replaced by MCP alone. strength: medium
Explicit premises:
  • Portals traditionally provided catalog, docs, sandbox, key management, analytics, and governance functions.
  • MCP only covers discovery/invocation connective tissue, not governance, analytics, access management, onboarding, or lifecycle management.
  • Agent consumption of APIs is growing rapidly (cited Gartner/IDC predictions).
Implicit premises:
  • Governance, analytics, and lifecycle management remain necessary regardless of how capabilities are discovered.
  • An organization cannot simply drop portal infrastructure once an MCP server exists, because operational/compliance needs persist independent of the discovery mechanism.
  • The same underlying capability surface can and should serve two structurally different consumption patterns (human browsing vs. agent runtime querying) without maintaining two disconnected systems.
Inferences:
  • Organizations that treat MCP server creation as sufficient ("any team can generate an MCP server from an OpenAPI file") will under-invest in the governance work the author says actually matters, and will likely face the access-control, auditing, and lifecycle problems the piece flags as unsolved by MCP alone.

Narratives

  • Stripe and Twilio held up as canonical examples of documentation-first developer portals; Spotify's Backstage cited as an internal-portal example aggregating documentation, service endpoints, and governance policies.
    → Establishes the baseline of what a mature (human-facing) developer portal looks like, against which the agent-native redesign is then argued.
  • Twilio quoted as saying its agents "don't browse dashboards — they need a machine-readable way to provision the full stack."
    → Supports the proposition that agent consumption patterns are structurally different from human browsing, using a named vendor's own framing as evidence rather than the author's assertion alone.

Questions addressed

  • ✅ Are developer portals still necessary now that MCP exists?
    No — MCP is necessary but not sufficient; portals remain necessary as the governance/analytics/lifecycle layer MCP doesn't provide.
  • ✅ What concretely should a portal do differently to serve agents well?
    Structured semantic endpoint descriptions, documented multi-call workflows, well-described (not just present) MCP servers, and runtime-oriented discovery mechanisms.
  • ⭕ How should organizations sequence or prioritize this redesign relative to existing human-facing portal investment?
