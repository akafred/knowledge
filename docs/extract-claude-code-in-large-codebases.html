How Claude Code works in large codebases: Best practices and where to start

At scale — multi-million-line monorepos, decades-old legacy systems, and organizations with thousands of developers — Claude Code's effectiveness is determined less by the underlying model than by a deliberately built harness (CLAUDE.md, hooks, skills, plugins, MCP servers, plus LSP integrations and subagents) and, just as importantly, by a durable organizational ownership structure (a dedicated owner or team, cross-functional governance, scheduled re-review as models evolve) that keeps good setups from staying tribal and adoption from plateauing.

Key terms

  • Agentic search
    Claude Code's approach to codebase navigation: traversing the live file system, using grep, and following references the way a human engineer would, with no embedding pipeline or centralized index to build or maintain.
  • Harness Agent Harness
    The ecosystem built around the model — specifically five extension points (CLAUDE.md, hooks, skills, plugins, MCP servers) plus two additional capabilities (LSP integrations, subagents) — that the article argues determines Claude Code's large-codebase performance more than the model itself.
  • Agent manager
    An emerging, named organizational role: a hybrid PM/engineer function dedicated to managing an organization's Claude Code ecosystem — settings, permissions, plugin marketplace, CLAUDE.md conventions — as opposed to a single engineer's informal, part-time stewardship.
  • DRI (directly responsible individual)
    The minimum-viable ownership structure for organizations without a dedicated agent-management team: one person with explicit authority over settings, permissions policy, the plugin marketplace, and CLAUDE.md conventions, and responsibility for keeping them current.
  • Progressive disclosure (for skills) Progressive Disclosure
    Loading specialized expertise (a skill) only when the task at hand calls for it, rather than keeping all possible domain knowledge present in every session — the mechanism skills use to avoid context bloat in a codebase with many distinct task types.

Arguments

Organizations adopting Claude Code at scale should invest in a dedicated infrastructure/ownership function before broad rollout, not retrofit one after problems appear. strength: medium
Explicit premises:
  • Rollouts that spread fastest had dedicated infrastructure investment in place before broad access.
  • Bottoms-up adoption fragments without centralization, and knowledge stays tribal without someone assembling and evangelizing conventions.
  • In regulated organizations, governance questions come up early and are best addressed via cross-functional working groups established before rollout.
Implicit premises:
  • The cost of standing up a dedicated owner/team before usage data justifies it is lower than the cost of a fragmented, slow-adopting rollout — an assumption about relative costs the article doesn't quantify on either side.
Inferences:
  • An organization currently running a bottoms-up, ungoverned Claude Code rollout should expect to plateau, and should backfill a DRI or agent-manager role rather than waiting for the plateau to resolve itself.
Test, lint, and context configuration should be scoped per-subdirectory rather than applied uniformly at the repo root, especially in large monorepos. strength: high
Explicit premises:
  • Running the full test suite for a one-service change causes timeouts and wastes context on irrelevant output.
  • CLAUDE.md files at the subdirectory level can specify the commands that actually apply to that part of the codebase.
Implicit premises:
  • The codebase's directory structure already maps reasonably well onto independently testable/buildable units — a premise the article itself partially contradicts by noting that 'in compiled-language monorepos with deep cross-directory dependencies, per-subdirectory scoping is harder to achieve.'
Inferences:
  • Monorepos with clean service/directory boundaries will see easier Claude Code adoption than monorepos with deep structural coupling across directories — coupling, not raw codebase size, is the harder variable.

Questions addressed

  • ✅ Does a bigger or better model matter more than the surrounding tooling for large-codebase performance?
    No — the harness (the ecosystem built around the model) determines performance more than the model alone, per the article's framing, though no comparative data isolating the two variables is given.
  • ✅ How should a large organization avoid 'good setups staying tribal' as more engineers adopt Claude Code?
    Plugins (bundling skills/hooks/MCP configs into installable packages) distributed through managed marketplaces, combined with a dedicated owner (an agent manager or DRI) who assembles and evangelizes conventions.
  • ✅ Does a CLAUDE.md configuration stay valid indefinitely once written?
    No — instructions calibrated to a weaker model's limitations can actively constrain a newer model, so scheduled review (every three to six months, or after major model releases) is recommended.
  • ✅ Who should be accountable for an organization's shared agent configuration, and does one engineer's personal setup practices transfer to team/org scale?
    A DRI at minimum, an 'agent manager' role or dedicated team at larger scale, typically sitting under developer experience/developer productivity functions, with cross-functional working groups for governance-heavy (regulated) contexts.

  • uninformedEvery claim is drawn from Anthropic's own enterprise engagements (named customer vignettes, Applied AI team experience) with no comparative or quantitative evidence — no measured adoption-speed difference between organizations with vs. without a dedicated owner, no data on how much LSP integration improves navigation accuracy, no basis given for 'every three to six months' as the right review cadence versus some other interval. This is the same evidentiary gap previously flagged in Anthropic's own earlier Claude Code best-practices article.
    Read next: Look for an independent, non-vendor study of large-codebase Claude Code (or comparable coding-agent) rollouts with adoption-speed or defect-rate metrics tied to specific organizational structures.
  • incompleteThe article names an 'agent manager' as an emerging role but doesn't address its reporting line, seniority, or success metrics, nor whether it's intended as a permanent org-chart fixture or a transitional role expected to dissolve once practices mature (the way some organizations treated an early 'DevOps team' as transitional) — a distinction that matters directly for how a reader should design the role.
    Read next: Track how this role is described in future Anthropic materials or independent org-design writing on AI-tooling ownership roles.
  • incompleteThe governance section names the problem ('how do you prevent thousands of engineers from independently rebuilding the same thing') but describes only up-front controls (a defined set of approved skills, required review, limited initial access) without describing any mechanism for detecting duplication after the fact, or for sunsetting redundant skills/plugins once an organization is already past the 'limited initial access' stage.
    Read next: Look for platform-engineering or internal-developer-portal practices on deprecating/consolidating redundant tooling once adoption has scaled past initial rollout.
  • incompleteThe 'actively maintaining CLAUDE.md' section recommends scheduled review and pruning but doesn't address the risk that removing an old compensatory rule or hook could regress behavior in an edge case the newer model still doesn't fully handle — the article's framing of review-and-prune reads more confidently certain than the underlying risk (removing a safeguard without being sure it's actually obsolete) would warrant.
    Read next: Look for guidance or tooling on testing/validating that a removed CLAUDE.md rule or hook is genuinely redundant before deleting it, rather than relying on developer judgment alone.
