12-Factor Agents: Patterns of reliable LLM applications — Dex Horthy, HumanLayer

Reliable production LLM agents are built not by adopting an agentic framework that hides the hard parts, but by applying ordinary software-engineering discipline — owning your prompts, your control flow (the loop/switch-statement/context-window triad), and your execution/business state — to what is fundamentally a stateless-function (LLM) called inside a small, deterministic, developer-controlled loop.

practical · argumentative — A conference talk distilling a published '12-factor agents' GitHub framework (borrowing the 12-Factor App naming convention) into a set of prescriptive engineering patterns for building production LLM agents, argued from the speaker's experience interviewing 100+ founders/builders.

Key terms

  • 12-factor agents
    A set of patterns (deliberately modeled on Heroku's 12-Factor App) for building LLM-based applications that are reliable enough for production, extracted inductively from observing what successful builders were actually doing to existing codebases rather than prescribed top-down.
  • tool use is harmful
    A deliberately provocative framing (parodying Dijkstra's 'Goto Considered Harmful') arguing that treating tool calls as a magical, ethereal agent-environment interaction obscures the fact that a tool call is just an LLM emitting JSON that deterministic code then acts on — demystifying it is what lets you engineer it well.
  • owning your control flow
    Keeping the loop/switch-statement/context-window-building logic as code you write and can modify, rather than ceding it to a framework's internal agent loop — because only this gives you levers like break, switch, summarize, or LLM-as-judge inside the loop.
  • micro agents
    Small agent loops of roughly three to ten steps embedded inside an otherwise mostly deterministic DAG/pipeline, handling one bounded decision point rather than the whole workflow.
  • LLMs are pure/stateless functions
    The model itself carries no memory between calls and cannot be made 'smarter' mid-task; the only lever an engineer has over output quality is what tokens are placed into the context window on each call.

Arguments

Reliable agent engineering is software engineering 101 applied to LLM calls, not a new discipline requiring an AI background. strength: medium
Explicit premises:
  • The naive LLM-agentic loop model breaks down on long workflows due to context-window degradation.
  • Treating the LLM call as a stateless function and everything else (loop, switch, state, control flow) as ordinary code gives you the levers needed to engineer around that degradation.
  • Patterns like DAG orchestration, pause/resume via state IDs, and REST/MCP-fronted services are decades-old software patterns, not novel AI patterns.
Implicit premises:
  • Software engineers already possess the relevant skills (switch statements, while loops, state machines) and lack only the specific LLM-adjacent patterns (tool-call-as-JSON, context-window curation) to apply them.
  • A framework's value should be measured by how much non-AI-hard infrastructure it removes, not by how much of the agent's own reasoning loop it owns.
Inferences:
  • Teams that cede control-flow ownership to a framework are trading away exactly the levers (break/switch/summarize/judge) needed to clear the 70-80%-to-production quality gap the opening anecdote describes.
Agent reliability is bottlenecked almost entirely on context/token quality, not on model capability or framework sophistication. strength: medium
Explicit premises:
  • LLMs are stateless functions: tokens in, tokens out.
  • The only way to affect output quality (short of retraining the model) is to control what tokens go in.
Implicit premises:
  • Context curation effort (hand-writing prompts, summarizing errors, choosing what to stringify) scales with the difficulty of the task in a way that generic framework defaults cannot match.
  • 'Getting past the quality bar' is a threshold phenomenon, not a continuous improvement — implying diminishing returns from generic tooling and increasing returns from hand-engineering.
Inferences:
  • Future gains from larger context windows (e.g. 2M-token Gemini) will not substitute for this discipline, since the talk explicitly argues that unconstrained token volume degrades rather than improves reliability.

Narratives

  • The speaker's own early DevOps agent: given a Makefile and told to 'build the project,' it executed steps in the wrong order; two hours of iterative prompt-fixing eventually produced a reliable prompt — at which point the speaker realized a 90-second bash script would have solved the underlying problem.
    → Supports the proposition that not every problem needs an agent, and frames the entire talk's motivating tension: effortful agent engineering sometimes reveals the task didn't need an agent at all.
  • The HumanLayer internal deploy bot: a mostly-deterministic CI/CD pipeline hands a single ordering decision (deploy frontend or backend first) to a small agent loop; a human intervenes mid-loop to override the order; the pipeline resumes deterministically to run end-to-end tests, falling back to a rollback agent on failure.
    → Concretely illustrates 'micro agents embedded in a deterministic DAG,' pause/resume via state, and human-in-the-loop override — the talk's central architectural recommendation made tangible.

Questions addressed

  • ✅ Why do agents that reach 70-80% quality on a task stall there instead of improving further with better prompting alone?
    Because past that threshold, further gains require hand-engineering individual tokens/context rather than iterating on a framework-generated prompt — a qualitatively different (not just more effortful) activity.
  • ✅ What should a framework for building LLM agents actually provide, given that frameworks are widely criticized?
    Infrastructure/plumbing (state persistence, pause/resume, protocol handling) rather than the agent's reasoning loop itself — the talk frames this as a 'wish list,' not a rejection of frameworks as such.
  • ⭕ How should an agent decide between acting (calling a tool) and escalating to a human?
    A technique (push the decision to the model's first generated token) is offered as a means to make this choice more legible to the model, but the talk does not resolve when/how often this decision should favor the human versus the tool.

Gaps

  • incompleteThe talk does not address how a team coordinates or reviews this hand-engineered, token-by-token prompt and control-flow discipline across multiple engineers over time — it is framed entirely from a single practitioner's vantage point, with no discussion of code review, documentation, or onboarding for the 'owned' control flow and prompts.
    Read next: extract-humanlayer-advanced-context-engineering-ace-fca.json and extract-horthy-no-vibes-allowed-complex-codebases.json (same author's later, team-scale essays) take up exactly this gap — team mental alignment, review at the plan/research layer, and scaling the practice beyond a single motivated practitioner.
  • incompleteThe claim that 'tool use is harmful' is framed rhetorically but the talk does not examine any downside of the demystified view itself — e.g., whether treating tool calls as 'just JSON and code' obscures real risks (prompt injection via tool outputs, tool-call hallucination against live systems) that a 'the model is doing something special' framing might have made more salient as a safety concern.
