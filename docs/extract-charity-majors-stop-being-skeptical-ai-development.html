Stop being skeptical about AI for development with Charity Majors

Gergely Orosz (interviewing Charity Majors, CTO/co-founder of Honeycomb) · article · 2026-08-12 Reader 🖥️

AI skepticism about software development, though rational as recently as 2025 given the industry's track record of over-promised transformative technologies, has become irrational in 2026 because the model-plus-harness combination (Opus 4.5 running inside Claude Code) crossed a genuine, cloud-computing-in-2010-scale capability threshold — so the live question for engineers is no longer whether to adopt AI but how to build the validation discipline (tests, evals, conformance checking, observability) that makes shipping AI-written, unread code safe.

practical · mixed — A practical, action-directing piece (stop being skeptical; build validation systems; take small acts of control) delivered as Orosz's numbered-takeaways synthesis of a podcast conversation. It mixes personal narrative (Majors's own three-stage change of mind), analogical argument (cloud in 2010, pets-to-cattle), and flat assertion (contrarian one-liners on code review and DevOps) without much direct evidentiary support for any single claim. Note on source fidelity: the fetched content is Orosz's written takeaways article about the episode, not the full spoken transcript — several timestamped segments (e.g. 'Junior engineers' at 1:16:31, 'What effective leadership looks like' at 1:07:45) are listed but not summarized in the 13 takeaways, so this extraction reflects only the curated subset Orosz chose to write up.

Key terms

  • harness Agent Harness
    The engineering layer wrapped around a model (Claude Code, specifically) that turns raw model capability into usable, serious infrastructure — Majors treats the harness, not the underlying model, as the variable that actually flipped her assessment of AI's generational significance.
  • pets to cattle
    Borrowed from cloud infrastructure's 2010s shift (individually repaired servers vs. Terraform/Kubernetes-style disposable, regenerable instances), reapplied to code: instead of hand-editing broken code, generate new, verifiably-correct code to replace it.
  • non-deterministic systems
    Software whose behavior/production process (AI-authored code, AI-run agents) is not fully predictable or human-verified line-by-line, requiring compensating discipline elsewhere in the pipeline.
  • AI-pilled / anti-AI
    Majors's shorthand for the two camps in the adoption debate — not meant as an insult to either side; she explicitly says both camps are 'getting important things right.'
  • agency (in the anxiety/excitement pairing) Agency
    The presence or absence of felt control over one's own situation, which Majors claims is the physiological differentiator between anxiety and excitement in the face of the same disruptive change.

Arguments

Continued blanket AI skepticism about software development was defensible through 2025 but is no longer defensible in 2026. strength: medium
Explicit premises:
  • Skepticism through 2025 was grounded in a real track record of over-promised, under-delivered transformative technologies (COBOL, neural nets, no-code/low-code).
  • Since November 2025, the model-plus-harness combination (Opus 4.5 in Claude Code) represents a genuine, generational capability jump, comparable in scale to cloud computing's 2010 mainstreaming.
Implicit premises:
  • A prior track record of failed transformative-technology promises justifies skepticism only until qualitatively new evidence appears, at which point the skeptic should update.
  • Charity Majors's own personal experience and professional judgment (a credentialed practitioner and industry voice) is sufficient evidence that the industry-wide threshold has, in fact, been crossed — not merely that it has been crossed for her personally.
Inferences:
  • If harness quality rather than raw model capability is the load-bearing variable, then evaluations of 'is AI ready for production software engineering' should be re-run whenever the harness materially changes, not just when a new model ships — meaning static skepticism ('AI isn't there yet') is itself methodologically suspect regardless of which direction it points.
Code review is overrated as a human contribution to software quality. strength: low
Explicit premises:
  • Humans are good at conversation and deciding what to build.
  • Humans are not good at reading code to check for correctness, syntax, and bugs (implied by contrast).
Implicit premises:
  • Automated or AI-assisted verification (tests, evals, conformance checking) can perform the correctness-checking job as well as or better than human review.
  • The primary value humans add to engineering is upstream (deciding what to build), not downstream (checking that it was built correctly).
Inferences:
  • If code review is deprioritized, the verification burden it informally carried must be absorbed by evals/tests/conformance checking — teams that cut review without building that replacement capacity are taking on pure risk, not making an even trade.
  • Junior engineers, who have historically learned to read and critique code partly through the review process, would need a different mechanism for that skill formation if review is deprioritized — a mechanism this document does not name.
Non-deterministic (AI-authored) software systems require more engineering discipline, not less. strength: high
Explicit premises:
  • AI-written code reduces the trust historically placed in code, because a human did not write it and may not fully understand it.
  • Discipline must therefore increase elsewhere in the pipeline — specifically in validation (tests, evals, conformance testing) — to compensate.
Implicit premises:
  • Overall system trustworthiness is roughly conserved: reducing trust in one component (human authorship) requires proportionally increasing trust-generating investment in another (verification) to hold reliability constant.
Inferences:
  • Teams that adopt AI coding without proportionally investing in verification infrastructure are running an undisclosed trust deficit, even if short-term code output looks acceptable.

Questions addressed

  • ✅ Was AI skepticism about software development rational through 2025?
    Yes — because prior transformative-technology promises (COBOL, neural nets, no-code/low-code) had repeatedly fallen short.
  • ✅ Is AI skepticism about software development still rational in 2026?
    No — because the harness/model combination crossed a genuine capability threshold in November 2025, comparable to cloud computing's 2010 mainstreaming.
  • ⭕ What would it take for an engineer to be fully comfortable shipping code they have not read?
    Named as the question engineers 'need to answer' and pointed at in general terms ('engineering is building the systems that validate this code'), but the article never specifies what those validating systems must actually guarantee — coverage thresholds, what evals catch versus miss, what 'comfortable' would look like in practice.
  • ⭕ What is the right human role in an AI-heavy development workflow, if not code review?
    Partially: humans should focus on conversation and deciding what to build, while verification shifts to automated systems — but the article doesn't address who validates the validators, or how junior engineers acquire the skills review used to teach them, despite the episode itself apparently covering 'Junior engineers' as a separate segment not summarized here.
  • ✅ Why did 20 years of DevOps fail to connect engineers to their code's behavior in production?
    Ops people learned to code (that half worked); software engineers never learned to understand their code running in production (that half failed).
  • ✅ How should anxious engineering leaders respond to AI-driven disruption?
    Increase personal agency — e.g., consider returning to IC work — while the window to do so easily is still open, partly because AI experience is about to become a baseline hiring filter.
