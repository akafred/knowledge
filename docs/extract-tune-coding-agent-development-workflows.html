Coding Agent Development Workflows

Nick Tune · article · 2026-01-07 source ↗ Reader 🖥️

Agent HarnessArchitecture Decision RecordsCoding AgentsContext EngineeringOrganizational LegibilitySpec-Driven Development
Making an autonomous coding agent reliable enough to go from ticket to mergeable pull request requires converting as much of the surrounding process as possible into explicit, versioned, tool-agnostic artifacts — deterministic scripts, a single shared source of truth for conventions that every agent and review tool reads, and structured task templates that reject underspecified work — because agent reliability is bounded by the explicitness of what surrounds it, not by the model's capability alone; and the harder unsolved problem this creates for teams and organizations is deciding how explicit conventions must be, who owns them, and at what level (team vs. org) they should be standardized.

practical · mixed — Primarily expository/how-to (a first-person account of a specific workflow with diagrams and config snippets), shifting into argumentative territory in the 'Key challenges for teams and organizations' section where the author makes explicit claims about what AI-assisted development requires organizationally.

Key terms

  • Task Implementation
    The specific phase from the moment an agent/developer starts a ticket (self-assigns, marks in-progress) until a pull request is open and ready to merge or needs feedback.
  • single source of truth for conventions
    A set of convention/standards documents (coding standards, anti-patterns, testing, architecture overview, ADRs) stored once, not coupled to any particular AI tool, and referenced directly by every agent and third-party tool (the coding agent, the local review subagent, and CodeRabbit via its own config) so they can't give contradictory feedback.
  • continuous improvement mindset
    Treating every manual intervention or tool-flagged issue as a signal to push detection further upstream (first try a linting rule, then fall back to a documented convention) so it is caught automatically next time rather than repeatedly caught by hand.

Arguments

Reliable, high-quality autonomous coding-agent work requires converting as much of the surrounding process as possible into explicit, versioned, tool-agnostic artifacts (scripts, shared conventions, structured task templates, layered quality gates) rather than relying on the agent's judgment alone or on ad hoc human intervention after the fact. strength: medium
Explicit premises:
  • Deterministic steps should be scripted, not left to AI interpretation.
  • Multiple review tools must share one source of truth or they produce contradictory, time-wasting feedback.
  • Every manual catch should be converted into a rule or doc update so it's caught automatically next time.
  • Task-definition quality determines implementation quality, so a structured, reject-if-incomplete template is used before implementation begins.
Implicit premises:
  • An agent's reliability is bounded primarily by the explicitness and consistency of what surrounds it (context, conventions, gates), not primarily by the underlying model's raw capability.
  • Organizations that already have clear, explicit, consistently-applied conventions are structurally better positioned for this workflow than organizations whose standards are tacit or person-dependent.
Inferences:
  • Because this approach requires making tacit team knowledge explicit, teams for whom that was already hard (inconsistent conventions, person-dependent judgment) face a harder transition than their nominal tooling readiness would suggest.
  • The organizational challenge of agent-based development is substantially an exercise in making existing-but-unwritten team knowledge legible, not purely a technical/tooling problem.

Questions addressed

  • ✅ How do you make an autonomous coding agent's output predictable and standards-compliant rather than erratic?
    Scripted determinism for mechanical steps, a shared tool-agnostic conventions source for interpretive judgment, a structured task template upstream, and a layered quality-gate pipeline downstream.
  • ⭕ Should quality checks happen locally (agent + subagent review), in CI/third-party tools (CodeRabbit, SonarQube), or both?
    Currently both, as a deliberate belt-and-braces choice; the author explicitly floats removing some checks later but hasn't done so.
  • ⭕ Who authors, maintains, and arbitrates the single-source-of-truth conventions once more than one person (a team, not a solo developer) has a stake in them, and what happens when team members disagree?
