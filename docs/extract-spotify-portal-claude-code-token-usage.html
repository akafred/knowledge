Portal by Spotify cut my Claude Code token usage by 90%

Dimitri Mazmanov · article · 2026-09-03 source ↗ Reader 🖥️

Agent HarnessAI Unit EconomicsClaude CodeContext EngineeringDelegated Editing & Document CorruptionHooksModel RoutingToken Efficiency
Because most of what a coding agent does is I/O rather than reasoning, routing that I/O-bound work (bulk file reads, pattern-following boilerplate generation) to a cheap worker model — and enforcing that routing deterministically via harness-level hooks rather than relying on advisory instructions the model can ignore — cuts Claude Code's token spend by around 90% on the delegated work while reserving the frontier model for editing, debugging, and anything safety-critical.

practical · mixed — A personal engineering report structured as a how-to: it opens with a narrative problem statement, argues a general thesis (I/O work should be routed off the frontier model), documents a concrete mechanism (Portal AiKA Modes + a three-layer Claude Code plugin called shunt), cites benchmark evidence, and closes with install instructions. The propositions are ultimately in service of 'you should route I/O work to a cheap worker model and enforce it with hooks,' not a claim about what is true in general.

Key terms

  • I/O
    Coding-agent work whose token cost is dominated by moving and restating text through the model rather than by any decision the model makes — reading files to answer a question, generating boilerplate that follows an existing pattern, updating docs. The category the author claims is safe to hand to a cheaper model.
  • Mode (AiKA Mode)
    A declarative agent definition in Portal by Spotify — instructions, model, parameters like temperature, and attached MCP tools — that runs on an ephemeral, serverless-like runtime and is callable by name from the Portal CLI or API, with no infrastructure or API-key management.
  • Worker model
    The cheaper model (Gemini 2.5 Flash in the author's examples, but configurable) that a Mode actually runs on, doing the delegated I/O work in place of the orchestrating frontier model (Claude).
  • shunt
    The Claude Code plugin (hooks + scripts + skills) that enforces routing of I/O-heavy work to Portal modes, replacing an earlier CLAUDE.md-based advisory version.
  • Delegation Delegated Editing & Document Corruption
    Routing an entire sub-task's execution (reading a set of files and answering about them; generating a file from a spec and reference) to the worker model such that the corpus or generated code never enters Claude's own context — Claude sees only the compact result.

Arguments

Coding-agent token spend can be cut by roughly 90% on I/O-heavy tasks without sacrificing output quality where it matters. strength: medium
Explicit premises:
  • Reading files to answer a question and generating pattern-following boilerplate are I/O tasks, not reasoning tasks.
  • A cheaper worker model (Gemini 2.5 Flash) given a tightly scoped, output-only prompt can perform these I/O tasks adequately.
  • Benchmarking across four scenarios on a Java monorepo showed a mean ~90% token savings on the bulk-read scenario.
Implicit premises:
  • The four benchmark scenarios and the one Java monorepo generalize to other codebases and task mixes.
  • The worker model's output being 'adequate' was judged by the author's own inspection rather than an independent or blinded evaluation.
Inferences:
  • Teams with high per-seat token spend and an I/O-heavy mix of Claude Code usage should see comparable savings from a similar routing setup — though the piece never establishes what fraction of a typical coding session is genuinely I/O-bound versus reasoning-bound, so the achievable session-level (not per-delegated-task) savings remain unestablished.
Routing decisions must be enforced by the harness (deterministic hooks), not left to the model to self-apply from written instructions. strength: high
Explicit premises:
  • The CLAUDE.md-based version of the routing rules was advisory: Claude could ignore them.
  • Every project needed its own copy of the CLAUDE.md rules, with no central update path.
Implicit premises:
  • A model instructed to prefer a cheaper path, without being directly constrained from taking the expensive path, will not reliably follow that instruction across many turns and contexts.
Inferences:
  • Any cost-control policy for an agent that depends on the model reading and voluntarily following prose instructions is fragile by default and should be treated as a stepping stone toward a hook-enforced implementation, not a stable end state.

Narratives

  • The opening vignette: "Reading five files to answer a question about one method. Generating a test file that follows the exact same pattern as the twenty test files next to it. Updating docs after a meeting."
    → Dramatizes the I/O-versus-reasoning distinction before any argument is stated, so the reader recognizes the pattern in their own agent usage before being told the fix — carries proposition 1 without arguing for it abstractly.
  • The evolution from a block of advisory routing rules in CLAUDE.md (which Claude could ignore and which had to be copied into every project) to the shunt plugin's PreToolUse hooks that block the expensive call outright.
    → Narratively demonstrates the 'guardrails must be enforced, not merely advised' argument through the author's own iteration rather than stating it as an abstract design principle.
  • The worker model missed a subtle thread-safety bug that Claude then spotted in seconds once given the right context.
    → A concrete before/after case that grounds the 'you can't delegate reasoning' boundary claim in a specific failure rather than an assertion.

Questions addressed

  • ✅ How can AI coding-agent token/cost spend be reduced without giving up frontier-model quality where it matters?
    Route I/O-heavy work (bulk reads, pattern-following boilerplate) to a cheap worker model via hook-enforced delegation; keep the frontier model for editing, debugging, and safety-critical or architectural work.
  • ✅ What kinds of coding-agent work are safe to delegate to a cheaper model, and what kinds aren't?
    Safe: understanding-oriented bulk reads and boilerplate generation from an existing pattern. Unsafe: edits that require precise locations, debugging, architectural decisions, and safety-critical code.
  • ✅ How do you make a token-saving routing policy actually stick, given that a model can choose to ignore written instructions?
    Enforce it at the harness level with PreToolUse hooks that block the expensive tool call outright, rather than relying on the model reading and following a policy document.
  • ⭕ Once a task has been delegated and the worker model returns a confident-looking summary, how is that output verified as actually correct, beyond the one anecdote where a bug happened to be caught?

Gaps

  • incompleteThe ~90% savings figure is measured across only four scenarios on a single Java monorepo, run and interpreted by the author, with no description of how the scenarios were selected, no independent replication, and no confidence interval — a self-benchmark on one codebase presented as a general result.
    Read next: Compare against vendor-claimed general model-routing savings of roughly 20-30% (extract-pragmatic-engineer-pulse-smart-model-routing#p2) to see whether Portal's much higher figure is a genuine property of narrowly-scoped I/O delegation or an artifact of scenario selection and codebase choice.
  • incompleteThere is no account of how 'good enough' worker-model output is verified on an ongoing basis. The piece surfaces exactly one failure (a missed thread-safety bug), caught only because Claude was independently asked about the same code — it doesn't describe any systematic check for cases where a confident-looking bullet summary is subtly wrong and nobody re-reads the source to catch it.
    Read next: extract-pragmatic-engineer-pulse-smart-model-routing#g2 raises exactly this evaluation gap for routing systems generally — read together for the recurring 'good enough is asserted, never verified' critique.
  • uninformedNo systematic latency or throughput accounting beyond a rough 10-30 second range and a 30-second hard cap; no data on how often the line-count threshold forces marginal-size reads through the expensive path anyway, and no measurement of cumulative added wall-clock time across a full real session.
    Read next: extract-cloudflare-code-mode-mcp-server#g4 flags the identical missing latency/wall-clock analysis for a different token-saving pattern (Code Mode) — this looks like a recurring blind spot across token-optimization write-ups worth reading together.
  • incompleteThe article frames the setup as requiring 'zero code,' but that's zero code once an organization has already stood up a Portal (AiKA) instance with modes, plugins, and marketplace access configured — it doesn't address what the equivalent hooks/scripts/skills layering costs to build from scratch for the (much larger) population of Claude Code users without an existing Portal-shaped platform.
    Read next: Read against platform-engineering and agent-tool-management material on what it actually takes to stand up a shared internal AI platform, to price the 'zero code' claim against the platform-build cost it presupposes.
