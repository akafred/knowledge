Loop Engineering

Addy Osmani · article · 2026-06-07 Reader 🖥️

Agent HarnessAgent SkillsCognitive SurrenderLoop EngineeringMCP (Model Context Protocol)Multi-Agent OrchestrationOrchestration Tax / Human Review Bottleneck
Loop engineering means replacing yourself as the person who prompts the coding agent turn-by-turn with a designed system — automations, worktrees, skills, plugins/connectors, and sub-agents, plus externally-persisted state — that prompts the agent for you; but because that system can't distinguish between someone using it to move faster on work they understand and someone using it to avoid understanding the work at all, the engineer's judgement doesn't disappear, it relocates one level up, from prompting to system design, which Osmani argues is harder, not easier.

practical · expository essay with an embedded framework (taxonomy of five building blocks + one worked example), closing in a hedged counter-argument — Reads as the latest installment in Osmani's serial diagnosis (harness engineering -> orchestration tax -> intent debt -> loop engineering); it names and packages a practice rather than reporting an experiment, and structurally reverses itself at the end, undercutting its own contrarian headline.

Key terms

  • Loop engineering Loop Engineering
    designing the outer, autonomous system — automations, worktrees, skills, connectors, sub-agents, persisted state — that repeatedly invokes an agent harness without a human prompting each turn
  • Loop (as recursive goal)
    "a recursive goal where you define a purpose and the AI iterates until complete"
  • Automations ("the heartbeat")
    scheduled, cadence-driven runs that do discovery and triage on their own and route findings to a triage inbox, distinguishing a loop from a one-off run
  • /goal vs. /loop
    /loop re-runs on a cadence; /goal keeps going until a separately-graded, verifiable stopping condition holds — a fresh model grades whether the work is done rather than the model that did the work
  • Maker and checker
    splitting the sub-agent that drafts/implements from the sub-agent that reviews/verifies, because the model that wrote the code is "too nice grading its own homework"
  • "Sits one floor above the harness"
    loop engineering as a layer above his own previously-coined agent-harness engineering: the harness is what a single agent runs inside, the loop is what runs the harness on a timer and feeds itself

Arguments

The individual engineer no longer needs to be skilled at turn-by-turn prompting; the skill that now matters is designing the loop that prompts the agent. strength: medium
Explicit premises:
  • Steinberger and Cherny, both credible insiders, independently report they no longer prompt agents directly — they design loops instead.
  • The five loop primitives are now native, shipped features in both major coding-agent products, so building a loop no longer requires bespoke tooling.
  • A worked example ("What one loop looks like") shows the human designing the system once, never prompting any individual step.
Implicit premises:
  • Whatever made someone good at prompting (crafting the right instruction, iterating conversationally) transfers into system-design skill, and market/attention will reward the latter going forward.
  • A maker/checker sub-agent split substitutes adequately for the human's own turn-by-turn judgement of quality.
Inferences:
  • from 'credible insiders no longer prompt directly' plus 'the capability is now productized' to 'prompting skill is being superseded as the thing to get good at'
Loop engineering does not reduce the engineer's responsibility — it relocates and intensifies it, into verification, comprehension, and resisting cognitive surrender. strength: high
Explicit premises:
  • Verification is still on you; a loop running unattended is a loop making mistakes unattended, and 'done' is a claim, not a proof.
  • Comprehension debt grows faster, not slower, as a smoother loop ships more code the human didn't write.
  • The comfortable posture of no longer forming an opinion about the loop's output (cognitive surrender) is more tempting exactly when the loop runs itself.
  • Two people can build the exact same loop and get opposite outcomes depending on their posture toward it.
Implicit premises:
  • A system that increases agent throughput without a matching increase in human review/understanding capacity accumulates unpaid orchestration tax (drawn directly from Osmani's own prior orchestration-tax essay).
Inferences:
  • because the loop cannot distinguish deep-understanding use from understanding-avoidant use, the engineer's judgement and design intent — not the mere presence of the five building blocks — is what actually determines the outcome

Narratives

  • "What one loop looks like": a morning automation runs a triage skill that reads yesterday's CI failures, open issues, and recent commits, and writes findings to a markdown file or Linear board; for each worthwhile finding, an isolated worktree is opened and a sub-agent drafts a fix while a second sub-agent reviews the draft against project skills and existing tests; connectors open the PR and update the ticket; anything the loop can't handle lands in a triage inbox for the human; the state file is 'the spine' that lets tomorrow's run pick up where today's stopped.
    → makes the abstract five-piece framework concrete as a single illustrative composite scenario — presented in first person as 'one shape I keep using,' with no named repo, no metrics, and no claim of measured outcomes; it is a plausibility sketch, not a case study

Questions addressed

  • ✅ What does 'loop engineering' mean and why would you build one instead of prompting an agent yourself?
    A loop is a designed system (automations, worktrees, skills, connectors, sub-agents, persisted state) that autonomously finds work, hands it to agents, checks it, and decides the next step, replacing the human as the one holding the tool turn-by-turn.
  • ✅ What concrete components does a loop require?
    Five building blocks plus one place to remember state, mapped concretely onto both the Codex app and Claude Code.
  • ⭕ Does loop engineering eliminate the need for prompting skill and human judgement?
    The piece answers this two different ways — a strong 'yes, prompting is over' at the top and a hedged 'no, direct prompting is also effective, it's about balance' at the bottom — without ever reconciling the two.
  • ⭕ How many loops/agents can one engineer responsibly run at once?
    Referenced only by pointing back to the separate 'orchestration tax' post; not answered within this piece.
  • ⭕ Once a loop is triggered, which control-flow/algorithmic pattern should it actually run (critique-and-rewrite, plan-and-replan, tree search, debate, etc.)?
    Never addressed — the five building blocks are infrastructure/product primitives, not the algorithmic shape of what happens inside a single automated run.
