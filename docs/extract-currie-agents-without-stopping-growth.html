How I Use Agents Without Stopping My Own Growth

Jared Currie · article · 2026-05-27 source ↗ Reader 🖥️

Agent Planning ArtifactsAgentic EngineeringCognitive SurrenderDesirable Difficulty & Productive StrugglePull Requests & Async Code Review
Agentic coding tools are safe to lean on only if the developer deliberately keeps exercising the judgment they would otherwise outsource — by planning before delegating and reviewing generated code as if reconstructing its reasoning themselves — because the tools amplify whichever posture the developer brings to them.

practical · expository — First-person practitioner reflection arguing for specific habits (plan-first, slow-review) to preserve engineering judgment while delegating execution to agents. No data, no citations — a personal-practice essay, not an empirical or theoretical argument.

Key terms

  • outsource thinking
    Accepting an agent's plan or code without independently verifying or comparing it against one's own reasoning, so the agent's output becomes the extent of one's understanding of the system.
  • planning muscle
    The habit of independently sketching an approach (outline, files to touch, assumptions to validate) before an agent proposes one, exercised deliberately so it doesn't atrophy.
  • understand at a surface level
    Approving code because it compiles and passes tests without tracing what it actually does to data access, network behavior, or performance under real use.

Arguments

Developers using coding agents should deliberately sketch their own plan before delegating implementation, and should review generated code by tracing its real consequences rather than trusting that it compiles and passes tests. strength: medium
Explicit premises:
  • Agents make it easy to outsource thinking by generating plausible-looking plans and code.
  • Blindly accepting agent output risks shallow understanding of the system.
  • Software development requires judgment (system design intuition, trade-off assessment, critical review) that an agent cannot supply.
Implicit premises:
  • Judgment is a skill that atrophies without practice and can only be maintained by continuing to exercise it, even when a faster alternative (accepting the agent's output) is available.
  • A developer can reliably tell, in the moment, whether they are engaging critically or merely rubber-stamping — i.e., surface-level acceptance is a detectable and avoidable failure mode, not something that can happen unnoticed.
Inferences:
  • If judgment atrophies without practice, then any workflow optimization that removes the friction of planning or deep review (even a well-intentioned one) trades short-term speed for long-term skill loss — a cost the essay never puts a number on.
  • The prescription implies a personal, individual-level defense (habits one developer chooses to keep) rather than a team- or organization-level one (metrics, gates, review policy) — the essay's remedy operates entirely at the level of individual discipline.

Questions addressed

  • ✅ How can a developer use agentic coding tools heavily without letting their own engineering judgment atrophy?
    By deliberately continuing to plan independently before delegating, and by reviewing generated code deeply enough to trace its actual consequences rather than trusting surface signals (compiles, tests pass).
  • ⭕ Is the discipline the author describes something innate to how they personally work, or a practice that generalizes — could a less disciplined or more time-pressured developer sustain it, and would it survive at team scale rather than as an individual habit?
