Building features at the speed coding agents enable creates 'cognitive debt' — an accumulating gap between what has been built and what the engineer still understands — which, like technical debt, must be deliberately repaid (through upfront planning, disposable prototyping, and PR-based review) or it will erode confidence and slow you down.

Key terms

  • cognitive debt Cognitive Debt
    Borrowed from Margaret-Anne Storey: the accumulating gap between how a system was built (by a fast-moving coding agent) and how well the engineer actually understands it — repaid by rebuilding a mental model (reading code/docs, writing tests, running experiments), not by a mechanical fix.

Arguments

Developers should deliberately schedule points to repay cognitive debt — planning before an agent writes code, and reviewing via pull request afterward — rather than let agent-driven speed compound an ungrounded understanding of their own system. strength: medium
Explicit premises:
  • Cognitive debt accumulates the same way technical debt does: unaddressed, it compounds and eventually slows you down.
  • Rebuilding a mental model (via planning beforehand, or review afterward) is the repayment mechanism.
Implicit premises:
  • A developer can accurately self-assess the moment they're 'a little bit overwhelmed' and intervene before shipping something they don't actually understand.
  • Reviewing a pull request is itself sufficient to rebuild genuine understanding, rather than a comfortable but superficial check.
Inferences:
  • If the author's second forecasted future (code as an abstraction manipulated by agents, with engineers operating on specs/constraints/outcomes) materializes, the unit of 'repayment' shifts from understanding code to understanding specifications — which would make a PR-review practice focused on code obsolete as a repayment mechanism, not just insufficient.

Questions addressed

  • ⭕ How will the tension between coding-agent speed and cognitive debt play out over time?

  • ⭕ Does reviewing a pull request actually restore the engineer's genuine understanding of agent-written code, or just the feeling of having checked it?
