Terraform Introduces tfpolicy, an HCL-based Policy-as-Code Framework

Sergio De Simone · rss · 2026-07-29 source ↗ Reader 🖥️

Policy-as-CodeSoftware Supply-Chain Security
HashiCorp's tfpolicy replaces the separate policy-as-code layer (Sentinel, OPA) with an HCL-native framework embedded directly in Terraform's own workflow, enabling relationship-aware, pre- and post-deployment governance without a second policy language or tool.

practical · expository — A short news report relaying HashiCorp's own framing of a new product (tfpolicy); it argues implicitly for adopting the tool by contrasting it favorably with existing policy-as-code approaches, but does so mostly by quoting HashiCorp rather than building an independent case.

Key terms

  • tfpolicy
    HashiCorp's specific new HCL-based, declarative policy-as-code framework built directly into Terraform's own workflow, distinct from the generic category 'policy as code' and from HashiCorp's older Sentinel product.
  • relationship-aware / contextual policy evaluation
    Evaluating policy rules against how resources relate to each other and against external data-source lookups, rather than validating each resource's attributes in isolation at plan time.
  • post-deployment evaluation
    Checking policy compliance against the actual, already-provisioned infrastructure state, not just the planned change set — catching violations only visible after resources exist.

Arguments

Organizations governing Terraform-managed infrastructure should adopt tfpolicy over external policy-as-code layers like Sentinel or OPA. strength: medium
Explicit premises:
  • Existing policy-as-code layers can't express rules dependent on relationships between resources or on external context that changes across the infrastructure lifecycle.
  • tfpolicy uses the same language (HCL) already used to define Terraform infrastructure, reducing the number of tools and languages teams must maintain.
  • tfpolicy can evaluate policy after deployment against real infrastructure state, not only against the plan.
Implicit premises:
  • Consolidating the policy language with the infrastructure language is more valuable than the separation-of-concerns benefit of an independent policy tool usable across systems beyond Terraform (as OPA is).
  • A policy framework built and controlled by the same vendor that builds Terraform is adequate for governance workloads that might otherwise call for a vendor-neutral engine.
Inferences:
  • Because full capability requires HCP Terraform (the paid managed product), organizations running open-source Terraform without HCP Terraform must either upgrade or continue relying on Sentinel/OPA to get comparable governance — a lock-in dynamic the article does not flag.

Questions addressed

  • ✅ How can platform teams enforce infrastructure governance without maintaining a separate policy language and toolchain alongside Terraform?
    By embedding policy directly in Terraform's own HCL workflow (tfpolicy) instead of a separate DSL (Sentinel) or external engine (OPA).
  • ✅ How can policy evaluation account for context that changes across the infrastructure lifecycle — e.g. relationships between resources — rather than validating resources in isolation at plan time?
    Via relationship-aware policy rules and data-source lookups, plus post-deployment evaluation against actual provisioned state.
  • ⭕ Does concentrating both infrastructure definition and policy enforcement in the same HCL/HCP Terraform product create a governance vendor-lock-in risk, given that full tfpolicy capability requires the managed HCP Terraform service?
