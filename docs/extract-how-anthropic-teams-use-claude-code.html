How Anthropic Teams Use Claude Code

Across nine internal teams spanning both engineering (Security, Inference, RL Engineering, the Claude Code team itself) and non-engineering functions (Legal, Growth Marketing, Product Design, Finance via Data Infrastructure), Claude Code's value comes less from writing application code per se than from acting as a general-purpose interface to unfamiliar systems, documentation, and workflows -- letting people without coding backgrounds independently build and run working software, and letting engineers extend their reach into unfamiliar domains -- provided teams invest in persistent context files, checkpoint-heavy supervision, and an explicit sense of which tasks warrant autonomous versus closely-supervised execution.

practical · mixed — A curated internal case-study collection (expository per-team profiles plus narrative anecdotes) assembled in service of a practical argument: here is how to adopt Claude Code across technical and non-technical functions, with tips implicitly recommending specific practices to the reader's own organization.

Key terms

  • auto-accept mode / 'slot machine' workflow
    Letting Claude Code work fully autonomously for a bounded period (minutes to tens of minutes) after committing a clean checkpoint, then either accepting the complete result or discarding it and restarting, rather than attempting to correct a partially-wrong result in place.
  • task classification intuition
    A developed sense, specific to one's own codebase and team, of which tasks are safe to hand to Claude Code autonomously (peripheral features, prototyping, work in unfamiliar languages) versus which require synchronous, closely-monitored collaboration (core business logic, critical fixes).
  • Claude.md / plan-then-build workflow
    A project-level context file documenting workflows, conventions, constraints, and even the user's own skill level, combined with a two-phase pattern of extensive planning in a conversational interface (Claude.ai) before moving to implementation in Claude Code.

Arguments

Teams should route a task to one of two distinct supervision modes -- fast autonomous/checkpoint-and-accept, or slow synchronous/closely supervised -- based on the task's risk and centrality, rather than applying one default mode to everything.
Explicit premises:
  • Peripheral, low-priority, or domain-unfamiliar work (Vim mode, visualization dashboards, routine refactors) succeeds well under autonomous, checkpoint-heavy supervision
  • Core business-logic changes require real-time monitoring for code quality, style, and architecture compliance
  • Discarding and restarting a bad autonomous attempt is cheaper than trying to correct it in place
Implicit premises:
  • A task's appropriate supervision mode is knowable in advance from its position in the codebase or business (peripheral vs. core), not only discoverable after a failed attempt
  • The cost of running the wrong mode -- over-supervising a safe task, or under-supervising a risky one -- is asymmetric enough to justify explicit, deliberate classification rather than a uniform default
Inferences:
  • Organizations that don't develop this 'task classification intuition' explicitly will default either to over-supervising everything (losing the reported productivity gains) or under-supervising core-logic changes (risking production issues)

Narratives

  • The Data Infrastructure team's Kubernetes diagnosis: when clusters stopped scheduling pods, the team fed screenshots of Google Cloud dashboards into Claude Code, which guided them menu by menu to a pod-IP-exhaustion warning and then supplied the exact commands to fix it -- resolving an incident that would normally require pulling in a networking specialist.
    → Shows concretely that Claude Code's value in this report extends well beyond writing application code into cross-domain infrastructure troubleshooting, grounding the broader claim that teams use it as a general interface to systems outside their own deep expertise.
  • A Legal team member built a predictive-text communication app for a family member with a speech disability in about an hour, using native speech-to-text and voice banks -- filling a gap in existing accessibility tools that speech therapists had recommended but that didn't fully meet the need -- then validated the prototype by showing it to UCSF specialists.
    → Demonstrates the furthest extreme of the report's 'non-engineer builder' pattern: a lawyer with no engineering background solving a genuinely novel, personally consequential problem, grounding the report's advice to share imperfect prototypes in a case where the stakes of trying were low but the payoff was high.

Questions addressed

  • ✅ Can Claude Code provide real value to people and teams without software-engineering training, or is its benefit confined to professional developers?
    Non-technical teams and individuals (Legal, Growth Marketing's team of one, Finance via Data Infrastructure's help, non-developer Product Design staff) independently build and run working software with it -- the report frames this as one of its central findings, not a side note.
  • ✅ How should a team decide when to let Claude Code work autonomously versus supervise it closely in real time?
    Multiple teams converge on a risk/centrality heuristic: autonomous, checkpoint-and-accept-or-discard supervision for peripheral or low-stakes work; synchronous, detailed-prompt supervision for core business logic -- described across teams as 'task classification intuition.'
  • ⭕ Do the reported productivity and time-savings figures (e.g. 'research time reduced by 80%', '2-3x faster execution', 'ad copy from 2 hours to 15 minutes') reflect rigorous measurement, or self-reported impressions from the power users interviewed?
    The report doesn't say -- it presents these as 'top tips' and impact statements from interviews with the company's own power users, with no stated methodology, baseline measurement, or comparison group.
  • ⭕ What happens to the teams and processes this report's successes route around -- networking specialists for Kubernetes issues, engineers supporting designers' changes, IT/dev gatekeeping for new internal tools?
