What Is a Token? A Developer's Guide to Every Type

The word 'token' names unrelated technical artifacts across four domains -- identity/authorization state, numerical text representation for LLMs, blockchain asset ownership, and single-purpose application security -- so developers must learn each domain's specific token vocabulary and the engineering tradeoff each token type encodes (statelessness vs. revocability, cost vs. capability, security scope) rather than treating 'token' as one concept.

practical · expository — Primarily a categorized glossary/reference guide across four unrelated token domains (authentication, LLM, crypto, application/API). Genuine argumentative or evaluative content is limited to scattered comparative and best-practice asides (stateless vs. session-based tradeoffs, why tokens beat passwords, LLM cost/context-window implications) rather than a sustained thesis-driven argument.

Key terms

  • bearer token
    An opaque string that grants access to whoever holds it, without requiring additional proof of identity; the predominant access-token type used with OAuth 2.0. The article notes bearer tokens are often implemented as JWTs in practice.
  • opaque token
    Also called a 'reference token': a unique, random alphanumeric string generated by the authorization server that carries no readable or actionable information itself (implying it requires server-side interpretation, unlike a self-contained JWT).
  • JSON Web Token (JWT)
    An open standard (RFC 7519) for representing claims transferred between two parties as a compact, signable and/or encryptable JSON object.
  • access token vs. ID token
    The author explicitly distinguishes the two despite their similar issuance context: an access token is proof of authorization (what you can do), an ID token is proof of authentication (who you are).
  • session token
    A unique identifier, created at login and usually stored in a cookie or locally, that authenticates a user and lets the app manage session activity -- the sole token of session-based authentication, where state lives server-side (contrast to token-based auth's client-side state).
  • refresh token
    Enables obtaining a new access token without forcing the user to re-authenticate once the current access token expires.
  • context window
    An LLM's 'working memory,' measured in tokens, with a limit that varies per model; all input, output, and (where applicable) extended-thinking tokens count toward it.
  • OATH vs. OAuth
    Explicitly distinguished: OATH (Initiative for Open Authentication, founded 2004) is an industry collaboration standardizing one-time-password authenticator tokens (software/hardware OTP generators); OAuth is an open authorization protocol. The similar names are flagged as a real source of confusion.

  • explicitAn access token serves as proof of authorization, while an ID token serves as proof of authentication -- the two are functionally distinct even though both are typically issued during the same login flow.conf: high
  • explicitA bearer token grants access to whoever holds it (typically as an opaque string) without requiring further proof of identity, and is the predominant access-token type used with OAuth 2.0; in practice it is often implemented as a JWT.conf: high

  • explicitOpaque tokens carry no readable or actionable information themselves -- they are just a random string generated by the authorization server, unlike a JWT whose claims are inspectable in the token.conf: medium

  • explicitDespite the popularity of token-based authentication, session-based authentication is often adequate for many web applications.conf: medium
  • explicitThe tech industry has been moving toward passwordless authentication (passkeys, biometrics, magic links) in recent years.conf: medium
  • explicitOATH and OAuth are different things despite the similarity of the names -- OATH tokens produce one-time passwords, while OAuth is an authorization protocol -- and this is a real point of confusion among developers.conf: high
  • explicitAuthentication tokens are more secure than password-only verification because they are typically short-lived, encrypted, and specific to a user's session, application, or device, which makes them difficult to reuse if stolen.conf: medium

Arguments

Token-based authentication has become the dominant authentication method for application developers. strength: medium
Explicit premises:
  • The stateless, client-side model is highly scalable.
  • It is compatible with APIs.
  • Industry standards such as OAuth 2.0 and OpenID Connect have proliferated.
Implicit premises:
  • Standardization lowers integration cost and interoperability risk enough to outweigh the operational cost of managing token lifecycles on the client side.
Inferences:
  • Scalability + API compatibility + standard proliferation -> widespread developer adoption.
Authentication tokens provide stronger identity-verification security than a password-only approach. strength: medium
Explicit premises:
  • Tokens are usually short-lived.
  • Tokens are encrypted.
  • Tokens are specific to a user's session, application, or device.
Implicit premises:
  • An attacker who intercepts or steals a token has a narrower window and narrower scope of exploitation than one who steals a reusable password.
  • Passwords are frequently weak or reused, so any layer that isn't a static shared secret raises the practical bar for attackers.
Inferences:
  • Short-lived + encrypted + scoped -> difficult to reuse if stolen -> stronger security than passwords alone.
Developers building LLM-backed applications must actively track which token types their application uses and how many. strength: high
Explicit premises:
  • LLM pricing is usage-based on tokens.
  • Every interaction with the model generates tokens.
  • More tokens used means higher cost.
  • Context window limits are measured in tokens and vary per model.
  • Exceeding the limit causes an error; approaching it can degrade response quality.
Implicit premises:
  • Cost and output quality are both operationally significant enough to justify active token management as a distinct engineering practice.

Gaps

  • incompleteNo discussion of token revocation strategies -- how access/refresh tokens are invalidated on logout, compromise, or password change -- despite this being central to the very JWT-vs-opaque-token tradeoff the article gestures at (opaque tokens support server-side revocation via lookup; self-contained JWTs generally don't without extra infrastructure like a blocklist).
    Read next: Nordic APIs' own linked piece, 'JWT vs Opaque Tokens: Choosing the Right Token for API Security'; general OAuth 2.0 revocation (RFC 7009) literature.
  • incompleteThe article places authentication 'tokens' and LLM 'tokens' side by side under one umbrella term without ever flagging that they are entirely unrelated concepts sharing only a name -- a real source of confusion for developers moving into AI-augmented applications who may conflate 'token limit' (LLM context) with 'token expiry' (auth) or assume LLM tokens carry any security property at all.
    Read next: Any introductory LLM tokenization explainer paired with an OAuth/JWT primer, read side by side to make the non-relationship explicit.
  • incompleteNo treatment of token binding or proof-of-possession mechanisms (DPoP, mTLS-bound tokens) that address the exact weakness the article itself names in bearer tokens -- that a bearer token grants access 'to the party holding the token' with no additional proof of identity, so token theft is equivalent to full impersonation.
    Read next: OAuth 2.0 DPoP (RFC 9449) and mutual-TLS-bound access tokens (RFC 8705).
  • incompleteJWT alternatives designed to avoid well-known JWT signature/algorithm pitfalls (e.g., the 'alg: none' vulnerability, RS256/HS256 confusion) such as PASETO are not mentioned, even though the article recommends JWT as the default bearer-token implementation.
    Read next: PASETO specification and comparative JWT-vulnerability writeups.
  • incompleteClient-side token storage (localStorage vs. httpOnly/secure cookies) -- a major practical security decision for the 'stateless, client-side state' model the article describes -- is never discussed, despite being one of the most common real-world vectors for token theft (XSS).
    Read next: OWASP guidance on token storage for SPAs and mobile clients.
