Redesigning source control at Anthropic

Anthropic · article · 2026-10-13 source ↗ Reader 🖥️

Agent-Native DesignAgent-Scale Source ControlAgentic SDLCAutonomous SDLCCode Was Never the BottleneckInfrastructure EfficiencyPull Requests & Async Code ReviewSmall Teams & Compression
Because Claude has made code production cheap and pushed Anthropic's merge rate from ~2,500 to 30,000+ per day, human-scale developer infrastructure (git, merge queues, CI) became the bottleneck, so a seven-person team used Claude to build and migrate to Scion, an always-online, server-centric, horizontally scalable version control system in five months - and Anthropic argues other organizations will meet the same limits within 6-12 months and should apply Scion's ideas to git servers rather than copy Scion.

practical · mixed — A first-party engineering case study: expository (architecture of Scion), narrative (migration, the Mythos rewrite, the 'no' stories) and argumentative (git's distributed design no longer fits agent-scale monorepos; human-scale workflows like merge queues need rethinking). Practical in the Adler sense: it argues what source-control builders and git platforms should do. Written by the source control team (Nick G. et al.) and published by the vendor whose model produced the load, so measured figures and self-assessments are intertwined.

Key terms

  • Scion Agent-Scale Source Control
    Anthropic's in-house version control system for its monorepo: server-side commits/merges/rebases, thin caching client (scn), immutable content-addressed storage, metadata and blob/tree APIs
  • changeset
    The unit of work in Scion: an entry in a write-ahead log holding the list of files changed relative to its first parent plus content-addressed pointers to compressed contents; created server-side
  • derived data
    Everything not directly in the changeset (blame, path history, commit-graph skip lists, copy detection, path search indices), each defined recursively from the parent's value and computed by one generic mechanism, eagerly or lazily
  • agent-scale
    A regime in which swarms of agents (not humans) generate most commits and read most checkouts, so tools tuned for human rates, offline use and hand review strain
  • client-server asymmetry
    The server computes history, blame, commits, merges and rebases; the client is a thin layer with a bounded object cache, working-copy layout and filesystem monitoring
  • sparse and virtualized checkout
    Checkouts that contain only requested directories (sparse) or materialize file contents on demand (virtualized); in Scion they need no special protocol support because the client simply does not request unwanted trees
  • seeds / mirrors
    The standard git workarounds Anthropic used until they stopped scaling: repository snapshots in blob storage and, at peak, several hundred internal git mirrors
  • Antique
    Anthropic's code review surface, built and shipped alongside Scion, with semantic approval constraints and a merge queue component
  • superfan
    A Claude instance (via Claude Tag in a Slack channel) assigned to be obsessively focused on the health of one system component, with telemetry and log access
  • post-merge and pre-deploy testing
    The replacement for a global-lock merge queue: changes merge without being serialized against each other, concurrent conflicts are accepted, and testing happens after merge and before deployment, with Claude repairing conflicts

  • explicitSource control designed for agents rests on six principles: clients are always online; client-server asymmetry (the server does history, blame, commits, merges and rebases); a comprehensive source-control API for tools; everything horizontally scalable with no fully materialized copy and no packfile maintenance; commits that are cheap, incremental and lock-free with cost proportional to change size (and few refs besides main and release branches); and a working copy that is optional and sparse by design.conf: high
  • explicitIn Scion the unit of work is a server-created changeset in a write-ahead log (files changed relative to the first parent plus content-addressed pointers to blobs), so accepting changes needs no packfiles, locks, cross-server coordination or ref movement; a ref update is a compare-and-swap on a single Spanner row, separate from changeset creation.conf: high
  • explicitQueries such as blame, path history and ancestry are served from 'derived data' structures defined recursively over parent changesets and computed by one generic mechanism, which allows new types to be added when a faster operation needs one, per-type choice of eager versus deferred computation, and optimization without touching the client.conf: high
  • explicitBecause all Scion data is content-addressed and immutable, any server or cache can serve it without coordination; the client fetches only the trees and blobs it wants (no negotiation about what it already has), recursively from a root tree, through a strictly enforced tier of scion-daemon (per node), regional scion-cache and authoritative scion-server backed by Spanner and cloud storage, which makes sparse and virtualized checkouts need no special support and isolates failure domains.conf: high

Arguments

Git's decentralized, offline-capable design no longer fits Anthropic's monorepo, so source control should be rebuilt around a server-centric, always-online model. strength: medium
Explicit premises:
  • The monorepo is huge (about 100 GB history, 25 GB+ compressed working copy, ~25M CI checkouts per day).
  • Nearly all clients are agents and jobs that are online by definition.
  • Git's workarounds (shallow clones, sparse checkout, promisor remotes, hundreds of mirrors, seeds) bought time but grew harder to operate as the merge rate rose.
  • Prior art (Piper, Sapling) shows large monorepos can use server-centric source control.
Implicit premises:
  • Offline and peer-to-peer capability has no value for these clients (including developers).
  • Anthropic can afford to build and maintain a bespoke stack (VCS plus review, search, IAM, CI integration).
  • The costs of the workarounds are structural, not merely a matter of better-engineered mirrors.
Inferences:
  • Most git deployments are already centralized in practice, so they pay the distributed-design tax without its benefit.
  • The pain is concentrated in read fan-out (checkouts), which suggests git forges could capture much of the gain with server-side RPCs and better fetch protocols, as the authors recommend.
A small team can now build and migrate to a high-quality replacement for core infrastructure in months, because Claude writes the code and engineers supply design judgment.
Explicit premises:
  • Seven people built Scion, Antique and half a dozen related systems and completed the migration in five months while merges grew 10x.
  • Claude (Mythos snapshot) rewrote the ingestion pipeline 20x leaner and 4x faster; Claude found optimizations that would take experts weeks.
  • Claude's code volume enabled simulations of every non-trivial interaction, fuzzing and rate limiting.
Implicit premises:
  • The counterfactual (years, many more engineers) is accurate; there was no comparable control project.
  • Hermetic simulation and fuzzing are enough to trust agent-written infrastructure code.
  • The seven engineers' system-level understanding is available in other organizations.
  • Unlimited token budget and pre-release model access are not what made the difference.
Inferences:
  • The scarce resource shifts from implementation labor to design judgment and the ability to say no, so capacity scales with expertise, not token spend.
  • Migration timelines for other legacy infrastructure may compress, but only where tests and simulations can verify behavior.
At agent scale the merge queue and pre-merge CI gate should be replaced by post-merge and pre-deploy testing with agent-repaired conflicts. strength: low
Explicit premises:
  • Hundreds or thousands of changes can merge while tests run.
  • Anthropic could not effectively replicate the global repository lock used by industry-standard merge queues.
  • Claude can typically fix conflicts faster than humans can identify them.
Implicit premises:
  • Brief breakage of main is tolerable because nothing ships until pre-deploy tests pass.
  • Concurrent-change conflicts are mostly cheap, syntactic or locally semantic, and are detected reliably.
  • Fix-forward by an agent is cheaper than the throughput lost to serialization.
  • Deploy-time testing is a sufficient barrier for defects that interleave across independently valid changes.
Inferences:
  • The gate in the SDLC moves from merge to deploy, which makes pre-deploy verification capacity the binding constraint (compare back-pressure and verification-bound autonomy).
  • If CI does not gate merges, CI's role becomes diagnosis and ranking for agent repair rather than admission control.
Engineers remain valuable but their work shifts to design tradeoffs, steering and reviewing intent rather than reading every line. strength: medium
Explicit premises:
  • All engineers on the project rate Claude better at writing code than themselves.
  • Agents violate core system constraints (e.g. linear commit-log scans) and adversarial review over-engineers.
  • The team reviews every change request, examining intent rather than lines.
Implicit premises:
  • Intent can be assessed reliably without reading the code (tests, simulations and the reviewer's system knowledge close the gap).
  • The 'no' interventions require knowledge that agents lack and are not themselves learnable by the agent over time.
  • Review of every change is feasible only because this system's volume is a fraction of the 30,000/day company-wide.
Inferences:
  • Human review capacity scales with the number of people who hold system-level understanding, which becomes the limiting resource.
  • For the rest of the company's 30,000 daily merges, review must rely on different mechanisms (semantic approval constraints, automation); the post does not describe them.
Other organizations using AI coding tools will hit the same source-control pressure points within six to 12 months, so git platforms should adopt Scion's ideas on the server side. strength: low
Explicit premises:
  • Anthropic is first to see where human-scale tools strain because it uses Claude to write software far more than almost anyone.
  • Scion's concepts only make sense for enormous monorepos with tens of thousands of engineers or swarms of agents.
  • Git servers need not work like git clients; novel server architectures exist.
Implicit premises:
  • Other organizations' merge volumes will follow Anthropic's curve (adoption of agents scales with merges).
  • Git's client-visible model can absorb server-side changes (standardized RPCs, new negotiation) without losing compatibility.
  • Most affected organizations are not monorepo-scale, yet the premise limits Scion to enormous monorepos, leaving the 6-12 month claim's scope ambiguous.
Inferences:
  • Hosting providers (GitHub, GitLab) are the natural place for the shared-fix; this aligns with third-party reporting of load-driven platform strain.

Narratives

  • The 25-million-checkouts-a-day thought experiment: fetching the ~25 GB working copy naively for every CI checkout would be over 600 PB of git traffic per day, followed by the escalation from seeds and partial clones to several hundred internal mirrors.
    → Shows why git's workarounds stopped scaling and justifies the redesign; supports the diagnosis argument.
  • A handwritten prototype of the git-to-Scion ingestion pipeline is replaced after an early Claude Mythos Preview snapshot rewrites it with no further instructions: 20x less memory, 4x faster, invariants preserved.
    → Embodies the claim that model capability both created the need and accelerated the solution, and that Claude can preserve implicit invariants.
  • Multiple systems tried to find when a change merged to main by linearly reading the commit log instead of asking the code review tool; engineers had to tell Claude 'no'.
    → Illustrates that agents violate system constraints to satisfy local patterns, which is why engineers' design judgment remains necessary.
  • An adversarial reviewer was overly defensive about trusting another internal service, causing Claude to add excessive validation and complexity.
    → Shows that adversarial review has its own failure mode (myopic over-engineering), reinforcing the need for human steering.
  • Claude finds an algorithmic optimization to ancestry queries that missed one of the indexes, work that would have taken an expert days or weeks, then 'did it all again the next day.'
    → Supports the quality and optimization claim; suggests repeatable, cheap performance engineering.
  • Slack channels where a dedicated Claude 'superfan' watches one component (scion-daemon, scion-cache, Antique merge queue) like an engineer with nothing better to do than refresh charts.
    → Shows how agents become operational monitors that complement conventional alerts.

Questions addressed

  • ✅ How do you scale source control when agents and automated jobs multiply merges ~12x in four months and checkouts reach tens of millions per day?
    Replace git with Scion: server-side changesets, content-addressed immutable data, tiered caches, thin clients and an API for queries; reported >99% cache hit rate, 200x smaller footprint and two orders of magnitude faster checkouts.
  • ✅ Can a small team replace core infrastructure quickly and safely using an AI coding agent?
    Reported yes: seven people, five months, extensive simulation and fuzzing; engineers steer and review intent.
  • ⭕ What should the merge queue and CI gate look like when hundreds or thousands of changes merge while tests run?
    Only partly: the global-lock merge queue was not replicated; Anthropic relies on post-merge and pre-deploy testing and agent conflict repair. The CI question ('what does CI even mean') is posed but left open.
  • ⭕ How can the rest of the ecosystem benefit when Scion itself cannot be generalized?
    Offered as proposals to git platforms (server-side RPCs, new negotiation, composable sparse/shallow features) with no prototype or evidence they reproduce the gains.
  • ⭕ How is human review kept meaningful at 30,000+ merges per day and does the throughput gain translate into better outcomes?
    Barely touched: the Scion team reviews intent of every change, and Antique has semantic approval constraints, but company-wide review and outcome quality are not addressed.

Gaps

  • incomplete'Code changes merged per day' is the headline metric but is never defined (PRs? changesets? agent-authored vs human?) and no outcome data accompanies it: no size distribution, revert or incident rates, time-to-merge, or evidence that the 12x rise in merges reflects 12x more value rather than more, smaller changes. The claim that demand to merge code is 'practically infinite' rests on the trend line alone.
    Read next: Read DORA/AI-impact work on throughput versus stability and 'lines of code as a throughput proxy' critiques; look for any follow-up from Anthropic reporting revert, incident and rework rates alongside merge counts.
  • incompleteThe move from a pre-merge global-lock merge queue to post-merge and pre-deploy testing is reported without any data: how often main breaks, time-to-green, rate of concurrent-change conflicts, how conflicts are detected, how often Claude's repairs are wrong, or what pre-deploy testing catches that merge-time CI did not. 'Claude can typically fix these conflicts faster than humans can even identify them' is the entire safety case, and the failure case (a silent semantic conflict that passes both tests) is not discussed.
    Read next: Compare with post-commit review literature (commit serialization, auto-revert) and with Uber SubmitQueue-style speculative merging; look for corpus material on deterministic CI gates and change blast radius.
  • incompleteThe five-month, seven-person result is a single best-case self-report: pre-release Mythos access, an internal token budget the authors themselves call unmatched, in-house deep expertise, and an asserted counterfactual of 'years' with 'many more engineers' that was never measured. The post also states internal token spending doubles as a capability test, so the account is both case study and vendor demonstration. Transferability to organizations without these conditions is untested.
    Read next: Look for independent, non-vendor accounts of AI-assisted infrastructure migrations with time and cost baselines (e.g. large-scale agentic migrations and their transferable structure versus headline figures).
  • incompleteHuman oversight at 30,000+ merges a day is described only for the Scion team's own code ('we review every change request... examine the intent'); how the rest of the company's merges are reviewed is left to a one-line mention of semantic approval constraints in Antique. It is unexplained how intent is judged without reading the code, how comment-only versus logic changes are classified reliably, and what share of merges are autonomous.
    Read next: Read on auto-merge via fresh-context AI reviewers, review-of-intent versus review-of-code, and the human-review bottleneck in agent-heavy pipelines.
  • incompleteThe migration itself is thinly described: no account of cutover strategy, dual running, rollback, data-integrity verification of the git-to-Scion ingestion, handling of in-flight work during the move, developer reception, or the cost and dependency implications of building on Spanner. For a case study framed around migration speed, the hard organizational and risk parts are omitted.
    Read next: Read incremental-rewrite and pull-based migration accounts (strangler patterns, behavior-preserving rewrites validated against existing tests) for what a full account of an infrastructure cutover would contain.
  • incompleteAlways-online, server-authoritative design makes the Scion service a single dependency for every agent, job and developer, yet availability targets, outage experience, blast-radius containment beyond cache tiering, and disaster recovery are not discussed. The recommendation that git platforms adopt the lessons also comes without any prototype showing a git-compatible server reaches comparable gains.
    Read next: Look at third-party reporting on code-hosting platform reliability under agent load and at GitHub/GitLab server architecture work; read on cascading-failure resilience for centralized caching tiers.
