Agent-First Engineering: 9 Playbook Tips for a Zero-Human-Code Future

Key terms

  • agent-first engineering
    Designing a codebase's structure, documentation, and process around being read and acted on by coding agents as the primary consumer, with humans designing the environment rather than writing code directly.
  • table of contents, not a manual (for instruction files)
    CLAUDE.md/AGENTS.md should be a short (~100-line) index of pointers to deeper docs, read on demand, rather than an exhaustive upfront specification.
  • automated garbage collection (for code)
    Scheduled background agents that scan the codebase for bad/copied patterns and open small cleanup PRs automatically, replacing manual recurring cleanup time.
  • doc-gardening agent
    An agent that checks whether documentation still matches actual code and opens a fix-up PR automatically when it has drifted, keeping docs synchronized without manual upkeep.

Propositions

  • explicitCoding-agent instruction files (CLAUDE.md/AGENTS.md) should be minimal (~100 lines), pointer-based tables of contents rather than exhaustive manuals, because treating everything as important dilutes what the agent actually attends to.conf: high
  • explicitAny decision, spec, or architecture discussion not committed into the repository as a file is invisible to a coding agent and should be treated as not existing for agentic purposes.conf: high
  • explicitWhen an agent fails on a task, asking it directly what capability or visibility is missing from its environment is more productive than retrying the same prompt, because the agent can identify its own blind spots.conf: medium
  • explicitProject plans, including what is done and known tech debt, should be checked into the repo as versioned files rather than kept in an external tracker (e.g. Jira), because agents cannot access external tools the way they can read repo files.conf: high
  • explicitAgents reason more reliably about simple, well-established ('boring') tools and APIs than about clever or obscure libraries, because the former are heavily represented in training data.conf: medium
  • explicitLeft unchecked, agent-written code degrades a codebase by copying and propagating existing bad patterns; manual cleanup (a full day per week, in the cited example) does not scale as a countermeasure.conf: medium
  • explicitScheduled background agents dedicated to scanning for bad patterns and to detecting doc/code drift, each opening small automatic PRs, are a viable substitute for the manual cleanup and documentation-maintenance effort that doesn't scale.conf: medium
  • explicitThe engineer's role in 2026 shifts from hands-on coding to designing the environment (systems, scaffolding, leverage) in which agents write the code, and this shift confers a meaningful head start to those who adopt it early.conf: low

Arguments

Treating the codebase and its documentation as the agent's entire operating environment, and engineering that environment deliberately, is what allows agent-written code to scale without quality collapse. strength: low
Explicit premises:
  • Agents only see what is in the repo; anything else (Slack, Docs, Jira) is invisible to them.
  • Minimal, pointer-based instruction files preserve agent attention better than exhaustive upfront manuals.
  • Left alone, agent-authored code degrades by propagating bad patterns, and manual cleanup doesn't scale.
Implicit premises:
  • The single case cited (3 engineers, 1 million lines, OpenAI) generalizes to other teams and codebases.
  • Automated 'garbage collection' and 'doc-gardening' agents reliably distinguish genuinely bad patterns/stale docs from legitimate variation, without introducing their own noise or false-positive PRs.
  • A short instruction file plus progressive disclosure is sufficient context for an agent to find everything it needs, i.e. the 'deeper docs' it is pointed to are themselves well-maintained and discoverable.
Inferences:
  • If background cleanup/doc-gardening agents themselves need human review of their PRs, the 'automation' does not eliminate human engineering effort so much as relocate it from writing code to reviewing agent-opened cleanup PRs — a point the post does not address.

Narratives

  • OpenAI's team allegedly spent every Friday (20% of the work week) manually cleaning up codebase degradation caused by agents copying bad patterns, until this 'didn't scale' and they built automated garbage-collection and doc-gardening agents instead.
    → Supports the proposition that manual review/cleanup cannot keep pace with agent-authored code volume, and motivates the shift to scheduled background agents as the only scalable fix.
