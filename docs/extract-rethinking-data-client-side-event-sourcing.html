Podcast: Rethinking Data: Moving From the Traditional Three-Tier Web Stack to Client-Side Event Sourcing

Johannes Schickling · rss · 2026-07-27 source ↗ Reader 🖥️

Client-Side Event SourcingLocal-First Software
Client-side event sourcing — replaying an immutable log of events rather than syncing a mutable, auto-merging CRDT object — is a structurally different but equally legitimate way to achieve local-first software's goals, and should be adopted (like local-first itself) only when an application's core value genuinely depends on offline resilience, client-side speed, and user data ownership, since restructuring where and how data lives is one of the most fundamental and hardest-to-reverse decisions a team can make.

practical · mixed — A first-person narrative (Prisma -> Overtone -> LiveStore) grounds an argumentative core: when and how to adopt local-first architecture, and which of two competing technical strategies (CRDTs vs. client-side event sourcing) to use to implement it. The theoretical distinction between event sourcing and CRDTs is ultimately in service of practical advice ('adopt local-first only if X; then choose technology Y').

Key terms

  • Local-First Local-First Software
    A design principle where the client (not the server) holds the primary copy of data and processes changes immediately, giving offline access and no-round-trip speed — distinct from mere 'offline mode' bolted onto a cloud-first app.
  • Client-side event sourcing Client-Side Event Sourcing
    Treating the client's source of truth as an append-only, ordered log of events (not a mutable object), which is replayed to derive materialized state (e.g. a reactive local SQLite database); lets application logic evolve and be reapplied to full history rather than mutating state in place.
  • CRDT (conflict-free replicated data type) Local-First Software
    In Schickling's framing, a mutable-object abstraction (object, array, set, counter) with automatic, deterministic merge semantics across replicas — contrasted against event sourcing's append-only, replay-based model.
  • LiveStore
    Schickling's open-source local-first framework combining a client-side event-sourcing sync engine with a reactive, in-process SQLite database as the queryable materialized view; the successor to the Riffle research project (with Nicholas Schiefer and Geoffrey Litt).
  • Local vs. global (as an adoption heuristic)
    A heuristic for deciding whether local-first is appropriate: applications where speed/UX for a single user's own data is paramount (a personal note) favor local-first; applications where cross-user correctness is paramount (a financial transfer, a global social network) favor a traditional authoritative-server model.

Arguments

Client-side event sourcing is a legitimate, and for some applications superior, alternative to CRDT-based local-first architectures. strength: medium
Explicit premises:
  • Event sourcing lets a team replay history under new application logic rather than mutating an object in place.
  • Music-library metadata is messy, externally sourced from multiple changing services, and needs long-term schema evolution and de-duplication/tombstoning.
  • CRDTs are built around a mutable-object abstraction that is harder to reason about semantically when the data's shape and provenance keep changing.
Implicit premises:
  • Auditability and replayability are worth more, for this class of application, than the merge-conflict-free simplicity CRDTs offer.
  • The team is willing to absorb event sourcing's higher upfront architectural design cost.
Inferences:
  • Teams building on messy, multi-source data more broadly (not only music curation) may be better served by event sourcing than CRDTs, even outside a strictly local-first context.
Teams should adopt local-first architecture only after actively trying to talk themselves out of it. strength: high
Explicit premises:
  • Local-first requires substantially more upfront thinking about how data is decomposed and how it will grow.
  • The choice of data architecture is a foundational, hard-to-reverse decision, unlike swapping a web router or web server.
Implicit premises:
  • Most teams underestimate the cost of switching architectures after the app is built.
  • Unneeded architectural complexity carries a real ongoing cost even in a version that technically 'works.'
Inferences:
  • A short pre-commitment checklist (offline criticality, tolerance for poor connectivity, importance of user data ownership, whether the data model decomposes into bounded units) should precede any local-first technology selection.

Narratives

  • Schickling's arc from founding Prisma (server-centric database tooling) through a self-described 'technological trauma' over database migrations, to going all-in on local-first in 2020 via ideas from friends at Ink & Switch.
    → Grounds the claim that hands-on pain with schema/migration management on the server side is what makes event sourcing's replay-based schema evolution personally and professionally attractive to him — supports proposition 6 and argument 1 with lived motivation rather than abstract preference.
  • Overtone's handling of a track Spotify removes from its catalog: Schickling keeps a 'tombstone' preserving all the user's own tags, so that if the same track later reappears from another source it can be de-duplicated and reunited with its history.
    → Concretely illustrates proposition 6 (event sourcing's suitability for messy, externally-sourced, evolving data) and gives operational meaning to 'data ownership' beyond the bare fact of local storage.
  • The comparison to Uber's database growing from small per-city deployments to a globally scaled system, forcing repeated backend data-architecture rework — which Schickling frames as 'easier' than the equivalent local-first rework because it stayed purely a backend concern.
    → Supports propositions 2 and 4 (adoption should be deliberate) — illustrates why the same kind of growth-driven rearchitecture becomes comparatively harder and higher-stakes once it has to happen on the client, as local-first requires.

Questions addressed

  • ✅ How can a web application achieve the perceived reliability and speed of native desktop software?
    By moving the primary data copy and the change-processing loop to the client (local-first) instead of routing every interaction through a server.
  • ✅ Should a local-first app use CRDTs or event sourcing to implement its data sync?
    Depends on the data type and its provenance: simple, order-insensitive data (counters, sets) suits CRDTs; messy, schema-evolving, externally-sourced data suits event sourcing.
  • ✅ How does a local-first app preserve genuine user data ownership and portability if the user wants to leave?
    By exposing the raw event log and/or materialized database as a legible, well-schema'd artifact rather than an opaque one-off export dump.
  • ⭕ Is client-side event sourcing viable, or even superior, for real-time multi-user collaborative editing — the scenario CRDTs were specifically designed for?

Gaps
