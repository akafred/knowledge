The Pulse #158: New Ways Of Coding With AI Tools

Gergely Orosz · pdf · 2026-01-09 Reader 🖥️

Agentic LoopAnswerabilityCoding AgentsHuman-in-the-Loop
As AI agents get capable enough that engineers can plausibly have 'the AI did it' as an excuse, human accountability for whether software actually works as expected becomes more valuable, not less — and this accountability gap is also what separates two genuinely new ways of coding gaining traction right now: supervised, interactive human-in-the-loop AI use (where an accountable expert directs and verifies) versus unsupervised autonomous loops like 'Ralph' (which trade away real-time human judgment for throughput, and only now work because the underlying models crossed a capability threshold since November).

Key terms

  • Ralph
    An autonomous agentic loop technique (coined by Geoff Huntley) that repeatedly re-runs a coding-agent CLI against the same prompt/plan file until a project is done, with no human watching each step — contrasted with the interactive, step-by-step way most developers currently use AI coding CLIs.
  • human-in-the-loop (HITL) coding
    (Quoting Matt Pocock) The default mode most developers use today: give the CLI a task, watch it work, intervene when it goes off-track — explicitly contrasted with Ralph's 'long-running, autonomous, unsupervised AFK coding.'
  • accountable software engineer
    A person who can be held responsible for software working as expected and, crucially, can determine exactly what went wrong and why if it doesn't — contrasted with a non-technical person who used AI to build something and can only say 'the AI did it' when it breaks.

Arguments

The value of being a software engineer who can be held accountable for working software rises as AI makes it easier for anyone to produce code that merely looks correct. strength: medium
Explicit premises:
  • More mission-critical software will be built quickly, by a wider range of people including non-engineers, because AI lowers the barrier to producing something that runs.
  • Someone is always accountable when software fails to work as expected.
  • A trained engineer, unlike a non-technical AI user, can determine exactly what went wrong and why, and prevent recurrence.
  • LLM output can look authoritative to a non-expert while being substantively wrong, as demonstrated by the author's own legal-advice experience.
Implicit premises:
  • Organizations and individuals will, in practice, want or need someone to blame or hold responsible when AI-assisted software fails, rather than accepting 'the AI did it' as a terminal explanation.
  • The ability to debug and explain a failure is not itself something AI can yet reliably substitute for, even as it becomes better at generating the original code.
Inferences:
  • If accountability becomes the scarce, valuable skill, hiring and compensation should increasingly favor engineers who can diagnose and explain failures in AI-generated systems, not just those who can prompt AI to generate code quickly — a shift in what 'senior engineer' competence means.

Narratives

  • The author needed professional legal advice, got it stamped and in writing specifically so he would be protected and accountable, but while waiting four weeks for the lawyer's answer, ran the same question through Claude, ChatGPT and Perplexity; all three reasoned plausibly but reached the wrong conclusion because they lacked undocumented, insider regulatory knowledge the law firm had.
    → Grounds the accountability argument in a first-person case where confident-sounding AI reasoning was substantively wrong in a way only a domain expert could detect — the evidentiary basis for the CFO/payroll hypothetical that follows.
  • After a server ran out of memory and CPU, Tailwind's small, AI-stretched team SSH'd in, installed Claude Code, and used it as an impromptu DevOps engineer to diagnose that load (not a code bug) was the cause.
    → An implicit counter-case to the accountability argument above: a small team without dedicated specialist expertise used an AI agent successfully for exactly the kind of diagnostic work the CFO/payroll example says non-experts can't reliably do with AI — the piece does not reconcile the tension.

Questions addressed

  • ✅ Does AI's growing coding capability reduce or increase the market value of a professional software engineer?
    Increases it, specifically for the accountability function — determining why something broke and ensuring it doesn't recur — which the author argues AI and non-technical AI users cannot substitute for.
  • ✅ Why did the autonomous 'Ralph' loop technique only become practically viable in the weeks before this piece, rather than whenever the pattern was first conceived?
    Underlying model capability crossed a threshold (model improvements since November) that made unsupervised loops reliable enough to be useful, rather than the technique itself changing.
  • ⭕ Is the author's own accountability argument (engineers are needed because non-experts get fooled by confident-sounding AI output) consistent with the Tailwind anecdote in the same piece, where a small team with no dedicated specialist used an AI agent successfully for diagnostic work?

Gaps
