This coding agent doesn’t want your feedback — it ships without it

Darryl K. Taft · article · 2026-06-01 source ↗ Reader 🖥️

Agentic vs. Deterministic System DesignClosed-Loop Coding Agents (Compiler-Style vs. Chat-Style)Coding AgentsGuardrailsHuman-in-the-LoopModel RoutingVerifiability (as the Quality Bar)
AI coding tools have been optimizing the wrong variable — speed within a chat-based, human-reviewed iteration loop — when the real failure mode of AI-generated code is architectural (state management and concurrency); the fix is a closed-loop agent that internalizes review inside a deterministic, type-checking runtime and makes the developer's involvement in the loop optional rather than merely faster.

practical · mixed — Primarily a product-launch profile (expository), but organized around an explicit architectural thesis — that AI coding tools should be built as closed-loop, developer-optional systems rather than faster chat loops — which the piece argues for via Verlaguet's quotes and the mechanics of what Skipper does. Practical because the upshot is 'build/use tools this way,' not merely 'here is what is true.'

Key terms

  • closed loop Closed-Loop Coding Agents (Compiler-Style vs. Chat-Style)
    The prompt → generate → validate → fix cycle runs entirely inside the agent itself (model plus deterministic runtime and type checker), with no exposed step where a developer reviews or refines the output before it ships. Contrasted explicitly with Claude Code, Cursor, and Codex, which keep the developer inside that same cycle turn by turn.
  • reactive runtime
    A runtime (descended from the Skip language Verlaguet built at Facebook) in which a program is defined as a declarative graph of computation from inputs to outputs; the runtime automatically handles state management, cache invalidation, and concurrency, so the AI model generating the service never has to reason about what happens when one part of the state graph changes and another depends on it.
  • architecture problem disguised as a coding problem
    The recurring claim that correctness in software has always depended on structural decisions (how state, concurrency, and data flow are organized) rather than on the surface skill of writing individual lines of code — and that AI does not change this underlying reality, it only raises the stakes because AI can generate incorrect-but-plausible code far faster than architecture can be gotten right by prompting alone.
  • guardrails Guardrails
    Verlaguet uses the term narrowly and critically: real guardrails are deterministic tooling and runtime infrastructure built from scratch to structurally bound AI behavior (e.g., a reactive runtime that makes certain classes of bugs impossible), as opposed to what he says most competitors actually ship under that label.

Arguments

AI coding tools should be built as closed-loop, developer-optional systems rather than as faster chat-based collaborators. strength: medium
Explicit premises:
  • Correct software has always depended on architecture (state/concurrency structure), not on the coding step itself.
  • Existing agents (Claude Code, Cursor, Codex) speed up the human-in-the-loop chat cycle but do not change that underlying architecture problem.
  • A reactive runtime can manage state and concurrency correctness automatically, so the model generating the code never has to reason about state-graph dependencies.
Implicit premises:
  • If state/concurrency correctness is structurally guaranteed by the runtime, a human reviewing the code's surface form adds little additional safety.
  • Verifying correctness deterministically (type checks, execution in a container) is a sufficient proxy for verifying that the software does what the developer actually wanted.
Inferences:
  • This reframes trustworthiness in AI-generated code as a property of the surrounding deterministic system rather than of the model or of human oversight — an inference that would extend well beyond backend/API generation only where an equivalent typed, reactive substrate exists, and would not obviously transfer to domains (UI, algorithmically novel logic, under-specified requirements) that lack one.
Verification/guardrail tooling for AI-generated code must become incremental rather than batch (CI-style).
Explicit premises:
  • Model generation speed is increasing rapidly.
  • Waiting on 30–60 minute CI cycles will not be tolerable as generation speed increases.
Implicit premises:
  • Feedback value is time-sensitive: incremental, mid-generation feedback is usable in a way that slower, end-of-batch feedback is not, because by the time batch feedback returns the generation process has already moved on.
Inferences:
  • If this premise is right, it undercuts not just CI-gated review but human code review generally — human review is slower and less incremental than a 30–60 minute CI run — which is consistent with, but not explicitly stated as, an argument for removing developers from the loop entirely.

Narratives

  • The step-by-step account of what happens on a single Skipper run: receive a prompt, generate an OpenAPI spec from it, build the full service (routes, data mappers, validators, TypeScript types, unit tests), run it in a Docker container, and — if generated code fails type checks — fix it, up to eight attempts, before returning a result, all without a developer watching.
    → Makes the abstract 'closed loop' key term concrete, and implicitly argues that 'no review cycle' does not mean 'no verification' — verification still happens, just mechanically and internally (type checks, container execution) rather than through human judgment.
  • The comparison to React: 'the same idea applied to a backend service instead of a UI' — JavaScript handles the computation links between graph nodes, while the Skip runtime manages everything below that.
    → Supports the 'reactive runtime' key term by borrowing credibility from a proven, familiar pattern (React's declarative UI reactivity), implicitly arguing that an equivalent reactive substrate for backend state is a precedented engineering bet rather than a speculative one.

Questions addressed

  • ✅ What has the AI coding tool industry gotten wrong?
    It has optimized developer speed inside a human-reviewed chat/iteration cycle, when the actual failure mode of AI-generated code (state management and concurrency) requires a structural fix and removing the human review step, not a faster version of it.
  • ✅ Why do most competitors' 'AI guardrails' claims fail to deliver real guardrails?
    Because building real, deterministic guardrail tooling from scratch is a lot of work, so competitors default to prompting instead and market it as guardrails.
  • ⭕ What happens when Skipper's internal fix loop cannot resolve a type error within its eight-attempt budget?
  • ⭕ Does removing the developer from the loop generalize beyond typed backend/API service generation — e.g., to UI code, algorithmically novel logic, or under-specified requirements — or is it scoped to domains where a comparable reactive, typed substrate already exists?

Gaps

  • illogicalThe article states that Skipper makes the developer's involvement 'optional' and removes review/iteration/back-and-forth entirely, while the same paragraphs describe the developer supplying the prompt or OpenAPI spec that determines what gets built — and, implicitly, deciding afterward whether the resulting service is fit to deploy. The developer has not left the loop; they have moved to its specification and acceptance ends. The piece never acknowledges this as anything short of full removal, an equivocation between 'the review-and-refine sub-loop is internalized' (true, and interesting) and 'the developer's involvement is optional' (overstated, given the developer still authors the input and presumably judges the output before it ships to production).
    Read next: extract-agentic-code-review's proposition that 'the human does not leave the loop but moves up a level ... human-in-the-loop becomes human-on-the-loop' names exactly this dynamic and is a useful direct comparison; also worth reading anything Verlaguet or SkipLabs publish post-launch about how developers actually validate and accept Skipper's output before deployment.
  • incompleteThe article never explains what happens when Skipper's internal fix loop exhausts its eight attempts without passing type checks — does it return the last broken candidate, surface an error to the developer, or fail silently? Without an answer, 'ships without your feedback' is a claim about the happy path only; the framing hides an unspecified failure mode at precisely the point where developer judgment would otherwise matter most.
    Read next: A technical writeup, postmortem, or incident report on Skipper's real production failure behavior; more generally, material on retry-budget exhaustion and failure disclosure in agentic code-fix loops.
  • incompleteThe correctness claim rests entirely on type checks passing and the service running in Docker; it never addresses whether type-correct, running code is also semantically correct — i.e., whether it does what the developer actually intended. Type safety and intent-fidelity are different guarantees, and the article treats passing the former as sufficient evidence of the latter.
    Read next: Material on the gap between formal/type conformance and intent conformance in AI-generated code — e.g., discussions of formal methods noting a formal specification can be precisely wrong, or corpus material on what counts as sufficient verification for AI-generated code.
