Why your team doesn't need to use pull requests

infrastructure-as-code.com (Kief Morris) · article · 2021-01-02 source ↗ Reader 🖥️

Feedback LoopsPair & Mob ProgrammingPull Requests & Async Code ReviewTrunk-Based & Continuous Delivery
Pull requests were designed to vet contributions from untrusted outside contributors, so applying them to a trusted team's own code sacrifices Continuous Integration's fast feedback and flow for no corresponding risk-reduction benefit; teams should instead integrate continuously and get code review through pairing, periodic group reviews, or post-integration pipeline approval gates.

practical · argumentative — Argues for a specific team practice (adopt CI over PR gating for trusted team members) using a historical/origin argument plus a flow/feedback-delay comparison.

Key terms

  • pull request Pull Requests & Async Code Review
    A batch-and-wait control: a proposed change packaged as a reviewable unit that a human must approve before it is merged into the mainline — originally built to assess unknown outside contributors, not team insiders.
  • Continuous Integration (CI)
    Integrating and automatically testing every team member's code against the mainline at least once a day (not once per finished feature) so that conflicts and defects surface within minutes — a flow/feedback optimization, not merely 'having a CI server.'
  • trunk / mainline
    The single shared integration branch that every team member's work merges into, ideally daily.

Arguments

A team whose members share norms and trust should default to Continuous Integration rather than pull requests for integrating code. strength: high
Explicit premises:
  • PRs were built to manage risk from untrusted outside contributors.
  • PRs introduce an integration delay that CI is specifically designed to eliminate.
  • That delay disrupts flow (context-switching) and slows discovery of integration problems.
  • Review quality can be preserved through pairing, periodic reviews, or post-integration pipeline approval instead of a pre-integration PR gate.
Implicit premises:
  • The risk profile that justifies a pre-integration human gate (unknown contributor intent/quality) does not apply to a team that already shares norms and direction.
  • The cost of integration delay (slower feedback, flow disruption, bigger inventory/batches) generally outweighs whatever marginal extra safety a pre-integration gate adds for trusted insiders.
Inferences:
  • If delay-before-integration is the real cost of PRs, any review mechanism that delivers human review without sitting between 'done' and 'integrated' (pairing, post-hoc pipeline approval) should be preferred over a classic PR gate for internal teams.
  • Teams in regulated contexts that do require a pre-merge human sign-off as an audit artifact face a genuine exception the article doesn't resolve — satisfying that requirement without reintroducing PR's delay is a separate design problem.

Narratives

  • Making family members go through an airport security checkpoint to enter your own home.
    → Makes vivid, in one image, the proposition that PR-as-default misapplies a control designed for untrusted outsiders to people who have already earned trust.

Questions addressed

  • ✅ Does code need a second human to look at it before it ships?
    Yes — but 'needs review' and 'needs a pre-integration approval gate' are treated as separable requirements.
  • ✅ Is the pull request the only (or best) way to get that second pair of eyes?
    No — pairing, periodic review, and pipeline approval gates all provide it without CI's delay cost.
  • ⭕ What should a team do when a regulator or compliance framework explicitly requires a second-person sign-off as an auditable record?

Gaps

  • incompleteThe article flags regulated environments as an exception ('having each change reviewed by a second person is required') but doesn't say how to produce an audit-grade review record without reintroducing the PR gate it argues against for everyone else.
