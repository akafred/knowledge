Make Opus 5.5 Finish Long Tasks: A Reusable Harness Engineering Setup

beamnxw ./ · tweet · 2026-10-06 source ↗ Reader 🖥️

Agent HarnessAgent MemoryAgent SkillsClaude CodeAgent Context Files (CLAUDE.md / AGENTS.md)Context EngineeringGuardrailsLong-Running & Managed AgentsVendor Self-Reported MetricsVerifiability (as the Quality Bar)
A long Claude Code run on Opus 5.5 is best set up by defining before the run what it must leave behind (an openable result, inspectable evidence, and a saved progress note) and wiring seven documented Claude Code layers (stable CLAUDE.md facts, a reusable skill, scoped source access, tool-boundary permission rules, an evidence-returning reviewer subagent, per-job effort, and a /goal completion condition) so that the same procedure can be reused on the next task and judged on measurements of accepted work, not on borrowed vendor numbers.

practical · mixed — A practitioner how-to published as an X long-form post: seven numbered setup layers (CLAUDE.md, a skill, an MCP connection, permission rules, a reviewer subagent, effort setting, a /goal completion condition) plus a progress-note handoff and a measurement section, built around a single document-drafting example. Mostly mechanism and procedure, with copy-paste config snippets that lean on documented Claude Code features and link to Anthropic docs. No measured data of any kind is given: no run counts, completion rates, token or cost figures, or before/after comparison. The title's promise that the setup makes Opus 5.5 'finish' long tasks is an unevidenced claim. The one number mentioned (a 60% token reduction) is explicitly attributed to Anthropic's early-tester report and disclaimed as not transferable. The post's teaser summary mentions stopping unfinished runs from eating the budget, but the body contains no budget-scare hook or spend-enforcement mechanism; it offers only a model-evaluated turn limit in /goal and after-the-fact /usage inspection. The closing self-promotion ('follow for more alpha') marks the genre.

Key terms

  • harness Agent Harness
    The instructions, tools, permissions, state and checks that coordinate the model; in practice the set of Claude Code configuration surfaces (CLAUDE.md, skills, MCP, settings.json, subagents, /goal).
  • layer
    One of seven configuration responsibilities, each with a concrete Claude Code location and an observable output.
  • evidence
    A saved, inspectable artifact tying a claim to an opened source or an outcome (a claim/verdict/source table, output paths plus verification results), as opposed to the agent's say-so or the transcript.
  • progress note (progress.md)
    A structured handoff file (task, outputs, completed checks, decisions, open issues, one next action) that a fresh session reads to continue.
  • /goal completion condition
    A Claude Code goal evaluated against evidence the agent surfaces in the conversation between turns; the turn-limit clause is also model-evaluated, not a hard runtime limit.
  • accepted work
    A run's output after the human has inspected it and judged what corrections it needed; the denominator for evaluating a setup.
  • execution layer
    Permission rules and PreToolUse hooks that decide at the tool boundary what an action may do, as opposed to instructions the model may ignore.

Arguments

Defining deliverables, evidence and a progress record before starting makes a long Claude Code run likely to finish and be reusable.
Explicit premises:
  • A harness coordinates instructions, tools, permissions, state and checks around the model.
  • Each layer gives an observable output (a saved file, a table, a progress note).
  • A fresh session can resume from the recorded next action.
Implicit premises:
  • Long-run failure is mainly due to missing state, unclear completion criteria and unchecked outputs, rather than to model limits such as context decay or fatigue.
  • Instruction-following on CLAUDE.md, skills and the progress note is reliable enough over many turns.
  • The document-drafting example is representative of the long tasks the reader will run (including coding).
Inferences:
  • The same skeleton (fixed outputs, reviewer, completion format, progress note) should transfer to coding and research tasks with only the skill and reviewer swapped.
A dedicated evidence-reviewer subagent that returns a claim/verdict/source table is a sound way to verify draft outputs.
Explicit premises:
  • A subagent has its own context and configurable tools.
  • Each finding connects a claim to an opened source, and unresolved verdicts name the missing evidence.
  • Anthropic's evaluation guidance separates the transcript from the outcome left in the environment.
Implicit premises:
  • A reviewer from the same model family is independent enough from the drafter's errors.
  • Opened primary sources are themselves reliable and are what the reviewer actually reads.
  • The human will do the spot-checks the post recommends.
Inferences:
  • The unresolved verdict is more valuable than a confident pass: it converts silent uncertainty into a visible work item.
  • Checking the saved artifact, not the transcript, is the rule that keeps review honest.
Do not expect the 60% token saving from Anthropic's report to apply to your harness; measure your own on accepted work. strength: high
Explicit premises:
  • The 60% figure belongs to a model experiment.
  • Savings depend on the harness, task and acceptance criteria.
  • Usage must include delegated review and retries.
Implicit premises:
  • Vendor early-tester numbers are measured under conditions unlike the reader's.
  • The reader will actually run controlled one-change-at-a-time comparisons.
Inferences:
  • By the same logic the post's own recommended setup is also unmeasured, so the reader should treat it as a hypothesis to test.

Questions addressed

  • ✅ How do you configure Claude Code so that a long Opus 5.5 run produces inspectable results and can be resumed after a break?
    Seven layers plus a progress note: stable CLAUDE.md, a skill, scoped MCP access, deny rules and hooks, a reviewer subagent, per-job effort, and a /goal with explicit completion evidence.
  • ✅ How should you judge whether this setup is worth its cost?
    Measure accepted work on your own tasks (usage including retries, review time, corrections), change one component at a time, and do not borrow vendor figures.
  • ⭕ Does the setup actually raise the rate at which long runs finish, relative to no setup?
    Not addressed; the post asserts the outcome in its title and offers no completion data or baseline.
  • ⭕ How do you stop an unfinished run from consuming the budget (the teaser's framing)?
    Only partially: a model-evaluated 12-turn clause and after-the-fact /usage checks; the post says strict spending limits need execution controls and does not provide them.

'Finish' is never defined beyond the example's file-existence condition. The title's promise rests on mechanism plausibility alone, and the author's own advice to measure applies to the post itself.

    Read next: Generator/evaluator separation and LLM-as-judge reliability studies, plus work on verification capacity as the human bottleneck.
  • incompleteThe worked example is a short document-drafting task capped at 12 turns, not a multi-hour or multi-session coding run. Context rot, compaction loss beyond the root CLAUDE.md re-read, and task decomposition across sessions are not treated, so the claim for 'long tasks' is not exercised by the example.
