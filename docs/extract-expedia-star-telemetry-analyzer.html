Expedia Uses AI Driven Service Telemetry Analyzer to Accelerate Incident Investigation

Expedia built STAR, an internal AI-assisted observability tool, on the premise that a deterministic, human-validated, prompt-chained workflow over standardized infrastructure telemetry -- deliberately forgoing function calling, RAG, memory and autonomous tool use -- is the right way to accelerate production-incident root-cause investigation today, with engineers remaining the final validators of every finding.

practical · expository — InfoQ news reporting on an Expedia engineering blog post. It narrates a design decision -- a deterministic, prompt-chained workflow instead of an autonomous agent -- without the source text actually arguing for that choice over alternatives; the 'argument' extracted below is a reconstruction of the reasoning implied by the choice, not something the text defends explicitly.

Key terms

  • Time to Know (TTK)
    The elapsed time before responders understand what is wrong with a service and why -- presented as one of the two objective functions STAR was built to minimize.
  • Time to Recover (TTR)
    Time from incident onset to service restoration, used identically to the standard SRE sense but abbreviated without 'Mean.'
  • deterministic workflow (as opposed to an autonomous AI agent)
    A fixed, predefined sequence of steps -- collect telemetry, analyze via domain-specific prompts, consolidate intermediate findings, summarize into a report -- that the LLM does not deviate from by planning its own actions, calling functions, retrieving from a vector store, or invoking tools autonomously.
  • prompt chaining
    Sequencing multiple specialized LLM calls so each stage's output feeds the next stage, producing a consolidated diagnosis from several narrower analyses.

Arguments

A deterministic, prompt-chained workflow -- not an autonomous agent -- is the right architecture for this production incident-diagnosis tool. strength: low
Explicit premises:
  • The current implementation does not use function calling, RAG, memory, or autonomous tool use.
  • It instead relies on predefined workflows to generate consistent analyses.
Implicit premises:
  • Consistency and predictability of output matter more, for production incident diagnosis, than the flexibility autonomous tool-use would offer.
  • Autonomous agentic techniques would produce less consistent or less easily auditable output than a fixed prompt-chain.
  • Engineers can trust and act on a report more readily when they can predict and audit the fixed steps that produced it.
Inferences:
  • This design trades exploratory flexibility for reproducibility and auditability -- a trade-off the article never states or defends explicitly.
  • Because the roadmap proposes adding 'MCP based tool integrations' and 'conversational interfaces,' the deterministic architecture is implicitly a stage in an evolving system rather than a permanent ceiling -- raising the unaddressed question of whether those additions reintroduce the very autonomy the initial design avoided.

Questions addressed

  • ✅ How can engineers reduce the time needed to identify the root cause of a production incident?
    By building STAR: an internal tool combining infrastructure telemetry with LLM analysis via a deterministic, prompt-chained workflow, producing a structured root-cause report for engineers to validate.
  • ✅ Should AI-driven observability/incident tooling be built as an autonomous agent or as a constrained, deterministic workflow?
    Expedia chose the deterministic, prompt-chaining route explicitly, over autonomous agents with function calling, RAG, memory, or tool use.
  • ⭕ Does adding the planned future capabilities (MCP-based tool integration, conversational interfaces) undermine the deterministic-workflow rationale the current design relies on?
