Case Study: Refactoring at Scale with Agents

codescene.com · article · 2026-09-24 source ↗ Reader 🖥️

Behavioral Code AnalysisClosed-Loop Coding Agents (Compiler-Style vs. Chat-Style)Code QualityCoding AgentsLegacy & Organizational ForgettingTechnical DebtToken Efficiency
Large-scale legacy refactoring, once economically prohibitive, becomes tractable when a coding agent is paired with a deterministic code-quality feedback loop (CodeScene's Code Health metric) and automated correctness verification — demonstrated by uplifting a 300,000-line C codebase from Code Health 5.6 to a perfect 10.0 in three weeks for roughly $4,000 in tokens, work the author estimates would have taken 12-18 months of expert developer time before AI.

practical · narrative case study with argumentative framing — Written by Adam Tornhill (CodeScene founder/CTO) as a vendor case study: narrates a concrete large-scale refactoring project (credited to Daniel Webb and Dr. Markus Borg) and argues from it to a general claim about the economics of technical-debt remediation.

Key terms

  • Code Health Behavioral Code Analysis
    CodeScene's proprietary 0-10 code-quality score, used here as the deterministic target metric that refactoring agents optimize against and are judged by — chosen specifically because it was independently validated (in prior CodeScene research) as a proxy for productivity, defect density, AI correctness, and token efficiency, not merely a convenient automatable number.
  • Playbook
    An iteratively-built, versioned set of named refactoring recipes (with documented preconditions, success/failure outcomes, and additional notes) that the agents accumulate as they work through a codebase, making each subsequent refactoring task more effective than the last.
  • Domain-specific refactoring recipe (e.g. 'Shared Index Range', 'Action Parameter', 'Uniform Step Table')
    A named code transformation discovered by the agents that is specific to patterns in this particular codebase, structurally different from Martin Fowler's generic refactoring catalogue (Extract Function, Guard Clauses, Parameter Object, etc.), which the author treats as the generic 'foundation' that domain-specific recipes then adapt.
  • AI-ready code
    Code structured such that AI coding agents perform reliably and cost-efficiently on it — the stated end goal of the refactoring, and the reframing of 'code quality' as something done in service of AI performance, not only human maintainability.

Arguments

Large-scale technical-debt remediation, previously economically unviable for most organizations, is now a viable investment given the right agent/feedback-loop infrastructure. strength: medium
Explicit premises:
  • 300k lines of code were uplifted to perfect Code Health in three weeks for roughly $4,000, versus an estimated 12-18 months of expert developer time.
  • Code Health improvements have been independently validated to deliver real productivity, defect-reduction, and token-efficiency benefits downstream.
Implicit premises:
  • Organizations can obtain or build the necessary infrastructure (a deterministic quality-feedback loop, an automated correctness/equivalence check) cheaply relative to the refactoring itself — an assumption the article doesn't test outside its own tool and this one codebase.
Inferences:
  • Technical-debt backlogs previously deprioritized as unaffordable should be re-evaluated against this changed cost structure.
Safe large-scale AI refactoring requires two specific, non-negotiable ingredients: deterministic quality feedback (not the agent's own unaided judgment) and automated correctness verification (not human code review at this pace and scale). strength: high
Explicit premises:
  • The author states explicitly: 'the key... is ensuring that agents aren't working blindly,' citing deterministic quality feedback and automated tests/equivalence checks as 'absolutely essential' safeguards.
  • Code Health was pre-validated against outcomes before being adopted as the target metric, addressing the Goodhart's-law risk directly.
Implicit premises:
  • Human code review of 252,055 lines across 726 files in three weeks is not actually feasible at the depth needed to catch regressions — so the entire safety case has shifted from 'a human checked it' to 'an automated oracle checked it,' a premise the article assumes rather than argues.
Inferences:
  • Codebases lacking any deterministic, automatable definition of correctness (the common case — most business logic isn't as cleanly checkable as a game's replayable state) may not be able to replicate this result regardless of agent capability or token budget.

Narratives

  • The Street Fighter III: 3rd Strike case study itself: 300,000 lines of 1990s arcade-game C code, refactored under a replay-trace verification harness that confirmed 'we could still play the game as before.'
    → Makes the correctness-verification claim viscerally concrete and credible — a deterministic, replayable game state is a case where 'did we break anything' has an unusually clean, automatable answer, which is exactly what makes the rest of the argument's safety claims land.
  • A quoted practitioner reaction: 'I had my agentic coding wins in the past, but this is the first time I'm experiencing a true superhuman AI performance at scale. And I say that as someone with three decades of experience in large-scale system development.'
    → Supplies a credibility appeal from a named, experienced practitioner (implicitly Daniel Webb or Markus Borg) rather than the vendor's own marketing voice, supporting the magnitude claim about model capability (proposition 4).

Questions addressed

  • ✅ Can coding agents remediate large-scale technical debt economically, in a domain where human-driven rewrites have historically failed or been deprioritized as too risky and expensive?
    Yes, demonstrated at 300k LOC for roughly $4,000 and three weeks, given a deterministic quality-feedback loop and an automated correctness-verification harness.
  • ✅ Which refactorings should an agent apply at scale, and are they the same ones a human expert would reach for?
    No — the agents discovered and productized domain-specific recipes structurally different from a human's generic catalogue (Fowler), which the author treats as a genuine, if 'obvious in retrospect,' insight: generic refactorings are the foundation, domain-specific ones the adaptation.
  • ✅ Does this result mean technical debt is now a solved problem industry-wide?
    No — explicitly addressed and rejected: naive AI adoption onto unhealthy codebases, without this feedback/verification infrastructure, is argued to compound debt rather than resolve it.
  • ✅ Is the Code Health metric a legitimate optimization target for an agent, or just a convenient, gameable proxy?
    Argued legitimate, because it was independently validated against productivity, defect-density, AI-correctness, and token-efficiency outcomes before being adopted here — directly answering the Goodhart's-law risk the author names himself.

Gaps

  • incompleteThis is an n=1 case study, authored by the vendor of the Code Health tool being validated, on a codebase chosen specifically for having deterministic, frame-perfect replayable state — a correctness-verification advantage most enterprise codebases (external APIs, databases, UI, concurrency, production constraints) don't have. The article never addresses how correctness would be verified at this pace and scale without an equivalent deterministic oracle.
    Read next: Look for a second, independent (ideally non-vendor-authored) case study on a typical enterprise codebase lacking a replay-trace-style oracle, to test whether the result generalizes.
  • incompleteThe headline $4,000-tokens-vs-12-18-months-of-engineers comparison discloses neither the loaded engineer cost assumption, the token pricing used, nor whether the 12-18 month estimate is the author's own guess or drawn from a cited prior project — leaving the ROI figure directionally persuasive but not independently checkable.
    Read next: Request or look for the underlying cost model and a citation for the 12-18 month baseline estimate.
  • incompleteThe article states that 'many' refactoring attempts failed or made Code Health worse, and that documenting these failures mattered, but gives no quantitative failure rate — e.g. how many attempts were needed per successful recipe, or what fraction of the 22 recipes required multiple tries. This number would materially change how repeatable (versus lucky) the three-week headline figure looks.
    Read next: A follow-up post or dataset disclosing attempt-level success/failure counts, not just the final playbook.
  • incompleteThe playbook and its named recipes were discovered on a single codebase (C, a 2D fighting-game engine). The article doesn't address how much of the discovered playbook is reusable across codebases/domains versus specific to this one — which bears directly on whether the $4,000/three-week economics would hold on a second, unrelated codebase rather than being a one-off artifact of this particular code's structure.
    Read next: A second case study on a different language/domain (e.g. a typical enterprise CRUD service) testing playbook transfer.
