DoorDash Uses Envoy and Valkey for a 1.5M RPS Proxy Cache with 99.99999% Availability

Leela Kumili · rss · 2026-07-20 Reader 🖥️

Distributed Caching & InvalidationInfrastructure EfficiencyModularity & CouplingSoftware Design FundamentalsSRE & Incident Response
DoorDash's Entity Cache shows that moving caching out of individual services and into a transparent, infrastructure-layer proxy (Envoy + Valkey) — with event-driven invalidation, staleness-tolerant failure handling, and stampede-avoidance techniques — can absorb very large request volume at extremely high availability without requiring any application code changes.

practical · expository, with one embedded narrative — A news report (InfoQ relaying a DoorDash engineering-blog post) describing an existing production system and its measured outcomes. It doesn't argue for the pattern so much as narrate it and report DoorDash's own numbers as fact, with one production-outage anecdote functioning as informal proof of the reliability claims.

Key terms

  • Entity Cache Distributed Caching & Invalidation
    DoorDash's specific, named transparent-proxy caching platform built on Envoy and Valkey.
  • transparent proxy cache Distributed Caching & Invalidation
    A cache implemented as a proxy inside the service mesh that intercepts existing HTTP/gRPC calls, so services get caching without any code change or awareness that caching is happening.
  • dual TTL Distributed Caching & Invalidation
    Two separate expiry values per cached entry: a short one marking data as 'fresh,' and a longer one marking the outer bound past which even stale data won't be served — the gap between them is what's servable during an outage.
  • single-flight Distributed Caching & Invalidation
    A lock-free mechanism ensuring that when multiple concurrent requests miss the cache for the same key, only one upstream request is made and the result is shared, rather than each request independently hitting the upstream.
  • XFetch Distributed Caching & Invalidation
    An algorithm that proactively refreshes hot cache entries some random amount of time before their actual expiry, spreading refresh load over time to avoid many requests simultaneously hitting an expired entry.
  • 99.99999% availability (seven nines)
    The headline reliability figure DoorDash reports for Entity Cache itself.

Arguments

Entity Cache's centralized, infrastructure-layer caching is a superior approach to ad hoc, per-service caching for a large microservices ecosystem. strength: medium
Explicit premises:
  • Frequently accessed but infrequently changing data caused repeated requests, increased backend load, extra compute cost, and higher tail latency as DoorDash's microservices ecosystem expanded.
  • Entity Cache lets teams adopt centralized caching without implementing separate solutions within individual applications.
  • Entity Cache achieves 1.5M RPS at 99.99999% availability, >90% hit rates, and measured reductions in upstream requests, allocation rate, and latency.
Implicit premises:
  • Centralized, infrastructure-layer caching scales and generalizes better across many services than distributed, per-team caching implementations would.
  • The operational and complexity cost of running one shared caching proxy that many services now depend on is lower than the aggregate cost of many teams building and maintaining separate caches.
  • The specific numbers reported generalize from DoorDash's particular workload and traffic shape to caching problems more broadly, rather than being an artifact of DoorDash's specific request patterns.
Inferences:
  • From 'reduces backend load, reduces latency, and achieves a high hit rate' to 'this pattern is broadly recommendable for microservices architectures at scale.'
The staleness-tolerant design (dual TTL plus event-driven invalidation plus health-based rerouting) makes Entity Cache reliable enough to keep serving through infrastructure failures. strength: low
Explicit premises:
  • Dual TTL thresholds allow 'slightly stale' responses to be served during outages.
  • Envoy removes unhealthy cache instances and routes requests directly to upstream services when needed.
  • During an actual multi-hour outage, the system kept serving stale-but-valid data instead of failing.
Implicit premises:
  • The data cached by Entity Cache is generally tolerant of staleness across its consuming services — no endpoint proxied through it has real-time consistency requirements where serving stale data would itself be a correctness failure (e.g., live pricing, order status, checkout inventory).
  • A single observed outage is representative of failure-handling behavior in general, rather than a favorable, cherry-picked anecdote.
Inferences:
  • From 'this design worked during one observed outage' to 'this design is validated for production reliability at DoorDash's full scale and across all use cases.'

Questions addressed

  • ✅ How can a large microservices architecture reduce redundant service-to-service requests and the backend load/tail latency they cause, without requiring every team to build its own caching logic?
    Centralize caching in a transparent proxy (Entity Cache, on Envoy + Valkey) at the service-mesh layer, requiring no application code changes.
  • ✅ How does a shared cache stay fresh without expensive fan-out cache-invalidation broadcasts across a large distributed system?
    Kafka-based event-driven invalidation compares update timestamps to cached-response timestamps, rather than issuing distributed delete commands.
  • ✅ How does the cache avoid stampede/thundering-herd failures when many popular keys expire simultaneously under massive request volume?
    Lock-free single-flight deduplicates concurrent misses for the same key, and probabilistic early refresh (XFetch) refreshes hot entries before they expire.
  • ✅ What should happen to cached data and its consumers when the caching layer or upstream services experience partial failures — does the system fail closed (error) or fail open (serve something)?
    The system fails open: it degrades to serving slightly-stale data within a second TTL threshold rather than failing the request, and Envoy reroutes around unhealthy cache instances.
