Podcast: Securing AI Agents: Identity, Authorization, and the DPACT Framework

Sahil Agarwal · podcast · 2026-09-23 source ↗ Reader 🖥️

Agent Governance (Internal)Agent Identity & AttributionAgent SecurityDelegated Authority Grants (Bounded Task Grants)GuardrailsHuman-in-the-Loop
As AI agents shift from passive chat interfaces to autonomous 'delegated actors' that take real, consequential actions with sensitive data, organizations must replace broad, human-shaped, long-lived tokens with the DPACT framework — Delegation, Policy, Auditability, Context, and Time — so that every agent acts strictly on behalf of, and never as an impersonation of, an accountable human principal, within a bounded, auditable, expiring grant of authority, adopted incrementally rather than as a big upfront program.

practical · mixed — An interview (InfoQ Podcast host Olimpiu Pop with Sahil Agarwal, a Dropbox engineering leader building AI-agent identity/authorization systems) that argues for adopting a specific framework (DPACT) and a specific incremental adoption path — practical throughout, delivered conversationally with anecdote-driven evidence rather than formal argument.

Key terms

  • DPACT
    Agarwal's five-pillar framework — Delegation, Policy, Auditability, Context, Time — specifying the minimum categories of guardrail an agentic system needs: on whose behalf the agent acts, what it can/cannot do, a retrospective explainable record of its actions, the operational boundary it must stay within, and an explicit, enforced expiry of its authority.
  • Delegated (autonomous) actor
    Agarwal's term for what an AI agent now is, as opposed to a passive Q&A chat interface: a first-class entity that acts, chains tool calls, and makes decisions with real-world effect, ideally always 'on behalf of' a human principal.
  • Acting 'on behalf of' vs. 'impersonating'
    The load-bearing distinction of the whole framework: an agent should represent a human's intent and be traceable back to them, but must never assume the human's own identity/credentials to act indistinguishably as that human.
  • Bounded task grant Delegated Authority Grants (Bounded Task Grants)
    The target access primitive: a narrow, time-boxed, task-scoped authorization (bundling delegation + policy + context + time) that replaces a durable API key or long-lived token as 'the next platform perimeter.'
  • Overprivileged / over-restricted agent
    The two failure modes Agarwal frames DPACT as navigating between: an agent with unchecked broad access ('can do anything you ask it to do,' dangerous) versus one so gated by permission requests that it becomes 'worthless.'
  • Continuous authorization
    Re-evaluating an agent's grant at each step against policy, rather than authorizing once at session start — if scope increases or the agent enters a 'dangerous directory,' downgrade or revoke access.

  • explicitThe industry's access-model trajectory should move from 'give the agent a key' (a durable credential) to 'issue the agent a bounded task grant' (delegation + policy + context + time bundled into one scoped, expiring authorization), positioned as the next platform perimeter replacing long-lived API keys.conf: high

Arguments

Agents must be issued dedicated, bounded, time-limited delegated authority (DPACT-style) rather than durable, human-shaped credentials. strength: high
Explicit premises:
  • Agents now take real-world, consequential actions on sensitive data without a human validating each step, breaking the hierarchical, human-in-the-loop trust model traditional access control assumed.
  • Traditional token systems grant broad access for a session's full duration once issued.
  • A single incident of impersonation or a leaked long-lived credential creates open-ended blast radius and duration of exposure (as in the hiring-bot and food-ordering-bot incidents).
Implicit premises:
  • Bounded, expiring, task-scoped authority is technically and organizationally feasible to implement now, not merely an aspirational ideal.
  • The cost of over-restricting agents (permission-nagging, reduced usefulness) is acceptable relative to the cost of under-restricting them.
Inferences:
  • If bounded task grants become the default access primitive, most current agent architectures — which still pass human tokens or API keys directly to agents — are already operating with unacceptable risk and require re-architecture, not incremental patching.
Organizations should adopt agent governance incrementally (inventory-first), not as a big upfront program. strength: medium
Explicit premises:
  • The agentic-infrastructure industry as a whole is still immature ('we are not very mature... we are still learning').
  • A big-upfront governance program risks disrupting production work and outpacing team knowledge.
  • The first achievable maturity step today is knowing which agents exist and what authority they hold, not designing a perfect policy.
Implicit premises:
  • Visibility (inventory plus basic audit) is a precondition for effective policy design — you cannot write sound policy for an agent surface you cannot see.
  • Organizations will resist a governance program that blocks innovation, so the entry cost of adoption must be kept low.
Inferences:
  • Organizations that skip inventory and jump straight to building a policy engine are likely to produce incomplete or misapplied policy, since they do not yet know their full agent surface.

Narratives

  • A company's AI-driven hiring/interview chatbot had its token/agentic-info costs go haywire; investigation found applicants prompt-injecting the interview bot into writing Python scripts and other off-task content purely for fun, forcing the company to shut the feature down.
    → Concretely shows what happens when the Context and Policy pillars are absent: an agent's task boundary existing only as an unenforced intention ('supposedly its only task is to do interview style vetting') rather than an enforced constraint.
  • A food-ordering chatbot was similarly prompt-injected by end users asking it to tell jokes or write Python scripts, purely as token-maxing entertainment at company expense.
    → A second, independent example reinforcing that the failure pattern is systemic across agentic consumer interfaces, not a one-off — end users will probe and misuse an agent however they can if the agent lacks an enforced 'what it absolutely cannot do' boundary.
  • The closing analogy: hiring a babysitter or nanny for one's kids comes with a fixed time window, a spending cap (e.g. $10 for food), a bedtime, and explicitly withheld access to bank accounts, Social Security numbers, credit cards, and house keys.
    → Makes DPACT's five pillars intuitively legible by mapping each onto an everyday delegation practice, and argues the framework formalizes existing human intuition about bounded trust rather than inventing new principles for machines.
  • Agarwal references 'the first rendition of OpenClaw' as 'an amazing case study' for why agents must act on behalf of, rather than as, a user — without giving the specifics of what happened.
    → Cited as the seminal real-world case for the on-behalf-of/impersonation distinction, but left unexplained in this text — a narrative referenced rather than told, which is itself a gap (see below).

Questions addressed

  • ✅ How does an agent's required identity/authorization model differ from a human's, and why can't the human model simply be reused?
    The pre-agent model assumed a human always in the loop with known intent; agents break that assumption by acting, chaining tools, and deciding autonomously, so a distinct model (DPACT) is needed.
  • ✅ How should agents be granted access in practice — where is the boundary between over-privileged and over-restricted?
    Via DPACT's five pillars plus autonomy tiers keyed to an action's reversibility and blast radius (illustrated with the customer-service refund example).
  • ✅ How can an organization adopt agent governance without halting production work or requiring a big upfront program?
    The five-step incremental path: inventory, visibility, identity separation, review of high-impact actions, continuous authorization.
  • ⭕ Who authenticates the agent itself when it requests a scoped or on-behalf-of grant, and what secures the token-issuing/authorization service that hands out those bounded grants?
  • ⭕ How does DPACT compose across multi-agent chains — when an agent delegates to, or calls tools via, another agent — does the on-behalf-of grant and bounded time window propagate, narrow, or need re-derivation at each hop?

Gaps

  • incompleteDPACT is explicitly presented as a 'positional blueprint' with no reference architecture or worked technical spec for how each pillar (especially Time and Auditability) is actually enforced in a real stack — unlike, e.g., AWS Loom's concrete RFC 8693 token-exchange mechanism for preserving a delegation chain, or MCP's Enterprise-Managed Authorisation ID-JAG flow. The framework names the categories of guardrail needed but not the mechanisms.
    Read next: extract-aws-loom-ai-agent-governance (RFC 8693 delegation-chain token exchange) and extract-mcp-centralised-auth-enterprise (ID-JAG flow) for concrete technical primitives that could implement DPACT's pillars.
  • incompleteThe interview does not address multi-agent delegation chains — what happens to the 'on behalf of' principle and bounded task grants when an agent delegates to, or invokes tools through, another agent, rather than acting directly for a human. Agarwal notes agents 'can chain and call other tools' but never returns to how DPACT composes across those hops.
    Read next: extract-privilege-drift-multi-agent-systems, which documents exactly how permissions compound and drift across a multi-agent platform's shared resources and hops.
  • illogicalAgarwal insists an agent must never be identified via a human's own credential ('you cannot just be passing the same human tokens to an agent'), yet the corpus documents a shipped production system, Cloudflare WriteGuard, that deliberately identifies the agent via the human's existing OAuth credentials rather than a standalone agent identity, arguing contextual tagging (client, session) is sufficient for accountability. The interview neither engages with nor acknowledges this competing, already-deployed design choice.
    Read next: extract-cloudflare-writeguard-mcp-servers, which argues the opposite position with a shipped implementation.
  • uninformedDPACT is not benchmarked or validated against measurable outcomes. Agarwal cites two vivid but small anecdotes (a hiring bot, a food-ordering bot) and a self-applied, informal 'scoring rubric' against unnamed 'famous GitHub repos,' but offers no data on incident rates, breach frequency, or cost with versus without DPACT-style controls.
    Read next: extract-token-handling-ai-agents, whose cited empirical stats (88% of basic web-app attacks involve stolen credentials; one in three AI adopters already breached) would be a natural quantitative complement to DPACT's qualitative case.
  • incompleteThe interview never explains who authenticates the agent's own request for a scoped or on-behalf-of grant, or what secures the token-issuing/authorization service itself — the same structural gap already flagged repeatedly elsewhere in this corpus (companion pieces on agent token handling and on privilege drift in multi-agent systems) as agent identity being treated as solved rather than examined. DPACT restates the goal (a first-class on-behalf-of grant) without addressing the bootstrapping problem of how the agent proves it is the agent in the first place.
    Read next: extract-token-handling-ai-agents and extract-privilege-drift-multi-agent-systems, both of which raise this identical unresolved problem — read together to see the gap is now recurring across at least three independent sources in the corpus rather than a one-off omission.
