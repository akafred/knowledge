Remote pair programming: Tips, tools, and how to measure

Anna Monus · article · 2020-04-09 source ↗ Reader 🖥️

Pair & Mob Programming
Remote pair programming is a legitimate, synchronous variant of pair programming (two developers working the same codebase at the same time) whose main practical obstacle is tooling — picking the right real-time collaboration technology to emulate side-by-side presence — and whose value can be made visible to a business by correlating it with falling bug/error metrics.

practical · expository — A short vendor-blog explainer/tool-roundup (pre-AI, 2020) defining remote pair programming, suggesting metrics to justify it, taxonomizing three technical approaches, and listing then-current tools for each. Thin on argument — mostly definition plus a buyer's-guide tool survey; treated accordingly as a short extraction.

Key terms

  • Remote pair programming
    Two programmers working concurrently on the same codebase at the same time, but from separate physical locations via real-time collaboration tooling — the author insists it is defined by synchronicity, not merely by working on shared code.
  • Driver / Navigator Pair & Mob Programming
    The traditional pair-programming role split (one person writes code, the other reviews line by line) that screen-sharing tools are described as emulating.

  • explicitPair programming improves code quality and reduces bugs because two programmers approach the same problem from different angles and skill sets, giving each other continuous real-time review.conf: high

Arguments

Teams should adopt remote pair programming and treat its value as measurable, not just felt. strength: low
Explicit premises:
  • Pair programming produces higher-quality code and fewer bugs through continuous mutual review.
  • Error counts and performance are an established proxy for software quality.
  • If pairing effort correlates with falling error counts, that correlation gives the practice a defensible, quantified business value.
Implicit premises:
  • Fewer production errors (caught via crash-reporting/APM tooling, which the piece recommends — from a vendor that sells exactly that tooling) is treated as sufficient evidence of pairing's value, without addressing confounds such as task difficulty, team experience, or concurrent process changes.

Questions addressed

  • ✅ What technical options exist for making pair programming work when programmers aren't in the same room?
    Three approaches — terminal sharing, screen sharing, collaborative code editing — each with example tools, are presented as a complete taxonomy of 2020-era options.
  • ⭕ How can an organization justify the cost of pair programming in businesslike, quantified terms?
    The article suggests tracking error counts, development time, time-to-resolution, and satisfaction as candidate metrics, but does not show an actual before/after measurement or address how to isolate pairing's effect from other variables.

Gaps

  • incompleteThe entire piece treats remote pair programming as solved by choosing the right tool; it never engages the discipline/process side that later corpus material argues is actually decisive — driver/navigator rotation, communicating high-level intent rather than dictating keystrokes, pairing as the team's sensible default versus an occasional practice, and how pairing interacts with trunk-based delivery. A reader following only this article would conclude the hard part is tool selection, when the harder part (per later material) is organizational commitment and the norms around how pairs actually work together.
    Read next: Later corpus material on pair programming as process (not tooling) — the case for pairing as the default over async PR review, and the specific discipline of communicating intent rather than low-level steps — fills exactly this gap.
  • uninformedBy 2026 nearly every named tool in the 'live share' and 'cloud IDE' sections is defunct or marginal (Teletype for Atom was deprecated after Atom's 2022 sunset; Cloud9 was deprecated by AWS; Codenvy's Eclipse Che lineage never became mainstream), while the practice the article barely gestures at in passing — a third collaborator in the pair being an AI model rather than a second human — is, in the corpus's 2024-2026 material, the dominant form remote-adjacent pairing now takes. The article's entire tool taxonomy has been overtaken by a different axis of change (who/what the second 'pair' is) that didn't exist as a live option in 2020.
    Read next: Later corpus material on pairing with an AI agent as the second party (the pocket-sized 'developer + domain expert + agent' triad, and the 'pair programming with genies' framing) addresses what actually displaced the tool landscape this article surveys.
