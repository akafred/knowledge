Key terms

  • Routine
    A Claude Code automation defined only by a prompt, connected repos, connectors and a trigger; each run is a remote Claude Code session on Anthropic-managed infrastructure that Claude Code launches without a human typing a prompt.
  • Proactive agent
    An agent that is initiated by events or time rather than by a human pressing enter, and that reacts to problems (and opens a PR itself) instead of waiting to be asked.
  • Trigger (schedule-based vs event-based)
    What starts a routine: a time cadence, a native GitHub event (issue opened, PR labeled and merged, release cut), or your own HTTP POST to a webhook whose payload becomes context.
  • Context (as ceiling)
    Everything a routine can access - repos and connectors such as Slack, Google Drive, monitoring tools; 'whatever context Claude has, that's the ceiling of how successful Claude will be.'
  • Steerability
    The ability to guide a running or finished routine session and keep it 'honest': watch it live from web/CLI/desktop, ask questions mid-run, redirect or stop it, resume it later, use a second agent to review, and verify the output.
  • Agent-on-agent review
    A generator-critic arrangement implemented as two routines: one creates the docs PR, another triggers on PR creation and comments on it before a human sees it.
  • Connector
    A tool/data integration (GitHub, Slack, Google Drive, Datadog/Grafana, email/Twilio) attached to a routine so Claude can read context and take outward actions such as pinging you.
  • Deploy verifier
    A hypothetical routine triggered by a CD-pipeline webhook after each deploy that checks service health against monitoring data and issues a go/no-go on rollback, with autonomy graduated as trust grows.

Arguments

Routines make Claude Code a proactive teammate instead of a tool that waits for a prompt. strength: medium
Explicit premises:
  • Proactive agents today require you to build hosting, triggering and observability infrastructure yourself.
  • Routines supply managed infrastructure, schedule/GitHub/webhook triggers, and sessions that can be watched, steered and resumed.
  • A teammate notices problems and acts; a tool waits for enter.
Implicit premises:
  • Infrastructure burden, not model capability, is what stops teams from running proactive agents.
  • Being event-initiated is the defining difference between a teammate and a tool.
  • Steerable sessions are enough oversight for unattended agents with write access and outward connectors.
  • Running work on Anthropic-managed infrastructure with repo and Slack/Drive access is acceptable on data and trust grounds.
Inferences:
  • Any recurring developer chore with a detectable trigger becomes a candidate for delegation, which raises the volume of agent-authored PRs and review load.
  • Teams currently running Claude Code from cron or CI can migrate to routines, trading control for convenience.
How well a routine works is determined by three design decisions: trigger, context and steerability. strength: medium
Explicit premises:
  • Context is the ceiling on success.
  • Agent-on-agent review (generator-critic) can check output before a human does.
  • Live viewing, mid-session questions and resume let a human correct course.
  • Verifying the output (e.g. rendering the docs page) confirms it is right.
Implicit premises:
  • Failures of unattended agents are mainly setup and design failures that the author of the routine can fix, not model unreliability.
  • The output of the targeted tasks is cheap and reliable to verify.
  • More context is better, with no accounting for risk from broader connector access.
Inferences:
  • Connectors determine blast radius as well as the success ceiling, so the context decision is also a security decision.
  • Where output is hard to verify (design, judgment-heavy work), the framework offers little.
A deploy-verifier routine should start advisory and graduate to autonomous rollback as trust is earned. strength: medium
Explicit premises:
  • A CD pipeline can post a webhook after each deploy to trigger a session.
  • Claude with source code and monitoring tools can investigate service health and produce a go/no-go.
  • The human can read the analysis in the web session and continue working with Claude.
Implicit premises:
  • Monitoring data is a sufficient and trustworthy ground truth for a rollback decision.
  • The human can detect, by watching, whether the agent's judgment is actually good enough to hand over rollback authority.
  • Trust accumulates from observed correct decisions, without requiring any formal evaluation.
Inferences:
  • Staged autonomy needs a record of the agent's past decisions and outcomes to calibrate trust against, which the talk does not provide.
  • Rare-but-severe incidents will be underrepresented in the observed history that grants autonomy.
Documentation maintenance is a good fit for routines. strength: medium
Explicit premises:
  • Weekly Claude Code PRs are up 200% since the new year.
  • One engineer maintains the docs for Claude Code and the Agent SDK.
  • Routines on a weekly schedule and on GitHub issue-open diff source against docs and open PRs, pinging Slack.
Implicit premises:
  • Doc updates are low-risk, reviewable and reversible (a PR), so they tolerate autonomy.
  • Reviewing agent-opened docs PRs costs the engineer far less than writing the updates.
  • Claude can reliably judge from code diffs and issues which docs are out of date.
Inferences:
  • The automation converts a writing bottleneck into a review bottleneck unless the PRs are reliably good.
  • The pattern generalizes to other drift problems (config, changelogs, runbooks).

Narratives

  • Audience poll: who has run Claude Code on cron? Hands up. Who enjoyed building and maintaining that infra? One person.
    → Frames the infra burden as a shared, felt pain that routines remove (supports the proposition that infra, not capability, is the barrier).
  • A single documentation engineer ('our documentation queen') drowning as weekly Claude Code PRs rise 200%; she becomes an early adopter and sets up routines to keep docs current.
    → Shows speed-up in code production creating downstream maintenance bottlenecks that routines address; supports the docs-automation case.
  • Live demo: /schedule with a one-line weekly prompt; Claude asks clarifying questions (time, notification) and generates the routine and its instructions; the run on Monday at 10:00 reads the source repo, change log and docs repo and opens a PR.
    → Demonstrates that a routine can be created conversationally and that Claude writes its own operating instructions; supports the routine-definition and schedule-trigger claims.
  • Live demo: an issue-opened GitHub trigger starts a session with the issue passed in as context; the presenter knows a PR for it already exists and tells Claude to stop mid-run.
    → Shows event payload as context and real-time steering after kickoff; incidentally exposes that the routine had no awareness of in-flight human work.
  • Hypothetical: a deploy verifier triggered by the CD pipeline webhook that checks monitoring tools, recommends go/no-go on rollback, and may eventually roll back on its own as trust grows.
    → Illustrates the trigger / context / steerability framework and graduated autonomy.
  • Hypotheticals: an on-call investigator, and a PM weekly job reading GitHub issues and Slack posts to prioritize and open PRs.
    → Generalizes the pattern beyond docs to triage-style roles.

Questions addressed

  • ✅ How can a team run Claude Code proactively and unattended without building its own hosting, triggering and observability stack?
    Routines: managed infrastructure, schedule / GitHub / webhook triggers, and sessions that are normal Claude Code sessions.
  • ✅ How can humans keep oversight of agents that are meant to run with a human out of the loop?
    Watch, ask, steer, stop and resume the live session; add agent-on-agent review and output verification; graduate autonomy as trust builds.
  • ⭕ Which tasks are suitable for a routine, and how should one decide?
    Only a prompt to the audience to think of daily tasks, plus the trigger / context / steerability checklist; no selection criteria for what should not be delegated.
  • ⭕ What are the security, cost and failure-handling consequences of event-triggered agents with write access and outward connectors?
    Not addressed.

Gaps

  • incompleteNo security or permission model for unattended routines. The issue-opened trigger feeds untrusted external text (a GitHub issue) into a session that holds repo write access, Slack and other connectors, which is the lethal-trifecta shape; the talk advises giving as much context and as many connectors as the task wants ('context is the ceiling') without discussing prompt injection, scoped credentials, or what limits the blast radius of an event-triggered run.
    Read next: extract-claude-code-dynamic-workflows-harness-every-task (quarantine pattern for triage workflows) and the corpus's lethal-trifecta / delegated-authority-grants material for what a hardened routine needs.
  • incompleteNo cost, rate-limit or runaway-trigger discussion. A routine triggered on every issue, release or deploy runs a full agent session each time, but the talk gives no guidance on per-run cost, usage limits, deduplication of bursts, or guards against loops (e.g. an agent-opened PR triggering another routine).
    Read next: Corpus material on agent cost prediction and usage-limit rationing; operational limits documentation for routines.
  • incompleteNo evidence of effectiveness. The docs case reports the 200% PR growth and shows a working demo, but no acceptance rate of agent-opened docs PRs, false-positive noise, time saved, or the review load the routines put on the one documentation engineer; it quietly turns a writing bottleneck into a review bottleneck, and agent-on-agent review defers rather than answers that.
    Read next: Read against extract-osmani-orchestration-tax-is-you and the corpus's verification-capacity and measuring-AI-impact material; look for independent data on agent-authored maintenance PRs.
  • incompleteRoutines appear to be stateless across runs and unaware of in-flight human work. In the live demo the presenter has to stop the run because a PR for that issue already existed; the talk does not say how a routine deduplicates against open PRs, remembers prior runs, or recovers from partial failures.
    Read next: Corpus material on agent memory and durable execution (checkpoint-and-resume, idempotency) for what a repeatedly-triggered agent needs to be safe to rerun.
  • incompleteThe 'build your own cron and infra' comparison is a strawman: no comparison with existing alternatives such as headless claude -p in CI, GitHub Actions, or other vendors' scheduled agents, and no discussion of lock-in, data residency or what is lost by running on vendor-managed infrastructure.
