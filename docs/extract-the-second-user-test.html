The Second-User Test

Kaiyao Duan · rss · 2026-10-20 source ↗ Reader 🖥️

Capacity to Verify AI OutputCognitive DebtEvidence of Understanding (Polish ≠ Comprehension)Intent DebtMental Models & UnderstandingVerifiability (as the Quality Bar)
In an era when generative AI makes polished first versions cheap, a project's real understanding is revealed not by a successful first run but by whether a second person can rerun, question and modify it using only what the work itself makes visible - so creators should build 'handles' (explicit assumptions, recorded sources, replaceable components) that let others enter the work without a private briefing.

practical · mixed — A teacher's practitioner essay: one extended case (a student labor-economics paper) is used to motivate an assessment practice (hand the finished project to a second student) and a design vocabulary ('handles'), then generalized to AI artifacts outside school. Argues for what educators (and AI builders) should do, on the strength of one case plus an appeal to Tim O'Reilly's 'architecture of participation'.

Key terms

  • Second-user test (handoff) Evidence of Understanding (Polish ≠ Comprehension)
    Giving a finished-looking project to another student with responsibility to use, check or modify it, and observing whether the work still makes sense without its creator translating it. Used as an assessment of the creator's understanding, not merely of the artifact's packaging.
  • Handles
    Visible points of entry in a work that give another person something concrete to inspect or change without a private briefing: a named parameter, an explicit assumption, a test recording an earlier failure, a replaceable component, a retained intermediate dataset, a prompt whose context is written down rather than buried in a private chat.
  • Verification responsibility
    The economic and occupational role of a person who must check AI-produced candidate outputs, decide whether they are safe to use, and remain accountable for accepting them (topic of the student paper that serves as the case study).
  • Private context
    Everything that makes a work function but lives outside the artifact: the creator's memory of variable meanings and decisions, tool access, file structure, model behavior, private chat history, naming conventions, undocumented small decisions.
  • Architecture of participation
    Tim O'Reilly's idea, reused here: a technical artifact is more useful when others can enter it without negotiating privately with its creator (interfaces, conventions, documentation, modularity, replaceable components; in data analysis, recorded source versions and visible transformations).

Arguments

A successful first run is weak evidence of understanding; a successful second-user handoff is strong evidence. strength: medium
Explicit premises:
  • Generative AI lowers the cost of producing a convincing first version.
  • A first run only shows that one person-model-tools-data-context combination worked once.
  • A second user has only what the project makes visible.
Implicit premises:
  • Understanding of a work is demonstrated by the ability to reconstruct and change it from its visible parts.
  • The second user's failures are attributable to missing handles, not to the second user's lack of skill.
  • The creator cannot fake or outsource the work of making the project legible to others (or if AI helps, the result still passes the same test).
Inferences:
  • The same test can be applied by AI agents as 'second users' (cold-start agents are always second users), turning the handoff into an automatable check on externalized context.
  • AI could also be used to produce the handles themselves, which would weaken the test's link to the creator's understanding unless the creator must still defend them.
Handoff verification revealed a substantive design flaw, not just a packaging problem. strength: medium
Explicit premises:
  • The second student had to rerun analyses, record data versions, document dataset linkage and compare reported tables with outputs.
  • Doing this exposed shared survey items between verification responsibility and adaptive capacity.
  • The code was correct; the construct definitions were not clean.
Implicit premises:
  • The flaw would not have been caught by the original author because their familiarity masks it.
  • Forcing explicit documentation of data linkages is what surfaced the overlap in measure inputs.
Inferences:
  • Writing down a workflow is an indirect audit of the study's construct validity: documentation burden is itself a validity check.
  • The more tacit the pipeline, the more likely overlooked double-counting remains.
Copyable AI artifacts (prompts, skills, agent configs) are less portable than they look. strength: medium
Explicit premises:
  • Working conditions - tool access, file structure, model behavior, private memory, naming conventions - live outside the artifact.
  • Moving an artifact to a new context reveals what was never inside it.
Implicit premises:
  • Portability is a property of the artifact-plus-environment, not of the text alone.
  • Most creators underestimate how much the environment contributes because they never had to specify it.
Inferences:
  • Sharing a skill or prompt library without its environment contract is a common source of silent non-reproducibility.
  • The 'handles' list for prompts (written-down context) can serve as an environment contract.

Narratives

  • A student paper on AI and labor economics (Verification Responsibility in AI-Applicable Occupations) is handed to a second student for rerun and audit; the audit exposes undocumented data transformations and dataset linkage rules, then overlapping survey items between two measures, leading to rebuilt measures, traceable workflows, alternative specifications and robustness checks.
    → Shows that a procedural handoff becomes substantive review, supporting the claim that a second user finds what the creator stopped noticing; also illustrates handles (recorded versions, retained intermediates) being created under pressure.
  • Per-project variants of the handoff at Force Academy: change a parameter or replace a rule in a computational model; move an AI-supported workflow to a different model or environment; reconstruct one result from recorded sources.
    → Shows the test is adaptable and always probes for what should remain stable under change, grounding 'handles' in concrete project types.
  • Professional developers learn most after software leaves their hands (delivery, support, maintenance, unexpected use).
    → Analogy justifying why a handoff is a pedagogical import from production practice.

Questions addressed

  • ✅ When polished output is cheap, how can a teacher tell what a student actually understands?
    Give the project to a second student and observe whether they can reconstruct, question and modify it using only what the artifact makes visible.
  • ✅ How do you design work so that others can enter it (and so it survives its creator)?
    Build 'handles': explicit assumptions, named parameters, recorded source versions, retained intermediates, replaceable components, written-down prompt context.
  • ⭕ Does the handoff method scale and generalize beyond a research academy with small cohorts and self-directed projects?
    Not addressed; practice is described only at Force Academy with one detailed case.
  • ⭕ Can AI itself generate the handles (documentation, assumption lists), and if so what then does a successful handoff certify?
    Not addressed, although the essay's premise is that AI makes polish cheap.

Gaps

  • incompleteEvidence is a single hand-picked case narrated by the teacher who designed the practice; no comparison with other assessment methods, no data on how often handoffs surface real problems versus trivial ones, and no check of whether the flaw would have been caught without a second user.
    Read next: Look for controlled or at least multi-case studies of peer replication / code review as a learning or assessment mechanism (computational reproducibility audits, pair-programming assessment, the replication-crisis literature); compare with the uncontrolled classroom evidence in Freeman's studio approach.
  • incompleteThe essay never confronts that AI can also write the handles: a README, assumption list, test suite or prompt-context file can be generated as fluently as the first version, so a legible-looking artifact may again substitute for understanding. The test only works if the second user's probing questions cannot be answered by the same AI.
    Read next: Read on generated-documentation and generated-test quality (Osmani on tests satisfied literally rather than in intent; work on 'documentation drift'), and on adversarial/oral assessment designs where the creator must defend choices live.
  • incompleteEquating understanding with transferability omits cases where tacit expertise is real but hard to externalize, and it treats handles as costless; no accounting of the effort handles add or of when the test is disproportionate (throwaway work, exploratory prototypes).
    Read next: Tacit knowledge literature (Polanyi, Nonaka); cost/benefit of documentation in agile settings; Storey on when cognitive debt is repairable.
  • incompleteThe generalization to AI artifacts (prompts, skills, agent configs are less portable than they look) is asserted by analogy with no example or measurement from an actual agent-configuration migration, and no concrete 'handles' checklist for them beyond written-down prompt context.
    Read next: Case studies of migrating agent configurations across models/harnesses (model switching, vendor lock-in), evals that measure portability of skills and prompts.
