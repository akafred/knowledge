Microsoft Three-Layer LLM Routing Architecture for AI Agents on AKS

Claudio Masolo · rss · 2026-07-29 Reader 🖥️

AI Unit EconomicsCapability Provisioning (right-sizing to the task)Compute & Energy InfrastructureInference OptimizationModel Routing
Because agentic workloads generate large volumes of small, heterogeneous-difficulty LLM calls that a single router or load balancer cannot handle well, production routing on Kubernetes should be decomposed into three independent, composable layers — semantic model selection (RouteLLM), request governance (agentgateway), and live GPU-state-aware placement (the Gateway API Inference Extension's Endpoint Picker) — each solving exactly one of the three distinct signals (which model, how the call is managed, which replica) rather than one component trying to do all three.

practical · expository — A reporting/summary piece (InfoQ news format) describing Microsoft's reference architecture. It is practical because the whole point is prescriptive — how teams should structure production routing infrastructure — but the text itself is expository (describing an existing design) rather than argumentative in its own voice; the argumentative content (why decompose into three layers) is inherited from the source blog post being summarized.

Key terms

  • the three-choice decomposition (which model / how the call is managed / which GPU replica)
    The organizing frame of the whole architecture: routing for agents is not one problem but three orthogonal ones — semantic model selection, request policy/governance, and physical placement onto a GPU replica — each requiring a different signal and a different component to solve well
  • escalation threshold
    The calibration knob in RouteLLM that determines what share of calls get promoted from the weak/cheap model to the strong/expensive one; explicitly not a portable constant — it must be re-tuned per model pair and per team's real traffic mix
  • Endpoint Picker
    The component of the Kubernetes Gateway API Inference Extension that chooses which specific GPU replica of an already-selected model should serve a request, based on live signals (vLLM's KV-cache occupancy and queue depth) rather than static load-balancing rules

Arguments

Production agent routing on Kubernetes should be built as three independently composable layers rather than as one monolithic router or load balancer. strength: medium
Explicit premises:
  • Agentic loops generate very high call volume with wide variance in per-call complexity.
  • A single load balancer or router cannot simultaneously reason about semantic difficulty, request governance/policy, and live GPU state.
  • Purpose-built open-source components already exist for each concern: RouteLLM (semantic), agentgateway (policy/proxy), Gateway API Inference Extension (GPU-aware placement).
Implicit premises:
  • These three concerns are separable enough in practice that solving them independently does not lose performance to cross-layer interaction effects.
  • The composition of three different OSS/managed pieces behind one OpenAI-compatible endpoint will remain operationally coherent despite each piece evolving on its own release cadence.
Inferences:
  • Teams can adopt a subset of the stack and still benefit — the architecture is a menu of independently useful layers, not an all-or-nothing prescription.
  • Because GPU-aware placement has no managed equivalent, it becomes the one layer every self-hosting team must own regardless of which vendors they use elsewhere — a durable operational responsibility, not a commodity.

Narratives

  • A round-robin load balancer queues a 200-token completion behind a 100k-token prefill on a busy GPU pod while another pod sits idle nearby.
    → Illustrates concretely why naive load balancing fails agentic traffic and motivates the need for a GPU-state-aware placement layer (the Endpoint Picker)
  • The author's own block-quoted warning that several pieces are young, field names drift, and the whole setup was validated end-to-end only against specific pinned versions (Inference Extension v1.0.0, agentgateway v1.3.1) in mid-2026.
    → Functions as a narrative caveat about lived operational experience with pre-v1 infrastructure — signals that the decomposition is stable even though the implementation details are not

Questions addressed

  • ✅ How should LLM calls be routed for agentic (as opposed to chat) workloads running on Kubernetes?
    By decomposing routing into three independent layers — semantic model selection, request governance, and GPU-aware placement — rather than solving it with one component.
  • ⭕ Does routing to a cheaper model actually preserve output quality?
    Only demonstrated for the specific model pair RouteLLM was benchmarked on (95% of GPT-4's MT-Bench quality at ~26% escalation); the author explicitly states this does not generalize and must be recalibrated per deployment.
  • ✅ Is there a managed (non-self-hosted) option for every layer of the architecture?
    No — the semantic-routing layer has a managed equivalent (Azure Foundry model router), but the GPU-aware placement layer (Endpoint Picker) must always run in-cluster.
  • ⭕ What is the operational cost of building production infrastructure on pre-v1, actively-changing Kubernetes CRDs (Inference Extension, agentgateway)?

Gaps

The piece states plainly that the figure doesn't transfer to other pairs, but gives no methodology or tooling for how a team should actually validate or calibrate the threshold against its own traffic — the 'how do you calibrate this' step is asserted as necessary but never shown.
    Read next: Practical guides or tooling for online calibration of routing thresholds against live traffic and quality signals (e.g. shadow-routing, canary evaluation, human-preference feedback loops) — this is the same unresolved 'how do you actually verify good-enough' gap flagged in the Pragmatic Engineer smart-routing piece, now recurring in a concrete production architecture.
  • incompleteNo cost or performance numbers are given for the assembled three-layer system itself — Endpoint Picker's own latency/overhead, agentgateway's proxy tax, or the inference cost of running RouteLLM's classifier. Every efficiency figure quoted (95%/26%/85%) belongs to a sub-component in isolation, not the end-to-end stack a team would actually operate.
    Read next: Independent, end-to-end benchmarks of assembled LLM-routing stacks (not individual components) — comparable to the missing quantitative data flagged in the Netflix Triton+vLLM serving-platform piece.
  • incompleteThe article flags that the Inference Extension and agentgateway are 'young' and that CRD fields are still moving pre-v1, but never discusses the operational cost of tracking that churn in production — upgrade cadence, breaking-change history, or how a team without Microsoft's own platform expertise should pin and test across releases.
    Read next: Version-pinning and upgrade-management practices for pre-1.0 Kubernetes CRDs / operators in production; postmortems or case studies of teams that adopted similarly young infra and hit breaking API churn.
  • incompleteThe architecture routes some calls to Azure OpenAI (managed, off-cluster) and others to self-hosted KAITO pods (in-cluster, open models) purely on a cost/quality basis — the piece never asks whether that split should also be constrained by data sensitivity or compliance, i.e. whether some agent traffic should be forced onto the self-hosted path regardless of RouteLLM's cost-driven verdict.
    Read next: Enterprise AI governance and data-residency-aware routing — pairs with the same governance blind spot already flagged in the Pragmatic Engineer smart-routing piece and in claude-code-router's README.
