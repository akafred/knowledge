API Gateway and AI Gateway: Do You Need Both?

Janet Wagner · rss · 2026-10-21 source ↗ Reader 🖥️

Agent Governance (Internal)Agent SecurityAgent-to-Agent ProtocolsAI Cost Visibility & FinOpsGateway Control Plane (API / AI / MCP Gateways)GuardrailsMCP (Model Context Protocol)Model RoutingPlatform Engineering
API gateways govern inbound client-to-service traffic with request-based semantics while AI gateways govern outbound application-to-LLM traffic with token-based semantics, so most organizations building LLM-driven applications need both today, even though vendors are converging them into a single layer.

practical · expository — A short explainer from an API-industry publication (Nordic APIs) that defines two infrastructure components, contrasts them, and argues for an architectural action (run both). Mostly expository, with one practitioner anecdote as the only evidence for the recommendation.

Key terms

  • API gateway
    A reverse proxy specialised for APIs that governs primarily inbound traffic from clients to backend APIs/microservices (routing, request-count rate limiting, load balancing, authN/Z, protocol conversion, monitoring).
  • AI gateway Gateway Control Plane (API / AI / MCP Gateways)
    Middleware and single control plane for outbound application-to-LLM interactions: prompts and responses, and for some products MCP tool calls and A2A traffic; capabilities include model routing, semantic caching, token rate limiting, prompt enrichment, input/output guardrails and LLM observability.
  • Semantic caching
    Returning a stored response for similar (not identical) prompts, in contrast to API-gateway exact-match caching on URL and headers.
  • Token rate limiting
    Throttling by LLM input and output token count rather than requests per second/minute, so a 50k-token prompt and a 200-token prompt are not counted as equal.
  • AI traffic
    Prompts to LLMs and their responses, extended for some gateways to MCP tool-call requests and agent-to-agent (A2A) communication.

Arguments

Most organizations building LLM-driven applications need both an API gateway and an AI gateway. strength: medium
Explicit premises:
  • API gateways handle inbound HTTP traffic with request-based rate limiting, exact caching and schema/WAF security.
  • AI gateways handle outbound LLM traffic with token-based limits, semantic caching and prompt/response guardrails.
  • The two operate on different traffic types and directions and are not currently interchangeable.
  • A team that ran LLM traffic through Kong could not attribute token spend or cap budgets.
Implicit premises:
  • Applications that call LLMs also still expose or consume ordinary APIs, so both traffic types coexist in one organization.
  • Cost and safety controls for LLM calls must be centralized, not left to each application.
  • A single anecdote from one team generalizes to 'most companies'.
  • 'Both' means two separate deployed components, not one product with two policy sets.
Inferences:
  • Budgeting and chargeback for AI should be implemented at the AI-gateway layer, since token-level data does not exist at the API gateway.
  • Once platforms converge, the architectural decision becomes which policy sets to enable, not which gateway to deploy.
The API-gateway/AI-gateway distinction may soon disappear. strength: low
Explicit premises:
  • More vendors are developing platforms that house the capabilities of both.
  • Boundaries are steadily blurring.
Implicit premises:
  • Vendor product bundling reflects what buyers will actually adopt.
  • Token-aware and semantic features can be added to API gateways without the problems seen in the DIY case.
Inferences:
  • The 'category error' in the Kaur anecdote becomes a product-maturity question rather than an architectural one when a vendor ships both in one box.
  • The 'need both' advice has a shelf life that the article does not date.

Narratives

  • TrueFoundry ran Kong for microservices and also pushed LLM traffic through it; they had no idea what each team spent on tokens, no budget cap that fired before the bill, and request-per-minute limits that treated 50k-token and 200-token prompts identically. They moved LLM traffic to the TrueFoundry AI Gateway and kept Kong for everything else.
    → Supports the claim that API gateways cannot substitute for AI gateways on LLM traffic and the 'need both' recommendation.

Questions addressed

  • ✅ What is the difference between an API gateway and an AI gateway?
    Direction (inbound vs. outbound), traffic semantics (requests vs. tokens/prompts) and the specific capabilities in the comparison table.
  • ✅ Do organizations need both?
    Yes for most companies today: API gateway above a few services, AI gateway with multiple LLMs.
  • ⭕ Is the separation durable, or will the two gateway types merge into one product category?
    Asserted that convergence is happening but deferred to a linked article; no timeline, evidence or implication for architecture.
  • ⭕ Which gateway governs agent-to-API and MCP tool-call traffic, which is neither classic client-inbound nor LLM-outbound?
    Hinted at (some AI gateways cover MCP and A2A) but never addressed directly.

Gaps

  • incompleteThe case for 'need both' rests on a single anecdote from an AI-gateway vendor (TrueFoundry), while the article's own vendor lists show Kong, Gravitee, KrakenD and Tyk selling both categories. It never tests the obvious counter-case: an API gateway with token-aware plugins (which these vendors ship) used for LLM traffic, so the anecdote only shows DIY-on-request-semantics failing, not that two separate components are required.

  • incompleteThe decision rule is thin: 'more than a few services' and 'multiple LLMs' are given as triggers with no numbers, and the article never addresses the cost of running two gateways (latency, duplicated auth and policy, ownership) or says when a single-LLM team can skip the AI gateway.

  • incompleteAgent-to-API and MCP/A2A traffic does not fit the inbound/outbound split on which the whole contrast is built. The article mentions it in the intro and in the AI gateway definition but never says which gateway should own tool-call authorization, rate limiting or audit when an agent calls an API.
    Read next: MCP-gateway and agent-identity material on where tool-call authorization lives relative to API gateways (e.g. Morgan Stanley's API-layer governance argument, MCP gateway/registry patterns).
  • uninformedSecurity treatment is a feature checklist (input filtering, response validation, DLP). It does not consider the gateway as a newly concentrated attack target or single point of failure, nor how guardrail false positives/negatives change the calculus.
