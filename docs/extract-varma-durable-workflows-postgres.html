Article: Implementing Durable Workflows on Postgres Without an External Orchestrator

Raman Varma · rss · 2026-09-14 Reader 🖥️

Cascading Failure & System Resilience PatternsDurable Execution & Workflow CheckpointingLong-Running & Managed AgentsSoftware Design FundamentalsSRE & Incident Response
Durable workflow execution is fundamentally a database-checkpointing problem, so a team that already operates a relational database like Postgres at scale can implement production-grade durable execution — concurrent dispatch, idempotency, crash recovery, durable waits, and observability — as a handful of well-understood SQL primitives, without deploying a separate stateful orchestrator such as Temporal or AWS Step Functions.

Key terms

  • durable execution Durable Execution & Workflow Checkpointing
    A program that checkpoints its progress to an external durable system as it runs, so that if the process dies, another process can reload the last checkpoint and continue from there — "autosave from a video game, but for backend code."
  • SKIP LOCKED Durable Execution & Workflow Checkpointing
    The `SELECT ... FOR UPDATE SKIP LOCKED` clause used as the sole concurrency primitive: it lets one worker claim a row while every other concurrent poller skips past already-locked rows instead of blocking, giving one-worker-per-row claim semantics with no broker, leader election, or external lock service.
  • idempotent checkpoint Durable Execution & Workflow Checkpointing
    A step's output written exactly once via a primary-key/unique constraint on `(execution_id, step_id)`; a rerun after a crash is detected by a failed insert (or a check-before-execute read) and returns the prior stored result instead of repeating the step's side effect.
  • lease
    A time-bound ownership claim on a workflow_execution row, recorded as `owner_id` + `lease_expires` and renewed by a periodic worker heartbeat; when a lease lapses without renewal, a sweeper reclaims the row.
  • sweeper
    A periodic query (not a separate service) that resets `running` executions whose lease has expired back to `enqueued`, and separately re-enqueues `waiting` executions whose `wake_at` has passed.
  • exactly-once processing guarantee
    Used to describe the property that SKIP LOCKED gives: no two workers ever claim the same row.

Arguments

A relational database a team already operates (Postgres) is a viable, and for a defined class of workloads a superior, alternative to a dedicated external orchestrator for durable workflow execution. strength: high
Explicit premises:
  • Durable execution is fundamentally a checkpointing problem, and checkpointing requires writing to a durable external system.
  • The team already operates Postgres as its system of record and has invested in making it perform at scale.
  • Postgres primitives (SKIP LOCKED, unique constraints, timestamp columns) can implement concurrent dispatch, idempotency, and crash recovery.
  • An external orchestrator adds a new stateful system with its own deployment/security/monitoring lifecycle, sits as a single point of failure in the critical path, needs its own access-control/audit surface, and uses a data model that resists ad-hoc relational analysis.
Implicit premises:
  • Removing a system from the architecture is a net win whenever an existing system can absorb its function — the cost of one system doing two jobs is treated as categorically lower than the cost of two systems each doing one job.
  • The workloads in scope are I/O-bound automation pipelines with modest concurrency, running seconds to hours — the argument does not implicitly generalize to all workflow use cases, though the article's opening bullets and headline read as a general recommendation before this scope limit appears near the end.
Inferences:
  • Binding workflow durability to the same database as the system of record raises the blast radius of a single Postgres outage or major-version upgrade — the article names this coupling but does not weigh it as a cost against the isolation a separate orchestrator would provide.
  • The 'reuse infrastructure you already operate well' argument generalizes beyond workflow orchestration to other typically-external stateful services (job scheduling, feature flags, rate limiting) that a team with a mature Postgres operation could evaluate the same way — the author does not extend the argument this far.
Aggressive, short lease durations are safe to use because checkpoints are idempotent. strength: medium
Explicit premises:
  • If a lease is too short, a slow-but-alive worker can have its execution reclaimed and rerun by another worker.
  • Idempotent checkpoints, enforced via a unique constraint, guarantee that a rerun step returns the prior stored result instead of repeating a side effect.
Implicit premises:
  • The step's side effect and its checkpoint write are treated as if they were effectively one atomic unit — but the article's own mechanism (worker performs the side effect, then inserts into operation_outputs) leaves a window where a crash between the side effect and the checkpoint commit still produces a duplicate side effect on retry, which the unique constraint cannot prevent because nothing was written yet to conflict against.
Inferences:
  • The claim 'the database, rather than the application code, enforces idempotency' is only fully true for the checkpoint record itself; for steps whose side effect is not atomic with the checkpoint write, correctness still depends on application-level design (e.g., making the external call itself idempotent via a passed idempotency key), which the article does not flag as a residual responsibility.

Questions addressed

  • ✅ How do you make workflow execution survive process death (crashes, node drains, pod evictions, reschedules) without losing progress?
    Checkpoint state to Postgres after each step, plus a lease-and-sweeper pattern that detects and re-enqueues executions whose owning worker went silent.
  • ✅ How do you get exactly-once dispatch of queued work across multiple concurrent workers without a message broker or leader election?
    SELECT ... FOR UPDATE SKIP LOCKED inside a tiny claim transaction.
  • ✅ How do you make a workflow step idempotent so retries don't repeat its side effect?
    A unique constraint on (execution_id, step_id) in a checkpoint table, checked before a step executes — though see gap g2: this does not fully close the case where the side effect itself is not atomic with the checkpoint write.
  • ✅ At what scale, latency, or fan-out does the Postgres-backed approach stop being the right choice?
    When you need fan-out across thousands of workers with sub-millisecond dispatch latency, an external engine like Temporal is named as the better choice — but this is asserted briefly, near the very end, without quantifying the actual threshold.
  • ✅ How do you keep the queue table itself from degrading under sustained high-churn UPDATE/DELETE load?
    Autovacuum tuning, partial indexes on the hot row set, and partitioning completed executions away from the live queue.
  • ⭕ What happens to in-flight leases, waits, and transaction visibility during planned Postgres maintenance (major-version upgrades, planned failovers), as distinct from unplanned crash recovery?

Gaps

  • illogicalThe article states that SKIP LOCKED gives "exactly-once processing guarantees," but the mechanism it actually describes only guarantees exactly-once *claim* — a row is assigned to exactly one worker at a time. Exactly-once *effect* (the property practitioners usually mean by that phrase) depends on the separate idempotent-checkpoint mechanism introduced two sections later. Stating the stronger claim in the SKIP LOCKED section conflates dispatch-level and effect-level guarantees.
    Read next: Kleppmann's 'Designing Data-Intensive Applications' on effectively-once/exactly-once semantics, or Temporal's own documentation explaining why it separates at-least-once activity delivery from exactly-once effects via idempotency keys — the same distinction this article's own idempotency section implicitly relies on but doesn't name when making the SKIP LOCKED claim.
  • incompleteThe idempotency mechanism (unique constraint on operation_outputs, checked before executing a step) only guards against a duplicate *checkpoint write* — it does not, by itself, prevent a duplicate *external side effect* when a worker performs the side effect (e.g., an API call, a Slack message, a GitOps PR) and then crashes before the checkpoint insert commits. The article presents 'the database enforces idempotency' without discussing patterns other durable-execution systems use to close exactly this window (transactional outbox, idempotency keys passed to the external call itself, or a two-phase intent-then-commit record).
    Read next: Temporal's or AWS Step Functions' documented patterns for making side-effecting activities idempotent under at-least-once retry semantics — the same reading direction already flagged by extract-cloudflare-ci-pipelines-typescript-workflows#g3, which this article partially but not fully answers.
  • incompleteNo versioning strategy is described for evolving workflow or step logic while executions are in flight for long periods (e.g., a two-week human-approval wait). If the code for a step, or the shape of the JSONB input, changes between when an execution is enqueued and when it resumes, there is no discussed mechanism for detecting or handling that drift.
    Read next: Temporal's workflow-versioning / 'patched' API documentation, which exists specifically to solve this problem for long-running, resumable workflows.
  • incompleteThe two central scaling claims — 'tens of thousands of workflows per second on a single instance' and the 'sub-millisecond dispatch latency' threshold for preferring Temporal — are stated as bare figures with no benchmark methodology, hardware specification, step complexity, or measurement conditions, making the quantitative core of the scaling argument unverifiable by a reader trying to decide whether Kestrel's experience transfers to their own workload.
    Read next: A follow-up benchmark piece from the author or Kestrel's own engineering blog, if published, describing load-test methodology and hardware.
  • uninformedThe article credits MySQL 8.0+, MariaDB 10.6+, Oracle, Db2, and SQL Server with SKIP LOCKED-equivalent mechanisms in a single aside, implying the pattern ports cleanly across databases, but does not note that these engines differ meaningfully in isolation-level defaults and MVCC/locking implementation (e.g., MySQL's gap-locking behavior under REPEATABLE READ) — real portability risk for a reader who lifts the exact SQL onto a different database.
    Read next: Each database's own locking-read documentation, cross-compared for isolation-level defaults, before assuming this pattern is a drop-in replacement across engines.
