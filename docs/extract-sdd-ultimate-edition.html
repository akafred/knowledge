Software should actually work, and the way to get there with AI coding agents is to make the specification - ideally formal rather than just Markdown - the shared language between humans and agents (and between agents), written together with the agent and used by tools like Copilot to keep requirements consistent and decisions traceable.

Key terms

  • Specification is our shared language
    The spec is the common medium in which humans and AI agents (and agents among themselves) agree on what to build; it is not just documentation but the interface of the whole workflow.
  • SDD Ultimate Edition
    The speaker's name for her workshop variant of spec-driven development, apparently pushing beyond Markdown specs towards formal specification (TLA+, Lean) and verification; a demo repo and an 'open-lean-spec' repo are referenced.
  • Requirements integrity
    A named benefit of spec-following agents: requirements stay mutually consistent, contradictions are caught earlier, and decisions remain traceable back to requirements.

Arguments

Teams should write specifications as the primary shared artifact for AI-agent development, and consider formal specifications, because that makes agent output consistent and traceable. strength: low
Explicit premises:
  • Specification is a shared language for humans and agents
  • The spec also serves as the contract between agents
  • A spec-following Copilot gives requirements integrity, earlier contradiction detection and traceable decisions
  • A demo and a messy real project built with Copilot gave useful results
Implicit premises:
  • Contradictions and ambiguities in requirements are a major source of the bugs the talk opens with
  • A requirements spec co-written with an agent is trustworthy enough to serve as ground truth (the same agent that helps write it later checks against it)
  • Formal specification languages (TLA+, Lean) are usable by ordinary development teams at acceptable cost, and AI can bridge the skills gap
  • Results from a mortgage calculator and one research-simulation project generalize to other work
Inferences:
  • If the spec is the contract, review effort should shift towards reviewing and verifying the spec rather than only the code
  • Underspecified areas (like the frontend) are where agent output will be weakest, so spec coverage can be used as a predictor of quality

Narratives

  • Software development process 10 years ago vs now: now an AI answers 'What would you like to build today? I can do it in 5 minutes', and then, 'Sorry, I don't understand you.'
    → Dramatizes that fast AI generation without a shared language leads to misunderstanding, motivating specification as the shared language.
  • Mortgage-calculator demo built with Copilot following the spec and deployed to GitHub Pages, followed by a harder, non-standard case: a Sigma2 research simulation platform across two messy repos with tens of thousands of simulation files
    → Shows the approach working on an easy task and being stress-tested on a complex, real one, supporting 'balance complexity and usability' and the speed-quality-price-complexity tradeoff.
  • First version of the platform: backend good, frontend underspecified; Copilot tokens ran out and Claude was called in for help
    → Illustrates that quality tracks specification coverage and that cost/token limits are a practical constraint.

Questions addressed

  • ✅ How do we make AI-built software actually work given that agents are fast but bugs persist?
    Asserted resolution: write specifications (possibly formal) as the shared language and have the agent follow them.
  • ⭕ Is a Markdown specification enough?
    Raised and answered only by pointing to specs as code (TLA+, Lean) with a linked open-lean-spec repo; no visible argument for when Markdown suffices and when formal specs are needed.
  • ⭕ Does the approach hold up on non-trivial, messy, real-world work rather than toy tasks?
    Partially: useful results on a research simulation platform, but with an underspecified frontend, token exhaustion and an explicit speed-quality-price-complexity tradeoff left open.
  • ⭕ How is the requirements spec itself validated when it is co-written with the same agent that will implement against it?
    Not addressed in the captured text.

Gaps

The central 'ultimate edition' claim is therefore unsupported in the text.
