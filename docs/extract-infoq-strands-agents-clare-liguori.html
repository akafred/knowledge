Podcast: Strands Agents with Clare Liguori

InfoQ Podcast; host: Thomas Betts; guest: Clare Liguori (AWS, technical lead, Strands Agents SDK) · podcast · 2026-07-20 source ↗ Reader 🖥️

Building reliable production AI agents means resisting the instinct to constrain them with deterministic workflow logic -- which Strands's own case-study testing shows is measurably less accurate and more brittle than trusting the model -- and instead investing in a minimal model-driven design (system prompt, tools, model) supplemented by targeted runtime controls (evals, stateful 'steering hooks' backed by a full tool-call ledger, continuous evaluation against live traffic) that inject determinism only where and when the model actually needs it, with the harness's job now expanding from running a short reasoning loop toward sustaining long-running, resumable, self-tracking agentic work as the underlying models keep improving.

practical · mixed — An interview that is mostly practical (prescribing how to build and operate production agents) but is organized around a theoretical distinction the guest builds and defends over the course of the conversation: model-driven design vs. workflow-driven design, and later, agent harness vs. agent framework. Argumentative core (a directly stated, evidence-backed thesis about workflows vs. model-driven design) carried by narrative case studies (the mortgage example, the AWS console chatbot's evolution, the network-diagnosis agent).

Key terms

  • model-driven approach Model-Driven Agent Design
    Building an agent from just three choices -- a system prompt, a set of tools, and a model -- and trusting the model's own reasoning and tool-call planning to handle inputs, instead of pre-scripting control flow.
  • workflow (pejorative use) AI Workflow Patterns
    Developer-authored control-flow scaffolding (if/for/while statements, micro-agents, predefined branches) layered on top of the model to constrain its behavior -- treated as brittle and a source of downward-spiral maintenance.
  • agent harness vs. agent framework
    A framework is essentially a while loop -- cycling through model turns and tool execution until the model yields. A harness is the additional layer (context management, memory, persist-and-resume state, self-tracking tools like task lists) that lets an agent sustain long-running, complex, multi-turn work beyond what a bare loop supports.
  • steering hooks
    A Strands-specific layer on top of regular hooks: code or an LLM judge run before a tool call, but with access to 'the ledger' -- the full history of tool calls made so far -- enabling stateful, cross-call constraints that a normal pass/fail hook cannot express.
  • the ledger
    The full, ordered history of every tool call made so far within a single agent conversation, exposed to steering hooks so they can check accumulated state (e.g., 'has income verification been called and did it pass') rather than just the current call's inputs.
  • procedural memory (informal use)
    Clare's own loose label for storing an agent's successful past tool-call trajectories in a semantic-search database and retrieving similar past trajectories to guide handling of a new, related input.

Arguments

Adding explicit workflow scaffolding (if/for/while control flow, predefined micro-agents) to constrain agent behavior makes agents less reliable, not more. strength: high
Explicit premises:
  • Workflows are built based on anticipated inputs, but real users send unpredictable inputs, including compound questions.
  • Workflows accumulate patched-on if-statements as more unexpected inputs surface, creating a maintenance downward spiral.
  • Case-study data: simple instructions scored an 82.5% pass rate and steering hooks scored 100%, both compared favorably against a workflow-based approach.
Implicit premises:
  • Frontier and even many open-source models have become good enough at their own reasoning and tool-call planning that they don't need externally imposed control flow to sequence correctly.
  • A developer's model of 'what inputs will occur' is systematically incomplete, so hand-authored workflow logic permanently encodes that incompleteness into the system.
Inferences:
  • Agent frameworks built primarily around explicit workflow/DAG orchestration are solving the wrong problem for a broad class of agent use cases.
  • 'Correctness' for an agent should be defined as 'solves the customer's actual (possibly unanticipated) task,' not 'matches the developer's anticipated flow.'
Determinism should be injected into agents at runtime, locally and only where needed (steering hooks plus the ledger), rather than imposed globally ahead of time (workflows). strength: medium
Explicit premises:
  • A plain hook can check pass/fail on a single tool call's inputs but cannot easily enforce cross-call ordering constraints.
  • The ledger gives steering hooks the full history of tool calls so far, enabling an ordering check (e.g., income verification before mortgage approval).
  • Instructions alone ('do not call X before Y') are not reliably obeyed by models.
Implicit premises:
  • The failure mode developers actually fear -- an agent skipping a required precondition step -- is a narrow, nameable class of constraint, not a general need to script the whole conversation.
  • A targeted architectural check (ledger-based hook) can enforce that narrow constraint without removing the model's flexibility to handle adjacent, slightly different requests (e.g., 'would I be approved' vs. 'submit a mortgage').
Inferences:
  • Steering hooks function as a narrow, composable alternative to workflows for the subset of correctness properties that genuinely need hard guarantees, suggesting a spectrum between 'no determinism' and 'full workflow' that most agent frameworks don't currently expose.
Live-traffic evaluation must be a continuous, standing function, not a pre-launch gate. strength: high
Explicit premises:
  • The AWS console chatbot's pre-launch eval set assumed short 'what is X' questions and was tuned for conciseness.
  • Real users asked 'how do I' questions needing longer, instructional answers.
  • This mismatch was discovered only after launch, by watching traces and sample inputs.
Implicit premises:
  • No amount of pre-launch imagination fully anticipates the true production input distribution, so an evaluation program that stops at launch is structurally incomplete, not just occasionally unlucky.
Inferences:
  • Production agent teams need standing infrastructure (trace review, feedback signals such as thumbs-down or cursing at the agent) as a permanent organizational function -- reframing 'maintenance' for agentic systems as continuous re-evaluation rather than bug-fixing.

Narratives

  • A mortgage-processing agent example: a plain hook can block approving mortgages over a million dollars based on the current call's inputs, but only a steering hook with access to the full ledger can enforce that income verification happened before mortgage approval was attempted -- while still allowing a user to ask 'would I be approved' without submitting.
    → Makes the abstract 'ledger' concept concrete; supports propositions 3 and 4 and argument 2.
  • The AWS console chatbot's evolution from a 2023 super-simple prompt pipeline (Claude 2-era) into a full model-driven agent with sub-agents, including a network-troubleshooting sub-agent -- each capability jump driven by a new model generation, with old handwritten scaffolding thrown away each time.
    → Illustrates the model-driven philosophy's real payoff (capability growing with each model generation without a full redesign) and the emotional cost of discarding built infrastructure; supports propositions 9 and 13.
  • A network-issue-resolution agent needed roughly 15 sequential API calls to diagnose connectivity problems (e.g., 'why can't I SSH to this EC2 instance'), was reliable only up to about 10 calls, and was fixed by saving successful tool-call sequences to a semantic-search database and retrieving similar past trajectories for related new inputs.
    → Concretizes 'procedural memory' as a distinct, cross-conversation memory mechanism from the single-conversation ledger; supports proposition 12.
  • Thomas's anecdote about a company that limited an agent to 25 approved prompts, which then failed and repeatedly claimed it couldn't respond when asked anything outside that list.
    → From the interviewer, but functions as a shared data point both speakers build on: illustrates the mismatch between the responsible-AI instinct to over-constrain and how customers actually use agentic systems ('customers will use your service in ways you never predicted').

Questions addressed

  • ✅ How do you build a production-reliable agent without heavy, brittle workflow scaffolding?
    The model-driven approach (system prompt + tools + model), supplemented by evals and hooks for guardrails.
  • ✅ How do you know an agent 'works' when you can't rely on deterministic tests?
    Evals -- ideally scoped to tool-call correctness rather than subjective output judgment -- plus LLM-as-judge using a different/smaller model, plus continuous live-traffic evaluation.
  • ✅ How do you enforce specific hard behavioral constraints (e.g., ordering of tool calls) without reintroducing brittle workflow logic?
    Steering hooks backed by the full tool-call ledger.
  • ✅ What's the difference between an agent framework and an agent harness?
    Framework = the loop mechanics (model call, tool execution, repeat until yield); harness = the additional layer supporting long-running, complex, resumable work.
  • ✅ What does a production observability stack for agents need, beyond traditional software observability?
    OpenTelemetry traces treated as the primary signal, because agent 'hops' are internal tool calls; continuous comparison of live traffic against an evolving eval set.
  • ⭕ Does the steering-hooks/ledger approach actually satisfy the auditability and governance requirements that motivate 'responsible AI' workflow-engine architectures like Thomas's at Blackbaud, or does it just relocate the governance question to 'trust the check we wrote'?
  • ✅ If you were starting Strands over from scratch, what would you design differently?
    Build directly for long-running, complex-task harness capabilities (context management, persist-and-resume, task tracking) from the start, because models weren't capable enough for that when Strands was first built.

Clare reframes the question as one of reliability and accuracy, but never addresses whether steering hooks give the same hard, by-construction guarantee ('the agent literally cannot take this action') that a workflow engine's action-allowlist gives.

  • incompleteThe claim that 'the likelihood that a frontier model... does go run wild is in practice very small' is offered as a premise for not over-architecting guardrails, but no quantified rate, no definition of 'run wild,' and no discussion of how that likelihood should change with task stakes (mortgage approval vs. 'what is EC2') are given.
