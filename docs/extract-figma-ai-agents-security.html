Figma's security engineering team, as relayed by InfoQ from the company's own blog posts, holds that AI agents equipped with persistent, separated memory, tightly scoped tools, and strict human-review guardrails (draft-by-default PRs, anti-leak prompts) can absorb much of a security team's repetitive investigative and detection work -- reporting roughly 70% faster complex-alert resolution, 20% fewer on-call pages, 100+ newly found vulnerabilities, and 80% code-reviewer precision -- while insisting that the right balance between agent autonomy and human oversight remains an open, evolving question rather than a solved one.

practical · mixed — An InfoQ news brief reporting on two Figma engineering-blog posts (alert triage/investigation agents, and vulnerability/code-review agents). It is mostly expository (relaying Figma's own claims and quotes) but functions narratively as a case study, and closes with an argumentative frame (agents-vs-humans is a false binary; the right balance is still evolving) plus adjacent context (Wiz's GhostApproval report, OpenAI's sandbox-escape disclosure) that implicitly argues security teams should adopt agentic tooling cautiously rather than either rejecting or fully trusting it.

Key terms

  • steering memory
    One of the alert-triage agent's context inputs alongside Slack thread history and scoped tools -- described as a distinct memory type that shapes agent behavior, separate from the memory of past alerts and from learned database structures.
  • precision before recall
    Sullivan and Girardeau's tuning-order principle: fix an agent's false-positive rate (precision) before trying to improve its false-negative rate / coverage (recall), because a team's inventory of already-known historical bugs can only be used to measure recall, not precision.
  • draft by default
    A specific, tool-level safety control: pull requests an agent opens are automatically created in GitHub's draft state rather than ready-for-review, so an agent's code fix cannot be merged, or even flagged for standard review, without a human first promoting it out of draft.

Arguments

AI agents can safely take on significant security-operations workload (alert triage, vulnerability discovery, code review) without displacing human control. strength: medium
Explicit premises:
  • Agents reduced complex-alert resolution time by about 70% and on-call pages by about 20%.
  • Draft-by-default PRs and anti-leak prompts are built into the tools.
  • Human review and strict controls remain in place.
Implicit premises:
  • A roughly 70% speed improvement, if real and representative, outweighs the residual risk of agent error.
  • Self-reported efficiency metrics from the team that built and is publicly showcasing the system are a sufficient basis for judging the system's value.
  • 'Human review remains in place' is sufficient assurance against agent error on its own, without evidence about how much of the agent's work reviewers actually catch versus rubber-stamp.
  • The review/approval mechanisms Figma relies on (draft PRs, human sign-off) are themselves trustworthy control points -- an assumption the same article's own Wiz GhostApproval reference calls into question for approval prompts generally.
Inferences:
  • If review-gate trustworthiness is itself an open problem (per GhostApproval), Figma's 'human review remains in place' claim provides less safety assurance than the article's framing implies, because the review mechanism could itself be the failure point GhostApproval describes -- a connection the article never makes explicit.
Security and code-review agents whose output passes through human reviewers should be tuned to optimize precision before recall. strength: high
Explicit premises:
  • Historical bugs a team already has can only measure recall; they barely help with the precision that must be fixed first.
Implicit premises:
  • A low-precision (high-false-positive) agent will be distrusted or ignored by security engineers regardless of how much true coverage (recall) it eventually achieves, so trust must be earned before volume.
  • The customary intuition of maximizing recall/coverage first and then tightening precision is backwards specifically in a human-trust-gated deployment context, where every false positive costs a reviewer's attention.
Inferences:
  • The principle generalizes beyond Figma to any agent whose output is filtered through human review (alert triage, code review, vulnerability scanning) -- a generalization the article gestures at ('we can't tell you exactly what to do... but one main lesson is...') without stating explicitly.

Questions addressed

  • ✅ Can AI agents take meaningful ownership of security-operations investigative and remediation work without compromising safety?
    Resolved affirmatively per Figma's own account: scoped tools, separated memory, draft-by-default PRs, and anti-leak prompts are offered as the answer -- but this resolution rests entirely on Figma's self-reported figures.
  • ⭕ What is the right balance between agent autonomy and human oversight in security workflows?
    Explicitly left open -- the article states the balance 'is still evolving' and frames this as an industry-wide open question, not something Figma claims to have solved.
  • ⭕ Are the human-approval and review mechanisms that are supposed to make agent autonomy safe (draft PRs, approval prompts) themselves trustworthy?
    Not resolved, and not directly asked -- the article juxtaposes Figma's reassuring case study with Wiz's GhostApproval finding (approval prompts can be spoofed) but never connects the two or asks whether Figma's own PR-approval workflow could be vulnerable to the same class of trust-boundary gap.
