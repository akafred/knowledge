Presentation: The Future of Engineering: Mindsets That Matter When Code Isn't Enough

Ben Greene · rss · 2026-07-28 Reader 🖥️

Software engineers remain valuable in the age of coding agents not because they can still write code, but because building working systems still requires disciplined simplicity, deliberately protected comprehension, willingness to attack hard problems first, and human empathy for customers — capacities coding agents lack and that startups have always demanded of engineers under resource pressure.

practical · mixed — A 25-minute conference talk (InfoQ) plus extended Q&A, structured as six numbered 'startup lessons' each illustrated by personal anecdote, followed by unscripted audience dialogue that tests, extends, and sometimes deflects the lessons. It argues for adopting specific mindsets (practical), using borrowed frameworks (Jevons paradox, Gall's Law, the Einstellung effect) as expository scaffolding and anecdotes as implicit argument.

Key terms

  • Jevons paradox Jevons Paradox
    Making code cheaper to produce (via automation, now coding agents) does not reduce total engineering demand — it increases it, because falling cost drives rising consumption of software.
  • Gall's Law
    A complex system that works is always found to have evolved from a simpler system that worked; a complex system designed from scratch never works and cannot be patched into working — you must restart from a simple working version.
  • comprehension
    An actively maintained property of a system (or codebase) — the state where whoever needs to change it can understand it without excessive effort — that must be protected by discipline (code review, rewriting for the reader) every time the system changes, not a byproduct of having once written the code.
  • Einstellung effect
    Prior success and experience narrow an expert's perception of alternative solutions, causing them (and, by Greene's extension, coding agents trained on prior patterns) to default to familiar approaches even when better ones exist.
  • full-stack
    Used self-deprecatingly to mark a vanishing professional boundary: as AI lets non-engineers (Larry) build working software and lets Greene himself ship an Android app he barely understands at a component level, the term stops reliably distinguishing 'real engineers' from everyone else.
  • POC before MVP
    Greene's personal de-risking discipline: before committing to an approach, get a basic working version of every functional requirement that could plausibly be hard, specifically to convert unknown risk into known risk — distinct from an MVP, which optimizes for the easiest demonstrable version rather than for proving the hard parts work.

Arguments

Software engineers should embrace disciplined incremental simplicity (start simple, then add complexity) more urgently now, not less, despite coding agents' pressure to build big and fast. strength: medium
Explicit premises:
  • Code has been getting cheaper to produce for decades (assembly language, compilers) and coding agents are the latest, biggest step in that trend.
  • By Jevons paradox, cheaper code drives higher total demand for software and more pressure to build fast and big.
  • By Gall's Law, complex working systems only ever evolve from simple working systems; systems designed complex from scratch don't work and can't be patched.
  • Coding agents actively push toward more scope ('give me more tokens... should I continue') and so amplify, rather than relieve, the pressure to skip the simple stage.
Implicit premises:
  • Coding agents, lacking judgment about when a system is 'done enough' at a given scope, will generate arbitrarily large scope without a human discipline that stops and validates simplicity first.
  • Gall's Law and Brooks's observation about incremental system-building still hold when the speed of writing code changes — the underlying nature of complex systems is unaffected by how fast their parts get typed.
Inferences:
  • Teams that let coding agents auto-generate large scope without an enforced 'smallest working version first' gate should be more likely to ship unworkable, over-complex systems than teams that use agents to iterate on small, deployable slices — a comparative prediction Greene never actually tests or cites evidence for.
Comprehension must be actively protected as a first-class engineering practice, not treated as an automatic byproduct of writing code. strength: high
Explicit premises:
  • Perfection is unattainable; products will need to change based on what actually happens when released to the world.
  • To change something well, you must first understand it — 'the linchpin of change is truly comprehending what it is you've already built.'
  • Coding agents make it easy to generate large, never-understood codebases from the very first step.
Implicit premises:
  • Once a team loses comprehension of a component, the only remaining options are an expensive full rewrite or a permanent, feared workaround — there is no cheap third option.
  • A codebase generated but never understood by anyone is at least as risky as inherited legacy code with no departed-engineer institutional memory, except it can accumulate far faster.
Inferences:
  • Organizations optimizing purely for AI-driven throughput without a comprehension gate are trading a slower, historically bounded rate of technical-debt accumulation for a much faster, effectively unbounded one — a bet Greene implies will eventually force a public reckoning (his later point about companies 'exploding' publicly), though he never draws this connection explicitly.
Human empathy for customers is a source of durable competitive and professional value that coding agents cannot replicate or absorb. strength: low
Explicit premises:
  • Solving the first, surface-level problem a customer names is rarely enough to justify the effort required to adopt a solution.
  • Real product opportunity requires digging into customers' deeper pain, goals, and context — illustrated by the 'coffee' anecdote about a founder learning exactly when customers would use his product.
  • 'AI agents can't care, but we can.'
Implicit premises:
  • Producing useful product insight from empathy requires a first-person emotional relationship with the customer's experience, which Greene assumes — without arguing for it — that a language model cannot possess, however well it can simulate empathetic language.
  • Empathy is a trainable skill or mindset ('you practice it, you model it') rather than a fixed trait, which is why Greene believes engineers can deliberately cultivate it as a professional advantage.
Inferences:
  • If empathy is trainable and durably human, engineering organizations should invest as deliberately in developing it (e.g. structured customer-facing rotations, direct user observation) as they invest in technical training — a conclusion Greene gestures toward (talking about modeling it for children, employees, colleagues) but never states as an organizational recommendation.

Narratives

  • Building a proof-of-concept offline Android RAG app with Claude Code, which kept steering Greene toward an easier web-based MVP until he explicitly overrode it.
    → Supports the claim that coding agents default to avoidant, easy solutions and must be actively overridden to preserve the de-risking value of tackling hard requirements first.
  • Larry, a lighting designer with no software background, now deploys large-scale digital-display software (Salesforce Tower, Times Square) using AI assistance; Greene's mixed, half-joking reaction ('Should I feel threatened by Larry?').
    → Illustrates the dissolving boundary of who counts as a 'software engineer' and dramatizes the professional-identity anxiety underlying the talk's second half.
  • A founder-turned-investor asking Greene when customers would use his app, then pressing on whether it was 'breakfast coffee or after-lunch coffee' — revealing how intimate customer knowledge had shaped his own prior product's success.
    → Supports the claim that deep customer empathy generates product insight that surface-level requirements-gathering cannot.
  • The Silicon-Valley trope of sliding pizza under the door to avoid contact with outsiders (Microsoft, Netscape, id Software lore), tied to a broader claim about baked-in imposter syndrome.
    → Supports the (implicit) claim that engineers historically used opacity as a professional buffer against scrutiny and self-doubt — a buffer AI now strips away.
  • A junior engineer, Anthony, is handed a major story Greene privately believes is architected wrong; Greene lets him try his own plan, and Anthony independently discovers the flaw two days later and switches to Greene's approach.
    → Supports the claim that growing junior mastery sometimes requires deliberately not overriding a decision you believe is wrong, and letting the person discover it themselves.
  • Outcomes4Me's first version of a cancer-treatment-path feature made 'perfect sense' internally but was unusable to real patients; the team only discovered this by watching a patient try and fail with it, not from metrics.
    → Supports the claim that early pivots are driven by qualitative observation of user failure, not by quantitative metrics.
  • At InsightSquared and later Outcomes4Me, Greene modeled 'not understanding' code in public to normalize asking questions; the practice regressed when the company went remote during COVID, so he created a dedicated public Slack channel just for questions to force the culture back.
    → Supports the claim that comprehension and psychological safety must be actively, structurally re-institutionalized once informal in-person modeling is lost — a concrete practice that also closes an open gap about how comprehension gets operationalized (see closes_gaps).
  • A sophomore-year CS class ('Ten Great Theoretical Ideas of Computer Science') where students wrote a 2-bit processor from NAND gates on paper — knowledge Greene no longer remembers the details of but still values, contrasted with the Wright brothers' outsider status in aviation.
    → Supports the (implicit) claim that deep foundational knowledge and non-traditional entry into engineering are complementary sources of value, not competing ones.

Questions addressed

  • ✅ How do software engineers bring value when anyone can program computers?
    Yes, via the five (plus one bonus) startup-lesson mindsets: start simple, protect comprehension, do something new, attack hard bits first, care about impact, and get out of your box.
  • ✅ How do you teach empathy?
    By practicing and modeling it — in families, teams, and company culture — treating it as trainable rather than an innate, fixed trait.
  • ✅ How do you protect code comprehensibility over time, concretely?
    Through a comprehension-gated review discipline ('after correctness, think always of the reader') and a psychological-safety practice — a dedicated public Slack channel for questions — to sustain the culture once informal in-person modeling of curiosity (lost to remote work) is no longer available.
  • ⭕ If coding agents let new engineers skip low-level 'on-ramp' problems (like learning assembly), what happens to the pipeline of engineers who develop deep systems intuition?
    Greene affirms foundational knowledge remains valuable for digging beneath abstractions when needed, and separately offers a delegation model for growing junior judgment (the Anthony story), but never directly addresses whether an engineer who never personally struggled through low-level problems will develop the underlying intuition he himself relies on (e.g. 'I was pretty sure it was wrong').
  • ⭕ How do engineering leaders balance delivering products faster under AI pressure without sacrificing requirements or scope quality?
    Greene deflects toward general advice (better patterns, better platforms and tools, leveraging open source, engaging non-engineers to test corner cases) without directly answering the speed-versus-scope tradeoff the question asked about.
  • ⭕ Has AI agents' lack of empathy or agency concretely derailed a real project Greene knows of?
    Greene answers by analogy — coding agents behave like an outsourced team executing a spec without buy-in to the mission — rather than describing a concrete AI-specific incident, so the direct question is only loosely answered.

Gaps

  • incompleteThe talk's central, title-justifying claim — 'AI agents can't care, but we can' — is asserted as self-evident and is the load-bearing premise for the entire 'care about impact' mindset, but Greene never argues for it. He doesn't engage with the possibility that the customer insight he attributes to empathy (a founder learning exactly when customers drink coffee) could in principle be produced by systematic behavioral research an AI system could assist with or perform, without the engineer's own subjective 'caring.' Whether the product value comes from the caring itself or from the information caring happens to surface is left completely unexamined.
    Read next: Look for arguments (for or against) that ground human empathy's product value specifically in the phenomenology of caring, versus in the information that caring happens to surface — e.g. work on AI-assisted user research or computational empathy.
    closed byHow Do You Know That? — That gap flags Greene's load-bearing, unargued claim 'AI agents can't care, but we can.' This document's 'no endocrine system' framing (p7) supplies the mechanism Greene asserts without arguing: a model has no enthusiasm or drive of its own, so all the caring in AI-assisted work is supplied by the human — the working unit is 'us plus the genie,' not the model alone.
  • incompleteGreene's evidence throughout is drawn almost entirely from his own two startups (InsightSquared, Outcomes4Me) plus one recent personal side project (the Android RAG proof-of-concept); no comparative case is offered of a startup or team that ignored these mindsets and what happened as a result, nor of a larger, less resource-constrained organization successfully applying the same lessons. It is left open whether 'the lessons startups have always taught us' generalize past small, high-autonomy, high-trust teams.
    Read next: Seek accounts of these same mindsets (start simple, protect comprehension, attack hard bits first) applied — or failing to apply — inside larger, less autonomous engineering organizations.
  • illogicalThe Jevons-paradox argument (Lesson 1) establishes that total demand for software may rise as code gets cheaper, but Greene slides from 'aggregate demand for software rises' to 'therefore individual software engineers remain valuable,' without addressing whether rising demand is met by more engineers, or by fewer engineers each producing proportionally more software with agents — the same substitution question other Jevons-paradox-for-jobs arguments in the corpus explicitly raise as a disanalogy.
    Read next: See extract-karpathy-code-agents-autoresearch#g3 for the disanalogy debate (ATMs automating a narrow banking task vs. AI agents potentially automating the whole engineering task) that Greene's version of the argument does not engage with.
  • incompleteThe 'get out of your box' bonus lesson lists empathy, creativity/taste, learning agility, systems thinking, and high agency as the critical skills going forward, borrowed and extended from an unnamed source post ('I saw this post... I'll paraphrase... Go find it'), but Greene never names the source, examines whether these skills can actually be taught or measured at scale, or reconciles the list with his own admission that 'not everyone is going to be great at everything' — leaving unclear whether this is meant as a universal prescription or an aspirational ideal for a self-selected subset of engineers.
    closed byNetflix CPTO on AI and the future of product and tech roles | Elizabeth Stone — Provides a concrete, real-world example of how two of Greene's listed 'critical skills' — systems thinking and high agency — are actually operationalized at a major company: a lightweight, teachable heuristic for systems thinking (the one-click zoom-out), and an explicit account of why not everyone needs equal breadth (a small number of deliberately preserved deep specialists), which reconciles the list with Greene's own unresolved 'not everyone is going to be great at everything' caveat.
