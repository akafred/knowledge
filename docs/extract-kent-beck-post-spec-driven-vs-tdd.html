Agile & XPSpec-Driven DevelopmentTest-Driven Development
The common framing of Spec-Driven Development — write the complete specification, then implement — rests on a false assumption that implementation teaches you nothing that should change the spec, whereas TDD's tight test/code/fail/pass loop is structured around the opposite assumption: that you will learn continuously and must feed that learning back immediately.

theoretical · argumentative — A short LinkedIn post (67 words plus a two-panel diagram) that surfaces and rejects a single hidden assumption behind Spec-Driven Development, contrasting it visually with TDD's interleaved loop.

Key terms

  • Spec-Driven Development Spec-Driven Development
    As Beck characterizes it here: a workflow where the complete specification is written before any implementation begins, on the assumption that implementation will not generate information that should feed back into the spec.

Arguments

Spec-Driven Development, as commonly described, rests on a mistaken premise and should be viewed with suspicion. strength: medium
Explicit premises:
  • SDD-as-described requires writing the whole spec before implementation.
  • Writing the whole spec first only makes sense if implementation won't surface spec-changing information.
Implicit premises:
  • In real software work, implementation routinely surfaces information that should change the specification (a premise Beck treats as self-evident and doesn't argue for in this short post).
  • TDD's interleaved loop is the structurally correct response to that fact, making it an implicit positive counter-example to SDD.
Inferences:
  • If implementation reliably generates spec-changing information, then any process that finalizes the spec before implementation is structurally unable to incorporate that information without rework or waste.

Questions addressed

  • ✅ Does the standard description of Spec-Driven Development hold up under its own assumptions?
    No — it depends on an assumption (no learning during implementation) that Beck considers obviously false.

Gaps

  • incompleteBeck asserts that implementation teaches you things that should change the spec, and treats this as self-evidently true without any example, data, or anecdote in this post — unusual for his style elsewhere, where personal anecdotes typically carry the argumentative weight. The post also doesn't address the version of Spec-Driven Development that the corpus has already documented as explicitly built around iterative discovery (extract-when-ai-writes-the-code-specifications-need-an-exit-strategy's 'change brief' as part of an ongoing loop) — so it's unclear whether Beck is critiquing SDD as such or only a naive/batch variant of it that more careful SDD proponents have already moved past.
