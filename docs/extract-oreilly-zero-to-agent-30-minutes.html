Zero to Agent in 30 Minutes: Build a Workflow Agent with John Berryman

An AI agent is, at bottom, simply an LLM wrapped in an outer conversation loop and an inner tool-use loop, and the right way to build one is 'outside in' — get the non-AI application working first, stub the AI, then incrementally swap in a minimal validated agent, a small fixed toolkit, and a natural-language 'skill' — because this staged sequencing both de-risks the build and produces instructions plain enough that domain experts, not just engineers, can read and correct them directly.

practical · expository — A syndicated recap/write-up of a live webinar demo, opening with a short conceptual frame (what an agent structurally is) before reporting a numbered five-step build method as it was demonstrated. Reports what John Berryman did and said rather than arguing a contested thesis, and closes with a promotional pointer to a follow-on paid/free O'Reilly event.

Key terms

  • agent Agentic AI
    An LLM wrapped in two loops: an outer loop that passes messages back and forth to the user (shared with plain chatbots) and an inner loop that lets the model choose and run tools — the inner loop is specifically what turns an assistant into an agent.
  • outside in
    Berryman's name for a build sequence: get the traditional (non-AI) software working first, fake the AI with a static stub, then swap in a real but minimal agent, then a small toolkit, then a natural-language skill — moving from the deterministic outer shell inward to the AI core.
  • skill Agent Skills
    A natural-language artifact encoding an agent's context, decision criteria, and step-by-step workflow — including self-checking checklists — written instead of a coded state machine.
  • structured output
    Output requirements with validation (here, three fields: update type, internal notes, correspondence) imposed on the minimal agent specifically to keep the underlying model 'on track.'

Arguments

A team should build AI products 'outside in' — traditional software first, stubbed AI, then a minimal validated agent, then a small toolkit, then a natural-language skill — rather than starting from the AI component. strength: medium
Explicit premises:
  • Defining the AI component's exact input and output requires the surrounding non-AI system to exist first.
  • A static stub confirms the rest of the system works before the model is introduced.
  • Structured output plus validation keeps a minimal agent on track once it is introduced.
  • A small, well-known toolkit (read/write/edit/shell) suffices because models already know these tools from training.
  • Natural-language skills with built-in checklists let the agent self-verify its own workflow.
Implicit premises:
  • Isolating the AI component's risk from the rest of the system's risk is generally desirable in product engineering — a de-risking-by-sequencing principle imported from ordinary software practice (e.g. walking-skeleton style incremental builds) and applied here to AI without being argued for on its own terms.
  • A single demoed pipeline (candidate review) generalizes to AI products broadly.
Inferences:
  • If AI is the least predictable, most novel part of the system, isolating it last — after everything else is proven — minimizes the surface area exposed to that unpredictability at any given build stage; the piece implies this risk-management logic but never states it explicitly.
Programming agents in natural language ('skills') is preferable to traditional coded logic because it makes agent behavior legible and directly editable by non-engineers. strength: medium
Explicit premises:
  • Subject-matter experts can read the instructions driving the AI.
  • Subject-matter experts can examine faulty responses and see where the reasoning broke down.
  • Subject-matter experts can make updates directly instead of relaying feedback to a product manager and an engineer.
Implicit premises:
  • Removing the PM/engineer relay step is a net improvement rather than the loss of a useful check or translation function — the piece doesn't consider that engineers or PMs might catch problems an SME would miss, or that uncoordinated direct edits could introduce inconsistency or drift.
  • Natural language is a reliable enough encoding of decision criteria that reading it is equivalent to understanding what the agent will actually do at runtime — which glosses over exactly the gap ('examine faulty responses... where the reasoning broke down') the argument itself says still needs diagnosing.
Inferences:
  • If SMEs can both diagnose and fix agent behavior, the traditional requirements-relay role of product managers mediating between domain experts and engineers is at least partially disintermediated for this class of AI product.

Questions addressed

  • ✅ What, structurally, is an AI 'agent' as opposed to a plain chatbot?
    An LLM wrapped in an outer message-passing loop (shared with chatbots) plus an inner loop that lets the model choose and run tools; the inner loop is specifically what makes it an agent.
  • ✅ In what order should a team build an AI product to minimize risk?
    Traditional software first, then a stubbed AI, then a minimal validated agent, then a small toolkit, then a natural-language skill.
  • ✅ How much tooling does a new agent need to be useful?
    Start with four capabilities — read, write, edit, shell access — because models already know bash and CLI tools from training.
  • ⭕ How does an organization govern or maintain natural-language 'skills' once domain experts, not engineers, are editing them directly in production?
    Not addressed — the piece celebrates direct SME editing as the 'payoff' of natural-language programming without discussing version control, review, testing, or drift once non-engineers are the ones changing production agent logic.
