Does code quality still matter?

Mark Seemann · rss · 2026-07-23 source ↗ Reader 🖥️

Agent-Oriented Programming LanguagesCode QualityHuman-in-the-LoopRecursive Self-ImprovementTechnical Debt
Because code quality as currently understood is entirely reducible to the constraints of human cognition, Seemann argues that a hypothetical future in which LLMs alone write, read, and maintain code — in machine-optimized languages rather than human ones — could render today's code-quality concepts meaningless, yet some structurally analogous form of technical debt would likely still emerge from LLMs' own constraints, and only the LLMs' own accumulated experience (not humanity's software-engineering literature, which is inescapably about human cognition) could diagnose and correct it.

theoretical · personal essay / thought experiment — A speculative first-person essay that opens from a tweet and a long-running personal preoccupation, then works through a deliberately hypothetical scenario (a fully human-free coding future) rather than reporting on current practice. Seemann repeatedly flags his own uncertainty ('I honestly don't know') rather than asserting conclusions.

Key terms

  • code quality Code Quality
    An intrinsic, structural property of a code base — how it is structured, how readable it is, how easy it is to change — explicitly distinguished from 'software quality' and explicitly reducible, as currently practiced, to the constraints of human cognition
  • LLaMe
    Seemann's coined name for a hypothesized single programming language that emerges once no humans read or write code — optimized for LLMs to consume, generate, and manipulate rather than for human ergonomics
  • YOLO (a code base)
    Writing code with no attention to code quality — used both for humans doing it by hand and, by extension, for agentic code produced with no quality oversight
  • technical debt (in this essay's extended sense) Technical Debt
    Generalized beyond human-authored code to any accumulation of structural choices — even within a hypothetical LLM-native language or at the level of machine-code register allocation — that make a system more expensive to change later

Arguments

In a hypothesized future where humans no longer write or read code at all, today's notion of 'code quality' (defined by readability, method length, naming, coupling) would become meaningless, but a structurally analogous form of technical debt could still emerge and would need to be diagnosed and solved by LLMs themselves rather than by applying human software-engineering wisdom.
Explicit premises:
  • Code quality, as currently practiced, is reducible to human cognitive constraints (readability, comprehensibility, ease of human change).
  • If humans no longer write or read code, the constraints related to human cognition become irrelevant, and some code-quality notions (e.g. 'long method') may not even remain meaningful.
  • If no humans look at code, new programming languages optimized for LLM consumption/generation could emerge (hypothesized as 'LLaMe'), replacing human-ergonomic languages.
  • Even fully machine-oriented code (machine code, register allocation) still involves structural choices that differ in downstream cost, so an LLM-native language would likely also admit better- and worse-structured code.
  • Humanity's accumulated software-engineering literature is entangled with human cognition and would not transfer to identifying good/bad structure in an LLM-native language.
Implicit premises:
  • Technical debt is best understood generally as 'cost of future change,' not specifically as 'cost of future human comprehension' — so the concept can survive even when its human-cognition-specific manifestations (readability, naming) do not.
  • A single dominant LLM-native language ('LLaMe') is a reasonable simplifying assumption for the thought experiment, even though in reality multiple such languages, formats, or representations (or none at all, if LLMs converge on existing languages) could emerge instead.
  • LLMs (or their successors) are capable of an analogue of 'learning from experience' across generations/training runs in a way that is functionally comparable to how human engineering culture transmits lessons — an assumption the essay flags as uncertain but still relies on for its 'Acceleration' resolution.
  • The fact that humans could no longer read or verify LLaMe code themselves does not by itself prevent technical debt from existing in it — i.e., 'debt' is defined by cost-to-change, not by whether a human observer can perceive the debt.
  • Present-day incentives and safety practices (human review, human responsibility for code) are not permanent features of software development — the thought experiment requires assuming today's human-in-the-loop norm could actually be abandoned.
Letting LLMs produce software entirely without human oversight is more complicated than most AI optimists suggest.
Explicit premises:
  • There are at least three distinct possible futures for machine-native technical debt: it never materializes; it appears and is later solved (e.g. via LLM-to-LLM knowledge transfer); or it appears and is permanently unsolvable because its limitations lie beyond human cognition.
  • In the third scenario, humans would have no chance to troubleshoot a problem that is 'beyond human cognition' — i.e., a fully autonomous LLM software ecosystem could get structurally stuck in a way no human could diagnose or fix.
Implicit premises:
  • AI optimists' arguments for full automation implicitly assume that removing humans from the loop removes friction/cost rather than potentially introducing a new, less-legible form of it — an assumption this essay's thought experiment is designed to challenge.
  • The possibility of an unsolvable, human-illegible failure mode is itself grounds for caution even though Seemann assigns it no probability estimate — i.e., the mere existence of a bad, irreversible tail scenario is doing normative work in the conclusion independent of its likelihood.

Narratives

  • A tweet (attributed by Seemann to Tim Ottinger, in substance if not exact wording) asking why 'YOLOing' a codebase by hand is considered a bad idea but the same lack of quality oversight is tolerated when LLMs (agentic code) do it.
    → Serves as the essay's inciting provocation — reframes a familiar double standard (humans criticized for sloppy code, agents given a pass) into the essay's real question of whether that double standard is actually justified once humans exit the loop entirely
  • Seemann's reference to his own book, Code That Fits in Your Head, as the encapsulation of the idea that code quality reduces to human cognitive capacity.
    → Grounds the essay's central premise in Seemann's own established authorial position, letting him treat 'code quality = human cognition' as settled background rather than something this essay needs to re-argue

Questions addressed

  • ⭕ Does code quality still matter if LLMs, not humans, write and maintain all the code?
    Left explicitly open. Seemann argues today's cognition-based notion of code quality would likely become irrelevant, but some analogous form of technical debt (cost-to-change) could still emerge from LLM-specific structural constraints — he states repeatedly that he does not know which outcome obtains.
  • ⭕ Would LLMs, in a fully human-free coding future, use today's programming languages or something new?
    Seemann speculates that new, LLM-optimized languages (hypothesized as 'LLaMe') could emerge since existing languages exist mainly to serve human ergonomics, but treats this as a thought-experiment assumption, not a prediction he defends with evidence.
  • ✅ Can LLMs learn to avoid technical debt in an LLM-native language by drawing on humanity's existing software-engineering knowledge?
    No — Seemann argues this knowledge is deeply entangled with human cognition and is unlikely to apply to a language and constraint-set LLMs themselves would be subject to; LLMs would have to learn from their own experience instead.
  • ⭕ Could LLMs develop and transmit their own 'best practices' fast enough to prevent LLaMe technical debt from becoming a lasting problem?
    Presented as a speculative possibility (LLMs writing incident reports/think pieces for training successor models) rather than a resolved claim; Seemann repeatedly hedges ('I don't know, but I suppose').

Gaps

  • incompleteThe essay never specifies what would motivate humans to actually remove themselves from the code-review/responsibility loop, given that Seemann's own opening premise is that quality matters precisely because humans remain accountable for the code. The thought experiment assumes away the accountability structure (legal, commercial, safety) that currently keeps humans in the loop, without discussing why or how organizations, regulators, or liability regimes would ever permit that removal.
    Read next: Look for material on AI accountability and liability for autonomously-generated/deployed software (e.g. discussions of 'who is responsible when an agent's code causes harm') to see whether any serious proposal actually argues for full removal of human accountability, as opposed to full removal of human code-reading.
  • incompleteThe essay treats 'LLaMe' as if a single dominant LLM-native language would emerge, but does not address the more likely alternative that many competing model providers, toolchains, and legacy-interop requirements would produce multiple incompatible machine-oriented representations (or none at all, if models keep generating human-readable languages for interoperability with existing systems, tooling, and each other).
    Read next: Cross-reference with material on agent-oriented/agent-native programming language proposals (e.g. discussions of languages diverging into human-readable vs. heavily-typed/agent-specific forms) to see whether any convergence-vs-fragmentation argument is made explicitly elsewhere in the corpus.
  • tension not resolvedThe essay's own token-cost proxy for LLaMe code quality ('more resources (tokens?) for LLMs to understand') is asserted only parenthetically and with a question mark, yet it does the real work of reintroducing a 'quality' concept after the essay has just argued that human-cognition-based quality dissolves — Seemann does not acknowledge that he has effectively re-derived a form of code quality (cost-to-process) rather than eliminated the concept, nor connect this back to his own opening claim that code quality is 'reducible to human cognition.'
    Read next: Compare with material proposing token cost as a direct architectural-quality proxy in agentic development, to see whether that framing is developed with more rigor than Seemann's parenthetical aside.
  • incompleteThe essay does not engage with the possibility that LLMs already effectively 'read' code today (via their own context windows and training) using representations quite unlike human perception, which suggests the thought experiment's stark before/after framing (human cognition vs. some future LLM cognition) elides a more gradual, already-underway shift in what 'reading code' even means for a model versus a human.
    Read next: Look for empirical or interpretability work on how LLMs internally represent code (e.g. token-level vs. structural/AST-level processing) to assess whether 'LLM cognition of code' is already a distinct, non-human-cognition regime today, rather than only in Seemann's hypothesized future.
