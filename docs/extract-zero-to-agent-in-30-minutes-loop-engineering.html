Key terms

  • loop engineering Loop Engineering
    Replacing a sequence of individual human prompts with a single end-result the agent can check for itself -- the agent inspects code, adds tests, runs them, fixes failures, and verifies packaging, continuing until a defined goal is met, without a human prompting after each step.
  • verifiable goal
    A task framing (e.g. 'implement the resolver and be ready to ship with packaging') specific enough that the agent itself can determine whether it has been met, as opposed to a goal only a human can judge.
  • reviewer (agent)
    A second coding agent assigned to examine the first agent's work against the specification, give feedback, and run additional checks including adversarial probes -- distinct from the agent that writes the code.

Arguments

Defining a verifiable goal, rather than prompting step by step, lets an agent work through a coding task with less human intervention. strength: medium
Explicit premises:
  • A verifiable goal lets the agent inspect code, add tests, run them, fix failures, and verify packaging on its own
  • In the demoed example, the agent worked through the resolver task to completion this way
Implicit premises:
  • A goal can be reliably operationalized as something machine-checkable (tests passing, packaging succeeding) such that 'checks pass' is a trustworthy proxy for 'the task is actually done correctly'
  • The agent's self-assessment of having met the goal can be trusted without independent (human) confirmation
Inferences:
  • If the verification step itself is weak or gameable, the loop could converge on a state that passes its own checks without meeting the intended spec -- a possibility the article never raises
Adding a second agent as reviewer improves code quality and further reduces required human intervention beyond a single looping agent. strength: low
Explicit premises:
  • The reviewer agent examines the specification, gives feedback, and runs additional checks including adversarial probes
  • This two-agent pattern is presented as extensible to a larger team of specialized review agents
Implicit premises:
  • A second AI agent's review is an adequate substitute for (or meaningful complement to) human review
  • Agents built on different models or configurations bring genuinely independent perspectives rather than sharing systematic blind spots
Inferences:
  • If coder and reviewer share the same underlying model family, their 'independent' review may share the same blind spots -- a concern the article does not address, and one this corpus's own extract-20-loop-design-patterns#g6 raises directly about multi-evaluator patterns in general

Narratives

  • A single running example -- a package-version resolver with existing Python tests -- is walked through all three stages: explicit step-by-step prompting, then a verifiable-goal loop, then a two-agent (coder + Jam reviewer) collaboration.
    → Carries the entire argument for the staged escalation from prompting to loop engineering to multi-agent review; the reader never sees a case where an earlier stage fails or where the reviewer agent catches a real defect, so the example only ever illustrates success.

Questions addressed

  • ✅ How does a developer move a coding agent from fully human-prompted operation toward more autonomous operation?
    Via a three-stage escalation: explicit step-by-step prompts, then a single verifiable goal the agent iterates against, then a second agent added as reviewer (generalizable to a larger specialized team).
  • ⭕ Does a reviewer agent's independence hold when it is built on the same underlying model family as the coder agent it is reviewing?
  • ⭕ What happens when the 'verifiable goal' itself is under-specified, or the checks used to verify it are gameable?

Gaps

  • incompleteThe piece never addresses what makes a goal 'verifiable' for genuinely ambiguous coding work. The demoed task (a package resolver) already had existing tests to check against -- a ready-made oracle. A large share of real coding work lacks that: the article gives no guidance for defining a verifiable goal when there is no pre-existing test suite or spec precise enough to check against mechanically.
    Read next: extract-pragmatic-engineer-loop-engineering (on what a 'well-engineered' loop's completion criterion actually is) and extract-osmani-loop-engineering#p11 (verification remains a human responsibility even inside a well-designed loop, and 'done' is a claim the loop makes about itself, not a proof).
  • incompleteThe reviewer-agent pattern (examine spec, give feedback, run adversarial probes) is presented as inherently more rigorous than a single agent, without addressing whether coder and reviewer sharing the same underlying model undermines the independence the pattern depends on. This is the same unexamined independence assumption this corpus's own extract-20-loop-design-patterns#g6 raises about multi-evaluator patterns generally, and the mismatch is sharpened by extract-multi-agent-ai-production-security-operations#p3's explicit warning that reviewer safety logic should be codified as deterministic policy rather than left to an LLM reasoning at runtime.
