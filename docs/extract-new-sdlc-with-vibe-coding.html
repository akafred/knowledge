The New SDLC With Vibe Coding: From ad-hoc prompting to Agentic Engineering

Addy Osmani, Shubham Saboo, Sokratis Kartakis · pdf · 2026-06-15 Reader 🖥️

Agent HarnessAgentic EngineeringCode Was Never the BottleneckCoding AgentsContext EngineeringEvalsGuardrailsHuman as Orchestrator of AgentsModel RoutingSoftware FactoryVibe Coding
As AI increasingly handles code generation itself, what separates production-grade 'agentic engineering' from risky 'vibe coding' is not which AI tool a team uses but how deliberately it designs and maintains the harness, verification (tests + evals), and context around the model — so the discipline a team already has is what AI amplifies, for better or worse.

practical · expository — A practitioner whitepaper (Day-2 of a Google/O'Reilly-adjacent series) that argues teams and orgs should adopt specific practices (context engineering, test+eval verification, deliberate harness design) rather than drift into 'vibe coding'; propositions throughout serve that prescriptive aim even when stated as neutral description of 'how AI transforms each SDLC phase.'

Key terms

  • vibe coding Vibe Coding
    Karpathy's original sense, narrowed by the authors: prompting an AI, accepting its output without serious verification, and fixing errors by pasting them back into the prompt. Positioned as the low-structure end of a spectrum, not a synonym for 'using AI to code' generally.
  • agentic engineering Agentic Engineering
    The disciplined end of the same spectrum: AI as implementation engine within human-designed constraints, specs, tests, evals, and guardrails, with humans retaining architecture/correctness/quality oversight. Coined (per the paper) by Karpathy himself in early 2026 as a correction to vibe coding's overreach.
  • harness Agent Harness
    Everything around the model that turns a raw model into a working agent: instructions/rule files, tools, sandboxes, orchestration logic, guardrails/hooks, observability. Expressed as 'Agent = Model + Harness.' Team-owned surface area, not the model provider's.
  • context engineering Context Engineering
    The practice of supplying an agent with six structured types of context (instructions, knowledge, memory, examples, tools, guardrails), split into always-loaded 'static' context and on-demand 'dynamic' context (notably Agent Skills), as a discipline distinct from and more important than prompt wording.
  • the factory model
    A mental model where the developer's primary output is not code but the system that produces code: specifications, agents, tests/quality gates, feedback loops, and guardrails. The developer is the factory manager, not the assembler.
  • conductor / orchestrator
    Two modes a developer moves between: 'conductor' = real-time, synchronous, in-IDE, keystroke-level direction of a single AI pair-programmer (inline completion, chat-in-editor); 'orchestrator' = asynchronous, goal-level, multi-agent delegation where the developer reviews outcomes rather than watching code appear (background/terminal agents, CI/CD integration, multi-agent coordination).
  • the 80% problem
    AI agents rapidly generate roughly 80% of a feature's code; the remaining 20% (edge cases, error handling, integration points, subtle correctness requirements) demands deep contextual knowledge current models lack, and increasingly manifests as conceptual rather than syntactic errors that 'look right.'

Arguments

Agentic engineering is the lower-total-cost approach to AI-assisted development at real production scale, despite its higher upfront cost. strength: medium
Explicit premises:
  • Vibe coding has near-zero CapEx but hides compounding OpEx: token burn, maintenance tax, security remediation.
  • Agentic engineering has high CapEx (specs, tests, structured context) but low marginal OpEx because output is pretested and structurally sound.
  • Context engineering raises first-pass success rate, directly cutting the token cost of trial-and-error.
Implicit premises:
  • The hidden OpEx costs of vibe coding will actually be measured and attributed back to the original coding decision, rather than absorbed invisibly elsewhere in the organization (a different team doing cleanup months later).
  • The upfront CapEx investment will be recovered within a time horizon the organization cares about, rather than sunk into a system or team that gets reorganized or rewritten before the investment pays off.
Inferences:
  • Teams that lack cost telemetry or incident postmortems tying bugs/security issues back to code provenance will systematically underinvest in agentic engineering even where it is actually cheaper, because its savings never show up as a line item anyone owns.
Most agent failures, examined honestly, are configuration (harness) failures rather than model failures.
Explicit premises:
  • Public benchmarks show harness-only changes closing large capability gaps with no model change (Terminal Bench 2.0: outside Top 30 to Top 5; LangChain: +13.7 points via system prompt/tools/middleware alone).
  • The reflexive instinct when an agent errs is to blame the model, but the failure typically traces to a missing tool, vague rule, absent guardrail, or a noisy context window.
Implicit premises:
  • Gains measured in one controlled benchmark-competition setting generalize to the much larger, usually unmeasured population of everyday agent failures teams actually experience.
  • Teams have the observability needed to correctly diagnose a given failure as harness-caused versus model-caused — otherwise the claim 'most failures are configuration failures' is effectively unfalsifiable from inside an ordinary team without that instrumentation.

Narratives

  • Anthropic's engineering team reportedly had agent teams running on a multi-agent, MCP/A2A-coordinated architecture build a working C compiler in Rust over two weeks in early 2026, with humans setting direction and reviewing output but not writing the implementation.
    → Shows, rather than argues, that orchestrator-mode, multi-agent delegation is already viable for substantial real engineering work — grounding the abstract 'factory model' and 'orchestrator' propositions in a concrete, large-scope example.
  • Telling a CTO your team is 'vibe coding' their payment processing system will (and should) raise alarm bells; telling that same CTO the team practices 'agentic engineering' — AI implementation under human-designed constraints with test coverage ensuring correctness — is a fundamentally different conversation.
    → Dramatizes why the vibe-coding/agentic-engineering distinction is not academic: it implicitly supports the proposition that the distinction matters most at the point of organizational accountability (what you can defensibly tell a stakeholder), not just at the point of code quality.

Questions addressed

  • ✅ What distinguishes legitimate, production-grade AI-assisted development from risky ad-hoc prompting?
    The tests+evals verification criterion, embedded in the broader structure/verification/judgment spectrum.
  • ✅ Why do AI coding agents fail, and what should a team do about it?
    Attributed primarily to harness/configuration gaps rather than model limitations, prescribing deliberate harness engineering as the fix.
  • ⭕ Does AI actually make developers faster?
    Both a 25-39% productivity-gain figure and a 19%-slower METR finding are cited without reconciling when each applies — the paper leaves 'faster at what, for whom, verified how' open.
  • ⭕ Who inside an organization should bear the upfront CapEx of agentic engineering, and what happens if incentives don't reward that investment?

Gaps

  • illogicalThe paper cites both a 25-39% industry-survey productivity gain and METR's finding that experienced developers took 19% longer on certain AI-assisted tasks, in the same subsection, without reconciling when each applies — leaving the central 'does this make developers faster' question effectively answered by whichever statistic suits the surrounding argument at that point in the text.
    Read next: A study that segments AI productivity gains by task type, developer seniority, or codebase familiarity, rather than reporting a single aggregate figure.
  • incompleteThe CapEx/OpEx accounting (Figure 9) is a clean two-bucket schematic, but never addresses who inside an organization actually bears the upfront CapEx — often the platform/infra team or a specific engineer, who is rarely rewarded on the same cycle as the feature team that looks fast by vibe coding. The 'for organizations' advice ('treat it as an engineering investment') doesn't engage this incentive-misalignment risk at all.
    Read next: Team-topology or incentive-design material on how to attribute/reward harness investment separately from feature-delivery speed.
  • incompleteThe 'for organizations' section's team/org advice ('plan for hybrid teams of humans and agents... team structures all need to evolve') stops at a bullet point. It never addresses how on-call ownership, incident attribution, or performance review change when an agent authored the code under scrutiny — exactly the durable team-process questions an org the size of a telco would need answered before adopting this at scale.
    Read next: Material on agent-authored-code accountability: who is on-call for an agent's code, how incidents get attributed, how review credit/blame is assigned.
    closed byThe AI-Native SDLC playbook — Claxton's playbook is the detailed, stage-by-stage answer the gap asks for: it walks through exactly how team/org structure evolves — the product owner reviews intent.md and spec.md, the engineer reviews plan.md and the diff, the tech lead sets REVIEW.md policy and tunes it monthly, the release manager authorizes production deploys via a hook, and on-call shifts from reactive paging to triaging an autonomously-generated intent.md queue in Stage 6 — with governance embedded as hooks and managed settings rather than left as an unaddressed bullet point.
  • uninformedThe 'most agent failures are configuration failures' claim is drawn from two benchmark anecdotes where harness changes were deliberately isolated and measured in a competition setting; the paper never flags that ordinary teams lack this kind of controlled before/after measurement, so the claim may hold in benchmarks and be unverifiable — not merely under-evidenced, but structurally unfalsifiable — under typical team conditions without comparable instrumentation.
    Read next: extract-addy-osmani-quality-in-the-harness.json (same author's companion piece, which itself leaves open who builds/tests/maintains the harness's own checks on an ongoing basis).
