Lessons from building Claude Code: How we use skills

Claude · article · 2026-06-03 Reader 🖥️

Agent SkillsAgent Tool ManagementClaude CodeContext EngineeringHooksPlatform EngineeringProgressive Disclosure
Skills work best when treated as folders (not markdown snippets) that use progressive disclosure and hard-won gotchas rather than restating known behavior, are described for machine-triggered discovery rather than human summary, and are distributed and curated organically as they scale — with verification skills specifically deserving outsized investment because they have had the most measurable impact on Claude's output quality internally.

practical · lessons-learned engineering post / prescriptive taxonomy, written by a Claude Code team member (Thariq Shihipar) from internal usage at Anthropic (hundreds of skills in active use) — Structured as a practitioner field guide: an empirically-derived taxonomy (nine categories from cataloging Anthropic's own skills) followed by a list of discrete authoring tips, a distribution model, and a measurement mechanism. The categorization is grounded in real internal data; almost every individual tip is asserted from experience with no disclosed metric or before/after comparison.

Key terms

  • skill Agent Skills
    A folder of instructions, scripts, and resources an agent can discover, explore and manipulate — explicitly not 'just markdown files.'
  • Gotchas section
    A specific part of a skill built up over time from Claude's actual observed failure points ('this field is called @request_id in the gateway and trace_id in billing') — described as the highest-signal content in any skill.
  • progressive disclosure Progressive Disclosure
    Treating the entire skill filesystem — not just SKILL.md — as context engineering: pointing to references/, assets/, and scripts/ that Claude reads only when needed rather than front-loading everything.
  • railroading
    Writing skill instructions so specific/prescriptive that Claude loses the flexibility to adapt to the actual situation.
  • description field (for the model, not for humans)
    The SKILL.md frontmatter field Claude Code scans at session start across every installed skill to decide whether a skill applies to the current request — a trigger condition, not a summary.
  • on-demand hooks
    Hooks bundled inside a skill that activate only when that skill is invoked and only for the session's duration (e.g. /careful blocking rm -rf only when explicitly turned on) — as opposed to always-on hooks.
  • ${CLAUDE_PLUGIN_DATA}
    An environment variable giving a stable directory a skill can use to persist data (logs, JSON, SQLite) across invocations, enabling skills to 'remember' past runs.
  • plugin marketplace
    A Claude Code Plugin marketplace where skills are uploaded and users opt in to install them, contrasted with checking skills directly into a repo's ./.claude/skills.

Arguments

Verification skills deserve disproportionate engineering investment relative to other skill categories. strength: medium
Explicit premises:
  • Verification skills have had 'the most measurable impact on Claude's output quality' internally.
  • Techniques like recording a video of Claude's output or enforcing programmatic state assertions materially raise output reliability.
Implicit premises:
  • Whatever internal measurement produced this ranking generalizes across skill portfolios of different sizes and domains.
  • 'Measurable impact' reflects a real, if undisclosed, evaluation rather than an impression.
Inferences:
  • From a category-level observation about impact at Anthropic's scale to a general prescriptive claim ('worth having an engineer spend a week').
A skill's description field must be written as a trigger condition for machine discovery, not as a human-readable summary. strength: high
Explicit premises:
  • Claude Code builds a listing of every available skill with its description at session start.
  • This listing is what Claude scans to decide 'is there a skill for this request?'
Implicit premises:
  • A skill that is never triggered when relevant delivers zero value regardless of its internal content quality.
  • Authors default to writing descriptions as human-facing summaries unless told otherwise (the misconception the tip corrects).
Inferences:
  • Reasons directly from how the harness's discovery mechanism works to what content the field must therefore contain.

Narratives

  • The frontend-design skill was built by an Anthropic engineer iterating directly with customers on improving Claude's design taste, explicitly steering it away from classic AI-generated design tells like the Inter font and purple gradients.
    → Illustrates 'don't state the obvious' — a good skill pushes Claude out of its default behavior rather than restating what it already knows.
  • A standup-post skill keeps a standups.log with every post it has written, so the next run Claude reads its own history and can report only what changed since yesterday.
    → Illustrates the memory pattern for skills.
  • A data-science skill provides a library of functions to fetch data from an event source; Claude composes these on the fly to answer ad hoc questions like 'What happened on Tuesday?'
    → Illustrates 'store scripts and generate code' — giving Claude composable primitives instead of asking it to reconstruct boilerplate.
  • /careful blocks rm -rf, DROP TABLE, force-push and kubectl delete via a PreToolUse hook on Bash, but only when explicitly invoked — because having it always on 'would drive you insane'; /freeze blocks any Edit/Write outside a specific directory to stop Claude from 'fixing' unrelated code while debugging.
    → Illustrates on-demand, session-scoped hooks as opinionated but situational guardrails.
  • Concrete gotcha examples quoted verbatim: the subscriptions table is append-only so the correct row is the highest version not the most recent created_at; a field is @request_id in the API gateway but trace_id in the billing service though they're the same value; staging returns HTTP 200 even when a Stripe webhook didn't actually process, so payment_events must be checked for the real state.
    → Grounds the abstract 'gotchas section' advice in real, specific, non-obvious failure knowledge — the kind of tacit knowledge a skill is meant to externalize.

Questions addressed

  • ✅ What type of skills are worth making?
    The nine-category taxonomy derived from cataloging internal skills, used as a framework for identifying gaps in one's own skills library.
  • ✅ How do you structure a skill?
    A cluster of concrete tips: don't restate the obvious, build a gotchas section, use the filesystem for progressive disclosure, avoid railroading, think through setup/config, write model-facing descriptions, add memory, store scripts, use on-demand hooks.
  • ✅ When do you share skills with others?
    Check into the repo for small teams across few repos; move to an internal plugin marketplace as you scale, since every checked-in skill adds to model context.
  • ⭕ How do you know whether a skill is actually working (i.e. improving output, not just firing)?
    Only usage-frequency (PreToolUse invocation logging) is described; whether a triggered skill actually improved output quality, defect rate, or rework is never addressed.
  • ⭕ How do skills compose or depend on each other reliably?
    The post explicitly states this is 'not natively built into marketplaces or skills yet' — composition works only by informal by-name reference.
  • ⭕ Does the same skill behave identically across different agent harnesses (Claude Code vs. other coding agents)?
    Never addressed — the entire post is scoped to Claude Code's own configuration options (frontmatter, hooks, ${CLAUDE_PLUGIN_DATA}) with no discussion of portability.

Gaps

  • incompleteNo quantitative evidence is given anywhere in the piece. 'Measurable impact,' 'one of the most used extension points,' 'hundreds of them in active use,' and the nine-category catalog are all asserted without a single number, methodology note, or before/after comparison. A reader cannot tell whether 'measurable' means a rigorous eval or just an internal impression.
    Read next: Compare against extract-agent-skills-osmani#g1, which flags the identical evidentiary gap (26K GitHub stars as social proof, no defect-rate data) in a different skills-authoring post — this looks like a structural pattern across the whole skills-advocacy genre, not a one-off omission.
  • incompleteThe nine-category taxonomy is offered as a tool for 'identifying gaps in your own skills library,' but gives no guidance for the case it explicitly flags as a failure mode: a skill that legitimately needs to touch two categories (e.g. a CI/CD skill that also needs data-fetching context to decide on a rollout). The advice is only 'the best skills fit cleanly into one' — with no procedure for splitting or resolving a straddling skill.
    Read next: Would benefit from the kind of decision-procedure critique already applied to extract-20-loop-design-patterns#g1 (a pattern catalog without selection criteria) — the same 'taxonomy without a decision procedure' gap recurs here.
  • uninformedEvery practice described (organic bottom-up marketplace curation with no centralized gatekeeping team, checking skills into repos vs. a plugin marketplace, hundreds of skills in active use) is drawn from a single organization — Anthropic — with mature internal platform tooling, a large engineering org, and presumably existing CI/CD and review discipline. The post never acknowledges that this governance model may only work because of scale and maturity most readers' orgs (or a solo practitioner) don't have.
    Read next: Parallels the Google-centrism gap already flagged in extract-agent-skills-google-backed-ai-coding#g3 — worth reading both together as instances of a recurring 'FAANG-scale practice presented as universal' gap in the skills-advocacy corpus.
  • incompleteThe 'measuring skills' section describes only a PreToolUse usage-count hook — how often a skill fires — never whether the skill's output was actually good (defect rate, rework caused, correctness). Under-triggering is named as a problem to detect, but over-triggering / false-positive triggering (a skill's description matches too broadly and injects irrelevant context) is not discussed at all, despite the article's own earlier warning that every checked-in skill 'adds a little bit to the context of the model.'
    Read next: Cross-reference extract-agent-skills-osmani#g4 (cost of false enforcement / overhead-accuracy tradeoff) — a directly analogous gap about the cost side of skill triggering that this post also leaves open.
    closed byKafka App? There's a Skill for That — That gap complains the 'measuring skills' pattern (a PreToolUse usage-count hook) tracks only how often a skill fires, never whether its output was good. Etsy's telemetry pairs the invocation hook with a second, outcome-oriented signal — whether the invocation actually reached a completed pull request — moving one concrete step beyond raw usage-count toward outcome measurement, though it still stops short of defect-rate or rework tracking.
  • illogicalThe piece simultaneously warns against writing skill instructions that are 'too specific' ('avoid railroading Claude') and recommends filling the gotchas section with declarative always-do-X rules ('the subscriptions table is append-only, use the highest version'). Both railroading and a gotcha are stylistically the same speech act — a specific, prescriptive instruction — but the post treats one as a failure mode and the other as the highest-signal content, without ever explaining the line an author should use to tell them apart.
    Read next: No corpus doc yet addresses this tension directly; worth testing against the anti-rationalization-table pattern in extract-agent-skills-osmani#p7, which is closer to a principled distinction (a gotcha rebuts a specific rationalization the model has been observed to make, vs. a railroading instruction pre-empts a choice the model hasn't yet needed to make).
  • uninformedSkill-to-skill composition is acknowledged as working only informally today (reference another skill by name; 'the model will invoke them if they are installed'), but the post never discusses the failure modes this implies: what happens if the referenced skill isn't installed, or if two composed skills' instructions conflict. This leaves the same kind of router/dependency-reliability question open that extract-agent-skills-osmani#g2 raises about a different (custom, third-party) meta-skill router — except here there isn't even an explicit router to critique, just implicit trust that the model will sort it out.
    Read next: Read alongside extract-agent-skills-osmani#g2 and extract-skills-v1-1-wayfinder-flow-skills#p11 — the 'skills as a distribution unit for engineering practice' thesis these two other docs advance depends on composition actually being reliable, which this post concedes it isn't yet.
