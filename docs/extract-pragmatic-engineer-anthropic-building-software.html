How building software is changing at Anthropic

The Pragmatic Engineer · email · 2026-07-28 Reader 🖥️

Inside Anthropic, AI has not eliminated the traditional structure of software engineering (planning, PRDs, cross-team alignment, code review) so much as relocated where the effort and the bottleneck sit — from writing code to verifying it, and from one engineer working alone to fleets of parallel AI agents whose output is checked, merged, and increasingly re-reviewed by other AI, while every design assumption must now be re-tested at each new model generation.

theoretical · mixed — Journalistic reporting built from four on-the-record Anthropic interviews plus two extended case narratives (Claude Managed Agents, the Bun rewrite), used as evidence for a broader descriptive claim about where software-engineering practice is heading inside a leading AI lab. Expository/narrative in method, but the selection and framing serve an implicit argument — verification, not implementation, is now the bottleneck — more than a neutral survey.

Key terms

  • Claude Managed Agents Long-Running & Managed Agents
    Anthropic's pre-built harness product for production agents, runnable on Anthropic-managed cloud infrastructure, a customer's own infrastructure, or with any sandbox the customer chooses — an interface decoupling the agent 'brain,' the sandbox 'hands,' and the event-log 'session.'
  • Spiking
    Building a minimal, working end-to-end version of a system for a single real internal customer first (here: Claude Code's mobile backend), before generalizing the architecture for external customers — used to stress-test the design against real constraints rather than speculative ones.
  • Fanning out
    Jarred Sumner's term for distributing many independent chunks of work to many parallel Claude agent instances at once, with an orchestrator agent collecting suggestions and making the actual commits, rather than working with one agent sequentially.
  • Tokenmaxxing Token Throughput
    Gaming or inflating token-usage metrics that a token budget or leaderboard would otherwise incentivize; named here only to say Anthropic doesn't have this problem because there is no token budget or usage tracking to game.

Arguments

The rate-limiting step in AI-assisted software delivery at Anthropic has shifted from writing code to verifying it.
Explicit premises:
  • In the Bun rewrite, implementation took ~15% of total time versus ~85% on fixing/testing/verifying.
  • Thariq independently reports that most tokens across the org go to discovery, prototyping, and verification/testing rather than implementation.
  • Trust in merged code now has to come from automated review/scanning/fuzzing rather than a human reading every diff, because human reading no longer scales to the volume merged.
Implicit premises:
  • Current-generation coding agents can generate code fast enough that code-writing speed is no longer the binding constraint.
  • Verification tooling and practice have not sped up proportionally to code-generation speed, so the ratio of effort has inverted.
Inferences:
  • Organizations trying to capture AI coding productivity gains should prioritize investment in verification, testing, and review tooling over further investment in code-generation speed.
Manual, human-read code review and manual PR-merging are being displaced by chains of automated AI checks (code review, security scanning, fuzz testing), with either sampling/auditing by a human or a second, independent AI review as the final gate. strength: medium
Explicit premises:
  • Jarred frames the problem explicitly: 'how do you merge 100+ PRs a day... and make sure the code works?'
  • The Bun team already runs Claude code review, a dedicated Claude Security Scanner (11 runs on this rewrite), and fuzz testing as standard practice.
  • Jarred predicts a near-future auto-merge flow gated by a second, fresh-context AI's blast-radius judgment rather than a human's.
Implicit premises:
  • The volume of AI-generated code now merged exceeds what a human can responsibly read line-by-line at the rate it arrives.
  • The team judges the AI review/scanning/fuzzing layers to be trustworthy enough to substitute for some fraction of human reading.
Inferences:
  • If trust holds up under scale and incident rate, this pattern is likely to spread beyond one team/project inside Anthropic to become a default posture for high-throughput AI-assisted codebases generally.
Agent and product design assumptions must be treated as provisional and re-tested at every model upgrade rather than fixed once and left in place. strength: high
Explicit premises:
  • Anthropic deleted 80% of the Claude Code system prompt because the model got smarter and no longer needed that scaffolding.
  • The team reversed an earlier Markdown-by-default assumption in favor of HTML because current Claude models handle HTML well and it conveys richer structure.
Implicit premises:
  • Earlier engineering decisions were partly compensating for model limitations that later model generations removed.
  • Failing to re-test these assumptions means carrying dead-weight scaffolding (over-engineered prompts, suboptimal output formats) that no longer earns its cost.
Inferences:
  • Teams building AI products should schedule assumption-review as a recurring practice tied to each model release, not treat it as a one-time design decision.

Narratives

  • Before generalizing Claude Managed Agents for external customers, the Claude Platform team first built and shipped a narrower, real service for an internal customer (spinning up sandboxes and booting Claude Code for the mobile app), then re-architected around a 'brain' (agent) / 'hands' (sandboxes and tools) / 'session' (event log) split once that internal build surfaced hard problems — reliability when sandbox connections drop, and credential/access-control handling.
    → Supports the proposition that internal-customer-first, dogfooded prototyping surfaces integration problems earlier and more concretely than designing the generic/external-facing version up front.
  • Jarred Sumner's 11-day rewrite of Bun from Zig to Rust — 64 parallel agents, $165,000 in tokens, an orchestrator agent that alone made commits from other agents' suggestions to avoid conflicts, and Bun's own pre-existing, language-independent (TypeScript) test suite serving as the pass/fail oracle — is offered as proof of what became technically and economically feasible for one domain expert, where a full year of frozen feature/bugfix work would have been organizationally unacceptable for a small human team.
    → Illustrates the argument that verification (not implementation) is the real bottleneck, and that a pre-existing, trustworthy test suite is what makes a large AI-driven rewrite safe to attempt at all.
  • In Claude Managed Agents' credential architecture, all calls that need credentials go through a proxy holding a session token; the proxy alone fetches the actual credentials from a vault, and they are injected only at the egress boundary when the service is invoked — the agent, sandbox, and session itself never see them.
    → Shows a concrete security pattern (deterministic credential injection at the egress boundary, never inside the agent's own context) for keeping a powerful, autonomous agent from ever directly handling secrets it could leak or misuse.

Questions addressed

  • ✅ How do you let customers build production AI agents on infrastructure they trust (self-hosted or Anthropic-hosted) without every customer re-inventing 'harness infrastructure' from scratch?
    Claude Managed Agents: a brain/hands/session-decoupled architecture plus a vault-and-proxy credential model, arrived at via internal dogfooding before generalizing.
  • ✅ Can a large, mature codebase be rewritten to a safer language without an unacceptable freeze on bugfixes, security fixes, and features?
    Yes, for Bun specifically: a mechanical, minimal-behavioral-change rewrite validated against the existing test suite, executed via 64 parallel AI agents directed by the original codebase's creator, in 11 days.
  • ✅ How do you establish trust in code you personally can no longer read at the rate it is produced and merged?
    Layer automated, out-of-process verification (AI code review, a dedicated security scanner, fuzz testing) in place of exhaustive human reading, moving toward auto-merge gated by a second AI's judgment.
  • ⭕ Do the practices described (unlimited tokens, an original-creator-level domain expert directing the rewrite, an internal-lab audience willing to dogfood a new service) generalize to teams without Anthropic's token economics, bench depth, or internal customer base?
