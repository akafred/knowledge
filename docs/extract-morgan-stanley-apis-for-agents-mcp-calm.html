Presentation: APIs for Agents: Rethinking API Programs in the MCP Era

Jim Gough, Andreea Niculcea · rss · 2026-09-23 Reader 🖥️

Agent Governance (Internal)Agent-to-Agent ProtocolsAPI Products & SprawlEvolutionary Architecture & Fitness FunctionsMCP (Model Context Protocol)Platform EngineeringPolicy-as-Code
As agent protocols (MCP, then A2A, then whatever comes next) reshape how consumers reach enterprise systems, Morgan Stanley argues platforms should keep APIs as the stable, governed foundation and use Architecture-as-Code (CALM) to encode, version, and automatically enforce security/governance controls and deployment gates across every protocol adapter built on top — so the organization can adopt new interaction protocols quickly, and evolve already-deployed services at scale, without sacrificing safety or consistency.

practical · mixed — A practitioner conference talk arguing for a specific course of action (rethink your API program around Architecture-as-Code rather than around any single agent protocol), built mostly from five live demo narratives rather than abstract argument — expository framing around narrative/demonstrative evidence, with argumentative claims concentrated in the framing and summary sections.

Key terms

  • MCP (Model Context Protocol) MCP (Model Context Protocol)
    An open protocol for connecting LLM-based applications to tools and data, built around a discover/invoke/validate cycle. Its distinguishing primitives beyond a plain API are tools (structured operations), prompts (reusable parameterized instructions guiding behavior), and resources (documents/data brought into agent context) — but the protocol itself is 'dumb pipes': simple client-server interaction with security/governance only 'tending towards' first-class.
  • CALM Evolutionary Architecture & Fitness Functions
    FINOS's (financial open-source) 'Architecture as Code' project: a JSON-schema core model for expressing architecture as typed boxes and arrows, plus a CLI, a hosted registry/visual layer ('CALM Hub'), and AI integration (prompts/chat modes). It is the mechanism Morgan Stanley uses to make architecture, patterns, and controls machine-readable and enforceable.
  • Patterns
    Reusable architecture templates that encode a platform team's opinions; a developer instantiates a pattern into a specific 'architecture' and can only configure what the pattern exposes, not deviate from it. Morgan Stanley runs 110+ production deployments off three or four patterns.
  • Templates
    Handlebars-like generators that take an architecture (JSON) as input and emit deployable artifacts — Terraform, Helm charts, kube manifests, ConfigMaps.
  • Decorators
    A more recent CALM construct that pulls metadata (and other 'everything you want to know about an architecture') out of the core architecture JSON so the architecture document doesn't become one unmanageable blob.
  • Control requirement / configuration
    CALM's non-functional-requirements model: a 'control requirement' is an adjacent JSON schema specifying what must be true of a node or relationship (e.g., 'deny certain symbols'); a 'configuration' specifies how a specific architecture satisfies that requirement. Together they let controls be declared, attached to architecture elements, and automatically validated/enforced.
  • Deployment gates
    Automated checks run at each stage of promotion (pattern-conformance/CALM Hub lookup, CALM CLI schema+spectral validation, later smoke tests, entitlement checks, security review, drift detection, synthetic monitoring) that reject non-conforming architectures with specific, PR-style feedback before/after each environment.
  • Operational rollout
    Morgan Stanley's term for a platform-team-initiated, zero-downtime propagation of a new 'platform opinion' (e.g., a security patch, a resource-limit default) across all existing production deployments, driven off CALM Hub's record of what's actually deployed, without the owning teams having to act.
  • A2A (Agent-to-Agent) Agent-to-Agent Protocols
    A protocol/paradigm where independent systems discover each other ('is anything capable of doing this particular task?'), then exchange messages that build on tasks — explicitly contrasted with MCP's model of one thing calling tools on another. Jim compares it informally to Akka-style actor coordination.
  • Composite pattern
    A CALM pattern that references another pattern rather than duplicating it — e.g., the MCP architecture pattern references the Trades REST-service pattern as a system of its own, so the underlying API is described once and reused by every protocol adapter.

Arguments

Security and governance controls for agent-facing interactions should be implemented in the API (or API gateway) layer, not in protocol-specific adapters such as an MCP server.
Explicit premises:
  • New agent protocols keep emerging and any individual one is uncertain to persist ('who knows if MCP will be around at the end of this year?').
  • Protocol adapters are things you might 'build this stuff and maybe throw it away quite quickly.'
  • If a control is placed in the API and a new adapter (e.g., A2A) is added later, the control does not need to be re-implemented.
Implicit premises:
  • A control implemented once in a stable layer automatically protects every current and future adapter built on top of it, while a control implemented per-adapter must be duplicated for each new one.
  • The API is judged more durable ('stable contract layer') than any given protocol or adapter, so it is the correct place to anchor long-lived controls.
Inferences:
  • As agent protocols proliferate (MCP, A2A, and whatever comes next), the API/API-gateway layer becomes the highest-leverage place to invest governance engineering effort, and protocol-specific security work becomes comparatively low-leverage for controls that are protocol-agnostic.
Architecture-as-Code (CALM) lets a platform team push a new 'platform opinion' across all existing production deployments as a zero-downtime, developer-uninvolved 'operational rollout.' strength: high
Explicit premises:
  • CALM Hub holds the 'golden source' of versioned architectures — the platform knows what is actually deployed, where, at any time.
  • A new platform opinion is expressed as an updated CALM template; re-running CALM template plus deployment regenerates and reapplies the deployment artifacts.
  • Morgan Stanley runs hundreds of these rollouts per month and has patched 400+ gateways within an hour with no downtime for consumers.
Implicit premises:
  • Deployments are declarative and idempotent enough that centrally regenerating and reapplying them is safe to do without per-team human sign-off.
  • The platform team can be trusted with this unilateral push capability across 100+ teams' production services without that concentration itself becoming a single point of organizational or security failure.
Inferences:
  • This capability effectively centralizes emergency-response authority (e.g., for a Log4Shell-class event) in the platform team rather than in each service-owning team — a meaningful power and accountability shift the talk does not dwell on.
MCP's headline complexity is agent-side tool orchestration (selection, disambiguation, chaining, retries), not the protocol itself — so investment should go into gateways/control planes and tool governance rather than protocol-level tooling.
Explicit premises:
  • The protocol is described as 'just client-server interaction,' 'dumb pipes.'
  • Tool selection with one to five tools is easy; overlapping definitions and cost escalate 'very quickly' as the tool collection expands.
  • This has led to 'specialized gateways and control planes' that increasingly need to know business logic — something API gateways were traditionally told to avoid.
Implicit premises:
  • The number of tools exposed to any given agent will keep growing over time rather than staying small and curated.
  • English-language tool descriptions are inherently harder to disambiguate at scale than structured API contracts, so the disambiguation problem is structural, not a temporary tooling gap.
Inferences:
  • As MCP tool counts scale, organizations will need something like a 'second generation' of API gateway that understands business/semantic context — a genuinely new architectural layer, not just a configuration change to existing gateways.
Automated deployment gates that run identical conformance/security checks on every deployment let a platform scale trust without scaling human review effort per deployment. strength: medium
Explicit premises:
  • Gate 1 checks the architecture references an approved pattern via a CALM Hub lookup.
  • Gate 2 runs CALM CLI validation (JSON-schema + spectral) to catch missing placeholders and missing relationship controls.
  • Further gates (smoke tests, entitlement checks, security review, drift detection, synthetic monitoring) apply before and after production, with feedback surfaced early, PR-pipeline style.
Implicit premises:
  • Automatable, machine-checkable proxies (schema conformance, placeholder completeness, pattern reference) are a sufficiently faithful stand-in for the governance judgment a human reviewer would otherwise apply.
  • Developers will not routinely find ways to satisfy the letter of a gate while violating its intent — i.e., gates are not easily gamed.
Inferences:
  • Because gates are pattern-based, governance quality is bottlenecked by the quality and coverage of the patterns library itself — a flawed pattern propagates its flaws automatically and 'at scale' in exactly the way a good pattern propagates good defaults.

Narratives

  • Scenario 1 (Hello MCP): Claude is asked for 'top 10 Vodafone trades' and fails several tool calls — trying 'VOD', 'VOD.L', 'Vodafone' — before discovering an LSE ticker prefix and succeeding.
    → Shows, without arguing it abstractly, that natural-language-to-tool resolution is unreliable and 'chatty' even in a simple, well-scoped domain — supporting the claim that MCP's real complexity lives in orchestration, not the protocol (proposition 1, 13).
  • Scenario 2 (MCP Guardrails): after a denied-symbols control is added, Claude's repeated Vodafone query returns an error that the symbol is restricted and the user should contact compliance.
    → Dramatizes concrete, business-legible governance (a symbol you literally cannot query) in place of an abstract policy statement — supports proposition 4/6 and the API-vs-MCP-placement argument.
  • Scenario 3 (Deployment Gates): Andreea deliberately submits a 'rogue architecture' (wrong pattern reference, missing image-version placeholder, missing relationship controls) and shows the deployer rejecting it with specific JSON-schema and spectral errors, then submits a conforming version that passes.
    → Shows deployment gates functioning as designed — direct evidence for argument 4, while also implicitly testing (without fully resolving) whether gates can be gamed.
  • Scenario 4 (Platform Upgrades): a `kube describe` shows the MCP server pod has no resource limits; the platform team ships 'bundle v2'; re-running CALM template plus kubectl apply retrofits pod limits onto the already-running deployment without the owning team acting.
    → Concretely illustrates the 'operational rollout' mechanism (proposition 5, argument 2) — a small, low-stakes stand-in for the Log4Shell-class scenario described in prose just before it.
  • The two-years-to-two-weeks origin story: Jim recounts the first Morgan Stanley API taking about two years to ship, later about six months, now one to two weeks with CALM's automated security approvals — plus his boss's early skepticism about betting the program on an open-source project.
    → A compressed origin narrative implicitly arguing that Architecture-as-Code's payoff is measured in cycle time and organizational risk-taking, not just governance quality (proposition 8).
  • Scenario 5 (Future Proofing / A2A rebalancer): a Python script observes portfolio drift via a trades A2A 'agent card,' decides to rebalance, and books trades directly; Jim then critiques his own design choice in front of the audience ('if I was building it again this week, I'd probably design it architecturally a bit differently... have it be, this is what I've got, can you rebalance me?').
    → Shows the team learning, in public and inside their own reference implementation, that A2A's task-delegation paradigm differs from MCP's tool-call paradigm — supports proposition 9 while also functioning as an honest admission of incompleteness.

Questions addressed

  • ✅ What does MCP give us above what OpenAPI specifications already gave us?
    Technically, not much — the protocol is 'dumb pipes' and OpenAPI already described what APIs can do. The actual difference is social/adoption: business stakeholders get excited about MCP specs in a way nobody gets excited about an OpenAPI spec.
  • ✅ Where should governance/security controls for agent-facing interactions physically live — in the MCP server, or in the underlying API?
    In the API — demonstrated by deliberately placing the Vodafone-filtering guardrail in the MCP server first, then explaining it belongs in the API so it doesn't need re-adding for every future protocol adapter.
  • ✅ How do you evolve or patch a large fleet of already-deployed services without breaking teams' owned configuration or requiring their involvement?
    Via CALM Hub's golden-source record of what's deployed plus the 'operational rollout' mechanism: a new platform opinion is expressed as an updated template and reapplied centrally through the same gates as a normal deployment.
  • ⭕ How do agentic workloads change platform capacity planning and SLA modeling, which were built around request/response transactions?
    Named explicitly (new burdens: JSON-schema validation, pagination, output shaping, workflow management, retries, partial failures across chained tool calls) but no replacement capacity/SLA model is offered.
  • ⭕ When should you use MCP versus A2A?
    Partially: MCP models discrete tool calls, A2A models peer task delegation/discovery. But the team's own demo shows they are still finding the boundary — Jim says he would architect the same example differently if building it again.
  • ⭕ What happens when a deployment satisfies every automated gate (schema-valid, pattern-referenced) but is still architecturally wrong in a way the pattern didn't anticipate?
    Not addressed. The talk asserts later-stage 'security review' and 'drift detection' catch such cases but never shows or specifies the mechanism — an unacknowledged gap the speakers don't flag as open.

Gaps

  • incompleteThe talk's only concrete security example (the denied-symbols guardrail) is a business-logic/authorization control, not a protocol-level threat. It never engages MCP-specific attack surfaces — tool-description poisoning, malicious manifest redefinition, prompt injection via tool metadata — that the corpus has already mapped in detail elsewhere.
    Read next: extract-kale-securing-mcp-production-defense-in-depth, which decomposes MCP security into four separate layers (execution, management infrastructure, outbound trust, semantic integrity) this talk never touches.
  • incompleteThe claim that operational rollouts happen 'without touching the integrity of our user configurations' and scale to 400+ gateways patched within an hour is asserted with no discussion of failure modes: what happens when a platform-pushed change conflicts with a team's legitimate customization, or when the rollout itself introduces a regression simultaneously across 100+ services (the platform team's own push becoming the largest blast-radius event on the estate).
    Read next: Look for a follow-up talk or postmortem on a failed Morgan Stanley operational rollout, or compare against incident literature on centralized config-push failures (e.g., CrowdStrike-style single-push blast radius).
  • incompleteNo concrete replacement capacity/SLA model is offered for agentic workloads, despite explicitly naming the problem (dozens of chained, retried tool calls with partial failures replacing simple request/latency planning).
    Read next: Read for a proposed metric or model — e.g., something analogous to request-per-second but for tool-call chains, retries, and partial-failure budgets.
  • uninformedThe talk asserts deployment gates catch non-conformance but never addresses what happens when an architecture is gate-compliant yet still architecturally wrong in a way the pattern didn't anticipate — a limitation the corpus has already surfaced independently for agentic fitness functions (structural conformance checks prove an import exists or a schema parses, not that the change is architecturally sound).
    Read next: extract-agentic-fitness-functions-evolutionary-architecture, which explicitly separates deterministic structural gates from judgment-heavy architectural review.
  • incompleteThe Q&A culture-change question ('how did developer/architect culture change?') is answered only anecdotally, contrasting a 'configure a managed platform' path against a 'bootstrap then implement change' path, with no data on adoption resistance, teams that pushed back against losing configuration flexibility, or failed pattern rollouts.
    Read next: A platform-adoption case study or survey data on developer sentiment toward CALM-style mandated patterns, as a check on the talk's uniformly positive framing.
