How Do AI Agents Spend Your Money? Analyzing and Predicting Token Consumption in Agentic Coding Tasks

Longju Bai; Zhemin Huang; Xingyao Wang; Jiao Sun; Rada Mihalcea; Erik Brynjolfsson; Alex Pentland; Jiaxin Pei · pdf · 2026 source ↗ Reader 🖥️

Agent Cost AttributionPre-Execution Cost Prediction (Agent Self-Prediction)AI Unit EconomicsCoding AgentsContext Tax (Retry-Driven Cost Accumulation)EvalsToken Efficiency
Because agentic coding tasks burn tokens overwhelmingly through accumulating, cache-read input context rather than output generation -- and because that spend is highly variable, only weakly tied to human-perceived difficulty or to accuracy, and only weakly predictable by the executing agent itself before the task runs -- transparent upfront pricing for AI coding agents is not currently achievable, so consumption-based billing (with, at best, coarse-grained self-predicted budget alerts) is the only viable near-term model.

theoretical · argumentative — An empirical study (eight frontier LLMs x 500 SWE-bench-Verified problems x four runs) establishing descriptive facts about where and how agentic coding tasks spend tokens, then testing a specific capability claim (can agents predict their own cost pre-execution). The propositions are almost all 'X is true of agent token consumption,' but the paper explicitly frames its motivation and conclusion around a practical design question -- how agent pricing should work -- so the theoretical findings are marshalled in service of a practical argument about pricing policy (consumption-based billing remains necessary).

Key terms

  • Token consumption / token usage
    Used interchangeably (explicit footnote) to mean both input and output tokens used by an LLM agent across an entire multi-round trajectory, not per-call.
  • Agentic coding task
    A multi-round, tool-using, autonomous problem-solving process on a SWE-bench-style GitHub issue, carrying the full conversation history forward each round -- contrasted explicitly with 'code reasoning' (single-turn, no tools) and 'code chat' (multi-turn dialogue, no repository interaction).
  • Phase (Setup / Explore / Fix / Validate / Closeout)
    A five-way functional segmentation the authors impose on every trajectory's rounds, used purely for aggregation and reporting, not something the agent itself declares.
  • Cache read / cache creation / non-cached input
    The three sub-categories of input tokens under Anthropic-style explicit prompt caching: cache creation writes new context into the cache (priced at a chosen TTL, here the 5-minute rate); cache read retrieves previously-cached context at a steep discount; non-cached input is genuinely fresh, full-price prompt content.
  • Self-prediction
    The specific experimental design where the same coding agent used to execute a task is repurposed, via a different system prompt, to estimate its own future token cost before executing -- as opposed to training or querying a separate, external cost-prediction model.
  • Prediction overhead
    The ratio of the token/dollar cost spent producing a self-prediction to the actual cost of executing the task -- a cost-of-cost-estimation metric.

Arguments

Purely upfront, fixed-price billing for agentic coding products is not currently achievable, so consumption-based (usage-metered) pricing must remain the practical default. strength: medium
Explicit premises:
  • Token usage varies enormously across problems and across repeated runs of the same problem (up to 30x).
  • Frontier models can self-predict their own cost only with weak-to-moderate correlation and systematically underestimate real usage.
Implicit premises:
  • A viable pricing scheme must be either accurate-and-upfront or transparently usage-based -- there is no third option that is simultaneously fixed-price and reliably profitable/acceptable to users at this level of variance.
  • The executing agent's self-prediction, with its privileged access to the repository and its own planned tool calls, represents close to the best-case predictor available; if it cannot beat weak-to-moderate correlation, no cheaper external predictor is likely to do much better.
  • Providers and users would not accept a fixed price calibrated to a systematically-biased-low estimate (the underestimation problem), which is itself an argument against using current self-prediction directly as a pricing input.
Inferences:
  • If self-prediction is used operationally for 'budget alerts' as the paper suggests, and the bias is systematically toward underestimation, then alerts built on raw self-predicted numbers will themselves warn too late or too low unless a calibrated safety margin is added -- a practical risk the paper does not spell out even though its own data (Fig. 11) directly implies it.
Excess token spend on expensive-but-failed runs reflects redundant, unproductive agent exploration rather than genuinely deeper or more careful reasoning. strength: medium
Explicit premises:
  • Accuracy is non-monotonic in cost: it rises from minimum to low cost, then saturates or falls at higher cost quartiles.
  • The frequency of repeated file-view and file-modify actions on the same file rises sharply as cost quartile increases.
Implicit premises:
  • Repeated viewing/editing of the same file is a valid behavioral proxy for wasted, non-productive search, rather than, e.g., legitimate iterative refinement or necessary re-verification that a genuinely hard problem would require.
  • The correlation between high cost and repeated actions reflects agent behavior driving the cost, rather than both being downstream effects of the same underlying task ambiguity (a third-variable / confounding possibility the paper does not rule out).
Inferences:
  • If repetition itself (rather than an independent judgment of unnecessary repetition) is the operative signal, then a cheap real-time governor that caps repeated file actions per file could plausibly recover much of the wasted spend without hurting accuracy -- the paper stops short of proposing or testing this concrete mitigation, even though its own finding directly motivates it.

Narratives

  • The round-by-round case study of a single agent trajectory on task 'astropy astropy-7336' (Sec 5.3, Figure 9, Table 2): cache-read cost climbs as a smooth, steadily rising baseline while sharp cost spikes coincide with specific discrete actions (reading a new file, running tests, writing a final summary).
    → Makes the abstract phase-level finding ('cache reads dominate, spikes come from new-content actions') concrete and mechanistically legible -- it shows, rather than just states, that accumulated context is a slow-burning cost while the agent's own choices about what to newly ingest are what spike any given round.
  • The full worked in-context example embedded in the self-prediction system prompt (Appendix C.2): a synthetic SWE task about a version-comparison bug across a 50+ file codebase, walked through step by step (explore, read, test, estimate) and ending in a fully itemized JSON token-budget breakdown by phase.
    → Implicitly demonstrates the authors' own hypothesis about what 'good' self-prediction reasoning should look like -- systematic phase decomposition grounded in actual tool use -- and its presence/absence (tested in Appendix D) is used as evidence that demonstration improves calibration without eliminating the underlying underestimation bias.

Questions addressed

  • ✅ Where do AI coding agents spend their tokens?
    Overwhelmingly on accumulated, cache-read input context, concentrated in the Explore and Fix phases (about two-thirds of all rounds combined); output tokens matter mainly during Setup (planning) and parts of Fix/Validate/Closeout (code generation, summaries).
  • ✅ Which models are more token-efficient?
    GPT-5 and GPT-5.2 achieve strong accuracy at comparatively low token cost; Claude Sonnet-4/4.5 and Qwen3-Coder-480B operate in a higher-cost regime; Kimi-K2 is the clear outlier on both highest cost and lowest accuracy. This ranking is stable across shared success and shared failure task subsets, i.e., it is a property of the model, not the task mix.
  • ⭕ Can agents predict their own token consumption before executing a task?
    Partially: self-prediction captures coarse relative trends (weak-to-moderate correlation, up to 0.39) but is unreliable at the instance level and systematically underestimates real cost -- the authors explicitly conclude this remains 'a genuinely difficult task' and 'an open problem', not something they claim to have solved.
  • ⭕ If cost estimates are used operationally (budget alerts, tiered pricing, early-stop triggers), how should the systematic underestimation bias be handled so users aren't blindsided by bills exceeding the alert threshold?
    Not addressed. The paper documents the underestimation bias thoroughly (Fig. 11, Appendix D) but never proposes or evaluates a calibration correction, safety margin, or conformal-prediction-style interval that would make the biased point estimate usable for an actual budget-alert product.

Gaps

  • incompleteThe entire study uses a single agent harness (OpenHands) and a single benchmark (SWE-bench-Verified). The headline claim that token efficiency is 'an inherent characteristic of the model' (stable across shared success/failure subsets) is only shown to be task-invariant within one harness -- it is not shown to be harness-invariant. Whether Kimi-K2's outlier inefficiency is a property of Kimi-K2 itself, or of the specific way OpenHands' prompting/tool-calling interacts with Kimi-K2, is left untested; this is the mirror image of a gap already flagged against a different corpus benchmark (the Almedra GLM benchmark, which varies harness while holding the model fixed and never tests the reverse).
    Read next: Look for (or run) a study that benchmarks the same set of models across multiple harnesses (Claude Code, Cursor/Aider, OpenHands, a bare ReAct loop) on the same SWE-bench subset, to separate model-intrinsic token efficiency from harness-model interaction effects.
  • incomplete'Redundant' file view/edit actions are operationalized purely as repetition counts (viewing or modifying the same file more than once), with no independent check on whether any given repetition was actually unnecessary. A model re-reading a file because its context window evicted or compacted the earlier read is a mechanically different failure mode (context management / caching mechanics) from a model aimlessly re-exploring because it hasn't found the bug -- the paper's causal story ('redundant back-and-forth... reflecting inefficient search dynamics') doesn't distinguish these, even though they would call for entirely different fixes (better context retention vs. better search strategy).
    Read next: Look for work that instruments *why* an agent re-opens a file (context eviction vs. genuine re-exploration) rather than just counting repeats -- likely to intersect with this corpus's context-rot / context-engineering material.
  • incompleteGiven the well-documented, consistent underestimation bias in self-predicted token costs, the paper never tests the cheapest possible fix: applying a simple learned or fixed calibration multiplier to each model's raw self-estimate. Before concluding that 'making [self-prediction] reliable... remains an open problem,' a post-hoc calibration check would show how much of the practical problem a near-zero-cost correction already resolves.
    Read next: Read follow-up work on calibration of LLM confidence/self-estimates (Kadavath et al. on 'language models mostly know what they know', cited in this paper) for whether simple recalibration closes most of the underestimation gap.
  • incompleteThe entire cost-decomposition analysis (Sec 5, Fig. 8-9) fixes the Anthropic cache-creation rate at the 5-minute write tier for all reported figures. Cache-write TTL is a pricing-policy choice, not an inherent property of the task -- a 1-hour cache tier (which Anthropic also offers) would materially shift the reported cost split between cache-creation and cache-read, and potentially which phase looks most expensive. The paper presents its cost breakdown as if it reflects an inherent property of agentic coding tasks, when part of it is actually an artifact of the specific cache-tier choice made for the study.
    Read next: Re-run the same phase/round cost decomposition (Sec 5.2-5.3) under the longer 1-hour cache-write tier to see how much of the 'cache reads dominate' finding is robust to the pricing-tier choice versus an artifact of the 5-minute TTL selected here.
  • incompleteThe study is scoped entirely to coding tasks. Whether the central mechanistic finding -- that long-horizon, tool-using agents accumulate cost primarily through re-fed cache-read input context rather than output generation -- generalizes to non-coding long-horizon agents (research agents, browsing agents, ops/on-call agents) or is specific to code's characteristic re-read/re-edit access pattern on a small number of files is not discussed, despite the paper's own framing ('originally developed mainly for coding tasks... increasingly used in a wide range of tasks and domains beyond coding') explicitly raising and then dropping the question.
    Read next: Look for equivalent token-consumption breakdowns on non-coding agentic benchmarks (deep-research agents, browser-use agents, SRE/on-call agents) to test whether cache-read/input dominance is a coding-specific artifact or a general property of long-horizon tool use.
  • illogicalThe paper's own two headline variance figures disagree in magnitude but are presented as if they tell one consistent 'highly variable' story. The abstract and its most-quoted framing use 'up to 30x' as the run-to-run variance headline; but the paper's actual per-model statistic (Figure 2b: max/min cost ratio, averaged across all 500 instances) is roughly 2x -- 30x is a heavy-tail extremum from a distribution whose typical spread is an order of magnitude smaller. The pricing argument in the Discussion ('token usage... is highly variable and hard to predict') leans rhetorically on the more dramatic 30x figure without acknowledging that the typical case is far tamer, which matters directly for how alarming the pricing-unpredictability conclusion should actually be.
    Read next: Re-read Figure 2 and its caption carefully before citing this paper's variance claims elsewhere in the corpus; prefer the ~2x average-case figure over the 30x extremum when assessing how large a problem token-cost unpredictability actually is for typical (not tail-risk) pricing design.

Closes gaps elsewhere

  • The Almedra Token-Efficiency Benchmark, Updated For GLM 5.2 · g5 — The gap asks whether a fixed harness's efficiency ranking would hold across multiple underlying models. This paper runs the reverse but complementary experiment -- one fixed harness (OpenHands), eight different models -- and finds the model-level efficiency ranking is stable across shared-success and shared-failure task subsets, i.e. model identity is an independent driver of efficiency separate from task difficulty, partially answering the model-vs-harness disentanglement the gap calls for (though it does not itself vary harness, leaving the harness-invariance direction still open).
  • Agentics / Tech Things: Tokenmaxxing is dead, long live tokenmaxxing · g1 — This paper supplies general coding-task benchmark data on the accuracy-vs-cost relationship the gap calls for -- across 500 SWE-bench-Verified problems and 8 frontier models, accuracy peaks at intermediate cost and saturates/declines at the high end, countering an unqualified 'more tokens = better' generalization. The match is not exact: the gap's 'compounding correctness' claim is about iterative agent loops (restarting/re-prompting across iterations), while this paper's cost-quartile comparison is across four independent repeated runs of the same task, not accumulating loop iterations -- so this closes the 'does more spend reliably improve outcomes on general coding tasks' half of the gap without directly testing the loop-iteration mechanism itself.
