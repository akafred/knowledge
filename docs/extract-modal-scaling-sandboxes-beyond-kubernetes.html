Beyond Kubernetes at Modal: How to Scale 1 Million Concurrent Sandboxes in Seconds

Sergio De Simone · rss · 2026-09-23 Reader 🖥️

Post-Kubernetes / Decentralized Orchestration at ScaleSandboxing
Modal replaced Kubernetes-style centralized, strongly-consistent orchestration with a decentralized architecture — per-worker sources of truth, a parallel fleet of scheduling servers acting like load balancers, and a single Redis stream as the only shared bottleneck — to run over a million concurrent AI sandboxes, demonstrating that extreme-scale, millisecond-latency AI infrastructure requires walking away from, rather than extending, Kubernetes' coordination model.

theoretical · mixed — Primarily expository/explanatory: an InfoQ news piece reporting, in paraphrase and block quotes, how Modal's staff engineers diagnosed Kubernetes' scaling limits and redesigned around them. It carries practical design principles (horizontal-scalability-by-default, worker-as-source-of-truth) a reader could directly apply, and layers on argumentative commentary from two outside voices (Dowling, Jones) drawing broader interpretive conclusions the original Modal post doesn't itself make.

Key terms

  • sandbox Sandboxing
    An isolated, fast-starting execution environment for AI/agent-triggered code, engineered to be created and torn down at the scale of millions of concurrent instances and tens of thousands of creations per second.
  • horizontally scalable by default Post-Kubernetes / Decentralized Orchestration at Scale
    Modal's governing design constraint: any operation whose load is O(sandboxes) or O(nodes) must be able to scale out across independent servers rather than route through a single coordinating component.
  • source of truth (per worker)
    Each compute worker is authoritative for its own state, rather than a central durable store (like etcd) being authoritative for cluster-wide state.
  • scheduling as load balancing
    Replacing a single, serialized, globally-consistent scheduling decision with parallel scheduling servers that each independently pick a worker and negotiate placement via direct RPC, with the worker free to reject if it lacks capacity.
  • execution plane vs. coordination plane
    Alex Jones's distinction (quoted, not Modal's own term): the execution plane is fast, millisecond-latency, isolated code execution (what Modal built); the coordination plane is shared memory and overlapping security boundaries for multi-agent workflows (what Kubernetes-shaped systems remain suited for).

Arguments

Modal achieved horizontal scaling to millions of concurrent sandboxes because it replaced Kubernetes' centralized, strongly-consistent coordination model with a decentralized, load-balancing-style scheduling architecture. strength: high
Explicit premises:
  • Kubernetes' scheduling and etcd load both grow with node/pod count, and etcd is not natively shardable.
  • Modal made every O(sandboxes)/O(nodes) operation horizontally scalable by default.
  • Each worker holds its own state as source of truth instead of a central datastore.
  • A parallel fleet of scheduling servers replaces a single serialized scheduler.
  • Placement is negotiated via RPC accept/reject rather than centrally committed.
Implicit premises:
  • Centralized, strongly-consistent state stores (like etcd) are the fundamental scaling bottleneck of orchestration systems, not merely an implementation detail that could be tuned away.
  • A system where a placement request can be rejected and retried is an acceptable trade-off against the certainty of centrally-committed scheduling, at this scale.
  • The single remaining bottleneck — the Redis state-publishing stream — is qualitatively different from Kubernetes' etcd bottleneck, presumably because it sits in the observability/state-propagation path rather than the decision path, so contention there doesn't block progress the way etcd writes do.
Inferences:
  • Any orchestration system that keeps a single strongly-consistent store in the decision (not just observation) path will hit the same wall Modal diagnosed in Kubernetes, regardless of how well the store itself is tuned.
  • The architecture trades a small rate of failed/rejected placements (and retries) for horizontal scalability — implying a latency tail behind the reported median that the article never discloses.
The industry is heading toward decoupling the 'execution plane' (fast, isolated sandbox creation, which Modal built) from the 'coordination plane' (shared memory/security boundaries for multi-agent workflows, which remains Kubernetes-shaped systems' turf). strength: low
Explicit premises:
  • Modal succeeded by walking away from Kubernetes rather than trying to extend it.
  • Modal's achievement is described as 'the first credible signal that Kubernetes isn't adapting fast enough' for GenAI infrastructure needs.
Implicit premises:
  • Execution (isolation boundaries appearing in milliseconds) and coordination (shared state/security boundaries across multiple agents) are separable concerns that need not be solved by the same platform.
  • Kubernetes' architecture remains well-suited to the coordination plane's needs even though it is unsuited to the execution plane's needs — i.e., its limitations here are scale/latency-specific, not general.
Inferences:
  • If this decoupling holds, future AI infrastructure stacks will likely combine a Modal-like execution layer with a Kubernetes-like coordination layer via some integration boundary, rather than one platform replacing the other outright — a prediction the article surfaces but never spells out or tests.

Narratives

  • The single Redis stream that all workers publish state to is the system's one remaining bottleneck, empirically load-tested to remain viable past 100,000 workers.
    → Functions as a 'how far did they get' case example supporting the horizontal-scaling claim — it shows the architecture wasn't bottleneck-free, but that the residual bottleneck was pushed far past the point where Kubernetes' etcd-driven wall bites, lending credibility without overclaiming perfection.
  • The benchmark of creating 1 million sandboxes in under a minute with sub-0.5-second median startup time.
    → Serves as the article's headline proof-narrative, making the abstract architectural redesign concrete and quotable — the 'showing' that substitutes for a rigorous, independently-verified performance study.

Questions addressed

  • ✅ Why does Kubernetes-style container orchestration break down at million-sandbox / tens-of-thousands-of-creations-per-second scale?
    Centralized coordination and strongly consistent state (etcd) create load proportional to node/pod count, and etcd is not natively shardable, so high creation/churn rates hit a wall.
  • ⭕ How can a scheduling system remain correct and reliable without a centrally consistent view of cluster state?
  • ⭕ What are the failure modes and cost of the accept/reject RPC scheduling protocol — retry rates, latency tail, wasted scheduling-server attempts — at scale?
