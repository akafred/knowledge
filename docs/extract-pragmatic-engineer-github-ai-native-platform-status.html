Does GitHub still merit "top git platform for AI-native development" status?

The Pragmatic Engineer · email · 2026-04-03 source ↗ Reader 🖥️

Coding AgentsDeveloper Experience & FlowMulti-Agent OrchestrationStacked Diffs / Stacked Pull Requests
GitHub's reliability has collapsed to roughly one-nine availability under AI-coding-agent load, a startup (Pierre Computer) is already demonstrating the AI-native git infrastructure GitHub lacks, and the root cause isn't primarily a scaling problem but an organizational one — GitHub has had no CEO or North Star strategy since Microsoft folded it into its AI group, leaving it chasing Copilot revenue instead of building the agent-native platform its own infrastructure crisis shows it badly needs.

practical · mixed — A newsletter analysis piece (Gergely Orosz, re-sent as a free bonus issue; the paying-subscriber original ran about eight days earlier) mixing reported outage data, a quoted third-party technical analysis (Lori Hochstein), a quoted practitioner prescription (Mitchell Hashimoto), and the author's own diagnosis of GitHub's organizational dysfunction.

Key terms

  • North Star (for GitHub)
    Hashimoto's term for a single, measurable strategic anchor — specifically, being critical infrastructure for agentic code lifecycles — against which every GitHub product line and initiative should be re-evaluated, with the implication that most currently fail the test.
  • agent mailboxes
    Hashimoto's proposed first-class GitHub platform primitive for agent-to-agent and agent-to-human messaging, distinct from GitHub itself acting as an agent — GitHub should be 'a platform and not an agent itself.'
  • AI-native git platform
    The article's titular frame: a code-hosting platform architected from the ground up for the request volume, repo-creation rate, and traffic pattern AI coding agents generate — which the author argues GitHub currently is not, despite having an MCP server.

Arguments

GitHub's AI-era crisis is fundamentally an organizational/leadership failure (no CEO, internal Microsoft politics, no North Star) rather than a purely technical scaling problem. strength: medium
Explicit premises:
  • GitHub has lacked a CEO since Dohmke's departure, with Microsoft declining to backfill the role.
  • GitHub Copilot and GitHub itself are entangled in Microsoft-internal brand and organizational politics.
  • Without a CEO or clear direction, teams default to the locally safe choice (Copilot revenue) over structural fixes (reliability).
Implicit premises:
  • A reliability/infrastructure crisis of this severity at a company with Microsoft's resources is better explained by organizational dysfunction than by resource scarcity or an intractable technical problem.
  • The absence of a formal CEO is itself sufficient to produce directionless teams, rather than other explanations (e.g. a deliberate matrix/committee structure that could in principle still produce direction).
Inferences:
  • If the diagnosis is organizational, then technical fixes alone (more database capacity, better failover testing) will not resolve the underlying pattern of neglect — only a leadership/structural change would.
GitHub should narrow to a single agentic-infrastructure North Star and treat its current reliability crisis as proof it needs exactly the kind of AI-native platform Pierre Computer is already building. strength: low
Explicit premises:
  • Pierre Computer demonstrates throughput GitHub cannot currently match.
  • GitHub's own infrastructure is visibly failing under AI-agent load.
  • A platform doing many things poorly loses to a focused competitor doing one thing well.
Implicit premises:
  • Pierre's self-reported throughput numbers, though unverified and from a closed-beta product with few disclosed customers, are treated as a meaningful existence proof rather than requiring independent confirmation.
  • Being 'critical infrastructure for agentic code lifecycles' is treated as a viable, sufficiently large business in itself, distinct from (and not cannibalized by) the same AI agents' providers potentially building their own git-hosting layer.
Inferences:
  • If other coding-agent vendors (Anthropic, OpenAI, Cursor) also decide git hosting is strategically necessary infrastructure, GitHub's 'buy Pierre and refocus' path could face a land grab rather than a clear opportunity, a possibility the piece doesn't consider.

Narratives

  • Pierre Computer, founded by Jacob Thornton (former Coinbase/Medium/Twitter engineer and Bootstrap CSS creator), claims its Code.storage product sustained over 15,000 new repos per minute for three hours and created over 9 million repos in 30 days, versus GitHub's reported ~230 repos/minute as of October 2025.
    → Supports the proposition that an AI-native git alternative is already technically demonstrable, and functions as the concrete evidence behind Hashimoto's 'buy Pierre' prescription.
  • Mitchell Hashimoto (Ghostty founder, self-described heavy GitHub user) publishes an unsolicited four-point plan for what he would do if he ran GitHub, explicitly caveated as working from external information only.
    → Carries the article's clearest normative argument (North Star, kill Copilot, buy Pierre, re-evaluate product lines) through a credible practitioner's voice rather than the author's own assertion, lending it more weight while the caveat limits its evidentiary status.

Questions addressed

  • ✅ Does GitHub still deserve to be considered the top git platform for AI-native development?
    No, not currently — its reliability has collapsed under AI-agent load, it lacks AI-native infrastructure comparable to what a startup competitor already demonstrates, and it lacks the organizational focus (CEO, North Star) to fix this.
  • ✅ Why is GitHub's infrastructure failing under AI-agent load specifically, at a technical level?
    Hochstein's analysis: a pattern of saturation (databases scaling worse than stateless services) and failovers that expose configuration/telemetry gaps, worsened by GitHub's own ongoing system changes.
  • ✅ Why hasn't GitHub already built or acquired AI-native infrastructure, given the scale of the problem and Microsoft's resources?
    The author's diagnosis: no CEO, Microsoft-internal Copilot politics, and a resulting lack of a unifying strategic North Star, leaving teams to default to incremental Copilot revenue work instead.
  • ⭕ If multiple coding-agent vendors each decide they need their own AI-native git infrastructure, does that create one winnable market (as Hashimoto's 'buy Pierre' framing assumes) or a fragmented land grab GitHub can't simply out-focus its way into?
    Not addressed.

Gaps

  • uninformedPierre Computer's throughput claims are self-reported, from a closed-beta product with no disclosed customer details or independent benchmarking, yet are used as the article's central proof that an AI-native alternative to GitHub is already viable — the single biggest evidentiary load-bearing point in the piece rests on unverified vendor marketing.
    Read next: Look for independent benchmarks, customer case studies, or public incident history for Pierre/Code.storage once it exits closed beta, before treating the comparison as settled.
  • incompleteThe article asserts GitHub's stacked-diffs feature 'might be mostly obsolete' under AI agents without explaining the mechanism — whether agents reviewing/merging each other's work removes the human-review-scope problem stacked diffs exist to solve, or whether some other agent-specific dynamic is meant — leaving a specific, checkable claim unexamined just as it's introduced.
    Read next: Compare against extract-github-stacked-pull-requests, which frames stacked diffs entirely around reducing human reviewer cognitive load — if AI agents increasingly do first-pass review, that premise (and the obsolescence claim) can be tested directly; see also extract-latent-space-yegge-vibe-coding-manifesto's framing of merge collision as the still-unsolved 'wall' that stacked diffs/Graphite have NOT fully solved even for human-paced review, which is in tension with calling the whole workflow obsolete.
  • incompleteThe organizational diagnosis (no CEO, Copilot/Microsoft politics) is presented as the root cause of the reliability crisis, but the piece doesn't engage with the alternative or complementary technical explanations (tech debt, a concurrent datacenter-to-Azure migration, underestimated load growth) that this corpus's other, closely related GitHub-reliability extraction documents in detail — treating organizational and technical causes as alternatives rather than examining how they interact.
