No Vibes Allowed: Solving Hard Problems in Complex Codebases – Dex Horthy, HumanLayer

Agent HarnessAgile & XPAI SlopContext EngineeringContext Rot & Context LimitsHuman-in-the-LoopMulti-Agent OrchestrationOrganizational LegibilityProgressive DisclosureSpec-Driven Development
Solving hard problems in large, brownfield codebases with coding agents requires treating the context window itself as the scarce, team-visible resource to be engineered — through a research/plan/implement workflow with deliberate, frequent compaction — rather than either unreviewed 'vibes' or an over-literal, semantically diffused 'spec-driven development'; and the harder, still-unsolved problem is adapting team workflow, review practice, and culture to a world where most shipped code is AI-authored, not improving the agent tooling itself.

practical · argumentative — A conference talk arguing for a specific workflow (research/plan/implement with deliberate context compaction) over both unreviewed 'vibe coding' and an over-literal reading of 'spec-driven development.' Case-study narratives (a successful one-shot fix, a failed migration attempt) function as the evidence base; the talk closes with an explicitly organizational/cultural claim about adoption.

Key terms

  • slop / no slop
    Code (or documentation) that works or looks plausible but that nobody has reviewed, understood, or can vouch for; stale internal docs that have drifted from the real codebase are reframed as 'the amount of lies you can find' — slop in another form.
  • smart zone / dumb zone Context Rot & Context Limits
    Borrowed from Jeff Huntley's research: the smart zone is the portion of a context window (roughly up to ~40%, task- and model-dependent) within which the model still reasons and tool-calls well; beyond it, output quality degrades sharply (the dumb zone), and raw context-window size increases ('1M tokens!') do not fix this because they just add more dumb zone.
  • mental alignment
    The author's reframing of what code review is actually for: not primarily catching bugs, but keeping everyone on a team synchronized on how and why the codebase is changing. As AI increases code volume beyond what any individual (including a technical lead) can read, mental alignment shifts to happen via review of research/plan artifacts rather than line-by-line diff review.
  • compaction / intentional compaction
    Deliberately compressing the working state of a context window into a reviewable artifact (a markdown file with exact files, line numbers, and findings) before continuing or handing off to a fresh agent — contrasted with letting an agent silently drift into the dumb zone or compacting reactively only once things go wrong.
  • spec-driven development Spec-Driven Development
    A term the author argues is now broken by semantic diffusion (citing Fowler's 2006 coinage of that pattern, and the earlier fate of the word 'agent'): originally meaning something like 'treat the markdown spec as the source of truth and the code as assembly,' it now means anything from 'a more detailed prompt' to 'a product requirements document' to 'documentation for an open-source library,' making the label useless even though parts of the underlying practice (compressed intent, verifiable feedback loops) remain valuable under other names.

Arguments

Scarce human review attention in an AI-heavy SDLC should concentrate on research and plan artifacts, not on after-the-fact code-diff review. strength: medium
Explicit premises:
  • A bad research document or plan compounds into many more bad lines of code than a single bad line of code does.
  • No individual, including a technical lead, can read all the code an AI-accelerated team now ships.
  • The purpose of review is mental alignment — keeping the team synchronized on how and why the system changes — which plans/research can serve as well as, or better than, diffs.
Implicit premises:
  • Review value is proportional to leverage over downstream error propagation: catching a flaw earlier in the pipeline (research/plan) prevents more total bad output than catching it later (finished code).
  • A plan that is faithfully executed is a reliable proxy for the resulting code, so reviewing the plan substitutes for reviewing the diff without losing essential information.
Inferences:
  • This implies traditional PR-based line-by-line code review, calibrated for human-authored code volumes, is mismatched to an AI-accelerated SDLC and needs restructuring around the plan/research layer, not just faster or more automated diff review.
Multi-agent architectures built around role-played specialist sub-agents (front-end agent, QA agent, etc.) are a misuse of the sub-agent mechanism and likely underperform architectures built around context-boundary design. strength: medium
Explicit premises:
  • A sub-agent's structural value is forking a separate context window to isolate heavy search/reading work and return a compressed result.
  • Giving a sub-agent a job-title-like role does not grant it actual specialized expertise; its only resource is still the tokens in its own window.
Implicit premises:
  • Anthropomorphizing an agent's role is a category error that leads practitioners to optimize the wrong variable (perceived expertise) instead of the real one (context isolation and compression quality).
Inferences:
  • This directly implies that patterns elsewhere in current practice generalizing a 'coder/reviewer' two-agent pattern into larger teams of named-role specialist agents (security agent, compliance agent, frontend agent, backend agent) are building on the wrong mental model, even if they happen to also achieve some context isolation incidentally.

Narratives

  • The author and the CEO of BoundaryML record a podcast where the author attempts to one-shot a fix to BoundaryML's unfamiliar 300,000-line Rust codebase live; the resulting PR is approved by the company's own CTO, who initially doesn't realize it was done as a demonstration.
    → Shows (rather than merely asserts) that the research/plan/implement discipline can work in a genuinely unfamiliar, large, production brownfield codebase, validated by an independent, initially skeptical party.
  • In a follow-up, the author and the same collaborator spend 7 hours on a Saturday shipping ~35,000 lines of code to BAML; one resulting PR is merged a week later, with the collaborator estimating the work would normally take 1–2 weeks.
    → Extends the first story into a claim about not just correctness but velocity on complex work — though the author concedes some of the volume is codegen/golden-file updates, a caveat that qualifies the headline number.
  • The author and a different collaborator ('Blake') attempt to remove Hadoop dependencies from a large Java codebase and fail; after burning through generated research and plans, they abandon the AI-assisted approach and return to whiteboard-level first-principles analysis to find the real obstacles.
    → Serves as the talk's own counter-example, establishing the boundary of the method's claimed success and lending credibility to the success stories by showing the author is willing to report failure.
  • The film Memento (a man with no memory who must read his own tattoos to reconstruct who he is) is used as an analogy for an un-onboarded coding agent, which will fabricate context if not given it explicitly.
    → Makes vivid, via a well-known reference, why progressive/sharded onboarding context exists and what happens without it — and doubles as the origin of a term ('Memento agent') already used elsewhere in this corpus for the same phenomenon.

Questions addressed

  • ✅ Why do coding agents fail at complex tasks in large brownfield codebases, and can this be fixed without waiting for better models?
    Yes, via disciplined context engineering (research/plan/implement plus intentional compaction), demonstrated on a real unfamiliar codebase, with an explicitly named failure case marking the method's current limits.
  • ✅ Is 'spec-driven development' a coherent, well-defined practice?
    No — the term has semantically diffused into incoherence, though a version of the underlying discipline survives under the author's preferred framing (research/plan/implement, compaction, verifiable feedback loops).
  • ✅ What should sub-agents be used for?
    Context isolation and compression — explicitly not role specialization.
  • ⭕ How should teams adapt once the large majority of shipped code is AI-authored?
    Named as 'the hard part' and the central open organizational problem; the only guidance offered is that change must be top-down and cultural, with no concrete governance, incentive, or process redesign specified.
  • ⭕ What happens when the agent's actual implementation diverges from the plan that was reviewed for 'mental alignment'?
    Not addressed — the talk assumes the plan is a reliable enough proxy for the resulting code that reviewing it suffices.

Gaps

  • incompleteThe talk's two headline successes (the BAML one-shot fix, the 35,000-line 7-hour session) and its one named failure (the Hadoop removal) are all personal anecdotes from the author's own small team and network, delivered by a founder actively promoting his own company's product (HumanLayer, explicitly pitched at the talk's close). There is no systematic success-rate measurement, no control group, and no accounting of how much total effort — including the research and plans he says were 'thrown out' along the way — went into producing the showcased wins, leaving open whether the research/plan/implement discipline reliably generalizes beyond founder-level, highly motivated use.
    Read next: Look for independent, outcome-measured adoption of research/plan/implement-style workflows outside HumanLayer's own network and marketing, ideally with quantified success/failure rates across many tasks.
  • incompleteThe talk names a real organizational tension — senior engineers increasingly resenting the cleanup burden from AI-generated 'slop' shipped by less experienced colleagues — and asserts the fix 'needs to come from the top,' but offers no concrete governance model, incentive redesign, or review-process change beyond 'pick one tool and get some reps.' The specific senior/mid-level resentment dynamic it diagnoses is left entirely unaddressed by its own prescription.
    Read next: Look for team-scale-agent-platform or agent-governance treatments that go beyond individual tool adoption and address the specific cross-level resentment/burden-shifting dynamic this talk names but does not solve.
  • incompleteThe 'mental alignment via plan review' proposal replaces code review with plan review as the team's synchronization mechanism, but the talk never addresses what happens when the agent's actual tool-calling execution diverges from the reviewed plan mid-task — a known failure mode (agents drifting off-plan, over-editing, or rationalizing scope creep) documented elsewhere in this corpus. Plan review only delivers the claimed alignment benefit if plan and executed code reliably match, which this talk assumes rather than demonstrates.
    Read next: Compare against corpus treatments of agent scope drift and over-editing (e.g. scope-discipline material) to assess how often execution actually tracks an approved plan.
