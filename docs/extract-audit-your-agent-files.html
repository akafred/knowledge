Audit your Agent files

AddyOsmani.com · rss · 2026-08-27 source ↗ Reader 🖥️

Agent Config DecayAgent HarnessAgent MemoryAgent SkillsAgent Context Files (CLAUDE.md / AGENTS.md)HooksMCP (Model Context Protocol)Progressive Disclosure
Coding-agent configuration (CLAUDE.md/AGENTS.md, skills, hooks, MCP servers, memory) has a half-life because models and harnesses keep improving past what the rules were written for, so instead of accumulating it indefinitely or purging it wholesale, developers should audit it on a recurring cadence — using tools like /doctor, questioning whether each item's original reason still holds, and testing removal before committing to it.

practical · mixed — Argumentative-practical guide (you should audit your agent configuration on a cadence) built on cited empirical research and reinforced by personal-experience narrative and expository walkthroughs of tooling (/doctor vs claude doctor, skill loading budget).

Key terms

  • half-life (of agent configuration)
    The rate at which a written instruction's value decays as the underlying model and harness improve past the state that justified writing it — the file itself doesn't shrink on its own, so staleness accumulates silently.
  • /doctor
    The in-session Claude Code command that audits configuration: flags unused skills/MCP servers/plugins relative to context cost, slow hooks, duplicated CLAUDE.md guidance, and always-loaded content the agent could read from the repo instead. Reports findings before changing anything.
  • audit
    Not deletion by default — the act of asking, for each existing rule/skill/hook, whether the original reason it was added is still true, then testing removal before deciding.
  • listing budget
    The share of context window (defaulting to 1%) reserved for skill discovery — names and descriptions of all installed skills, always loaded; descriptions get shortened first when this budget is exceeded. Distinct from a skill's body, which loads only on invocation.
  • instruction value expires
    The author's summary lesson from the cited research: a written rule's usefulness is time-bound, not permanent, so files should be archived-and-reconsidered rather than only ever grown; hard constraints should move into tests/hooks/permissions rather than staying as prose.

Arguments

You should audit and selectively prune agent configuration on a recurring cadence, rather than either accumulating it indefinitely or deleting it wholesale on a fixed schedule. strength: medium
Explicit premises:
  • Bloat forms through a reactive ratchet cycle (error -> rule -> growth -> adherence drop) that nobody deliberately chooses.
  • Multiple independent empirical studies (100-repo config-smell study, 288-run context-file study, personalization study, source-vs-summary study, Anthropic's own 80% system-prompt cut) converge on the same finding: instruction value expires and unaudited accumulation carries real cost.
  • The dominant cost of clutter is confusion (discoverability, accidental triggering, forgotten ownership) rather than raw per-prompt token burn.
  • Removal is cheap to reverse when preceded by an archive step, which lowers the risk of testing a deletion.
Implicit premises:
  • A reason that justified adding an item can become invalid without anyone noticing, because nothing forces re-examination.
  • The 'delete everything periodically' guidance is hard to trust and act on precisely because there's no cheap, low-risk way to verify the deletion was safe — which the archive+test step is designed to supply.
  • Developers systematically underestimate how much configuration they've accumulated (the 250-skills anecdote, the author's own forgotten anti-slop skills) because nothing surfaces it without an explicit audit.
Inferences:
  • An organization's instinct to keep everything is a status-quo/loss-aversion bias rather than evidence the items are still earning their place.
  • Anthropic's willingness to cut 80%+ of its own system prompt with no measured internal-eval loss suggests professional harness builders don't trust their own accumulated instructions any more than individual developers should trust theirs.

Questions addressed

  • ✅ Do context files (AGENTS.md/CLAUDE.md) actually help coding agents succeed at tasks?
    No clear gain in correctness across 288 runs/17 tasks; they change workflow behavior (e.g. targeted testing) rather than success rate. Best used for things the model can't infer from code (expensive operations, generated files, unusual conventions), not generic advice or code summaries.
  • ✅ Do personalized skills (built from one developer's own history) outperform generic, community/pooled skills?
    No — a personal skill performed about the same as a borrowed one; a generic pooled skill did better overall. Personalization pays off mainly when a preference recurs across many similar tasks.
  • ✅ What does an installed-but-rarely-used skill actually cost you?
    Not primarily tokens (bodies load only on invocation; discovery uses a small budget). The real costs are degraded discoverability, accidental triggering/conflict, unowned maintenance, and loss of the owner's own mental model of the setup.
  • ⭕ How do you tell, at audit time, whether a surviving rule protects a real live constraint versus documenting a system that no longer exists?

Gaps

  • incompleteThe prescribed 'test without them' step is explicitly called a smoke test rather than proof, and the author notes agent outcomes vary even at low temperature — but no protocol is given for how many repeated runs, on how many representative tasks, would constitute sufficient evidence before committing to a deletion. Without that, 'test removal' risks becoming as arbitrary as the accretion it's meant to replace.
    Read next: Empirical work on how many repeated agent runs are needed to distinguish a real capability regression from run-to-run variance — akin to statistical power analysis applied to agentic evals.
  • incompleteThe entire audit workflow (archive, /doctor, test-removal, decide) is framed around a single developer's personal setup. It doesn't address shared/team CLAUDE.md, skills, or hooks where multiple developers depend on the same configuration — deleting something 'nobody remembers installing' carries social and coordination risk (who else relies on it? who approves the removal?) that a solo audit cadence doesn't surface.
    Read next: How team- or org-level agent configuration should be governed, versioned, and reviewed for pruning — ownership and change-control for shared CLAUDE.md/skill packs, analogous to platform-engineering governance of shared tooling.
  • uninformedThe cited personalization study used an LLM-based developer simulator rather than real developers (a caveat the author names), and the context-file study covers a specific harness/model pairing (Claude Code and Codex). The article doesn't discuss whether either finding would transfer to other harnesses, to less tool-augmented agents, or to real (non-simulated) developer populations, despite building a general prescription on top of both.
    Read next: Follow-up studies replicating the personalization and context-file findings with real developer cohorts and across multiple harnesses, to test whether the 'generic beats personal' and 'context files don't move correctness' results are harness-specific artifacts or general findings.
