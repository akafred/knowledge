Cloudflare Cuts 100 TB of Memory from 1.1.1.1 DNS Cache

Leela Kumili · rss · 2026-09-23 Reader 🖥️

Distributed Caching & InvalidationInfrastructure EfficiencyRust (Programming Language)
Cloudflare cut its DNS cache's per-entry memory footprint by 56% and freed ~100 TB of fleet-wide working-set memory, without sacrificing (and while improving) throughput and latency, by collapsing the in-memory representation of cache entries toward DNS wire format instead of a typed, allocation-heavy Rust structure.

theoretical · expository — News reporting on an engineering result: the author explains what Cloudflare changed and why it worked (understanding), not arguing that the reader should take a specific action. The implicit practical payload — 'represent cache data closer to wire format, avoid boxing enum variants' — is carried by the reporting rather than argued for directly.

Key terms

  • Big Pineapple
    Cloudflare's internal name for its DNS platform/resolver software that backs the 1.1.1.1 public resolver and stores 250B+ cache entries fleet-wide.
  • per-entry footprint
    The memory cost, in bytes, of a single DNS cache entry as measured in Cloudflare's benchmarks (953 bytes before, 420 bytes after) — the primary efficiency metric the article tracks across both microbenchmark and production numbers.
  • working-set memory
    The resident memory actively touched by running DNS cache processes across Cloudflare's fleet — what the ~100 TB freed refers to, as distinct from cache capacity or disk/storage.
  • wire format
    DNS's on-the-wire binary encoding, which Cloudflare's final design uses directly as the in-memory cache storage representation (a contiguous byte buffer), collapsing what would otherwise be two representations (in-memory typed structure, on-the-wire bytes) into one.
  • cache/memory locality
    How close together in memory related pieces of a cache entry sit, and how that affects CPU cache-hit behavior; used to explain why boxing larger Rust enum variants — despite shrinking stack size — was a net loss (separate heap allocations reduce locality) and why the final contiguous-buffer design is a net win.

Arguments

Storing DNS cache records as a contiguous byte buffer in (near-)wire format, rather than as parsed/typed Rust structures with per-field allocations, is the superior in-memory representation for a high-volume DNS cache. strength: high
Explicit premises:
  • Boxing enum variants added allocation overhead and reduced memory locality.
  • The wire-format buffer design removes enum and per-record allocation overhead and improves locality.
  • Frequently used record types can be copied directly into responses from the buffer.
  • Benchmarked per-entry footprint fell 56% and production p99/p90 memory fell substantially after adopting this design.
Implicit premises:
  • CPU cache locality and allocation count dominate the cost model at Cloudflare's request volume more than the convenience of a typed, idiomatic in-memory structure.
  • The parsing cost paid when a record actually needs decomposition (name compression) is rare or cheap enough not to offset the storage savings.
  • DNS wire format retains enough information to serve as an internal representation without losing data needed elsewhere in the resolver pipeline.
Inferences:
  • If wire-format-as-storage is a generally superior strategy for read-heavy, allocation-sensitive caches, similar representation-collapsing techniques could apply to other network-protocol caches (e.g. HTTP header caches, gRPC message caches) — the article never generalizes beyond DNS to test this.
The specific memory-representation techniques Cloudflare applied — especially avoiding boxed enum variants in favor of inline/contiguous storage — are not universally good practice; they are contingent on operating at very high request volume. strength: low
Explicit premises:
  • "A lot of these memory tricks only pay off once you're at Cloudflare's request volume; at a smaller scale the extra indirection from boxing variants can actually hurt cache locality more than it helps." (Reddit commenter)
Implicit premises:
  • The tradeoff between allocation overhead and access-pattern-driven locality benefits is a function of request volume, working-set size, or cache size.
  • Below some threshold, unboxed inline representations may not repay the fixed complexity/engineering cost of implementing them.
Inferences:
  • The article never identifies where that scale threshold approximately sits, or which proxy metric (QPS, entries per instance, cache size) determines which side of the tradeoff a given system falls on — so the caveat, while directionally plausible, gives readers no actionable rule.

Narratives

  • The five successive representation changes told as a sequence: Vec/String → Box<[T]>/Box<str>; combined record lists with compact offsets; bitflags for Booleans; owner-name omission reconstructed from the cache key; and the enum-boxing attempt that had to be abandoned before arriving at the final contiguous-buffer design.
    → Implicitly supports the proposition that large aggregate memory wins at scale come from compounding many small, individually modest representation changes — including a documented dead end (enum boxing) — rather than from one big rewrite.
  • Sebastiaan Neuteboom's LinkedIn quote: "It's not every day you get to save 100 terabytes of memory."
    → Provides human-scale, informal validation of an otherwise abstract fleet-wide number, functioning as social proof that the result is genuinely remarkable within the engineering team itself.
  • The Reddit commenter's counter-anecdote about indirection only paying off at Cloudflare's scale.
    → Functions as an implicit cautionary narrative — 'engineering wisdom from a hyperscaler doesn't transfer without checking your own scale' — supporting a gap/caveat rather than the article's main thesis, and left unresolved.

Questions addressed

  • ✅ Can a DNS cache's per-entry memory footprint be reduced substantially without sacrificing throughput or latency?
    Yes — footprint fell 56%, while insertion throughput rose 43% and lookup latency fell 19% simultaneously, contradicting a simple space/time tradeoff expectation.
  • ✅ Where should DNS record data live in memory — as typed Rust structures (enums, Vec, String) or as a raw wire-format byte buffer?
    The wire-format contiguous buffer wins for this workload, arrived at only after typed representations — including boxed enums — proved worse on allocation overhead and locality.
  • ⭕ At what scale, request volume, or cache size does this representation strategy stop paying off, or start hurting performance instead?
  • ⭕ What does the wire-format-as-storage design cost in code complexity, maintainability, or safety, relative to the typed Rust structures it replaced?

Gaps

  • incompleteNo accounting for the engineering/maintenance cost of moving from typed Rust structures (enums, Vec, String) to a raw contiguous byte buffer parsed manually against DNS wire format. Manual buffer parsing is exactly the kind of code where Rust's typed guarantees (exhaustive matching, borrow-checked ownership) normally do the most work; collapsing to a byte buffer likely trades some of that safety net for hand-written bounds-checking or `unsafe` code, which the article never measures or even mentions.

This leaves practitioners at smaller companies unable to judge whether these specific lessons (avoid boxing enum variants, prefer inline storage) apply to their own systems.

Box<[T]>/Box<str> and a contiguous wire-format buffer are naturally fixed-size once allocated; the article doesn't address fragmentation behavior of the allocator managing many differently-sized buffers over the cache's lifetime — a concern that Unbound/PowerDNS's slab-based allocation specifically targets, and which the article's own comparison paragraph raises but doesn't follow through on.
