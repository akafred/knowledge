The Interfaces Are Arriving

Tommy Tran · rss · 2026-09-11 source ↗ Reader 🖥️

Agent Governance (Internal)Agent-to-Agent ProtocolsAgent Tool ManagementMCP (Model Context Protocol)Cross-Vendor Protocol StandardizationSoftware Supply-Chain Security
Because rival AI vendors are now donating and independently implementing shared interoperability protocols (MCP, A2A) under neutral, foundation-based governance — repeating the historical pattern of Ethernet and the Language Server Protocol — engineering organizations should treat these protocols as durable, ownable infrastructure worth building on now, even though the standards themselves remain young and cannot resolve the deeper semantic-trust and cross-hop-delegation problems that lie beneath them.

practical · mixed — Opens as exposition (what MCP/A2A are, adoption figures, spec mechanics) and argument (why cross-vendor, neutrally-governed standardization is the year's most consequential AI news), then turns explicitly practical: it ends in a set of engineering-org recommendations (own the integration as an asset, build a security seam, curate a registry, version-pin, participate in standards bodies).

Key terms

  • Interfaces (the arriving ones)
    Standardized, neutrally governed, cross-vendor protocol contracts — MCP, A2A, and the emerging AGENTS.md/OTel conventions — that let AI systems and their tools/other agents interoperate without custom, one-off integration glue.
  • Semantic gap
    The residual space between what a schema formally declares (a tool's argument shape) and what the tool actually means or when it is appropriate to use — something a JSON Schema cannot capture and a model must still interpret.
  • Trust gap
    The further gap beyond the semantic one: a protocol (or a signed Agent Card) can carry a claim and bind it to an identity, but an organization still needs an independent basis for deciding whether that identity, publisher, or code deserves authority — the protocol transports the decision, it does not make it.
  • Neutral governance Cross-Vendor Protocol Standardization
    Standards stewardship by a directed fund under a foundation (Linux Foundation) with multiple, competing corporate cofounders and backers, as distinct from a single vendor unilaterally controlling a spec.
  • Behavioral annotations
    MCP's declared tool metadata (read-only, destructive, idempotent, open-world) that gives a host a policy vocabulary, but which the spec itself requires treating as untrusted unless attested by a trusted server.

Arguments

Engineering teams should treat internal MCP servers as durable, owned infrastructure assets — with owners, versions, tests, and upgrade policies — rather than as one-off integration glue. strength: medium
Explicit premises:
  • Standard interfaces change the economics of integration work that used to be custom glue for every agent/tool/host pairing.
  • Models and hosts will keep changing while the interface contract, server implementation, schemas, and authorization wiring can endure.
  • Language servers followed exactly this path: editors came and went around a stable interface.
Implicit premises:
  • Investment in an integration layer only pays off if that layer's useful life outlasts the churn of the systems built on top of it — the LSP analogy is being generalized into a lawlike expectation, not treated as a one-off historical coincidence.
  • Formal organizational ownership (named owners, versioning, tests, upgrade policy) is what actually captures durability once protocol stability exists — protocol maturity alone is not assumed sufficient.
Inferences:
  • If the interface layer is genuinely durable, the natural organizational response is to fund a small platform team that owns the shared MCP server surface the way platform-engineering teams already own other paved-road infrastructure — the essay's 'owners, versions, tests' language implies this without stating it.
Shared protocols cannot substitute for an organization's own judgment about which identities and code deserve authority — they only carry that judgment through a system once it has been made elsewhere. strength: high
Explicit premises:
  • A schema captures shape, not meaning; a model must still interpret a tool's free-form description.
  • A digital signature on an Agent Card only ties a statement to an identity, not to that identity's trustworthiness.
Implicit premises:
  • Trust is fundamentally a human/organizational judgment about reputation, incentives, and track record — not a property that can be computed from richer protocol metadata, no matter how much metadata a future spec revision adds.
  • Interoperability and security are separable axes: a protocol can be maximally interoperable while faithfully carrying claims from an untrustworthy or malicious party.
Inferences:
  • Organizations that treat 'the spec handles it' as sufficient — skipping their own vetting, allowlisting, or curation layer — remain exposed no matter how mature MCP or A2A become; the essay implies but never states this general principle, gesturing at it only through specific recommendations (allowlist, curated catalog).

Narratives

  • The recurring historical comparison to Ethernet ('networking became an ecosystem when machines could agree on interfaces') and the Language Server Protocol ('language servers replaced a separate integration for every editor-language pair with one interface on each side'), invoked at both the opening and the closing of the piece.
    → Implicitly carries the central inductive leap — that MCP/A2A will follow the same maturation arc from contested multiplicity to durable, competitor-agnostic infrastructure — without the author having to argue for that generalization from first principles. The historical parallel does the persuasive work that direct argument about MCP/A2A's own future cannot yet do, since that future hasn't happened.

Questions addressed

  • ✅ Is the MCP/A2A donation to neutral foundations a substantive shift or corporate PR?
    Substantive: the author's test is independent cross-vendor implementation, and cites first-class MCP support across ChatGPT, Claude, Cursor, Gemini, Copilot, and VS Code, plus 150+ organizations backing A2A, as satisfying that test.
  • ✅ Can a shared protocol substitute for an organization's own security/trust judgment about the tools and agents it connects to?
    No — explicitly resolved via the semantic-gap-to-trust-gap argument: the protocol carries a trust decision through a system, it does not make that decision for the organization.
  • ⭕ How should authority narrow (attenuate) as a request passes through a multi-hop chain of agents and tools?
    Explicitly left open: 'No common mechanism defines how those rights should attenuate across an arbitrary chain. Platforms currently solve this locally or leave too much authority in place.'
  • ✅ Should engineering teams invest in this infrastructure now, given how young and unstable it admittedly is (five protocol revisions in under two years, registry in preview, telemetry conventions unstable)?
    Yes, but hedged: build now with version-pinning, thin internal adapters behind the protocol code, and a budgeted expectation of migration — invest in the interface pattern, not in any single current revision.
  • ⭕ What happens to the engineering organizations that do not (or cannot) participate in the Agentic AI Foundation / A2A standards process while 'the rules written now... become assumptions embedded in future products'?

Gaps

  • incompleteThe closing wager — 'the interfaces are likely to last' — is stated with confidence but the essay never specifies what would falsify it: a major founding vendor forking MCP, a rival protocol displacing it, or one founding company (e.g. Anthropic, as MCP's originator and steward) accumulating outsized influence inside the supposedly neutral Agentic AI Foundation. Without a falsification condition, the durability claim is unfalsifiable as stated.
    Read next: Track the Agentic AI Foundation's actual governance structure and voting/veto rights among Anthropic, Block, OpenAI, and the supporting companies (Google, Microsoft, AWS, Cloudflare, Bloomberg) over the next 1-2 years, and watch for defections or competing forks.
  • incompleteHaving correctly identified that no common mechanism yet defines how authority should attenuate across a multi-hop agent-to-agent-to-tool chain, the essay stops there rather than surveying the candidate approaches already being tried elsewhere — RFC 8693 token exchange for delegated actor chains, or connection-level enterprise-managed authorization (EMA) anchored in an identity provider — leaving the reader without a sense of how close or far a solution actually is, or which approach the author thinks is most promising.

Quantity of adoption and quality/safety of that adoption are treated as moving together; the evidence that they diverge sharply is not addressed.
