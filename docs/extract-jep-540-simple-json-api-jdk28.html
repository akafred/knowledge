JEP 540 Proposed to Target JDK 28 with a Simple JSON API

A N M Bazlur Rahman · rss · 2026-08-17 source ↗ Reader 🖥️

Changeability & OptionalityModularity & CouplingSoftware Design FundamentalsWorse Is Better
JEP 540 proposes a deliberately narrow, strict, immutable, dependency-free JSON API for the JDK standard library — trading the completeness of libraries like Jackson and Gson for interface simplicity — and ships it as an incubating module so the community can pressure-test its navigation, exception, conversion and construction ergonomics before the design is finalized.

theoretical · expository — News reporting on a JDK Enhancement Proposal's design and status. It is mostly explanatory (what the API does, how it is shaped) rather than argumentative, but it carries an implicit design-philosophy argument: a JDK-provided JSON API should trade completeness for narrow scope, strictness and zero dependency, with incubation as the mechanism for testing that bet.

Key terms

  • Incubator module
    A JDK API distribution status (here jdk.incubator.json) that ships the feature for real use and feedback while explicitly reserving the right to change it incompatibly or remove it before it becomes a permanent, guaranteed part of the platform.
  • Strictness
    The parser's refusal to accept any deviation from RFC 8259 — no comments, no trailing commas, no other syntax extensions, and rejection of duplicate object-member names — with no lenient/permissive mode offered as an alternative.
  • tryGet vs. tryValue
    Two distinct optional-access methods that let the API distinguish 'this member is absent' from 'this member is present and explicitly JSON null': tryGet() returns an Optional containing JsonNull for an explicit null, while tryValue() returns an empty Optional for JsonNull.

Arguments

A minimal, strict, immutable, dependency-free JSON API belongs in the JDK standard library, even alongside mature third-party alternatives.
Explicit premises:
  • Common JSON tasks (config reading, REST response inspection, small payload generation) don't require data binding or streaming.
  • Direct access methods on the sealed JsonValue hierarchy avoid repeated casting during traversal.
  • Incubator-module status lets the design change or be withdrawn based on feedback, lowering the cost of getting details wrong up front.
Implicit premises:
  • The value of eliminating an external dependency for simple JSON work outweighs the cost of building and maintaining a second, narrower JSON implementation alongside already-popular libraries.
  • Strict RFC 8259 conformance (no comments, no trailing commas, no duplicate keys) is worth its ergonomic and interoperability cost, because a standard-library API should model the specification rather than the permissive JSON most real-world documents actually use.
Inferences:
  • If JEP 540 reaches Target and ships, some application code doing simple JSON work could drop Jackson or Gson as a compile-time dependency, shrinking dependency trees for that use case.
  • Because the parser rejects duplicate keys and offers no lenient mode, migrating existing code from a permissive third-party parser to this API could newly fail on real-world JSON documents that were previously accepted.

Questions addressed

  • ✅ Should the JDK ship a built-in JSON API when mature third-party libraries (Jackson, Gson) already exist?
    Yes, for a deliberately narrow slice of common tasks — not as a general replacement for those libraries.
  • ✅ How should a minimal JSON API expose typed access without excessive casting?
    A sealed JsonValue hierarchy with access/conversion methods declared directly on the interface, plus pattern-matching switches over the sealed subinterfaces.
  • ✅ How should the API distinguish a missing object member from one explicitly set to JSON null?
    tryGet() returns Optional<JsonValue> containing JsonNull for an explicit null; tryValue() returns an empty Optional for JsonNull, and both are empty when the member is absent versus present respectively.
  • ⭕ Is rejecting duplicate JSON object-member names the right strictness call given RFC 8259 only recommends (not requires) uniqueness?
    The article names it as an interoperability risk but does not resolve whether the tradeoff is correct.
  • ⭕ Why did the JDK's earlier attempt at a JSON API (JEP 198, 2014) never get delivered, and does JEP 540 avoid whatever caused that?
    The article mentions JEP 198 existed and was broader in scope, but does not explain why it stalled or whether JEP 540's narrower design specifically addresses that failure.

Gaps

  • incompleteConstruction ergonomics (wrapping every Java primitive in a factory call before it can enter a JSON object or array) is flagged as 'one likely area for feedback,' but the article never explores what alternative designs — builder APIs, varargs helpers, or implicit boxing conveniences used by other JSON libraries — might resolve it, or why the JEP authors chose explicit factories over those alternatives in the first place.
