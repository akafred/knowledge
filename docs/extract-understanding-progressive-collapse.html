Presentation: Understanding Progressive Collapse: How To Avoid A Cascading Failure

Sam Newman · rss · 2026-08-19 source ↗ Reader 🖥️

Cascading Failure & System Resilience PatternsIronies of AutomationModularity & CouplingSRE & Incident Response
Progressive collapse — civil engineering's term for a small, localized failure cascading into a system-wide catastrophe — is a productive lens for distributed-systems resilience: mitigation requires reducing hazards, strengthening components, and reducing interconnection together, but each mitigation (redundancy, multi-region, circuit breakers) carries real cost and complexity and can itself introduce new interconnection and new failure modes, so teams must apply these techniques as conscious, business-contextualized trade-offs rather than default best practice.

practical · mixed — Primarily practical/argumentative: Newman argues software teams should adopt a three-part mitigation framework, applied consciously and case-by-case rather than by rote. But the talk is delivered mostly through narrative case studies (Ronan Point, the AWS us-east-1 outage, his own 'Sauron' incident) that carry the argument, plus an expository segment translating a civil-engineering NIST report into a software framework.

Key terms

  • Progressive collapse Cascading Failure & System Resilience Patterns
    A situation where a small failure, innocuous in isolation, cascades into a significantly larger collapse of the wider system — borrowed directly from civil engineering (Ronan Point) and applied to distributed digital systems.
  • Root cause
    A misleadingly singular framing Newman argues against; he insists on 'root causes' (plural) and treats the search for one blameable trigger as an oversimplification that leaves systemic cascade-susceptibility unaddressed.
  • Resilience engineering Cascading Failure & System Resilience Patterns
    A paradigm that accepts failure is inevitable and focuses on mitigating impact and enabling recovery, contrasted explicitly with 'traditional safety management.'
  • Bulkhead Cascading Failure & System Resilience Patterns
    A shipping-derived metaphor for compartmentalizing failure so it cannot spread — in software, isolating resources (e.g., separate connection pools per downstream dependency) so one failing dependency cannot exhaust shared capacity.
  • Reduce interconnection
    One of Newman's three mitigation categories: minimizing the pathways through which a local failure can propagate — includes bulkheads, circuit breakers, and (his broader claim) treating identical deployed code across sites/vendors as itself a form of interconnection and correlated-failure risk.
  • Interconnection (as failure vector)
    Extended beyond physical network topology to include shared code, shared infrastructure, and shared vendor dependencies — 'a bug that takes down your system on AWS could just as likely take down your system on Azure' if the code is identical.

Arguments

Teams should not treat elimination of a single root cause as sufficient resilience work; they must also reduce a system's capacity to cascade once some trigger occurs. strength: high
Explicit premises:
  • Systems are getting bigger and more complex.
  • Not all triggers can be eliminated (lightning strikes; gas explosions; race conditions).
  • Removing one trigger (e.g., banning open fires) is useful but not by itself sufficient to prevent catastrophic outcomes.
Implicit premises:
  • The triggering event and the system's structural susceptibility to cascade are separable causal factors that can be addressed independently.
  • Reducing cascade-susceptibility yields resilience benefits that persist even against unanticipated or unremovable future triggers.
Inferences:
  • Organizations should audit systems for cascade-prone structure proactively, independent of any specific past incident, rather than only reacting to the trigger a given incident revealed.
Resilience mechanisms are not unconditionally beneficial; adding them can introduce new interconnection and new failure modes, sometimes causing exactly the failure category they were meant to prevent. strength: high
Explicit premises:
  • AWS ran multiple DNS enactors specifically for redundancy against availability-zone failure.
  • That redundancy created the race condition (two enactors racing to apply/overwrite plans) that caused the DNS route deletion and the entire outage.
  • Circuit breakers can make partial failure worse and cause retry storms when misconfigured.
Implicit premises:
  • There is no complexity-free way to add resilience to a system — every mitigation introduces new surface area, referencing David Woods's work on this general property of complex systems.
Inferences:
  • Resilience investment likely has diminishing or even negative returns past some context-specific point, so 'add more redundancy/protection' cannot be treated as a default best practice — it needs the same cost/benefit scrutiny as any other engineering investment.

Narratives

  • Ronan Point (1968): a tower block built quickly post-war using a prefabricated large-panel system assembled by lower-skilled workers; a small kitchen gas explosion blew out a load-bearing outer wall with no alternative load path, causing four floors above to collapse in a 'concertina' effect and kill four people. A later forensic demolition revealed some joints had been filled with newspaper and cigarette packets instead of concrete.
    → Establishes the definition and stakes of 'progressive collapse'; also implicitly supports the proposition that underlying resource/skill decisions, not just the triggering event, produce structural fragility.
  • The October 2025 AWS us-east-1 outage: a DynamoDB subsystem managing DNS routes had two components (a DNS 'planner' and multiple redundant 'enactors'); a slow plan and a subsequent faster plan raced, and the old plan completing last wiped out all DNS routes, cascading to network load balancers, EC2, EKS, and dozens of downstream consumer products (Alexa, Ring, Slack, Snapchat, smart mattresses, smart litter trays).
    → Supports both the general progressive-collapse thesis and specifically the redundancy/complexity paradox argument — the same redundancy meant to strengthen the system caused its failure.
  • Newman's own incident with 'Sauron,' a used-car/motorbike/caravan classifieds site built as a Strangler Fig migration: a downstream legacy site began hanging on connections; overly lenient 30-second timeouts exhausted the shared connection pool, which then blocked unrelated request types (motorbikes, jet skis); users compounded the failure by repeatedly hitting refresh.
    → Illustrates all three mitigation categories concretely (load shedding as hazard reduction, per-service redundancy as component strengthening it wasn't worth paying for, and per-downstream connection pools/circuit breakers as interconnection reduction) and grounds the business-cost-benefit proposition.
  • Monzo, a UK bank, built a clean-room stand-in system with no shared code, on a different cloud (GCP vs. its core AWS system), to provide continuity of critical banking functionality independent of a vendor or a shared-code bug.
    → Supports the claim that reducing interconnection must extend to shared code and shared architecture, not just physical site/vendor diversity.

Questions addressed

  • ✅ What causes a small failure to cascade into a system-wide catastrophe, and how can distributed systems be designed to mitigate that?
    Via the three-part framework: reduce hazards, strengthen components, reduce interconnection — applied together, contextually.
  • ✅ Is identifying and eliminating a single root cause sufficient resilience work?
    No — explicitly rejected in favor of addressing cascade-susceptibility as well as triggers.
  • ✅ Should organizations default to multi-cloud or multi-region architectures?
    No — it is a legitimate but costly, complex option to be weighed consciously against the specific risk being hedged (site failure vs. vendor/supplier failure vs. data sovereignty), not adopted reflexively.
  • ✅ Can the very mechanisms meant to add resilience introduce new failure modes?
    Yes, demonstrated concretely via AWS's DNS-enactor redundancy causing its own outage, and via circuit breakers worsening partial failure/causing retry storms.
  • ✅ How should teams prioritize which mitigations to implement and on what timescale, especially in the aftermath of an incident? (Q&A)
    Translate protection work into business terms (recovery point/time objectives, cost) and prioritize by impact-to-cost ratio, then negotiate explicitly with business owners about what will and won't be funded.
  • ⭕ Does AI-agent-built software risk a Ronan-Point-style structural flaw from using less-skilled builders (junior-developer-replacing agents) to build faster? What guardrails are needed? (Q&A)
    Newman gestures at needing stronger QA/SRE-style verification roles and better 'guidance from a context point of view,' but explicitly states the industry doesn't yet know what 'good' looks like for verifying agent-produced software: "I don't think we're nowhere near it yet."

Gaps

  • incompleteThe talk never offers a framework or heuristic for deciding, in advance and quantitatively, when the interconnection/complexity cost a resilience mechanism adds (redundancy, circuit breakers, multi-region) outweighs its benefit — the only guidance given is qualitative ('have a conversation as a team,' negotiate cost with the business owner). There is no attempt to measure or bound the complexity a given mitigation introduces before deploying it.
    Read next: Resilience-engineering and safety-II literature (Hollnagel, Woods) on quantifying trade-offs between robustness and complexity; chaos-engineering practice for empirically testing whether an added mitigation actually reduces or relocates risk before it ships.
  • incompleteNewman explicitly leaves the AI-agent guardrails question open in the Q&A, but the talk never develops what a structural, Ronan-Point-style progressive collapse specific to AI-agent-produced software would actually look like — e.g., whether a single flawed architectural pattern an agent replicates across many services or many repositories is the software analogue of Ronan Point's shared, flawed prefab construction system, and if so, what 'reduce interconnection' would mean for a fleet of AI-generated services sharing the same generative pattern or the same underlying model.
    Read next: Corpus material on agentic engineering and code-quality risk from AI-generated code at scale; look for post-incident analyses of correlated failures traced to a shared AI-generated pattern or shared prompt/skill.
  • incompleteNewman's claim that multi-cloud hedges against 'vendor failure' as opposed to 'site failure' doesn't engage with the shared upstream dependencies that nominally independent cloud vendors still have in common (root DNS, major CDNs, BGP routing, common upstream registries like npm/PyPI, common certificate authorities) — his own 'shared code is a form of interconnection' argument implies these shared substrates could still produce correlated multi-cloud failure, but the talk doesn't extend the analysis that far.
    Read next: Internet infrastructure dependency-mapping research (e.g., studies of correlated cloud/CDN/DNS outages) that quantify how much 'independence' multi-cloud actually buys once shared internet substrate is accounted for.

Not caching-specific, but directly on-point for centralized-infrastructure shared-fate risk.
